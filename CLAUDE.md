# FrontierJS — Map

Bun-workspace monorepo: a schema-seeded fullstack framework. One mental model — three realms, three nouns:
**Data (Model) → API (Service) → UI (Resource)**, plus Deployment (Release) and Testing (Suite).
Everything derives from `db/schema.lite`; growth happens outward and traces back.

`ARCHITECT.md` §2 is the default vocabulary for design discussion. Depart from it when a different word is materially clearer — then fold the clearer word back in rather than keeping two.

## Evolution policy

FrontierJS is pre-alpha. **Prefer evolving existing designs over preserving them.** Existing behavior is evidence, not a constraint.

Only two things are binding: the **Invariants** below, and rulings in `DECISIONS.md`. Everything else may change — prefer simplifying, removing duplication, and improving consistency over reproducing what is there. **Preserve the mental model, not the mechanism.**

Where docs disagree, assume different stages of a pre-alpha design and reconcile, rather than treating either as wrong.

**This file is only what is live.** History belongs in `packages/*/CHANGES.md`, open defects in `ISSUES.md`, settled arguments in `DECISIONS.md`. A line here earns its place by changing what someone does in the next hour.

## Invariants

Don't violate without an explicit decision; record it in `DECISIONS.md` if you do.

1. **Dependency direction** — `Litestone ← Junction ← Sierra`, never reverse.
2. **Model names are PascalCase singular** (`model Lead` → `db.lead`); `@@external` exempt. Three resolvers depend on this agreeing.
3. **App layout** — `db/` at the root and each SURFACE a directory beside it: `api/`, `web/`, `site/` (the public prerendered site), `widgets/` (embeddable scripts) and `extension/` (a jetty browser extension). Most sub-projects carry `config/ src/ public/ test/ dist/ deploy/` (db/ doesn't). Configuration lives in `config/`, `vite.config.js` included. Which surfaces an app has is the app's business — api-only, web-only, **site-only**, **widgets-only** and **extension-only** are all whole projects — but a surface inside another one is not: folded into `web/`, it inherits the SPA's build, port and release. A surface earns its own directory when its config, its tests and its release are all different answers, which is what `site/`, `widgets/` and `extension/` are. **`site/` has a fourth and it is the decisive one — OUTPUT**: one Vite root is one `dist/`, and `vite build` empties `outDir`, so a `target: 'static'` site living inside `web/` is deleted by the next SPA build with nothing said (`FJS-D127`, `FJS-449`). `fli check`'s `app-layout` reports a static config found inside another surface. Canonical: root `README.md` §Project Structure. Never *derive* a config path from where `vite.config.js` sits — probe, or be told.
4. **One owner per translation.** Exactly one place turns a thrown value into an HTTP status, one wraps/unwraps the result envelope, one parses `$`-params into `ctx.directives`, one announces a mutation, one startup phase list every caller runs. Implementations are in §Bridge index. Add to the owner, never beside it.
5. **One owner per `app.<thing>`.** Claim it with `app.claim(name, value)`; type it by augmenting an exported interface, never by redeclaring the property — declaration merging requires identical types, so a redeclaration silently loses. The verb is `claim` and not `provide` because **a Provider is a third party the app speaks to** (`FJS-D06`) — `/metrics` contributions go through `app.registerMetricsSource(name, fn)` for the same reason.
6. **Access is declared in the schema, not in hooks.** Gates, `@encrypted`, `@guarded`, `@@transitions` are enforced at the Data boundary. `x-gate` on the client is a UI affordance only — unknown answers are permissive and the server enforces regardless. No exceptions.
7. **Protected fields are redacted in the audit trail.** `@encrypted`/`@guarded`/`@secret` log as `[redacted]` in field entries and in `before`/`after` snapshots.
8. **Caller-supplied names never enter a SQL pattern.**
9. **Patch semantics: an explicit `null` clears.** Test key presence (`key in updates`), not `??`.
10. **A `$`-PREFIXED KEY is transport syntax only.** `$limit`, `$offset`, `$orderBy`, `$select` are how a directive travels on a wire; `ctx.query` is filters, `ctx.directives` is `{limit, offset, orderBy, select}`, and no `$`-prefixed KEY survives the bridge. The rule is about the prefix on a parameter name and about nothing else — junction's ambient `$`, the service call in progress, is a different thing that happens to share a character (Bridge index § API internals). **Two boundaries read the convention** — junction's bridge off a request, sierra's router off a URL onto `page.query` + `page.directives` — and the table they read it by is one module, `@frontierjs/toolbelt/directives`, one row per directive so a Data-realm feature that grows a per-call option cannot arrive half wired. **What the VALUES mean is the sibling module, `@frontierjs/toolbelt/query`** (`FJS-D125`) — a string is a number only if `String(Number(v)) === v`, `true`/`false`/`null` are themselves, structure is bracket notation, and `?code="5"` is the escape. Three readers: junction's transport, junction's client writing one, sierra's router. **Not a WS frame**, which is JSON and already carries its types.
11. **The nearest delegation root owns an event.** Roots nest; a handler must fire once.
12. **Mesa compiler output is reproducible** — scope ids are content-addressed, which is what makes CSS dedupe work across the two compilers a static build runs.
13. **`@frontierjs/css` is the styling language.** Style with a tone (`danger`) and a treatment (`outlined`), never a color. UnoCSS is supported *alongside* it as an opt-in layer a consuming app configures (`packages/css/README.md` §Using it with UnoCSS). A package in this repo ships no utility classes — a component needing Uno to look right is unusable by an app that does not run it.
14. **Typecheck baselines ratchet down only.** `scripts/typecheck-baselines.json`, one number per package; absent means 0. `bun run typecheck -- --update` writes an improvement back.
15. **A clean compile is not proof of valid JS.** Compiler tests parse their output.
16. **Runnable examples are verified, not sketches.** A broken one is a bug.
17. **Four markdown files at a package root is the standard** — `README.md`, `CLAUDE.md`, `PROJECT_STATE.md`, `CHANGES.md`; everything else in `<pkg>/docs/`. **`AGENTS.md` is a permitted fifth and is not required** (`FJS-D163`): it is the same KIND of thing as `CLAUDE.md` — a root document whose whole value is being findable at the root, under the name other tools converged on — but it addresses a CONSUMER of the package rather than a contributor to it, so a package nobody writes against does not owe one, and the two are not folded because one audience has the source and the other has a tarball. **It only reaches that audience if `files:` ships it**, which is decidable from `exports.snapshot.md` and was false for litestone until it shipped one. **A sixth is a question, not a refusal**: `package-root-md` warns and names it, because the rule cannot tell a stray design note from the next thing everyone needs at the root. Answer it — move the file, or record an allowance saying why it stays. Generated `*.snapshot.md` is exempt; it is gated output, not documentation.
18. **In a Sierra app, `src/resources/` holds `.mesa` files, and a resource file carries its model's default form.** A Resource is a UI-realm noun, written in the UI-realm language. The data half is `<script module>` — `createResource` and the model's own verbs — which runs once at import and is what every other module imports (Mesa VISION §11, rule 30); that half is required. **The markup half is the form and it is optional**: with it, a create or edit page is `<Order />` and nothing else, and a page wanting a different form passes children, which `<Form>` already lets win. A file with no `<script module>` is a component in the wrong folder (`FJS-D112`).
19. **A resource file is named for its noun — PascalCase, singular — one Resource per file.** `App.mesa` exporting `export const apps`; the same split the Data realm makes between `model App` and `db.app`. Where a model exists the filename IS the model name, so an irregular is visible (`AlertRule.mesa` exporting `alerts` says `model:` must be stated). A resource over no model takes its service noun, singularised.

## Running things

**Always `cd` into the package and run its own script.** Runners differ per package and a wrong runner produces failures that belong to nothing. `bun run --filter '*' test` from the root runs them all, one each. `bun test` instead of `bun run test` runs bun's own runner over whatever it finds — in mesa that is ~35 failures that are runner artifacts.

**`bun run ci` is the whole of CI and it is not a GitHub feature.** One node script runs thirteen phases and `.github/workflows/ci.yml` does nothing but call it, so it runs identically on a laptop. `ci:fast` skips the suites, `--only <pkg>` narrows typecheck and tests, and `bun run hooks:install` points `core.hooksPath` at `scripts/hooks`, whose `pre-push` runs the fast tier — the suites belong in the workflow, because a pre-push costing minutes teaches everyone `--no-verify`. Every allowance is a named entry with a reason in `scripts/ci-allowances.json`.

| Phase | What fails it |
| ----- | -------------- |
| `hygiene` | a source file `.gitignore` hides, and **a dependency or a clock inside the substrate package** — `@frontierjs/toolbelt` may be imported by litestone and mesa only because it depends on nothing, so a non-relative import under its `src/` fails the build |
| `structure` | an architecture rule broken in this repo's own apps. It runs `packages/cli/core/checks.js`, the same engine `fli check` gives a client app, because two implementations of one rule is how a framework ends up breaking rules it publishes |
| `registers` | an id a register issued twice, a citation pointing at nothing, a ruling nobody named — `packages/cli/core/register-check.js`, the engine behind `fli register:check` |
| `snapshots` | a committed `*.snapshot.*` that no longer matches its source. It carries **no list of what exists**: every snapshot names the command that wrote it in its own header, and that command is rerun with `--check` from the file's own directory, so a new KIND of snapshot costs a generator and never a CI edit. The command comes out of a file in the repo, so it is restricted to a known binary and a shell-free argv, and a snapshot naming no generator fails rather than being skipped. **Discovery alone fails open**, so the expectation comes from the BASE REF — a snapshot tracked where the branch left main and absent now is a failure, because a generated artefact that stops existing takes its check with it in green. A deliberate removal is a named entry under `removedSnapshots` |
| `access` | nothing, by design. **The one phase that reports rather than judges** — *what did this branch do to who may do what*, printed per app against the base ref — because a branch that widens access is usually a branch doing its job, and a red that fires on every feature trains everyone to skip the phase. The gate is `fli test:access --from <ref> --strict`, which belongs on the branch that deploys |
| `coverage` | a package with no `test` script that `exemptPackages` does not name |
| `registry` | a `@frontierjs` package `fli new` writes into an app's `package.json` that npm has never heard of. **It asks the half the register cannot see**: every id there is a statement about the WORKING TREE, and a user's experience is the tree AND the registry, which drift independently. The list is read from `core/app-config.js`, the module `fli new` itself reads. A version gap is a NOTE; an unpublished package is allowed by name under `knownUnpublished`, which fails once it IS published; no network is a named skip that `FJS_CI_REQUIRE_REGISTRY=1` makes fatal |
| `advisories` | an advised package **reachable from a PUBLISHED package's runtime `dependencies`**, since that is the set every app installs — walked from each package's own directory and resolved the way node resolves, because bun installs into `.bun/` with symlinks and a path guess reports every advisory as dev-only. A **comparison rather than a scan**: a vitest advisory is not something an app installing this framework can be hurt by. The resolved version is printed beside the advisory's range and **the two are never compared**, because a range parser here would be a security judgement made by a regex. `knownAdvisories` is the named allowance; `FJS_CI_REQUIRE_AUDIT=1` makes a no-network skip fatal |
| `scaffold` | **the phase no suite can replace.** It packs every publishable package, scaffolds an app against the tarballs, installs it, builds it, runs that app's own `bun run check`, then scaffolds a model into it and builds again (`scripts/scaffold-build.mjs`). An app in this repo resolves sierra to `packages/sierra/` and never to a node_modules path, so the code that only runs for an *installed* app runs nowhere else here. It grades each package's `files:` field for free, and **its per-run `--cache-dir` is load-bearing**: bun caches a tarball by name *and* version, so a shared cache serves the previous run's bytes and the phase passes against a broken tree |
| `typecheck` | a *raised* baseline (Invariant 14) |
| `deploy` | the pipeline an app actually deploys with, in two halves. `fli new` → `make:deploy` → `deploy:local` **once per package source**, each ending in a **register and login through the prefix the app's own `web/config/sierra.config.js` names**, because a health answer says the process is up and not that the app works. `--source npm` is the only thing here testing the PUBLISHED framework; `--source local` is the working tree containerised, which needs `core/vendor.js` to pack the tree into the build context, since a Docker build can see neither a `link:` spec nor a tarball outside it. The second half is **`deployJournalCycle`, the only thing that runs `fli deploy`** — deploy → deploy → crash → resume → revert, an unbound attachment, a declared binding key nothing carries, and the build a browser compares against, all against `localhost` as a real deploy machine with real docker, a real journal and a real revert. `core/machine.js` is the one owner of *(host, script) → the argv that runs it there*, and the script travels on **stdin** to `sh -s`, so the same script reaches the same shell with or without an ssh prefix; the only thing it does not exercise is ssh itself. Its sharpest assertion is that an unchanged redeploy mints the SAME Release. Full tier only. Without a daemon it reports a named note and passes, and `FJS_CI_REQUIRE_DOCKER=1` turns that skip into a failure, which the workflow sets; `knownDeployFailures` exists for publish order, where the scaffold gives an app a package nobody has published |
| `tutor` | a command renamed out from under a lesson, a scaffold whose default gate moved, an answer the framework changed. It **executes the tutorial** — eight lessons, `--tmp --yes`, on test-tier ports, each lesson a command whose every step ends in a probe against the running world rather than an exit code: a port that answers, a table in `sqlite_master`, a row read back out of the file the app wrote, the same POST answered 201 with a token and 401 without. It is the phase for the one document that had no compiler behind it. A port already held is a SKIP rather than a finding, because the lessons refuse a busy port rather than moving to the next one; `knownTutorFailures` is the ratcheting allowance |
| `tests` | a suite. A suite known to fail is named, so a NEW failure is loud |

**The browser drives need their servers started by hand, first.** They exit 1 naming the missing process. All need Chrome. **The *Start first* column is READ** — `packages/cli/core/preflight.js` parses it, `runnables.js` puts the resolved steps on the drive's row, and `fli gui` walks them behind one button, skipping anything already answering. So the order in a cell is the order they are run in, `nothing` is the explicit empty answer rather than a blank, prose after the em-dash is not read, and a step whose script has been renamed is a `fli check` error (`drive-preamble`) rather than advice somebody notices is wrong. What it cannot see is the drive's own check, which is the half `--preflight` would close.

## House style

Match the file you are in first; this is what the repo does when there is no local precedent.

- **Comments explain the failure, not the mechanism.** `// increment the counter` is noise; `// vite hops ports silently, so the drive would talk to the other app` is the house voice.
- **A comment must be load-bearing. Delete it otherwise.** Test: if it vanished, could someone editing this file make a mistake it would have prevented?
  - **No edit history in code** ("used to be", "this replaced X", "merged 2026-08-08"). That is `CHANGES.md`, `DECISIONS.md` and git. Narrow exception: a past bug stated because the shape still invites it (`--ring` in `tokens.css`), where the history IS the warning.
  - **No dates in code comments.** If the comment needs one, it belongs in a decision record the code points at.
  - **No persuasion** — "the whole point", "deliberately", "which is exactly why", italics for emphasis. State the constraint flatly; if it needs selling, it needs a ruling.
  - **Never narrate your own edit.** The reader does not know a change happened.
- **Never put a backtick in a comment inside a template literal.** A SQL schema, an nginx config and a shell script are all written as one here, and a comment quoting `an identifier` closes the literal — the file then fails to PARSE, so the failure is nothing to do with what the comment says and points at a line further down. Twice in one day: `packages/caravan/src/db.ts` (every `bun run api` and therefore every drive) and the nginx deploy template (the cli suite). Use plain words or `--` quoting; the cli's *every shipped command compiles to parseable JS* test is the only thing that catches it, and it only covers `commands/`.
- **Every non-trivial file opens with a header block** — what it is, and what it is for. Test harnesses document their own traps at the top (`example/web/test/verify.mjs`).
- **Section dividers inside a file**: `// ─── name ──────` (box-drawing, padded to a consistent width). Not `// ---`, not banner boxes.
- **Aligned columns** where a run of lines is parallel — imports, object literals, `const` blocks. See `example/api/src/app.ts`.
- **Prose in the docs is sentence-shaped, not bullet-shrapnel.** Bold the claim, then say what it cost. Numbers earn their place by being measured.
- **American spelling** throughout, prose and identifiers alike (`behavior`, `serialize`, `color`) — flipped from British in `FJS-D192` (see `DECISIONS.md`), `example`'s `ProductVariant.colour` renamed to `color` along with it since nothing here has ever been deployed. One exception remains: `cancelled`, a persisted enum value on several `@@transitions` models across `example` and `basecamp` — renaming a value already written to a running app's database is a migration, not a find/replace, and nobody asked for that one yet.
- **No semicolons**, single quotes, 2-space indent, in TS and JS alike (`packages/css`'s own build/test scripts are the one holdout). TypeScript in junction, auth, caravan, conduit, notifications; plain ESM JavaScript in litestone, mesa, sierra, ui, css, jetty. Do not introduce TS into a JS package.
- **Fake clients hide real bugs.** Cross-package behavior is tested against the real dependency — `{ post: {…} }` passed every test and failed every real Litestone client.
- **A new `on*` states its tier** (`FJS-D06` §1) — **Hook** may mutate the arguments or halt the operation, **Guard** answers allow/deny, **Observer** receives and cannot act. The word goes on the option that holds it: conduit's callbacks are `observers:` because a throw in one is swallowed, and `management.hooks` beside it keeps *hook* because that pipeline can refuse the call.
- **A new defect gets an `FJS-###` in `ISSUES.md`**, not a paragraph in a package file. A ruling closes an `FJS-D##` and moves to `DECISIONS.md`. Check a new `.gitignore` rule against `git status --porcelain` — an ignore glob hid twenty source files once.

## Live hazards

**Correct behavior you have to know about.** Things that are *wrong* live in `ISSUES.md`, one id each; things that are *fixed* live in `CHANGES.md`. If a rule here is pinned by a test that cannot be deleted quietly, it does not need to be here.

**Data**

- **Two owners decide whether a schema is legal, and the line between them is what CAN be expressed.** The parser refuses what cannot work at all — `@unique`/`@@unique`/`@@index` over a field with no column (a `@computed` in a `@@unique` makes a table SQLite refuses at boot, naming nothing the author wrote), a fractional `@default` on `@scale`/`@money` (an INTEGER of minor units takes `DEFAULT 12.99` and the first defaulted row is refused at runtime), a `@relation` across two `database` blocks (a foreign key resolving nowhere, `no such table` on every create). These are derived from one FACET — *what does the column physically hold* — rather than ruled pair by pair over a hundred-word surface, which is how three of them stayed open while their sibling `@unique` × `@encrypted` had a good message (`FJS-721`); `@generated` is outside the set, being a real column. **What is merely legal and WRONG is `litestone advise`**, whose own contract is that every rule in it parses — `@@fts` over an encrypted column is one of those, and adding it to the parser too made that rule unreachable and broke its own test. Reach for the parser when the schema cannot be built, and for `advise` when it can be built and should not be.
- **A composite `@@unique` naming a NULLABLE column is a parse error, and single-column `@unique` over one is not** (`FJS-D130`). Two NULLs never compare equal, so the tuple index admits `(1, NULL, NULL)` twice while refusing the same pair with values — the constraint holds exactly where nobody doubted it. `@@unique([a, b], nullsDistinct: true)` is how a schema says it meant that, emitting identical DDL. **`@@unique([a], where: <expr>)` is the other answer and usually the one wanted** (`FJS-603`) — *at most one OPEN row per parent*, which is what effective dating is built on, and getting there means moving the nullable column OUT of the tuple and into the predicate. A predicate cannot ride a table constraint, so it emits a standalone `CREATE UNIQUE INDEX … WHERE`, migrates by one DROP and one CREATE, and does NOT make a relation one-to-one. Its literals are inlined, because SQLite prohibits a bound parameter in a partial index predicate. **`@@softDelete`'s clause is not ANDed in**: on a unique index the predicate IS the constraint, so ANDing it would free the slot a deleted row holds. A `@from` correlates on **every** column of its relation's key, in three places, or a join on the first column alone answers a count of real rows to a question nobody asked; a write naming a `@from` field refuses by name.
- **A drive that cleans up through the API cannot free a `@unique` on a soft-deleting model, so a fixed fixture key makes it single-use** (`FJS-530`, `FJS-546`, `FJS-547`). A DELETE over HTTP soft-deletes, the kept row still holds the value, and the next run's create is a 409 the drive does not check — so the id is `undefined` and the failure surfaces three steps downstream, in a drive that passes once per seed. **Two ways out and they are not interchangeable.** Mint the key per run — and check the two things that bite that fix: a `@upper` column stores a lowercase id uppercased, so a later search for it silently misses, and `@length(3, 20)` refuses a prefix plus a run id. Or RELEASE the value in the sweep, which is what to reach for when the drive's own expectations name the literal: read with `?$withDeleted=true`, `PATCH /{service}/{id}?$withDeleted=true` the reference aside, and delete only a row that is still live — a second DELETE is a no-op against something already gone.
- **`litestone introspect` output must PARSE, and the property that holds it is a FIXED POINT** (`FJS-594`). It is the adoption door — a database you already have into a `.lite` — and also what `fli db:pull` runs. Reading a database built from the output must give the same output, asserted over the seven corpus schemas and the 188-model `openmrp` fixture. No substring assertion can see what that catches: a SQL expression default emitted as a string LITERAL, whose quotes `ddl.js` doubles on every pass; an `@@index(where:)` re-emitting the clause `createIndexes` ANDs on for `@@softDelete`, nesting a level deeper each time; a **relation field named for the table it points at**, which takes a real COLUMN's name and deletes it, since the parser keeps one field per name; and an **enum name colliding with a MODEL name**, which makes that model's own relations resolve as enums and become TEXT columns. **Anything here that writes `.lite` owes the same property.** The output is graded as well — `src/import/tiers.js` is one table for both converters, `--report` writes the list and `--strict` fails on `changed`.
- **A soft-deleted row keeps its `@unique` values, and `restore()` is why.** Freeing the slot would make `@unique` false for every read that includes deleted rows — `findUnique(withDeleted)` legitimately matching two — and would make the way back fail whenever a stranger took the value first. So a write naming a value a deleted row holds is refused by name (`SoftDeletedUniqueError`, 409) rather than by SQLite, and releasing a slot is a decision the app makes: `update({ …, withDeleted: true })` moves the value, `delete({ …, withDeleted: true })` stops keeping the row. **A LIVE holder is the other half and it is a different error** — `UniqueConflictError`, also 409, naming the field with the value redacted where the column is protected, and carrying `errors` so a form marks the box rather than showing a banner. Two classes because the ways out differ: restore-or-release, against send another value. Every create AND update path translates, since SQLite's own sentence names a physical table and reaches nobody (`FJS-441`). Membership is spelled `@@allow('read', auth().id in memberIds)`, the list always the RIGHT operand, so an audience held on the row does not have to become a service where-clause.
- **A soft-deleted parent's children have THREE fates and each has a spelling.** `@@softDelete(cascade)` stamps them, `@hardDelete` on the relation field destroys them, and **`@keep` leaves them live on purpose** — which is what a plain `@@softDelete` already does, and the parser warns about it because forgetting the cascade and meaning it look identical. *The customer goes, the receipts stay* is that shape and it is not rare: `example`'s `Customer.orders` is `@keep`, and without it removing a customer either destroys every order they placed (`onDelete: Cascade`) or hides them, neither of which is what a shop means. It covers the whole subtree beneath that child, and says nothing about removing the child directly. The warning names all three ways out, so the third is discoverable from the thing that complains about it.
- **`auth().x` is graded against a DECLARED set, and only where there is one** (`FJS-666`, `FJS-667`, `FJS-668`). An absent claim is `NULL`, so `NOT (NULL = 1)` excludes EVERY caller while the create path's `null === true` excludes none: one misspelling is a lockout on read and an open door on create, and the side that refuses reads exactly like a policy doing its job. The set has **four sources** — the eight names litestone reads itself (`id`, `capabilities`, and the six `FrontierGateGetLevel` grades a caller by, none of which is a column), the `@@auth` model's own columns, the `tenancy { claim }`, and **`createClient({ claims: [...] })`** for a claim resolved per request, which is on no row and in no schema. That last is a client option rather than a `.lite` keyword because junction already declares the list and generates `principal.snapshot.md` § Claims from the resolver's own `describe()` (`FJS-D181`). **A schema with no `@@auth` and no `claims:` is ungraded and says so**, once per distinct set of names; `claims: []` is a statement where absent is silence. **A field-level `@allow` runs the same walk**, and a typo there fails CLOSED, stripping the column from every row, so the schema, the build and every assertion on the refused side agree with the mistake. **An absent claim means one thing rather than two**: `evalJs` propagates NULL the way SQLite does, an `@@allow` holds only on TRUE and an `@@deny` fires on TRUE and UNKNOWN alike. `x == null` keeps its own branch and answers a boolean, because that is how this language spells `IS NULL`.
- **A `@@gate` refuses, a `@@allow` filters — so a wrong policy is an empty screen, not an error.** The two rules underneath, and the order every layer reads in, are `packages/litestone/docs/access-control.md` § *Combining them*: **a refusal must never confirm a row exists** (which is why create is the one policy that throws — the payload IS the row), and **whose mistake is it** — `@guarded`/`@system` throw because no caller was ever meant to send that column, a field `@allow('write')` drops because the same form body is legitimate one level up. A gate throws naming the model and the level; a policy compiles silently into the WHERE. Every read that legitimately crosses a policy's scope must be `asSystem()`, or it returns nothing with a 200. Declare one model at a time and run the app's drive between them. **`fli test:access` writes the whole declared surface to a committed `db/access.snapshot.md`** — gates, policy predicates, protected fields, and per declared move its gate AND its `@system`, which stay separate columns because they compose: `@system @gate(5)` is both, and folding one into the other renders the widest narrowing a state machine can express identically to an ungated move (`FJS-613`). The `snapshots` CI phase fails a stale one, so a gate that moved is a diff rather than a production refusal. **`--from <ref>` asks the other question and writes nothing**: what this branch did to who may do what, graded `widens` / `narrows` / `undecidable` / `new`. It is not `release:check` with a different word — *can N-1 still serve* and *who may now do more* disagree by construction, and a removed `@@gate` is an expand and the widest change there is. A predicate whose text moved is reported rather than guessed, and an allow→deny inversion is the same answer for the same reason (`FJS-D131`). `--strict` is the gate; the `access` CI phase only prints.
- **A schema change is a deploy question before it is a migration**, and `fli release:check` is the one that asks it: can the release still serving and the release starting share one database? Expand — N-1 keeps working, so the deploy can be taken back. Contract — it cannot, and that deploy is the **pivot**, after which only forward. Unknown counts as contract. `db/release.snapshot.md` is the surface it diffs, `--from <ref>` is the question a deploy asks, `--strict` fails a branch on anything but expand *including no baseline at all*. **Access is in the comparison, which is the half no generic deployer can reach**: raising a `@@gate` takes reads away from a release still serving them, and adding an `@@allow` empties a screen with a 200. A required column with no default is the one contract handed back as a plan — expand, backfill, contract — rather than a refusal.
- **A BULK write may not name a transitions field** (`FJS-D182`). `updateMany` matches rows with a WHERE and never reads them, so there is no `from` to grade — and skipping that check took the whole ladder with it: a `@gate(5)` move, a `@system` move and a move the schema does not declare were each allowed through it (`FJS-671`). Not reachable over HTTP, since junction's `bulkByRow` selects its targets and writes them one at a time through `update()`; what is reachable is a hand-written service, job or script. The refusal is the **KEY and not the verb** — `BulkTransitionError`, **400** rather than 403, because no level and no grant answers it, the verb is wrong rather than the caller — and `upsertMany`'s `update:` half refuses with it while its insert half, being a create with no from-state, does not. **Every other column stays bulk-writable in the same call.** `asSystem()` still writes it and says so, because `update()` announces its bypass through `emitTransitionEvent` and a bulk write reaches none.
- **A move asked for BY NAME is not the same question as an update carrying the column** (`FJS-611`). `transition(id, name)` desugars into `update()`, and carrying the value a row ALREADY holds is legitimate there, because a form round-trips the whole row — so the check returned early and enforced nothing. Asked for by NAME the same row state means the opposite: the move did not happen here. The early return took the gate, the capability and `@system` with it. The compare-and-swap was never the missing half — the UPDATE has always carried `AND status = <from>` — and `$transaction` made it WORSE, since serializing the callers means each re-reads after the winner committed, which is precisely the state the early return called a no-op. A move onto the state the row already holds is a `TransitionConflictError` carrying `actual` and `retryable: false`, where losing a race to a DIFFERENT move stays `retryable: true`: two opposite races under one class, and `isStaleWrite()` reads the flag. **The caller is graded before the row's state** — a gate is about the caller and the declared move, so somebody who could never make it is told that rather than being told where the row is. That ordering applies to a named move and to nothing else: an ordinary update matching no `(from, to)` pair has identified no move, so **naming the move is what makes its gate askable**. `asSystem()` bypasses all of it, so a job moving a row through one is still guarded by its own read.
- **A freeze that depends on STATE is not expressible, and `@@gate` is where you notice.** A gate is per MODEL, so *a payslip under a draft run may be removed and one under a paid run may not* has nowhere to live: `example`'s `Payslip` had `9` on delete, which made `revert: calculated -> draft` strand its own payslips and collide on the next calculation, and `8` lets the system remove one and says nothing about when. The rule ends up in application code beside the aggregate ones — `revertPayRun` reads the PARENT's state before touching a child, which is a different shape from *the lines sum to the total* and is worth counting separately when the cross-row spelling is ruled (`FJS-D162`'s open DELETE question, met from a direction it did not anticipate).
- **`asSystem()` grades at 8, and `9` is LOCKED — not reachable through the ORM by any client.** So `@@gate("…9")` on a write is not *only the application may* — it is *nothing may*, the system context included, and a module that posts through `asSystem()` gets an `AccessDeniedError` naming the model and `required: 9, got: 8`. The two are a real pair rather than a fencepost: `8` is *the application acting on its own behalf* and `9` is *there is no code path at all*, which is what makes an append-only table declarable — `example`'s `JournalEntry` is `@@gate("5.8.9.9")`, read by staff, posted by `api/src/domain/ledger.ts`, amended by nothing. Reading the ladder does not separate them; writing `9` where `8` was meant produces a table that migrates, snapshots and passes every check, and refuses the first write the application makes.
- **You cannot run without gates.** A schema declaring any `@@gate` auto-installs `GatePlugin({ getLevel: FrontierGateGetLevel })` — a declared-but-unenforced gate is fail-open. Installing your own replaces it; installing none does not disable it. Contract: **absent = the app does not model this stage; only `null` grades down**, and standing (`isSystemAdmin`/`isOwner`/`isAdmin`) is checked before the lifecycle.
- **Under `strategy database` four seams belong to the tenant path rather than the single-client path.** A session is verified at the TRANSPORT, before any hook — so `IAuth.verifySession(token, from?)` carries the request's host and headers, which is the only way an app whose people live per tenant can authenticate anybody (`FJS-487`). A raw route (`app.get`/`app.post`) runs inside the request scope, so `requestMeta()` works inside `/auth/login` and inside a webhook (`FJS-488`). `announceDataWrites` taps each TENANT's client on first open rather than one app-wide client (`FJS-489`). And the per-request principal resolver runs for an ANONYMOUS caller, exactly as `withLitestoneDb` does — a claim is what a caller with no session carries, and skipping them makes every guest basket a 404 (`FJS-490`). A `jsonl`/`logger` database stays schema-global and is written by every tenant's client, so its index is idempotent by primary key (`FJS-491`).
- **Tenancy is declared in the seed and there are two strategies.** `tenancy { }` at the top of `schema.lite` — `strategy database` is one SQLite file per tenant plus a registry that indexes them, `strategy row` is one database and a tenant column. Every reader asks one resolution (`db.$tenancy` / `registry.tenancy` / `resolveTenancy`), and precedence is **option → declaration → default**, which is what stops `litestone tenant create` and the running app disagreeing about where a tenant lives. **Row tenancy desugars into `@@deny`, never `@@allow`** — allows are OR'd within an operation, so an allow would widen every read to the whole tenant — plus a `@default(auth().<claim>)` stamp, and it is two rules because `checkCreatePolicy` runs BEFORE the stamp: an absent column is legitimate on create and belongs to nobody on read. A model with no tenant column is reported by name at parse; `@@tenant(none)` says it spans tenants on purpose. `asSystem()` is the only way across, which is what a cross-tenant tier is built on. `packages/litestone/docs/multi-tenancy.md`.
- **`$setAuth(user)` RETURNS a scoped client, it does not mutate.** `db.$setAuth(u)` then `db.thing.create(…)` grades as anonymous, with no warning. It is `const userDb = db.$setAuth(u)`.
- **A Litestone client THROWS on an unknown property, and `createClient` refuses an unknown OPTION by name** — never `undefined`, so a typo'd accessor is loud, and a typo'd capability no longer quietly fails to apply (`FJS-579`: `autoMigrate: true` is not an option, does nothing, and was passed by five of litestone's own test files, every one of which opens a fresh database where creating and migrating are the same thing). The refusal comes off a rest capture, so what counts as unknown is whatever the destructure did not bind; `autoMigrate` is answered rather than suggested at, naming `autoMigrate(client)` and why it stays a call. The cost: feature-detection is itself a throwing expression. `typeof db.$maybe === 'function'` explodes; use `'$maybe' in db` or a `try`. A capability that depends only on the schema belongs on **every** flavor of client — root, `$setAuth`, `asSystem`, `$scopedBy`.
- **A CAPABILITY is a grid beside the ladder, and a finer grant REPLACES the coarse one rather than adding to it** (`FJS-D146`). `@@capabilities` on a model grades its writes and its named moves (`(all)` adds read); `@capability` on a column grades that column's write; both are ANDed with the `@@gate`, which stays the floor. What makes the fine tiers worth having is what an update's payload is partitioned BY: a key carrying `@capability` is graded by that column's grant, a key that is the transitions field is graded by the MOVE it resolves to, and everything else is what `Model.update` is for — so `Environment.variables` can be handed to somebody who holds no other edit on the environment, and `Server.reboot` alone reboots. **A CREATE keeps both**, since `Model.create` is the grant for the row existing at all. **A move the ENGINE makes is nobody's grant** — `@system`, or a gate of 8 or 9 — so it is out of the derived set and out of any picker, and is refused AS `@system` rather than as a missing grant that would not have helped. **A verifier hands its synthetic caller every declared capability** (`atLevel`, `verifyRowPolicies`, `verifyTenantIsolation`), or a policy that filters correctly is reported as *the call threw*, which is true and is about the grid (`FJS-351`). **The caller's set is `auth().capabilities`** (`FJS-D151`) — one name the framework fixes rather than the app, because litestone's grid reads it; what an app chooses is which COLUMN it comes out of, and under tenancy that column is on the membership row, so the same person holds a different set per tenant (`FJS-D149`). **A `Capability[]` column carries its own escalation guard** — subset, never a rank — and that guard is undefined under `asSystem()`, which has no principal: an app whose membership writes go through one still needs the rule said in a hook, and needs BOTH axes there, since two roles can hold the same grid and differ on the ladder.
- **`@immutable` is a column written once, and `asSystem()` cannot drop it either.** It refuses the KEY rather than comparing the value — the same number sent back is refused too — because nothing in the language can see the stored row beside the incoming one, and a form that round-trips a frozen column is one that would have overwritten it the day somebody changed the box. So it reaches the client as `readOnly` **in the update schema alone**: the one column kind whose answer differs by mode, since a create form must still offer the box. It is what a DOCUMENT is (`FJS-D162`) — an invoice's number, the instant it was issued, the total it was issued for — and the correction is a new row beside it. It says nothing about DELETE and nothing about the row: to freeze a row when it reaches a state, freeze its columns and let `@@transitions` own the state column. Refused at parse beside `@version` and `@updatedAt`, which the engine writes on every update.
- **`asSystem()` does not bypass a `@check`, a `@@check` or an `@@arc`, and it bypasses everything else.** The gate, every row policy, `@guarded`, `@system` and every field `@allow` are this package's rules and the system client drops all of them (`FJS-519`); a CHECK is in the TABLE, so SQLite refuses a system write exactly as it refuses anybody's. That is the reason to reach for one: a rule that must hold against a job on `db.`, a migration, a seed and `fli tinker` cannot be declared any other way — a validator runs here and a service hook is not on the path. The cost is the other side of the same fact: it cannot be evaluated in a browser, so it arrives as a refusal rather than as an affordance, and the refusal is a `ValidationError` (400) whose sentence comes from the attribute's own message argument — without one the person reads `is not valid` and the expression goes to `err.constraint`. `packages/litestone/docs/schema.md` § Constraints the database enforces. **`@@arc([orderId, productId])` is the third and the one with a shape rather than an expression** — several optional foreign keys of which exactly one is set, which is *this row points at an Order OR a Product* keeping a real FK, a real cascade and a real `include`, where the polymorphic `subjectType`/`subjectId` pair keeps none of the three and needs a job to sweep what the database will not. Adding one is a **contract** for `release:check`, like any row invariant. One column per member and it stops scaling around six — the signal that the target set is OPEN, which is the case no relation can serve and the one `FJS-D189` refuses rather than solves (`IDEAS/polymorphic-relations.md` prices the real thing: 69 single-valued `.targetModel` reads are the cheap half, and the expensive half is that `policy.js` compiles the TARGET's own policy into a subquery, so N targets is N gates and a caller who reads one model and not another sees half a list as a 200).
- **Raw SQL requires `asSystem()` once a schema declares access rules.** `db.sql` and `db.$setAuth(u).sql` throw; `db.asSystem().sql` is the bypass, and it can write. Raw statements enforce no `@@gate`/`@@allow`/`@guarded`/`@scoped`/`@@softDelete`. Coarse per schema on purpose — deciding per statement means parsing it, and a wrong validator grants a *false* guarantee. `where: { $raw: sql\`…\` }` keeps every policy and is the hatch to reach for. A JS migration is exempt: the runner hands it the system client.
- **A field `@allow` is a PREDICATE and it is compiled into SQL, both ways** (`FJS-D129`). Not a strip and not a JS check against the payload, because both of those were holes. A READ predicate is AND-ed into the caller's arguments as a **sibling** of their `where` — sibling, because a conjunct inside it is complemented by their own `NOT` — so a column they may not read cannot be filtered or sorted on, and a value that used to come back by binary search in seventeen requests comes back as nothing. A row-dependent one therefore narrows to the rows it admits rather than refusing, which is the case the feature exists for; the cost is that an `OR` branch naming the column narrows the whole read. A WRITE predicate is the WHEN of `SET col = CASE WHEN … THEN ? ELSE col END`, so it reads the STORED row — grading it against the payload lets a caller write a column on somebody else's row by stating `ownerId: me` in the same payload. **CREATE is the exception and keeps the JS evaluation**: there is no stored row and the payload IS the row. Through a relation both refuse by name.
- **`@guarded` is not a level** — a system-context lock taking only `(all)`; `@guarded(5)` does not parse. Per-role column access is field-level `@allow('read', auth().role == 'admin')`. It locks **both directions**: a non-system write naming a guarded column is refused with an `AccessDeniedError` naming the field, where it used to land silently while the read strip made it look refused. `@encrypted` alone is not a guard — it hides a value from a reader and stays writable, which is what a caller submitting a secret needs. The two are not exclusive — `@secret` expands into exactly `@encrypted @guarded(all)` — but writing both by hand is `@secret` spelled out, and the choice worth making is which ONE you want: `@allow('write', …)` for a column some callers may set, `@guarded` for one only `asSystem()` touches. A **required** `@guarded` column makes its model uncreatable below level 8.
- **A column your `getLevel` reads must not be writable by the caller being graded.** A gate is per MODEL, so `@@gate("4.4.4.5")` on an identity table says *any signed-in caller may write any other person's row* — `role`, `isAdmin`, a status, whatever the ladder is graded from. `@frontierjs/auth`'s `User` ships the shape: a level for what kind of caller, `@@allow('update', id == auth().id || auth().isAdmin)` for whose row, `@allow('write', auth().isAdmin)` for which columns. **`8` is not a stronger `5`** — it means nothing outside `asSystem()` has anything to say to this model, which is true of credential material and false of the table an app's own screens list; raising the gate just moves the surface into the bypass. `DECISIONS.md` § Access control.
- **A stored value names the KEY that wrote it** (`FJS-D183`). The envelope is `v2.<kid>.<payload>`, the kid a domain-separated HMAC of the key truncated to eight hex characters — it identifies a key without being one, so it is safe in a column, a log line and an error. `$rotateKey` runs **one transaction per DATABASE**, so a crash between two commits leaves each database saying which key wrote it and the rotation resumable. **An unknown kid still tries the ring**: GCM's tag is the authority and the kid is only the ORDER. `createClient({ previousEncryptionKeys })` is read-only, the old key STAYS on the ring after a rotation, and re-running one finishes it. **A half-rotated schema is not supported**, and that is a consequence rather than a limit: a deterministic encoding is a function of the key, the operand is widened across the whole ring at all four spellings of equality, and every equality filter over a not-yet-rotated row would answer nothing. **A caller may not send a ciphertext-shaped value** (`FJS-715`) — the same check gates the HASH path, so a `v1.`-shaped value used to skip hashing entirely. **A decrypt that fails is RAISED** (`FJS-716`), naming the kid wanted and the kids held; the one column that still degrades is `@secret(rotate: false)`, because that loss is declared and raising would make the whole row unreadable to punish a column the app already gave up.
- **A relative `database { path }` resolves against the process CWD, and a schema can be told otherwise.** The same schema then means a different file depending on which directory the command was typed in, and nothing fails — SQLite creates the file, litestone creates the directory above it, and every tool reports on the new empty database (`FJS-449`: studio served an empty `db/db/shop.db` for nineteen hours; a `vite build` from a surface root prerendered twelve product pages as **zero products, exit 0**). `resolveFrom: 'schema'` anchors to the APP ROOT — the schema file's directory, or its parent when that directory is `db` — which is what every litestone CLI call site does. **A schema assembled in memory says where it would have lived**: `path:` beside `schema:` when the app read a file and appended to it, or `resolveFrom: '<dir>'` (a directory or a `file:` URL) when there is no file at all, which THROWS on an anchor that is not a directory. `createTenantRegistry` takes `path` the same way, and there it matters twice: `tenancy { dir }` and `tenancy { registry }` are written against the SCHEMA FILE's own directory, not the app root — the one place the two bases differ. An override (`db`, `databases: { … }`) is unaffected and must be: code is written against the process. **The default stays the CWD**, because isolation-by-CWD is a real contract a seed test depends on. **Creating the DIRECTORY for a database is announced** — creating the file is ordinary, the directory is the signal every instance of this had in common, and the message names the cwd because `db/shop.db` from two different directories prints the same string.
- **`createClient({ db })` names MAIN's path and nothing else.** It overrides a declared `database main`, so `db: ':memory:'` is the in-memory test client; a SECOND declared database keeps its declared path regardless. `databases: ':memory:'` is the shorthand that moves them all, jsonl and logger included. Precedence: `databases: ':memory:'` > `databases: { main: { path } }` > `db` > the declaration.
- **A scaled column is bounded at 2^53 and a plain `Int` is not.** `Int @scale(n)`/`@money` promise an exact round trip, and the round trip goes through a JS `number` at both ends — `bun:sqlite` answers a `number` on every path, a column read and an aggregate alike, so past 2^53 the rounded double is stored and a DIFFERENT number is read back in silence, two minor-unit values collapsing into one (`FJS-583`). Nine places therefore leaves **seven** figures in front of the point rather than the nine that reasoning from the 64-bit column gives. Both ends refuse it — the boundary by name, in a different sentence from the fraction refusal because they are different mistakes, and the column with a `CHECK`, because a migration, a seed, a raw statement and `asSystem()` never reach the boundary. **The column whose values genuinely go past 2^53 is `Int @big`** (`FJS-D174`): it uses the whole 64 bits and the price is that values cross as a **string of digits**, since a `BigInt` is exact and `JSON.stringify` throws on one — which is every response, every frame and every audit snapshot, and node-postgres answers `int8` the same way. Storage stays `INTEGER`, so ordering, a range filter, an index and `AUTOINCREMENT` are all still numeric. **It emits no `CHECK` and `@scale` does**, which is a measurement rather than an inconsistency: `STRICT` already refuses all three ways a wide value stops being exact, so `@scale`'s bound is the narrower one and only a CHECK can hold it, while `@big`'s IS the column's own. `@@noStrict` is the one shape that earns it. `litestone import` maps a foreign `BIGINT` onto it, keys and foreign keys exempt. **`@scale` stops at 9 and `FJS-575` closed rather than raising it** (`FJS-D154`): a precise accumulated total fits no 64-bit integer at any scale and belongs to rounding and allocation.
- **The migration differ compares an ENUMERATED list of dimensions, so *in sync* means *in sync on every dimension it reads*.** Six issues of litestone's history are one dimension arriving in the DDL emitter and not in `diffSchemas` — generated columns, CHECK, table uniques, index order, index sorts, index predicates — each reading as a green tick over a database that is not the declared one. There is a catch-all under it (`FJS-D186`): once the enumeration has spoken, the two `sqlite_master`s are compared whole and the leftovers are `diff.residue`, announced by `autoMigrate` and printed by `db push` and `db diff`. It is **not part of `hasChanges`**, because nothing there can write a migration for a dimension it cannot see and a change that never resolves would migrate on every boot for ever; and it does not block, because the commonest cause is the **adoption door** rather than a defect — a real database has a `COLLATE NOCASE` on its email column or a hand-written index, which this language cannot say. `{ acceptResidue: true }` is the caller stating it, beside the `acceptDataLoss` it is modeled on, and it clears the record rather than filtering the output. **Adding the missing dimension is what makes it go quiet**: a residue is a question about the differ, and the answer is usually a comparison it is not making yet.
- **A new column with an EXPRESSION default costs a table rebuild, and one with no default at all is refused.** SQLite takes an expression default in `CREATE TABLE` and refuses one in `ALTER TABLE ADD COLUMN`, where it wants a constant — so `@default(now())` on a new column is a rebuild, and a rebuild is itself refused where the app made its own index or trigger over that table, which has to be moved into the schema first. A `NOT NULL` column with no default is **blocked whether or not the table holds rows**, deliberately: migrating an empty table and refusing a populated one migrates on every developer's machine and blocks at the deploy. `autoMigrate` answers `{ state: 'blocked', reason }` and prints it — it used to answer `migrated` with the reason inside a SQL comment, so the app ran against a table missing a column its own seed declares and every write of it was silently stripped (`FJS-604`, `FJS-605`).
- **Litestone emits columns verbatim camelCase and `DateTime` as ISO-8601 TEXT.** Hand-written SQL assuming snake_case or epoch-ms will not match.
- **Every timestamp litestone writes comes from the CLIENT's clock, and a raw `UPDATE` therefore stamps nothing.** `@default(now())`, `@updatedAt` on create and on update, `@@softDelete`'s stamp, `now()` in a policy and the retention cutoff all read `createClient({ now })` — which is what makes `advance('100d')` then `$retain()` a test anybody can write. **`@updatedAt` is not a trigger** (`FJS-531`): a trigger reads SQLite's clock and nothing else, so a frozen clock cannot be staged — and RETURNING is evaluated before an AFTER trigger anyway, so naming the column in the SET clause only ever helped while the two values differed (`FJS-396`). The column DEFAULT stays as the floor, so a raw INSERT still stamps; a hand-written UPDATE owns its own. What no clock reaches is a raw statement and a `@derived` expression reading `now()`, which is compiled once at startup.
- **An audit row says WHERE the write came from, and junction is what tells it.** `correlationId` · `source` (the call, `orders.pay`) · `origin` · `ip` · `userAgent` · `tenant`, filled from `db.$logContext(fn)` — a function the client is handed and calls when it builds an entry, the same shape as `now` and for the same reason. The direction is forced: litestone must not learn that a request exists (Invariant 1), so junction installs a closure over its own store, in `createApp({ db })` and on the per-tenant tap. A throw in it costs the columns and never the write. `correlationId` is the one no audit package in the field carries and it is the join `$.log` exists for on the other side; `source` stands where laravel-auditing puts `url`, because the same write arrives over HTTP, over a socket frame with no URL, and from a job with no request at all. **`db.$logStats()`** answers `{ written, dropped, lastError, lastWrittenAt, lastDroppedAt, lastRetainAt }` and junction puts it on `/metrics` as `audit`, because `fireLog` is fire-and-forget and a trail that stopped recording reads exactly like an app doing no work.
- **A `driver logger` trail is written by every process, and the index database's write transaction is what serialises them** (`FJS-D180`). A byte offset cannot be computed before an append or recovered after it — `statSync(f).size` then `appendFileSync` is two syscalls — so `create`/`createMany` hold `BEGIN IMMEDIATE` on the companion index across the pair, and the index row naming the offset commits with it. A transaction rather than a lockfile, because a lockfile has no answer for a writer that dies holding it. **The sidecar is in WAL and compaction must never unlink it**: an unlink leaves `-wal`/`-shm` behind and a live process's next write then answers `ok` while writing into an inode with no directory entry, where a rollback journal answers `SQLITE_READONLY_DBMOVED` — WAL turns a crash into a lie, so the two are one decision. **Compaction holds the same lock across its READ**, not just its write-back: locking the write alone leaves the window and widens it, because compaction then waits while the writer appends. So an append waits for a compaction, which is the correct trade — the alternative is a destroyed audit row. `packages/litestone/src/drivers/jsonl-index.js` is the one owner.
- **A `9`-gated table cannot be tidied up, by anything** — `asSystem()` grades 8, so a test or a drive that writes to an append-only model cannot remove its own fixtures through any client, and every row held by a foreign key from one is stuck with it. `example`'s `verify:retro` is the case: leaving the rows was not an option either, because a backdated employee goes on producing arrears and `verify:payrun` sweeps every employee there is. The way out is `asSystem().sql`, which enforces no gate and no policy and binds to TABLE names — worth budgeting for when a `9` goes on a model a fixture writes to.
- **An audit row names the TABLE, not the model** — `model: 'pay_window'` for `model PayWindow`, where every other name that crosses a boundary is the model's. So `auditLogs.findMany({ where: { model: 'payWindow' } })` is a 200 with no rows, which reads as *this model is not logged* and is indistinguishable from a missing `@@log(audit)`. `before` and `after` are JSON STRINGS and `records` is a stringified array of ids, so nothing in a JSONL trail joins to anything: it is a record and not a dimension. **`@@log` may name a SQLite database instead**, which is what makes it one — `database main { … model AuditRow }` with `model` REQUIRED there (there is nothing to synthesise into, and a table the app never declared carries no gate, no policy, no index and no migration). A declared trail is an ordinary model: its `Json` columns come back parsed, it joins to `User`, a row policy scopes it, a cursor pages it, litestream replicates it, and `@@gate("5.8.9.9")` makes it append-only at the Data boundary — the engine's own write still lands, because it goes through a system context at 8. Writing `9` for create instead gives a trail that migrates, snapshots, passes every check and refuses the first row the engine writes.
- **An effective-dated write BACKWARDS overwrites the prior belief, and only the log holds it.** A window is closed by moving `effectiveTo`, so backdating a correction moves it to an earlier instant in place — after which the row cannot say what it once ran on, and an as-at read at a PAST date answers differently than it did before. That is correct, and it is the opposite of what a forward raise does, which is why the two are worth knowing together: `effectiveFrom`/`effectiveTo` holds VALID time and nothing holds *when we learnt it*, so **anything that must reprint as it was issued has to have FROZEN it** — `example`'s `Payslip` names the `PayWindow` it was computed under and copies every figure, which is the only reason a backdate cannot reprint history. A report that re-derives from the terms table instead is correct until the first correction and wrong silently afterwards (`example`: `verify:retro`).
- **`@@log(audit)` records a WRITE; `db.$audit()` records an EVENT — and the second one throws.** A sign-in is not a write to `User`, and a *failed* one is not a write at all, so nothing the logger can see names the actor or the attempt. `$audit({ operation, model?, records?, actorId?, meta? })` is the one way to put a row there by hand — an unknown key is refused by name, `actorId` defaults to the calling client's principal (a system context has none), and a stated value beats `onLog`'s. **It awaits and throws where `fireLog` is fire-and-forget**, because there the record is a side effect of a write that already succeeded and here it is the point. `meta` is NOT redacted — it is yours, so do not put a secret in it. On every flavor of client.
- **A per-call flag the model cannot SATISFY is refused by name, and so is a method.** `onlyDeleted` on a model with no `@@softDelete` used to answer the LIVE rows — the opposite of the question, with nothing saying the flag had not applied — and `search()` below `@@fts` threw a bare `Error` that reached a caller as a 500. Both are `CapabilityNotDeclaredError` now: **400**, naming the model and the attribute that would make the request legal — `onlyDeleted`/`onlyTemplates` on every read and write, plus `search()`, `optimizeFts()`, `restore()` and `transition()`. **`withDeleted`/`withTemplates` do not refuse**: they ask to widen, and a model that hides nothing already answers everything, which is what generic tooling (Studio's row browser, a *show deleted* toggle) is asking for.
- **A cursor and an offset never combine, and `$after` wins.** A caller sending both has named no position either one of them means. Growing a window is also not a chance to ask a different question — `more()` reuses the last `load()`'s query and directives, because a cursor minted under one ordering names no position in another, so a new filter or a new sort is a `load()`. And **a list is a set of ids in an order**: one row cannot be in it twice, which is what stops a row that arrived on the socket mid-scan from being in both the list and the next slice.

**An unknown `where` key is refused, on a read as on a write** (`FJS-D169`). SQLite resolves an identifier it cannot bind as a string literal, so the query does not run broader — it runs a different one and answers nothing. `client.service('x').find({ limit: 100 })` is the shape that reaches it: the FIRST argument is the filter, `limit` belongs in the second. `find()` answers the list envelope; `findData()` is the rows.

**API**

- **`ctx.params` does not exist anywhere in Junction, and `ctx.route` is not it.** A `ServiceContext` splits into `auth` (the principal) / `client` (`ip`, `userAgent`, `headers`) / `route` (path captures alone) / `locals` (per-call scratch, where `withLitestoneDb` puts `db`); a `TransportContext` carries the same `route` and puts headers at `ctx.headers`. **The four have four different rules and that is the substance** — `auth` is frozen and PROPAGATES to a nested call at any depth, `client` propagates, `route` is router-only (`{}` internally), `locals` is fresh per call and does NOT propagate. `packages/junction/CLAUDE.md` § The two contexts is the reference and `tests/context-contract.test.ts` runs it. Stale Feathers idioms survive in old notes; reading `ctx.params.user` yields `undefined`, so a role check silently passes for everyone. Also: `before: { all: [...] }` applies to *every* method, machine-facing endpoints included.
- **Absent is not null on `auth`.** A call naming no `auth` inherits the principal in scope; `{ auth: { user: null } }` means *as nobody, deliberately* and stays anonymous. Same distinction Invariant 9 makes about a patch, and it is the only way to ask what a stranger would see.
- **The gate runs before anything an app wrote, and `validated:` is the phase after the derived layer.** `gateAuth` is a service-level AROUND hook, so it wraps every before hook at either scope; the validators (`autoValidate`, `autoFilter`, `autoSort`) still trail the app's, because a before hook shapes `ctx.data` and it is the shaped payload that must satisfy them. As one appended layer instead, an app rule that reads the database reads it for strangers: on `example` an unauthenticated POST naming a customer that does not exist answered 400 and the same request naming a real one answered 401, an existence oracle over a gated table (`FJS-403`). Leading the per-method list would not close it, since `resolvePipelines` runs `before.all` ahead of `before.<method>`. The order is **`around(gateAuth) → before → validated → method → after`**, and `validated:` is where a rule that reads the database off `ctx.data` belongs — it needs a caller the gate has graded and a payload the validator has coerced (`FJS-D124`). An APP-level `around` hook is still ahead of the gate, and must be: `withLitestoneDb` establishes the client it grades against.
- **A query string is PARSED, and the schema still wins.** `?qty=5&live=true&qty[gte]=3` reaches a service as numbers, booleans and structure — `@frontierjs/toolbelt/query`, one module for junction's transport, junction's client and sierra's router. Before it the two TRANSPORTS disagreed and the socket was the correct one: it spreads filters into a JSON frame, while HTTP `String()`d every scalar, `JSON.stringify`d every operator object and dropped `null` outright, so an app worked until its socket dropped and then silently filtered on text (`FJS-450`). **A string is a number only if it round-trips** — `'007'`, `'+1'`, `'1.50'`, `'1e5'` and a snowflake id all stay text — and `?code="5"` is the escape for the rest. **Where a model exists it has the last word**: `id String` filtered by `?id=5` reads 5 and Litestone converts it back to `'5'`. Stated gotcha, not a defect.
- **Raw routes (`app.get`/`app.post`) take `{id}`, not `:id`** — `:id` registers as a literal segment and 404s silently forever.
- **A plugin reads `junction.config.js` in `boot()`, never in `register()`.** `configure()` runs `register()` synchronously and junction does not load the config file until the `load-config` start phase, so a block read in `register()` is the config as it was *before* the file. Every app configures its plugins at module scope, which made caravan's whole `caravan:` section unreachable — `admin: true` in a config file mounted nothing, and the only app it appeared to work for was one that hand-loaded the config and passed it to `createApp` (`FJS-431`). `boot-plugins` runs after `load-config` and before `service-routes` and `listen`, so routes mounted there are still served.
- **A missing config DIRECTORY is not a missing config file.** An absent file is an optional miss and stays silent — an app may declare nothing. An absent directory is a path that resolves nowhere, and `loadConfig` now warns naming it: `basecamp` read `api/config` for its whole life without that directory existing and took junction's defaults every boot, with its CORS `*` for everyone (`FJS-430`). `fli check`'s `surface-config` is the static half.
- **`apiPrefix` moves EVERY route the app registers**, auth's `/auth/login` and caravan's `/jobs` included, because the `app.get`/`app.post` shortcuts are its one owner. A path that must not move is registered on `app.http.router` directly. An app that sets a prefix proxies one path, not one per plugin.
- **An `Idempotency-Key` on a mutating request now executes once and replays the first answer** — claimed in `callService`, so it holds over HTTP and the socket alike. The replay runs **no hooks**, so an app effect living in one does not happen twice *and does not happen on the replay at all*. Keyed by `(service, method, principal, key)`; a failed call releases the key, an in-flight duplicate is a retryable 409.
- **Every READ carries `$withDeleted`; on a WRITE only `update`/`patch` by id do.** That is the escape hatch a `SoftDeletedUniqueError` points at — a deleted row keeps its `@unique` values, so *move the value aside* is `PATCH /{service}/{id}?$withDeleted=true`, and without it there is no request an app can make that frees the slot. The default is fail-closed: the same request with no directive is a 404. **A bulk patch does not read it** — `bulkByRow` selects its targets through litestone's own filter, so a widened WHERE would match nothing. **`remove` declines it by NAME**: against an already-deleted row the only action left is to destroy it, the one write that defeats `@@softDelete`, and a directive on the ordinary DELETE would hand that to every caller who may remove a row with no separate permission to grade. It always refused; it refused with a 404 about a row that is plainly there, which reads as the row being gone rather than as the flag being declined. Graded on the REQUEST rather than the row's state, and silent on a model that hides nothing (`FJS-523`).
- **`hasRoute()` is a matching question, not an existence one** — every app registers `GET /{service}`, which matches almost anything. Use `hasExactRoute(method, path)` for "is this mounted", `routePaths(method)` for what landed where.
- **Where an app's services are is PROBED, not derived** — `./services` then `./src/services` beside the ENTRY file, first one that exists, and `resolveServicesDir` is the one owner of that list. A missing directory is a silent no-op, so the app boots, `/health` answers, and every route those services would have mounted is a 404 (`FJS-458`). The miss is on the boot banner: `autoload=` names the directory or the candidates that were looked at. **A DECLARED directory is never probed around** — `services: { dir }` or `createApp({ autoload })` that is absent is reported by name rather than replaced, because a relative path resolved against the wrong working directory lands on nothing and looks exactly like an app with no services. **Under a test runner the entry is the TEST FILE**, so an app that needs its services in a test states an absolute path.
- **What an app ANSWERS, what it RUNS with no caller, what it can TELL somebody, and who a caller BECOMES are each committed beside the API, in `api/`.** Four snapshots, each written by `junction <cmd> --app <module> [--services <dir>]` and each read off a BUILT app, because none of the four is a fact a file tree can answer: a hook chain resolves at construction, a job file registers itself by being autoloaded, a notification takes its type from its own FILE NAME, and a principal resolver is wired in application code. So the module must expose an app **without listening**, which is what the `api/index.ts` / `api/src/app.ts` split is for (`fli check`'s `surface-src`); an app that made them one file guards `app.start()` with `import.meta.main`. They sit in the surface they describe, the same rule `db/`, `web/` and `site/` follow, and the `snapshots` CI phase fails a stale one.

| Snapshot | Command | Holds | The silence it breaks |
| --- | --- | --- | --- |
| `surface.snapshot.md` | `junction surface` | methods after the policy, custom methods as `collectCustomMethods` resolved them, the hook chain in RUN order with the derived hooks leading it, every mounted path with `apiPrefix` applied, plugins in configure order | a 405 in production for a verb a `methods:` list stopped naming |
| `jobs.snapshot.md` | `junction jobs` | every registered handler's declaration — queue, cron, zone, attempts, retry delay — and every `app.scheduler` timer, expression as written | a schedule that stops being registered is *nothing happening* (`FJS-327`, `FJS-328`) |
| `notifications.snapshot.md` | `junction notifications` | every declared type and the transports it can format for | a type that stops being registered THROWS, at the moment somebody was owed a message, usually inside a job, hours after the deploy |
| `principal.snapshot.md` | `junction principal` | tenancy · resolver · claims · standing · what the rules reach · the three refusals · per-tenant configuration | a resolver emitting the WRONG tenant leaves every other artefact byte-identical and CI green (`FJS-514`) |

Four rules cut across them. **The two job registries are separate sections** — `app.jobs` survives a restart, `app.scheduler` does not and runs in every replica (`FJS-D36`) — and *no queue installed* reads differently from *a queue with no handlers*. **Names, never values, and no live state**: a claim's name is a fact about the app and its value is a caller, and a next run or a queue depth moves between two boots. **A duck-typed registry that is absent is a stated absence**, a different fact from one that found nothing. And **a notification's type is PERSISTED** (`notifications.type`, read by the browser to pick a renderer), so a type that moves here orphans every row written under the old string. **The cost of living in `api/` is that the app must boot from there**: the `snapshots` phase reruns each generator from the snapshot's own directory, and junction's `configPath` defaults to `./api/config` against the CWD, so an app that does not state it describes an app booted on junction's defaults. An app that moves them states `configPath` anchored to its own module, exactly as it states `autoload`, and anchors any relative path its config carries.
- **An irreversible effect belongs in `ctx.afterCommit(fn)`, not in an `after` hook.** `after` is after the METHOD: hooks run in sequence, so an email sent from one goes out and a later one throwing still fails the call — and under `transactional:` the row is rolled back with the email already gone. What is queued runs once, on the success path, after the announcement, and after the commit where there was one. **Observer tier** — a throw is logged and emitted, never reported as the call failing, because the write is committed and the broadcast is out. **Not durability**: a crash between the two loses the effect, and `ctx.enqueue` is the verb that survives it
- **`ctx.enqueue(job, payload)` is the durable half, and it is a second VERB because a closure cannot be persisted** (`FJS-D35`). It writes a row into the app's OWN database inside the calling method's transaction, so the intent commits with the write or rolls back with it; `app.configure(outbox())` is the relay that hands it to `app.jobs` and marks it delivered. **The row can be in no other database** — litestone opens one connection per declared `database` block and holds one transaction manager over main's, so a row in a second block survives the rollback that was supposed to take it. The queue stays a separate file, which is what makes the handoff **at-least-once**: the relay dispatches under the OUTBOX ROW's id and caravan's `dispatch({ id })` treats a taken primary key as work already queued, so a crash between the two replays into a no-op. Refuses by name outside a transaction, without the model, and with no relay — a row nothing delivers is worse than a refusal. `fli outbox:install` writes the import line, and `/metrics` answers `outbox: { pending, delivered, failed, lastPassAt }`.
- **A payload key that is not a column is declared `@transient`, and it arrives at `ctx.transients` — never at `ctx.data`.** The mirror of `@computed`: no column, written by the caller, never read back (`FJS-D23`). `autoValidate` validates it with the model's own rules and then LIFTS it off the payload, because the Data boundary refuses a transient key by name — a service passing `ctx.data` on whole fails the write rather than the field. Fresh `{}` per call, does not propagate, `{}` on a model that declares none. **A bulk write carrying one is refused**: the rows a service receives are the ones that passed validation, so an index-aligned array would pair one row's value with another row. Undeclared is still deleted in silence, which is what the declaration is for.
- **`update` is `patch` with an id REQUIRED, and it MERGES** (`FJS-D179`). Feathers' word for it is a full replace and this is not one: the write is litestone's `table.update`, so a `PUT` stating only `title` leaves every column it did not name where it was. What the id buys is that a REST client's `PUT` can never reach patch's query path, which is a bulk write. It was validated against the CREATE-mode schema until `FJS-663`, which omits `@version` — so the version a `PUT` carried was stripped and the Data boundary refused the write for not carrying one, making every `PUT` to a versioned model a 400 naming the field the request had just sent.
- **The METHOD decides list vs single.** `find` must answer a list or it throws `ResultShapeError`; an array is a list; the bulk `{data,errors}` protocol is a list on any method; everything else is a single and travels whole. A service answering one thing names it and calls it as a custom method; a summary alongside rows is its own named method.
- **A header the caller varies per call must be DECLARED, or it works until the socket connects.** `config.http.callHeaders: ['x-cart-token']`; the client sets it with `setCallHeader`. A WebSocket frame has no headers of its own, so the value rides `meta.headers` and the server merges only declared names — undeclared, the header is simply absent and whatever reads it sees nothing, which for a token-scoped row policy is an empty result with a 200 or a 404. The same declaration is what gets it past a cross-origin preflight. What may NOT travel this way is the identity: it belongs to the upgrade.
- **The client's address is declared, never discovered.** `X-Forwarded-For` is a list the caller can start and the shipped nginx template APPENDS to (`$proxy_add_x_forwarded_for`), so the leftmost entry is their claim and the rightmost is what nginx observed. `http.trustProxy` says how far back to believe it — `false` (the socket alone), `true` (one hop, which is what that template is), `<n>` hops, or trusted proxies by address/CIDR — and the chain is read from the RIGHT. Both ways of getting it wrong are live and neither is visible from the other: reading the leftmost hands the rate limiter's key to the caller, and leaving it unset behind a proxy gives the whole internet one bucket — which is what every deployed app had, since the option existed on the transport and reached it from no config key at all (`FJS-744`). A CIDR list only works if `::ffff:10.0.0.1` is read as the v4 address it is, which is what a dual-stack listener reports.
- **A socket stays alive because the SERVER pings it, and an app calls nothing.** The channels plugin pings an idle connection every 15s and evicts one silent for 40s; any frame counts, and the browser client answers from its message handler rather than a timer — a timer is throttled to ~1/min in a hidden tab, slower than the eviction window. `client.startHeartbeat()` is for a client whose server predates this and is otherwise the wrong reach; nothing called it for as long as it was the only half that existed, so every app flapped on a ~35s cycle with a reconnect hiding it (`FJS-366`).
- **Never call `ws.send()` directly.** Bun answers `-1` for buffered and **`0` for discarded** past ~16.9MB of unacknowledged data on one socket (`maxBackpressureLimit` is accepted and ignored). `transport/send-queue.ts` is the one owner of a send: it holds a dropped frame, flushes on `drain`, preserves order, and past `http.wsMaxQueued` (8MB) closes with 1013 so the client reconnects.
- **Caravan owns the clock; `app.scheduler` is in-process only** (`FJS-D36`). Two timers exist and they are not the same feature — `app.scheduler` has no persistence, no retry and no principal, and is gone with the process; `app.jobs` is durable work. **A timer that dispatches into a queue is the QUEUE's schedule**, registered with `app.jobs.schedule(name, expr, fn)`: firing `app.jobs.dispatch(…)` off `app.scheduler` buys a clock with none of the queue's durability while looking like it has it. **Caravan's clock is safe to run in two processes and junction's is not** — a cron fire is dispatched under `cron:<job>:<epoch-minute>`, so a second replica's fire is a no-op rather than a second row, and a `running` row is owned by a heartbeating instance so recovery reclaims only what a crashed one left (`FJS-294`). A schedule that came from a database ROW also needs `app.jobs.unschedule(name)` when the row stops being true, and re-registering at boot — neither registry survives a restart. `app.scheduler` is for work with no row behind it: a cache sweep, a metrics tick.
- **A background job runs as whoever asked for it, and a job nobody asked for runs as the app.** Caravan records the principal in scope at `dispatch()` and Junction re-resolves them when the job runs (`app.runAs`), so `ctx.app.service('x').patch(…)` from a handler names no `auth` and inherits one. **An id is stored, never a session** — a caller demoted between asking and running is graded at the standing they hold *now*, where a replayed snapshot is a privilege outliving its own revocation. No enqueuer (a cron fire, boot) resolves to `createApp({ system })`, the one place an app says who it is acting on its own behalf; declaring none is valid and gives `null`. `example/api/src/core/gate.ts` is the pattern. Still true: `db.asSystem()` is the wrong fix, because it writes at the Data boundary where nothing announces and every open tab keeps the stale row.
- **`IAuth.sessionFor(userId)` is how a principal is rebuilt without a credential**, and it must never be wired to anything a request can name — it proves nothing. Optional; a provider lacking it makes `runAs(userId, …)` throw by name rather than quietly downgrade.
- **Junction resolves every Bearer token through `IAuth.verifySession()` and calls `verifyApiKey` nowhere** (`transport/http.ts`). One door: a key is only verified if the *provider* falls through to its own `verifyApiKey`. A third provider inherits that job.
- **A job attempt has no bound unless one is declared, and `oldestRunningMs` is how you see the ones that do not.** `timeout` on a handler, a job file or a queue; absent means no bound, honestly, because a default would kill every legitimately long job in every app that upgraded. A timeout is an ordinary failure — it counts as an attempt and retries on the same ladder as a throw — and **it does not stop the handler**, since nothing in JavaScript cancels a promise: the abandoned invocation may still be writing while the retry runs, so it is announced (`caravan.job.orphan`) rather than swallowed. A handler that never yields is unreachable either way; the timer needs the event loop. For the jobs nobody bounded, `stats().queues.<q>.oldestRunningMs` separates a stalled queue from a busy one — `running: 1` reads identically for both — and it is asked of the database, so another replica's stuck job is in the answer (`FJS-295`). `drainTimeout` bounds `stop()`.
- **Caravan's `unique` is a lock on work IN FLIGHT, not an idempotency key.** Once a job is terminal the key is free. A key built from a row id is not one either — SQLite reuses ids.
- **A job in `jobsDir` is named by its file and declares its own schedule.** `send-email.job.ts` is `send-email`; a `defineJob` naming anything else is refused at load rather than registered, because a handler answering to `send-emial` is a dispatch that silently never runs. `cron` is a `handle()` option — a `*.job.ts` file carrying one is scheduled by being autoloaded, and `schedule()` is sugar over the same registration. The definition is also the dispatch handle: `dispatch(sendEmail, data)` states no name and types the payload. **The queue's database opens on first use**, which is what lets every key of `junction.config.js`'s caravan section apply — and means a dispatch before `app.configure(…)` opens it at the DEFAULT path.

**UI**

- **The route table is a naming convention over a file tree, so it is committed too.** `sierra routes --config config/sierra.config.js`, run from the app's **web root**, writes `routes.snapshot.md` — every URL with its file, the layout the scanner resolved (none where a page declared `reset`), the meta a layout pushed down onto every page under it, and what each `_module.mesa` wraps. On a `static` target **`publishes:` leads the file** in its own section: it is the one line that turns off the fail-closed publish check, and it lives in one page's frontmatter. One config is one target and its name carries — `sierra.static.config.js` → `routes.static.snapshot.md`. The `snapshots` CI phase fails a stale one.
- **A node is the synced truth for a row; a view remembers what it READ.** `resource.record(id)` is live, so a push moves the value on screen — and it does not move the `@version` this screen holds, which is why the two are separate (`FJS-341`, `FJS-D138`). A draft belongs to the form and enters neither. Two more that are less obvious than they look: a node write with the **same object** does not notify, because a push writes the node on arrival and the list it lands in writes it back through while assembling itself; and **removal is the record view's own state, never the node's** — clearing the shared node would shorten every list holding the row before that list ran its own removal accounting, and two resources over one service share a proxy. **Optimism cannot be asserted in a browser here**: every in-flight marker a page offers is also true for a moment AFTER the call answers, because the WS push lands before the `await`'s continuation runs, so *the status moved while the toast was spinning* passes with the optimistic write taken out. It is asserted where it can be negative-controlled, in `junction/tests/nodes.test.ts` and `sierra/tests/resource-record.test.js`.
- **A `@from` column moves when a CHILD row is written, and nothing announces the parent.** `Plan.currentPrice` is `@from(PlanVersion, max: price, where: "effectiveTo IS NULL")`, so repricing writes a `PlanVersion` and the `Plan` row does not move — no broadcast names it, and a record view watching the plan holds the old price for ever. There is no event for a live store to apply, so the screen that made the change is the one place that knows: `record().refresh()`. Same shape for every aggregate a parent carries.
- **A live store holds what its last `load(query)` asked for, so a patch can take a row OUT of it.** A row moved out of the filter is removed rather than updated in place — there is no other event for leaving a filter. A record the schema cannot judge (a `select` dropped the filtered column, the filter names a relation, `$search`) triggers a reload instead of a guess. The row is also PLACED — `orderBy` decides where, and the first page trims what falls past `limit` — but **past page 1 a new row is refused**, because nothing in a browser knows whether it belongs on an earlier page. That, and a gap a removal leaves, count on `resource.stale`, which `load()` clears and a view renders as *3 new — refresh*. **`changed` is the event that names no row** — what a bulk write or a `select: false` write announces — and the store's answer to it is the reload it already gives an undecidable record, coalesced per burst. Not `stale`: a counter describes a gap the list knows the shape of, and *some unknown rows moved* is not one.
- **`@version` is the revision a screen READ, and a push does not move it.** `createResource` records a version off every call result and off a load that was not superseded — never off the store, because a WS push reaches the store as an upsert, moves the number, and moves nothing the person is looking at. Remembering it off the store makes a save from a screen holding a DRAFT carry a revision nobody there had read, which wins the race the column exists to lose: the other person's write erased with the guard in place and no error anywhere (`FJS-341`). The cost is a 409 where a silent success used to be, and that 409 is the right answer — a caller who has genuinely read the newer revision states it, which `<Form record={row}>` already does by editing the row whole. **The 409 says which two revisions disagreed**: `VersionConflictError` declares `data = { model, field, expected, actual }`, junction's error boundary carries a declared plain-object payload, and `resource.conflict(err)` answers the numbers where `fieldErrors()` answers the sentence — the half a status and `retryable` cannot express, which is what a *reload* against *overwrite* prompt needs. **The API-side sibling**: junction derived ONE create-mode JSON Schema and compiled the patch validator from it, so `autoValidate` stripped the version off every patch and `@version` did not work through a service at all (`FJS-335`).
- **A write drops the columns the SERVER owns, and the version column is the one exception.** `@system`, `@generated`, `@computed`, `@from`, `@version` and a tenancy stamp all reach the client as `readOnly`; a create is safe because `make()` never seeds one, and an EDIT form is not, because it is handed a row the server wrote and sends the whole thing back. The Data boundary refuses `@system` BY NAME, so the person sees a 403 about a column that is not on their screen (`FJS-526`). `stripReadOnly` runs first in the resource's create/patch pipeline — ahead of coerce, blank and validate, so nothing judges a value that will not be sent — and it takes a KEEP list rather than dropping everything read-only, because `@version` is marked read-only and is the one the server requires back. A key with no field rule behind it is left alone: a `@transient` is legitimate, and guessing there is how a strip breaks a working app.
- **A `File` column's control sends the bytes WITH the record, and there is no upload step.** A `File` anywhere in a payload turns the create or patch into `multipart/form-data` at the client, the bridge merges it back into `ctx.data`, and `FileStorage` stores it — so submitting the form IS the upload, on the one route carrying the gate, the row policies and `@accept` (`FJS-409`). What the field holds until then is the browser `File` itself; the resource's write pipeline passes one through untouched. **The value has three shapes and only one of them is ever sent**: `undefined` where nothing is set, the URL a READ resolved the stored reference into, or the `File` just chosen. `undefined` back from the control means *leave the stored file alone* and `null` means *clear the column* — a form that conflates them drops a photograph on every edit that did not touch it.
- **`createResource` coerces, blank-strips and validates by default.** A bad create throws `ResourceValidationError` in the browser with the request never made, and an untouched text box writes NULL rather than `''`. A resource whose service accepts a shape the model does not describe needs `{ validate: false }` — the symptom otherwise is "the button does nothing" unless something renders the throw. `<Form>` renders it.
- **`@system` is the column an application writes and its caller does not** — readable by anyone, refused on write by name. The orthogonal sibling of `@guarded`, which locks both directions. It reaches the client as `readOnly`, so a generated form does not offer it and `make()` does not seed it; it is **out of create-mode `required`**, because listing a server-written column there refuses every create in the browser naming fields the caller was never meant to send (`FJS-095`). The app fills it by naming the column on the write — `db.order.update({ where, data, system: ['trackingCode'] })` — which keeps the gate, the row policies and the audit actor, where `asSystem()` drops all three to write one value. A required `@system` column that nobody filled fails at the write, saying which side is missing.
- **`<Form {resource} />` with no children IS the form** — every writable column in schema order, each with the control its type implies, over the one table in `field-rules.js`. Children win (the caller is writing it); `only` narrows and orders, `except` removes, `auto` forces either way. **DEFAULT children, and only those** — `_auto` is `auto ?? !$slots.default`, so `slot="actions"` composes with the generated list rather than replacing it, which is what lets a Resource's own default form (Invariant 18) supply a button row without turning generation off for every page under it. A `{#snippet actions()}` beats the slot where both are given, because a prop is the more specific statement. A column the table cannot place is **warned about by name** rather than dropped. **The shape to beware is an `{#if}` around a `slot=` child**: `slot=` is an attribute on an ELEMENT, so the BLOCK is default content, `$slots.default` is truthy, and the form renders with no controls in it (`FJS-607`). It is not silent — a form that generated nothing AND holds no control, over a resource that had fields to offer, warns naming them, asked of the DOM at mount because children arrive as opaque content and counting them says nothing about whether any is a control. The fix is to render both buttons unconditionally, which is what every resource file here does.
- **Everything a component reaches for is on `$`, and `$` is legal only as the object of a member expression** (`FJS-D132`). `$.onMount`, `$.emit`, `$.tick` — the bare `$onMount` spelling is refused by name, pointing at its replacement. **Five members are the exception and the bare spelling is the CANONICAL one there** (`FJS-D135`): `$props`, `$attributes`, `$slots`, `$context` and `$async` — the ones read as a bag and a key rather than called — because that spelling sits in markup, where `$.` is JavaScript punctuation in the middle of HTML. Both spellings are one binding aliased at emit, and the bare names stay RESERVED, so declaring one at script top is refused rather than shadowing it. **`$` may not be destructured, aliased, shadowed, passed or defaulted-to**: several members are COMPILED rather than read — `$context.k = v` becomes a provide call, `$.inspect` is stripped when `debug` is off, `$.mounted` is counted for its one-per-component rule — so through a copy each one compiles, parses and silently does nothing. It does not exist in `<script module>`, which runs outside any instance; import from the runtime there, where `$onMount` and `$onDestroy` keep the bare spelling because they are module exports rather than the door. **Four prefixes and each is a different KIND** (`FJS-D137`) — `$` the door, `$:` the label (a JavaScript label, a namespace of its own, so no rule above touches it), `$$` the compiler's own locals, and `__` the CALLING CONVENTION: `__anchor`/`__props`/`__block` are the component function's parameters and `__prev` is the render callback's. `__` does not converge on `$$` because three of the four are read BY NAME out of compiled output by jetty's build plugin (`FJS-D134`); all four are reserved, so declaring one is refused rather than shadowing a parameter and failing at mount. **Two names wear a single `$` and are protocol rather than either tier**: `$class`, the prop `{class}` travels under, and `$dom`, the key a block factory answers with.
- **A Mesa instance `<script>` exports exactly two things.** `export let` is a prop, `export function` is a method on the component's instance API; every other export form is refused by name. **`bind:this` means two things** — on a COMPONENT it gives that instance API (props read through the child's own signals, so `ref.count` is live and writable), on an ELEMENT it gives the node.
- **On an ELEMENT `bind:` means the DOM writes back, so it is `value`, `checked`, `files` — plus `group` and `this` — and every other `bind:x` there is refused, naming `x={expr}`** (`FJS-D136`). Nothing changes `readonly` or `colspan` but you, so there is no second direction; and for the eight attributes whose DOM property is spelled differently (`for`/`htmlFor`, `class`/`className`, `readonly`/`readOnly`, …) there was no FIRST direction either — `bindInput`'s generic branch is `el[name] = v`, which writes a JS expando the DOM never reads. `bind:class` was the measured one (`FJS-478`). **On a COMPONENT `bind:x` is an ordinary two-way prop and is unaffected**, which is every non-form `bind:` in this repo.
- **Mesa's scoped styles do not reach into child components.** Use `:global(...)`; the selector subject carries the hash (`button` → `button.mHASH`). A dynamic `class` MERGES, never replaces — all dynamic classes route through `bindClassPassthrough`.
- **An overlay that is present is not an overlay that is visible.** Kit overlays fade in with `el.animate(…, { fill: 'forwards' })`; an assertion that only asks `querySelector` passes against a fully invisible full-screen backdrop. Assert computed opacity and hit-testing.
- **Headless Chrome delivers almost no rendering lifecycle after load.** Anything behind `IntersectionObserver` must be set up before it; `requestAnimationFrame` hangs. Working pattern: `packages/sierra/tests/fixtures/island-site/verify.mjs`. **`getComputedStyle` goes stale after a class change** — `el.matches()` and `document.styleSheets` report the new state while computed styles stay frozen, and forcing layout does not help. To check a post-click style change, read the rules that match the element.
- **A component rendered at BUILD time may import a sibling by relative path, and that had never worked.** `renderComponent` writes the compiled module to a temp directory, so `'./money.js'` resolved against the temp directory and was not there — a bare specifier survives (Node walks up to a `node_modules`) and an absolute one survives, so the only casualty was the ordinary case of a page or an island importing its own neighbor. Rewritten to an absolute PATH now, not a `file://` URL: Node takes either and Vite's import-analysis refuses the URL (`FJS-438`).
- **On a static target, dev is an SPA and the build is files, and only the build checks anything.** A `render: static` route's `load()` runs in Node at build time and its companion may never enter the browser graph (`FJS-543`). It runs on the DEV SERVER too, which is a Node process: `/__sierra/static-data` executes the loader and the browser gets JSON, so `vite dev` shows the site with its data. What the route table emits is a **fetch shim and never an import**, which is what keeps `FJS-543` closed. Two consequences: it imports the companion the way the BUILD does — a plain `import()` keyed on mtime, not `ssrLoadModule`, which rewrites the module and withholds Bun's `import.meta.dir` — so the dev server must be `bun --bun vite`, exactly as `build:site` always has been. `dev: { staticData: false }` restores the old behavior. A route on a static target that is NOT prerendered keeps its loader and runs it in the browser like any client-routed page. `target: 'static'` is the SPA's Vite config plus a prerender pass in `closeBundle`, so `vite dev` on a `site/` surface serves the routes client-routed — and the publish check, the island chunks, one HTML file per route and the refusal when a `render: static` route emitted nothing all live in the build. **A page that works in dev and fails in the build is the normal case.** **A companion is build-time only and the static build says so**: its loaders are dropped from the client route table, because rolldown otherwise follows every `.meta.js` into the browser graph — a storefront's companion imports the app's own Litestone client, and the published directory carried `db.js`, the DDL emitter and the migration engine as fetchable files on a public origin.
- **A static route that produced no page fails the build where it was broken, and warns where it opted out.** *Not found* and *no paths* are a page opting out; `load()` threw and *render failed* are a broken build and now throw naming the route (`FJS-439`). Sharing one warning list between the four puts a broken build's one line among the bundler's own, exits 0, and says *no route declares `render: static`* about a page that plainly declares it.
- **Vite injects the built `<script>` at the first textual match for the body tag and does not skip comments.** Mention it inside a comment in a hand-written `index.html` and the build succeeds, `dist/index.html` looks right, and the page loads no JavaScript. Never write the body tag in a comment.
- **A `var()` naming a token nothing defines drops the whole DECLARATION**, so a design system can be linked, matched and ignored line by line. An undefined custom property is invalid at computed-value time — `gap: var(--space-4)` is not a wrong gap, it is no `gap` property at all, and `border: 1px solid var(--border)` is no border. Nothing reports it: the stylesheet is in the bundle, every selector matches, and a browser drive asserts what a page SAYS. `example/site/` shipped its whole public storefront that way, on a Tailwind-shaped ladder the package does not have, with `verify:site` green throughout (`FJS-545`). The ladder is **named, not numbered**: `3xs 2xs xs sm md lg xl 2xl 3xl 4xl 5xl 6xl`, each rung `calc(base × var(--density))`. `fli check`'s `css-token-undefined` is the guard and it reads the table off the CSS the app installs. **A fallback is the opt-out and it means something** — `var(--knob, var(--color-primary))` is a knob a caller may set, and nothing is dropped.
- **A class name is not checked by anything**, which is the same failure one layer up and has no guard: `.list` where the vocabulary says `.rows divided`, `.input` for `.field`, `.button` for `.btn`, `.stack-sm` for a rhythm the package does not ship. `@frontierjs/css`'s `vocabulary.json` is the list — the terms with their classes, plus `anatomy`, whose entry for a term carries the one canonical markup block. Read it rather than guessing; a class nothing defines is markup that looks styled and is not.
- **A code sample highlighted with `prefix: true` loses its first character.** `glow()` strips a leading `+`, `-` or `>` as a diff/callout marker, and all three are legal first characters in CSS (`> .child`, `+ .sibling`). `--` is disambiguated; the combinators cannot be, so **a CSS caller passes `prefix: false`**.

**Repo**

- **`bun install` resolves `workspace:*` to a COPY under `node_modules/.bun/`, not a symlink.** An edit to `packages/mesa/src/compiler.js` is invisible to importers until reinstall, so a suite can go green against a stale snapshot. In-repo tests import workspace source by relative path. `packages/ui`'s hand-made symlink will not survive a reinstall.
- **Nested directories are invisible to the `packages/*` glob** — uninstalled, untested, unrunnable. Four cases, all deliberate and named in `scripts/ci-allowances.json` § nonMembers: `mesa/mesa-bench`, `oracle/mockup`, `orion/mockup/api-engine`, `toolbelt/mockup/datetime`. **A fifth is a CI note naming the path**, so the way this goes wrong is by someone reading the note as noise, not by silence.
- **Publishing a package silences every loose peer range that names it.** While a sibling is unpublished a peer of `"*"` fails at install with the name in the error; the moment it exists, the same range resolves from the registry without a word. **Below 1.0 a caret pins the MINOR** — `^0.1.0` is `>=0.1.0 <0.2.0` — which is both the behavior wanted for a pre-alpha peer and the trap in the other direction, where a stale caret excludes the only published copies. Nothing catches either shape from inside the workspace: a `workspace:*` devDep answers first and the range is never consulted. **`fli ws:exports` commits the published surface** — `exports.snapshot.md` at the root, one section per publishable package: the top-level entries its tarball actually contains (asked of `bun pm pack --dry-run`, never derived from the globs), every `exports`/`bin`/`main`/`types` target marked with whether that tarball holds it, and the peer ranges naming a sibling. A declared entry point `files:` does not publish is a broken install, decidable from the listing alone. The `snapshots` CI phase fails a stale one.

The current seams. Reach for them before grepping. They may move, merge, or change signature as long as ownership and dependency direction hold.

**Data → API**
- `$setAuth(user)` / `asSystem()` — the Data-boundary checkpoint / bypass — `litestone/src/core/client.js`
- `$tapEvents(fn)` — every write, announced. `event` is `create` · `update` · `remove` · `transition`, and a transition carries `transition` (the move's name) and `record` where the others carry `result`. **Two shapes and the write says which**: `scope: 'row'` (one row; `result` is it, or `null` where `select: false` skipped the RETURNING) or `scope: 'collection'` (`count` rows matching `where`, never built). Stated, never read off `result` — that is two facts. A bulk write's shape is the per-call `announce` — `collection` (default) · `rows` · `none`, floor at `createClient({ announce })` — because the batch size is a property of the call, not the model (`FJS-D34`)
- `withLitestoneDb(db)` — per-request scoped client on `ctx.locals.db`; auto-installed by `createApp({ db })` — `junction/src/core/litestone.ts`
- `gateAuth()` + `autoValidate()` — schema-derived 401s/400s for model services — `junction/src/core/litestone.ts` + `core/service.ts`
- `validateInput(type)` — **the same 400 for a method no model describes.** `autoValidate` derives from a MODEL and covers create/patch on a model service; every other method a service answers took `ctx.data` on trust. A `methods:` entry may be `{ method, input }`, and `input` names a `type T { … }` in the app's own seed — so the seed stays the one owner of what a shape is, and the payload compiles through the same `jsonSchemaToJunctionSchema` → `createSchema` pair, carrying `@label` and the author's `x-messages` into a 400 that renders in `<Form>` like a CRUD one. A CRUD name may carry one, replacing the model-derived validator. **A named type that is not there THROWS** where a missing model warns: an absent model definition is a config that used to work, an `input:` is a statement the author just made. **Declaring an input also declares the SURFACE** — `{ method: 'pay' }` narrows exactly as `'pay'` does, so a service gaining its first `methods:` answers 405 to every verb it did not name; `surface.snapshot.md` carries the policy-applied list AND the inputs, so that is a CI diff rather than a production 405. Transforms do NOT cross (`FJS-401`) — `@trim` is a Data-boundary rule, and the two boundaries apply transforms on opposite sides of validation, so they would disagree about what is *valid*
- `needsBackfill` on a release finding → `fli release:check` — **the middle step of a split, made checkable.** `classifyPivot` refuses a contract on a required column and hands back *expand → backfill → contract*; it grades the two deploys and stops after naming the COLUMN, because which mechanism fills it is a question about the running application and litestone sits below the package that answers it. So the finding carries `{model, field}` and `packages/cli/core/backfills.js` reads the app's own source for a `defineBackfill` naming that pair — SOURCE rather than a directory convention, the way the thirteen source-reading `fli check` rules work, because a rule keyed on a path reports a correct app as missing one. What no command can answer is whether it has RUN: that is a row in the deployed database, and it says so (`FJS-D157`)
- `sessionGateLevel(user)` — `SessionContext` → litestone's 0–7 scale; pass to `GatePlugin({ getLevel })`. Litestone cannot import Junction, so this is **a hand copy on both sides — change one, change both**
- `toDataPrincipal(user)` — the other half of the same translation: `SessionContext` → the principal `auth()` reads (`userId` → `id`). Applied at both `$setAuth` call sites. Without it every row policy compares against `undefined` and matches nothing, silently. **Two functions, one boundary**: change either and ask whether the other needs it too
- `resolveTenancy(schema)` / `registry.tenantFor({host, headers, principal})` — **the one reading of `tenancy { }`**. The declaration is a Data-realm fact and *which tenant is this request for* is an API-realm question, so the API asks rather than re-deriving; `createApp({ tenants })` installs `withTenantDb`, which assigns the same `ctx.locals.db` that `withLitestoneDb` does and therefore replaces it. Under `strategy row` nothing is swapped and `tenantClaimGuard` refuses a signed-in principal with no claim, because the alternative is an empty list with a 200 on every screen
- `accessorCandidates()` — `model Post` ⇄ service `posts` ⇄ `db.post`; shared by query, gate and validation so a naming slip cannot disable just one
- `db.$checkWhere(accessor, where)` → `[{key, suggestion, allowed}]` — the one definition of "is this a valid filter key", asked rather than copied; junction's `autoFilter` calls it. An unknown accessor answers `[]` — *I cannot judge this* is not *this is wrong*
- `db.$checkOrderBy(accessor, orderBy)` → `[{key, reason, suggestion, sortable, message}]` — the sibling, identical contract; junction's `autoSort` calls it. **Both halves throw** (a bad sort key returns the right rows in the wrong order, which nothing can see). `reason` separates *no such field* from *`@computed`, so SQLite can neither sort nor paginate by it* and from *`opaque`* — an array, a `Json`, a `File` or an encrypted column, whose stored TEXT is a serialization rather than the value, so ordering by it is always plausible and never what was asked. A `@from` field sorts

- `db.$readAs(accessor, row, principal)` → the row as that principal would have read it, or `null` — **the fifth sibling, and the one that exists because a BROADCAST IS NOT A SELECT.** `@@allow` compiles into a WHERE, so a row reaching a caller through a query is filtered by construction and one reaching them through a WebSocket frame was filtered by nothing: an anonymous socket received whole `Order` rows the same caller was answered 401 for (`FJS-631`). Takes its subject as an ARGUMENT for `$capabilitiesFor`'s reason — the asker holds one client and is answering about somebody else. Three questions in the order every layer here reads them: the **gate** (about the caller alone, an integer comparison, and the whole answer for a stranger), the **row policy** (`policyVerdict`, in JS against the row in hand — no query), then the **field policies**. Shaping a row that has already been read is safe because every protection STRIPS for a non-system reader and a recipient is never system, so no decrypt branch runs; what it gives up is that the row is not re-read, so a `@from`/`@computed` is the writer's. **Fails closed** — an undecidable policy throws and a throw refuses. `db.$readGrading(accessor)` → `'open' | 'graded'` is the half that keeps it cheap, and an unknown accessor is `graded`, the opposite of the other siblings' `{}`: there uncertainty means *I cannot judge this*, here it is a permission
- `db.$primaryKey(accessor)` → the key's columns, **in key order**; `[]` for an unknown accessor. The sixth sibling, same contract on every flavor of client. It exists because the layer above has to know whether a row can be named by ONE value: `expandCompositeId` stamps `@id` on every member of an `@@id([a, b])`, so asking the FIELDS answers all of them and in declaration order, while the key's own order — the order its implicit index is prefix-matched on — is stated only on the model attribute. Junction's derived `get` reads it to refuse a one-value id by name, because a URL segment is one value and the key is several (`FJS-694`)
- `db.$protectedFields(accessor)` → `{ field: 'guarded' | 'encrypted' | 'hashed' }` — **which columns must never be written down in plain text.** The third sibling, same contract: unknown accessor answers `{}`, every flavor of client answers the same. `@@log(audit)` redacts these in litestone's own JSONL (Invariant 7); an application keeping an audit table of its own had nothing to ask and could only hand-copy the names, which go stale the first time somebody adds a `@secret`. The value names WHICH protection because the three are not interchangeable

Both `$check*` live on **every flavor of client** — root, `$setAuth`, `asSystem`, `$scopedBy`. Filterability is a fact about the schema; auth has no bearing on it.

**Schema → API/UI**
- `generateJsonSchema(schema)` — consumed by junction validation and sierra's `build/schema-plugin.js` → `registerSchemas(defs, modelNames)`. **`$defs` is the whole definition table** (models, enums, `type T`, FileRef) and must stay whole — enum fields emit `{"$ref":"#/$defs/Plan"}` and both sides resolve it. Model names travel separately. Full key reference: `packages/litestone/docs/jsonschema.md`. **Three readers and no build that breaks when it changes shape** — a keyword that stops being emitted makes a form stop validating, silently — so `litestone jsonschema --snapshot` commits `db/jsonschema.snapshot.md`: `$defs`, enum values, per model the gate/relations/transitions and one row per field (type + default, required, label, keywords, which rules `x-messages` answers for), then what CREATE mode accepts. The `snapshots` CI phase fails a stale one
- `ctx.system` — **the `@system` columns THIS CALL is supplying**, `junction/src/core/context.ts`. A `@system` column is written by the application and refused when a caller's payload names it; litestone's hatch is `system: ['col']` on the call, which keeps the gate, the row policies, `@@softDelete` and the audit actor where `asSystem()` drops all four. A hook that DERIVES such a column could not reach it — a hook shapes `ctx.data` and the write happens downstream on the caller's own client, so the derived value arrived at the boundary indistinguishable from one the caller sent, and every customer create over HTTP in `example` was a 403 (`FJS-644`). `ctx.system.add('slots')` in a hook; `systemFields(ctx)` in `core/litestone.ts` is the one reader, called at each of the five derived write args. **A Set that hooks ADD to and `readonly`**, because `before.all` and `validated.create` each legitimately derive their own column and an assignment from the second silently drops the first's. Naming a column widens one CALL and never the model, and an empty set is not *all*. `$.system` reads it and `$.system =` is refused by name. `@guarded` gets no equivalent by design (`FJS-D178`)
- `ctx.transients` — **the `@transient` half of a payload, lifted off `ctx.data`.** Declared in the seed, emitted `writeOnly` into the create/update JSON Schema and absent from the read modes, so a generated form offers a control for a value no read answers. `liftTransient` in junction's `autoValidate` is the one place it moves; `isStoredField` in litestone's `ddl.js` is the one answer to whether a field is a column at all
- `ServiceTypes` — **the schema's TYPES on the far side of the wire**, where JSON Schema is its rules. `litestone types --augment junction` emits `service name → row` plus the module augmentation that registers it with `@frontierjs/junction/client`, so `client.service('posts')` and `resource('posts')` infer with no type argument and an undeclared column is a compile error in the browser. Keyed by the plural through `@frontierjs/toolbelt/inflect`, like every other name that crosses (Invariant 2), and **audience-split**: the API generates the system row, the browser the client row, because one file for both tells browser code a `@guarded` column exists that every response strips. An app that generates nothing has an empty registry, which is `never`, so every call keeps the open shape it had
- `@label` → `title`, validator messages → **`x-messages`**, keyed by rule name *and* by the JSON Schema keyword it compiles to. Litestone owns the keyword table (`jsonschema.js`); Junction's `schema.ts` and Sierra's `field-rules.js` look up the keyword they failed. A field's label is read off the field's OWN schema, never a `$ref` target
- `buildFieldRules()` / `validateAgainstFields()` / `coerceToSchema()` / `normalizeBlanks()` — `sierra/src/junction/field-rules.js`, a **leaf module** with no Junction-client import so it runs in plain Node and can be compared against junction's server rules rather than copied. Order: **coerce → blankToNull → validate**. All three on by default (`{ validate: false }` opts out; the test is `!== false`, so a threaded-through `undefined` does not disarm it)
- `controlFor(rule, {field, model})` / `formFieldList(fields, {only, except, model})` — same module, **the one place a field becomes a control**, so a generated form and a hand-written one cannot disagree about what a `Float` is. Reached through the resource (`resource.formFields()`, `resource.options(fk)`) rather than imported, because `@frontierjs/ui` peers only on mesa and css and importing sierra would invert the dependency. **A `Json` column answers `json`**, which the kit binds to `JsonInput`: it is the shape the schema stops describing, so there is no field list under it and the editor is the document's own syntax. **It is matched on the ABSENCE of a type, not on `type: 'object'`** — litestone emits `Json` as `{}`, since a document may be any of the seven things JSON can hold — and two shapes are carved back out of *no type* because neither is a document: a `File` column, which `$ref`s FileRef and derefs to an ordinary object (`x-litestone-file` is carried for exactly this), and a `$ref` nothing resolved, which `buildFieldRules` records as `unresolvedRef`. An array answers `json` too. A field it has no control for answers `control: null` **with a reason**, because dropping it would make a new column absent from a form with nothing saying so. **`registerControl(name, resolve)` is the way in**, and it is HALF of a contributed control: this side answers a name, `@frontierjs/ui/controls` binds that name to a component, and a name is the only thing that can cross a boundary where one side must run in plain Node and the other may not import sierra (`FJS-D17`). Last registered is asked first, so an app beats the kit it imported; a `readOnly` column is not offered to the registry at all
- `labelFieldInfo(fields, fallback, declared)` → `{field, source}` — **which column identifies a row to a person**, one owner, because a foreign key holds an id and nobody recognises an id. The declaration is `@@label(field)` in the seed, reaching the client as `x-label-field` and resolved once per resource onto `resource.labelField`; a picker asks the resource rather than scanning. **A declaration is not checked against the field rules and must not be** — the case it exists for is a `@generated` full name, which is `readOnly` (the scan skips those) and absent from a create-mode registry altogether, while the consumer reads it off a fetched row. Litestone refuses at parse every shape a picker cannot use, by name, because the options query SORTS by this column and searches it with `contains`. `source` is the other half: `declared` · `conventional` (one of eight names) · `scan` (the first plain string — a guess) · `fallback` (the id). Every step down used to be silent, and the two guessing tiers now say so once per field, naming the model and the fix — a `Person` with `firstName`/`lastName` labels every option *Ada, Ada, Ada* and looks like it worked (`FJS-392`)
- `x-values` → `rule.values` → `controlFor` / `resource.options()` — **a declared value set, from the seed to the request a picker sends** (`FJS-D120`). `valueset <Name> { source · value · scope · where }` in `.lite`, `@values(<Name>[, required|open|suggested])` on the column, BESIDE `@relation` rather than instead of it. **A bound column is asked before its foreign key**, because a bound FK is both and the set is the narrower answer — it names the scope the list is narrowed by and the column a person reads, where the relation names neither. Strength picks the control and the two weak ones pick the SAME one — `required` a picker, `open`/`suggested` a combobox with `allowNew` — because what separates them is what the server does with a new value, not what a caller may type; a bound array is a multiselect where an unbound one is still `json`. **Every narrowing travels as a NAME** — `$checkWhere` validates a `$scope`, so it survives junction's `autoFilter`, which is what makes the offered list the list the Data boundary will accept. A declared `where` is SQL and a browser may never send SQL, so it **mints a `@@scope` on the source named after the set** and crosses the same way; the predicate itself never leaves the server (`FJS-430`). The enforcement is litestone's, through the CALLER'S own accessor — `x-values` is an affordance here exactly as `x-gate` is
- `resource.options(field)` → `{ options, total, truncated, error }` — **what a picker OFFERS, and why it has nothing to offer.** `error` is what separates *there are none* from *I could not ask*: both used to answer an empty list, which a person reads as the first one, so a service no name resolved to looked like a shop with no variants in it (`FJS-570`). It is said where the COUNT is said — `optionsNote` beside `truncationNote` in `@frontierjs/ui/utils.js`, composed through one `withNote`, so `Select`, `Combobox` and `MultiSelect` cannot word it three ways — and it is a NOTE rather than a field error, because the value may be legitimately absent and marking the field invalid would refuse a submit on every optional relation whose rows happened not to arrive (`FJS-587`). `<Form>` keeps it beside `pickers` off the same prefetch and `defaultControlProps` carries it, so a contributed control gets it without restating the builder
- `toFieldErrors(err)` — same module, also `resource.fieldErrors(err)`. **The one owner of "a thrown value → per-field messages."** Three shapes reach it because each hop wraps once: `err.errors`, `err.data.data` (a server 400 through the browser client — the double `data` is real), `err.data`. Returns `{ fields, message }`. **`errors` is how a Data-realm refusal reaches a control**: junction's boundary adopts an error class's own `errors` array ahead of its `data`, so `ValidationError` and `UniqueConflictError` land under the box that caused them with nothing taught to either side. An error whose payload is an OBJECT (`VersionConflictError`'s two revisions) is a form-level answer by construction
- `$context.form` — the UI-side form seam, provided by `ui/components/forms/Form.mesa` as `{ errors, submitting, disabled, fields, submitted, optionsFor, reportInvalid }`. Nine controls resolve their own label, constraints, `aria-invalid` and message from it; an absent form reads `undefined` and every fallback is what the control did standing alone. A stated prop always wins, including `required={false}`. **`reportInvalid(name, message)` is the one channel that goes the other way** (`FJS-404`) — a control saying *the value I am showing is not one I can hand over*, which nothing else in a form can know: a control whose element cannot hold every value the field may take writes only what it could convert, so the record keeps the last good value and every check on it passes while the screen shows something else. It is the fourth error source and merges LAST, over a server message and a live one, because it alone describes what is on screen now; it refuses a submit even in a HAND-WRITTEN form, where `FJS-316` deliberately stops the record-level checks, because the control that reported is on screen by construction; and `clearErrors()` leaves it alone, since it is about text still in the box and only its own control can retract it
- `buildRelations()` / `buildGate()` / `canAtLevel()` — same module. **`x-relations` is the only place a relation exists on the client**; `x-gate` is an affordance, never a boundary
- `x-version` — names the `@version` column an update must carry back, `readOnly` in the update schema and absent from the create schema. `createResource` remembers the version of every record it reads and puts it on the next patch. `resource.version(id)` / `.versionField` expose it
- `retryable` on a thrown error — the one thing a status cannot carry. A 409 is either a race (`VersionConflictError`, `TransitionConflictError` — re-read and re-apply) or a domain refusal (`TransitionViolationError`, `UniqueConflictError`, `SoftDeletedUniqueError` — show its message). Set it on any error class you own; `toFrameworkError` adopts it and it lands at `err.data.retryable`. `isStaleWrite(err)` reads it. **`junction errors` commits what a thrown value actually becomes** — `packages/junction/errors.snapshot.md`, every row executed through the boundary, Litestone's own classes constructed and run through it. Nothing above `toFrameworkError` reads anything but the result, so a class gaining or lacking a `status` changes a category with no test to fail; `FJS-255` is what the first run found
- `buildTransitions()` / `transitionsAt()` — `@@transitions` reaches the client as **`x-transitions` on the model, keyed by field**, never on the enum `$def`, because only a model can carry a per-transition `@gate`. **It is the GATE half of `db.<model>.transitions(row)` and only that half** (`FJS-495`): a move is an update, so a row policy refuses one exactly as a gate does, and the server grades both — the `update` policy against the row as it IS (one evaluation per call) and `post-update` against the row as it WOULD BE (one per target, the half that varies between moves). `x-transitions` carries a gate and not a predicate and a browser has no policy engine, so a move a policy refuses reads `allowed: true` there and 403s when pressed. **`refusedBy` is what keeps the two one shape** — `'gate'` · `'policy'` · `null` — because a screen renders *you are not senior enough* and *not this record* differently, and neither a status nor a non-null `gate` separates them: the gate is null for every ungated move a policy refuses. Permissive-when-unknown is the affordance contract, and a screen needing the graded list asks the SERVER
- `modelNameFor()` / `schemaFor()` — `sierra/src/junction/schema-registry.js`, over `@frontierjs/toolbelt/inflect`. **The inflection rules are one module and five callers** — litestone's table name and its introspection, junction's `deriveModelName`, sierra's registry and `createResource` — because a table name and the model name derived back from it are the same rules run twice (Invariant 2). Regular English plus a fixed irregular table, so `people` resolves `Person` unaided; genuine ambiguity (`lens`/`len`) cannot be reached by any rule and is said by hand — `createResource('lenses', { model: 'Lens' })`. A miss warns and degrades to a bare `make()`
- `authUserModel(db)` / `authMachineryModels(db)` — auth contributes INTO the seed, as two `.lite` files it ships (`auth/db/user.lite`, `auth/db/auth.lite`); `schema.ts` reads them and `authSchemaFragments(db)` is both, for a caller assembling one string in memory. **Split by owner**: `User` is `@@gate("4.4.4.5")` with policies an app changes, so `fli auth:install` appends it into the app's own `schema.lite`; the four `@@gate("8")` models go to `db/auth.lite` and are imported, so an upgrade reaches an installed app. The CLI reads the same bytes through auth's `exports` — it cannot import `schema.ts`, because `fli` runs on node and that file is TypeScript
- `extend model X { … }` — **what an app says about a model it did not write**, and the reason the machinery half is imported rather than pasted. A package owns its columns; where those rows sit in the installing app — the relation back to its own `User`, `@@log(audit)`, `@@tenant(none)` under row tenancy — is three facts the shipped file cannot know. Adds only: an extend naming no model, a field the model already declares, and a second answer to a single-valued attribute (`@@gate` twice) are each refused by name; `@@allow`/`@@deny`/`@@index`/`@@unique`/`@@check`/`@@trait` are repeatable. Collected across the whole import tree and applied once it is merged, so a file may extend a model it is imported BY, and applied before traits. **The opposite direction of `@@trait`**, which is opted INTO by the model and therefore needs its author to have known. basecamp carried hand copies of four of these for its whole life and one had `@guarded(all)` where auth writes `@secret`, with 137 green tests either side of the divergence — a copy is the failure this removes (`packages/litestone/docs/traits.md`)

- `attachments` → `checkAttachments(config.attachments)` → the `check-attachments` start phase — **what this app needs and does not own, and whether this environment binds it** (`FJS-D158`). The app DECLARES in `junction.config.js`; the environment BINDS, and the check reads `process.env`, not `fli deploy`'s recorded binding set, which goes into the Release for identity and revert and is applied by nobody (`FJS-585`) — so it is true however the variables arrived. **Not a second `defineEnv`**: `checkEnvField` is extracted from it and called by both, so *present, non-empty, a URL, long enough* has one owner. What an attachment adds is the three things a flat spec cannot say — these keys are ONE SERVICE, so a refusal names the service rather than a variable; ALL OR NOTHING, so `optional: true` forgives a service nobody bound and still refuses one **bound halfway**, which is the shape that reaches production and the one a per-variable check cannot see; and a DEFAULTED key is not evidence, or an unbound service with one default looks half-bound. **The refusal is at startup and `fli` is what makes it visible**: `showContainerTail` tails the container on a failed health check, on the revert path too, or the app's own clear sentence dies in `docker logs`

**Machine ↔ control plane**
- `signRequest()` / `verifyRequest()` — `@frontierjs/toolbelt/signature`, **the one definition of what a signed machine-to-machine request is**: method, path, timestamp, nonce and a hash of the body, joined with newlines. Three readers — conduit's transport signs outbound with it, basecamp's `requireOutpostSignature` verifies inbound with it, and `@frontierjs/outpost` does both. It exists because signing with no verifier reads as a scheme being enforced: basecamp's three machine endpoints took no credential at all behind a comment saying the transport had checked one, and an unsigned POST could point every fleet command at an address the caller named (`FJS-349`). The replay check runs LAST, so a caller who never held a valid signature cannot fill a nonce store, and storing nonces stays the caller's because this package does no I/O
- `requestMeta().traceparent` / `.tracestate` → conduit's default `trace` — **the outbound call hangs off the inbound request.** Junction CARRIES the caller's W3C trace verbatim and emits nothing: it traces nothing itself, and a parse there would be a second reading of the spec beside whoever continues the trace. Conduit's junction plugin is the first reader and defaults `trace` **under** the app's own opts, so an app with its own tracer replaces it whole and `trace: () => null` turns it off. An upstream trace is continued; with none, the trace id is DERIVED from the correlation id rather than minted per call, or six calls in one request are six unrelated traces — and a uuid needs no derivation, since junction mints correlation ids with `crypto.randomUUID()` and a uuid with its dashes out IS a 32-hex trace id (`FJS-742`)
- `ctx.$raw.rawBody` — **the body as bytes**, junction's half of the same seam. A signature binds a hash of the body, so a hook handed only the parsed object would have to re-serialize and both ends would have to agree on key order forever. Kept for JSON, urlencoded, XML and text; absent for multipart, where there is no single string

**API internals**
- `$` / `enterCall(ctx, fn)` / `currentCall()` — **the service call in progress**, `junction/src/core/context.ts`. A second ALS store, opened around the whole of `_callService` — pipeline, announcement, `afterCommit` drain, outbox handoff — so `$.db`, `$.data`, `$.id`, `$.locals`, `$.enqueue` are the call a function is inside rather than a parameter threaded to reach it. Plus `$.db` (`ctx.locals.db`) and `$.me` (`ctx.auth.user`) as derived accessors. Resolved on every read, never snapshotted: `transactional:` reassigns `ctx.locals.db` before the method runs. **Only junction's own contract keys can be assigned** — `data · query · id · result · error · statusCode · dispatch` — so `$.dispatch = false` works and an invented key is refused: what makes an ambient object dangerous is state nobody owns, not writes. **Outside a call it throws by name**, because an ambient dependency is an undeclared one and the whole of what makes that acceptable is a loud failure. NOT `runInServiceCall` below, whose narrower span the litestone write tap reads to suppress a double announcement. **`enterCall` is exported as the escape hatch** — `callService` opens the scope for every ordinary path, so this is for a hand-built context calling a method as a plain function (a unit test, an app invoking outside the pipeline); it nests and restores. Nothing shared with Invariant 10's `$`-prefixed keys but the character
- `$.config` / `app.configFor(tenant)` — **what this app is configured with, read at CALL scope**, `junction/src/core/config-scope.ts`. One owner, so a value that becomes per-tenant becomes per-tenant for every reader at once. **The source is `createApp({ tenantConfig, tenantConfigKeys })`** (`FJS-D126`) — a resolver answering a plain object per tenant, never a declaration, memoised as the PROMISE so two concurrent requests resolve once, with `invalidateTenantConfig(id?)` the explicit way out and a FAILED resolve deliberately not memoised. **The resolve happens where the tenant already is** — the around hook that sets `ctx.locals.tenantId`, and `runAs` — because a property read cannot await, and a resolver that throws FAILS THE CALL rather than quietly serving the floor, which is one tenant's mail under another's name. **`tenantConfigKeys` is required and `RESERVED_CONFIG_PATHS` is refused at BOOT** (`port`, `host`, `database`, `http`, `auth`, `apiPrefix`, `logging`): a database path handed to a tenant is every other tenant's rows, and the rest are read at boot with no tenant in scope. A key the resolver answers that the list does not name is refused by name, never dropped. **The list is committed**, as `principal.snapshot.md` § Per-tenant configuration. **The view is read-only and deep**: a writable view is a rebind wearing a different word, and the next reader after a write sees somebody else's tenant. `app.config` itself stays writable, since `loadConfig` merges into it at boot. A derived accessor like `$.db`, `$.me` and `$.log`, so it is absent from `ownKeys` and refuses outside a call; `app.configFor()` is the no-call half

# FrontierJS — Map

Bun-workspace monorepo: a schema-seeded fullstack framework. One mental model — three realms, three nouns:
**Data (Model) → API (Service) → UI (Resource)**, plus Deployment (Release) and Testing (Suite).
Everything derives from `db/schema.lite`; growth happens outward and traces back.

`ARCHITECT.md` §2 is the default vocabulary for design discussion. Depart from it when a different word is materially clearer — then fold the clearer word back in rather than keeping two.

## Evolution policy

FrontierJS is pre-alpha. **Prefer evolving existing designs over preserving them.** Existing behavior is evidence, not a constraint.

**Nothing here has shipped, so there is no back-compat to keep and no muscle memory to spare.** A rename is a rename: no alias for the old spelling, no deprecation window, no migration path, no flag kept so an existing call still works, no second name for one thing. `PHILOSOPHY.md` § IV's *familiarity vs. precision* is about the ECOSYSTEM's habits — the shapes a developer brings in from elsewhere — and never about this framework's own past, which has no users to confuse; reaching for it to argue that an existing spelling should survive reads the adjudication backwards, and is the way this policy is most often lost.

Only two things are binding: the **Invariants** below, and rulings in `DECISIONS.md`. Everything else may change — prefer simplifying, removing duplication, and improving consistency over reproducing what is there. **Preserve the mental model, not the mechanism.**

**A change that turns on a judgment call runs `decision-rules`** (`.claude/skills/`) — `PHILOSOPHY.md` § V's nine questions against the proposal, § IV where two goods are in tension, § VII for which kind of document may hold the answer. It fires on the ACT rather than on the doubt: adding an option, coining a noun, restating something already stated, choosing between two designs, or finding the code and a document disagree.

Where docs disagree, assume different stages of a pre-alpha design and reconcile, rather than treating either as wrong.

**This file is only what is live.** History belongs in `packages/*/CHANGES.md`, open defects in `ISSUES.md`, settled arguments in `DECISIONS.md`. A line here earns its place by changing what someone does in the next hour.

## Invariants

Don't violate without an explicit decision; record it in `DECISIONS.md` if you do.

1. **Dependency direction** — `Litestone ← Junction ← Sierra`, never reverse.
2. **Model names are PascalCase singular** (`model Lead` → `db.lead`); `@@external` exempt. Three resolvers depend on this agreeing.
3. **App layout** — `db/` at the root and each SURFACE a directory beside it: `api/`, `web/`, `site/` (the public prerendered site), `widgets/` (embeddable scripts), `extension/` (a jetty browser extension) and `desktop/` (a native shell with its screens bundled in). Most sub-projects carry `config/ src/ public/ test/ dist/ deploy/` (db/ doesn't). Configuration lives in `config/`, `vite.config.js` included. **A surface owns its `src/`, and `desktop/` alone may borrow another's instead**: `wraps: 'web'` in `desktop/config/desktop.config.js` builds `web/src` into `desktop/dist`, while the config, the tests, the release and the output stay the desktop's (`FJS-D263`). Which surfaces an app has is the app's business — api-only, web-only, **site-only**, **widgets-only**, **extension-only** and **desktop-only** are all whole projects — but a surface inside another one is not: folded into `web/`, it inherits the SPA's build, port and release. A surface earns its own directory when its config, its tests and its release are all different answers, which is what `site/`, `widgets/` and `extension/` are. **`site/` has a fourth and it is the decisive one — OUTPUT**: one Vite root is one `dist/`, and `vite build` empties `outDir`, so a `target: 'static'` site living inside `web/` is deleted by the next SPA build with nothing said (`FJS-D127`, `FJS-449`). `fli check`'s `app-layout` reports a static config found inside another surface. Canonical: root `README.md` §Project Structure. Never *derive* a config path from where `vite.config.js` sits — probe, or be told.
4. **One owner per translation.** Exactly one place turns a thrown value into an HTTP status, one wraps/unwraps the result envelope, one parses `$`-params into `ctx.directives`, one announces a mutation, one startup phase list every caller runs. Implementations are in §Bridge index. Add to the owner, never beside it.
5. **One owner per `app.<thing>`.** Claim it with `app.claim(name, value)`; type it by augmenting an exported interface, never by redeclaring the property — declaration merging requires identical types, so a redeclaration silently loses. The verb is `claim` and not `provide` because **a Provider is a third party the app speaks to** (`FJS-D06`) — `/metrics` contributions go through `app.registerMetricsSource(name, fn)` for the same reason.
6. **Access is declared in the schema, not in hooks.** Gates, `@encrypted`, `@guarded`, `@@transitions` are enforced at the Data boundary. `x-gate` on the client is a UI affordance only — unknown answers are permissive and the server enforces regardless. No exceptions.
7. **Protected fields are redacted in the audit trail.** `@encrypted`/`@guarded`/`@secret` log as `[redacted]` in field entries and in `before`/`after` snapshots.
8. **Caller-supplied names never enter a SQL pattern.**
9. **Patch semantics: an explicit `null` clears.** Test key presence (`key in updates`), not `??`.
10. **A `$`-PREFIXED KEY is transport syntax only.** `$limit`, `$offset`, `$orderBy`, `$select` are how a directive travels on a wire; `ctx.query` is filters, `ctx.directives` is `{limit, offset, orderBy, select}`, and no `$`-prefixed KEY survives the bridge — **and one the table does not name is REFUSED there by name** rather than dropped, while sierra's router drops it, because a refusal costs a retry on a request and a navigation on a URL (`FJS-D237`). The rule is about the prefix on a parameter name and about nothing else — junction's ambient `$`, the service call in progress, is a different thing that happens to share a character (Bridge index § API internals). **Two boundaries read the convention** — junction's bridge off a request, sierra's router off a URL onto `page.query` + `page.directives` — and the table they read it by is one module, `@frontierjs/toolbelt/directives`, one row per directive so a Data-realm feature that grows a per-call option cannot arrive half wired. **What the VALUES mean is the sibling module, `@frontierjs/toolbelt/query`** (`FJS-D125`) — a string is a number only if `String(Number(v)) === v`, `true`/`false`/`null` are themselves, structure is bracket notation, and `?code="5"` is the escape. Three readers: junction's transport, junction's client writing one, sierra's router. **Not a WS frame**, which is JSON and already carries its types.
11. **The nearest delegation root owns an event.** Roots nest; a handler must fire once.
12. **Mesa compiler output is reproducible** — scope ids are content-addressed, which is what makes CSS dedupe work across the two compilers a static build runs.
13. **`@frontierjs/css` is the styling language.** Style with a tone (`danger`) and a treatment (`outlined`), never a color. UnoCSS is supported *alongside* it as an opt-in layer a consuming app configures (`packages/css/README.md` §Using it with UnoCSS). A package in this repo ships no utility classes — a component needing Uno to look right is unusable by an app that does not run it.
14. **Typecheck baselines ratchet down only.** `scripts/typecheck-baselines.json`, one number per package; absent means 0. `bun run typecheck -- --update` writes an improvement back.
15. **A clean compile is not proof of valid JS.** Compiler tests parse their output.
16. **Runnable examples are verified, not sketches.** A broken one is a bug.
17. **Four markdown files at a package root is the standard** — `README.md`, `CLAUDE.md`, `PROJECT_STATE.md`, `CHANGES.md`; everything else in `<pkg>/docs/`. **`AGENTS.md` is a permitted fifth and is not required** (`FJS-D163`): it is the same KIND of thing as `CLAUDE.md` — a root document whose whole value is being findable at the root, under the name other tools converged on — but it addresses a CONSUMER of the package rather than a contributor to it, so a package nobody writes against does not owe one, and the two are not folded because one audience has the source and the other has a tarball. **It only reaches that audience if `files:` ships it**, which is decidable from `exports.snapshot.md`. **A sixth is a question, not a refusal**: `package-root-md` warns and names it, because the rule cannot tell a stray design note from the next thing everyone needs at the root. Answer it — move the file, or record an allowance saying why it stays. Generated `*.snapshot.md` is exempt; it is gated output, not documentation.
18. **In a Sierra app, `src/resources/` holds `.mesa` files, and a resource file carries its model's default form.** A Resource is a UI-realm noun, written in the UI-realm language. The data half is `<script module>` — `createResource` and the model's own verbs — which runs once at import and is what every other module imports (Mesa VISION §11, rule 30); that half is required. **The markup half is the form and it is optional**: with it, a create or edit page is `<Order />` and nothing else, and a page wanting a different form passes children, which `<Form>` already lets win. A file with no `<script module>` is a component in the wrong folder (`FJS-D112`).
19. **A resource file is named for its noun — PascalCase, singular — one Resource per file.** `App.mesa` exporting `export const apps`; the same split the Data realm makes between `model App` and `db.app`. Where a model exists the filename IS the model name, so an irregular is visible (`AlertRule.mesa` exporting `alerts` says `model:` must be stated). A resource over no model takes its service noun, singularized.

## Running things

**Always `cd` into the package and run its own script.** Runners differ per package and a wrong runner produces failures that belong to nothing. `bun run --filter '*' test` from the root runs them all, one each. `bun test` instead of `bun run test` runs bun's own runner over whatever it finds — in mesa that is ~35 failures that are runner artifacts.

**`bun run ci` is the whole of CI and it is not a GitHub feature.** One node script runs thirteen phases and `.github/workflows/ci.yml` does nothing but call it, so it runs identically on a laptop. `ci:fast` skips the suites, `--only <pkg>` narrows typecheck and tests, `--phase <name>` runs one by name (repeatable, and always in the table's order — `scaffold` packs what `deploy` installs), and `bun run hooks:install` points `core.hooksPath` at `scripts/hooks`, whose `pre-push` runs the fast tier — the suites belong in the workflow, because a pre-push costing minutes teaches everyone `--no-verify`. Every allowance is a named entry with a reason in `scripts/ci-allowances.json`. **`fli ci` is the same call from anywhere in the workspace** and forwards its argv untouched, so there is one flag set and one owner (`FJS-D255`); `fli ci -- --help` and `bun run ci -- --help` print the phase list and every flag, derived from the phase table rather than written out. In an APP there is no `scripts/ci.mjs` and `fli ci` says so, naming `bun run check`.

It carries **no list of what exists**: every snapshot names the command that wrote it in its own header, and that command is rerun with `--check` from the file's own directory, so a new KIND of snapshot costs a generator and never a CI edit. The command comes out of a file in the repo, so it is restricted to a known binary and a shell-free argv, and a snapshot naming no generator fails rather than being skipped. **Discovery alone fails open**, so the expectation comes from the BASE REF — a snapshot tracked where the branch left main and absent now is a failure, because a generated artifact that stops existing takes its check with it in green. The list is read from `core/app-config.js`, the module `fli new` itself reads. A **comparison rather than a scan**: a vitest advisory is not something an app installing this framework can be hurt by. The resolved version is printed beside the advisory's range and **the two are never compared**, because a range parser here would be a security judgement made by a regex. `knownAdvisories` is the named allowance; `FJS_CI_REQUIRE_AUDIT=1` makes a no-network skip fatal |

**Which drive proves a change is `fli proves`.** Run the package's own suite first, then `fli proves` (or `fli proves --from main` on a branch): it reads your diff against `DRIVES.md` and names each drive the change needs, with what to start before it. A change is not proved until those drives have run. Open `DRIVES.md` itself when a row needs its reasoning, when a drive refuses to start, or when you add a drive — every drive gets a row in both of its tables.

**A dev server serves the code it started with.** A `.mesa` module is transformed once and cached for the life of the process, so editing the compiler invalidates nothing and the app fails exactly as it did before the fix. Start the server the run will test, and refuse a port that already answers. Backgrounding a server from a tool call is unreliable here (`nohup`/`setsid` both drop it); what works is a script that spawns it, polls until it answers, asserts, and kills it — `example/web/test/verify-build.mjs` is the shape. **And a port that answers is not evidence the right process is on it**: `bun run api` spawns a CHILD, so killing the wrapper leaves the app holding its ports, the next start exits `EADDRINUSE` into a log nobody reads, and the readiness poll is answered by the process that never went away — a drive then reports on code that is not in the tree, green or red (`FJS-740`). `example/web/test/lib/preflight.mjs` asks reachability and FRESHNESS together, because separating them is how the second stops being asked: `/health`'s `uptime` against the newest mtime under `api/` and `db/`, since dev has no build stamp and mtime is the only fact both sides can see.

**Ports.** `port = env*1000 + category*100 + project*10 + service`. `packages/cli/core/ports.js` is the schema — the formula, the category map, and the `PROJECTS` registry. env: 7 test · 8 dev · 9 prod. category: 0 fe · 1 be · 2 widgetDev · 3 widgetServe · 4 ext · 5 tooling · 6 siteDev · 7 siteServe · 8 desktopDev. `packages/jetty/src/dev/fjs-ports.js` owns the extension slice (8400–8499 dev, 7400–7499 test).

The widget and site columns are why categories 2, 3, 6 and 7 exist: a surface that is both WRITTEN against and SERVED as its own origin needs two slots, and both `widgets/` and `site/` are that shape — a server while one is being written, a static origin once it is served, and neither is the SPA's. They are CATEGORIES rather than service digits on the `fe` row because the served half is not the SPA's second server, which is the one thing it is not. **The tooling block is the exception and is reserved whole**: 8500–8509 is dev/tooling/project-0, refused by the formula for every slot rather than for the ones currently assigned — a tool there is one somebody runs beside whatever app they are working on and types from memory, so it can neither take a number from the app's row nor be handed one at runtime. The numbers are derived, not chosen: a new app takes the next project id. Every id in `PROJECTS` is assigned and `DYNAMIC_PROJECT_FLOOR` starts the allocator above the highest, so a dynamic claim cannot land on an assigned app. **Every surface also has a NAME, derived from the same table**: `example.localhost` is 8010 and `api.example.localhost` is 8110 — the frontend takes the bare label, every other surface is a subdomain of it, and tools are under `fli.localhost`; `fli check`'s `dev-host-unique` refuses two packages whose names reduce to one label, which is `strictPort`'s failure one layer up. `fli proxy` maps Host to port (`packages/cli/core/proxy.js`); it wants 80 and falls back to 8504, and it is a TCP proxy because bun's `node:http` emits `upgrade` and hands over a socket nothing written to ever reaches the client, which would make junction's live layer and vite's HMR load and then silently stop. Nothing is rewritten — junction READS the Host and vite allows `*.localhost` — and the target is picked per CONNECTION, which no client that derives its Host from its URL can reach. **Strictly additive: every number keeps working and nothing may come to depend on a name.** **Every vite config sets `strictPort`** — vite otherwise hops to the next free port in silence, and the second app's drive tests the first app's app. A scaffolded app reads `FLI_PORT_FE`/`FLI_PORT_BE` when the broker set them; the literal is only the static default.

## House style

Match the file you are in first; this is what the repo does when there is no local precedent.

- **Comments explain the failure, not the mechanism.** `// increment the counter` is noise; `// vite hops ports silently, so the drive would talk to the other app` is the house voice.
- **A comment must be load-bearing. Delete it otherwise.** Test: if it vanished, could someone editing this file make a mistake it would have prevented?
  - **No edit history in code** ("used to be", "this replaced X", "merged 2026-08-08"). That is `CHANGES.md`, `DECISIONS.md` and git. Narrow exception: a past bug stated because the shape still invites it (`--ring` in `tokens.css`), where the history IS the warning.
  - **No dates in code comments.** If the comment needs one, it belongs in a decision record the code points at.
  - **No persuasion** — "the whole point", "deliberately", "which is exactly why", italics for emphasis. State the constraint flatly; if it needs selling, it needs a ruling.
  - **Never narrate your own edit.** The reader does not know a change happened.
- **Never put a backtick in a comment inside a template literal.** A SQL schema, an nginx config and a shell script are all written as one here, and a comment quoting `an identifier` closes the literal — the file then fails to PARSE, so the failure is nothing to do with what the comment says and points at a line further down. Twice in one day: `packages/caravan/src/db.ts` (every `bun run api` and therefore every drive) and the nginx deploy template (the cli suite). Use plain words or `--` quoting; the cli's *every shipped command compiles to parseable JS* test is the only thing that catches it, and it only covers `commands/`.
- **Every non-trivial file opens with a header block** — what it is, and what it is for. Test harnesses document their own traps at the top (`example/web/test/verify.mjs`).
- **Section dividers inside a file**: `// ─── name ──────` (box-drawing, padded to a consistent width). Not `// ---`, not banner boxes.
- **Aligned columns** where a run of lines is parallel — imports, object literals, `const` blocks. See `example/api/src/app.ts`.
- **Prose in the docs is sentence-shaped, not bullet-shrapnel.** Bold the claim, then say what it cost. Numbers earn their place by being measured.
- **A document an agent reads is written by `doc-hygiene`** (`.claude/skills/`) — the two loads it spends, the ladder from in-file step down to disclosed reference, and the four cuts (the delete test, cache, negation, sprawl). Reach for it before adding to a `CLAUDE.md`, a `SKILL.md`, or anything reached by a pointer. **A section a parser reads moves only with its parser**: modules read this file and `DRIVES.md` by path, and relocating one of those tables without the reader is a green build over a table nothing reads.
- **American spelling** throughout, prose and identifiers alike (`behavior`, `serialize`, `color`) (`FJS-D192`). One exception: `cancelled`, a persisted enum value on several `@@transitions` models in `example` and `basecamp`. **`fli check`'s `american-spelling` grades it**; `spelling-exempt` on a line is the escape, for a British form that is INPUT rather than prose (a synonym a searcher types, a column an app named itself), and the fetched corpus fixtures are exempt wholesale.
- **No semicolons**, single quotes, 2-space indent, in TS and JS alike (`packages/css`'s own build/test scripts are the one holdout). TypeScript in junction, auth, caravan, conduit, notifications, mcp, testing; plain ESM JavaScript in every other package. Do not introduce TS into a JS package.
- **Fake clients hide real bugs.** Cross-package behavior is tested against the real dependency — `{ post: {…} }` passed every test and failed every real Litestone client.
- **A new `on*` states its tier** (`FJS-D06` §1) — **Hook** may mutate the arguments or halt the operation, **Guard** answers allow/deny, **Observer** receives and cannot act. The word goes on the option that holds it: conduit's callbacks are `observers:` because a throw in one is swallowed, and `management.hooks` beside it keeps *hook* because that pipeline can refuse the call.
- **A new defect gets an `FJS-###` in `ISSUES.md`**, not a paragraph in a package file. A ruling closes an `FJS-D##` and moves to `DECISIONS.md`. Check a new `.gitignore` rule against `git status --porcelain` — an ignore glob hid twenty source files once.

## Live hazards

**Correct behavior you have to know about.** Things that are *wrong* live in `ISSUES.md`, one id each; things that are *fixed* live in `CHANGES.md`. If a rule here is pinned by a test that cannot be deleted quietly, it does not need to be here.

**The three realm catalogs are skills rather than sections** (`.claude/skills/`). A trap about `@@softDelete` costs nothing on a turn spent in sierra and everything on the turn it is needed, so each fires on its own realm and is otherwise the document it was here. Reach for one by name where the trigger has not fired, and add a new hazard to its realm's skill rather than here. **`/which-skill` is the order across all of them** — hazards, seams, registers, proof and record as one path — and it is user-invoked, so it costs no context until somebody asks.

| Realm | Skill | Fires on |
| ----- | ----- | -------- |
| Data | `data-hazards` | litestone · a `.lite` schema · a gate or row policy · a migration · tenancy · encryption · the audit trail |
| API | `api-hazards` | junction · a service · the hook pipeline · HTTP/WS transport · a raw route · a plugin · a job or cron |
| UI | `ui-hazards` | mesa · sierra · a `.mesa` file · a resource · a form · a live store · prerender · islands · `@frontierjs/css` |

**Repo** stays here, because it belongs to no realm.

- **A `file:` dependency (jetty's `file:../mesa`) installs a COPY under `node_modules/.bun/`, not a symlink.** An edit to `packages/mesa/src/compiler.js` is invisible to those importers until reinstall, so a suite can go green against a stale snapshot. In-repo tests import workspace source by relative path. `packages/ui`'s hand-made symlink will not survive a reinstall.
- **Nested directories are invisible to the `packages/*` glob** — uninstalled, untested, unrunnable. Two cases, both deliberate and named in `scripts/ci-allowances.json` § nonMembers: `mesa/mesa-bench`, `oracle/mockup`. **A third is a CI note naming the path**, so the way this goes wrong is by someone reading the note as noise, not by silence.
- **Publishing a package silences every loose peer range that names it.** While a sibling is unpublished a peer of `"*"` fails at install with the name in the error; the moment it exists, the same range resolves from the registry without a word. **Below 1.0 a caret pins the MINOR** — `^0.1.0` is `>=0.1.0 <0.2.0` — which is both the behavior wanted for a pre-alpha peer and the trap in the other direction, where a stale caret excludes the only published copies. Nothing catches either shape from inside the workspace: a `workspace:*` devDep answers first and the range is never consulted. **`fli ws:exports` commits the published surface** — `exports.snapshot.md` at the root, one section per publishable package: the top-level entries its tarball actually contains (asked of `bun pm pack --dry-run`, never derived from the globs), every `exports`/`bin`/`main`/`types` target marked with whether that tarball holds it, and the peer ranges naming a sibling. A declared entry point `files:` does not publish is a broken install, decidable from the listing alone. The `snapshots` CI phase fails a stale one.

# FrontierJS — Map

Bun-workspace monorepo: a schema-seeded fullstack framework. One mental model — three realms, three nouns:
**Data (Model) → API (Service) → UI (Resource)**, plus Deployment (Release) and Testing (Suite).
Everything derives from `db/schema.lite`; growth happens outward and traces back.

`ARCHITECT.md` §2 is the default vocabulary for design discussion. Depart from it when a different word is materially clearer — then fold the clearer word back in rather than keeping two.

## Evolution policy

FrontierJS is pre-alpha. **Prefer evolving existing designs over preserving them.** Existing behaviour is evidence, not a constraint.

Only two things are binding: the **Invariants** below, and rulings in `DECISIONS.md`. Everything else may change — prefer simplifying, removing duplication, and improving consistency over reproducing what is there. **Preserve the mental model, not the mechanism.**

Where docs disagree, assume different stages of a pre-alpha design and reconcile, rather than treating either as wrong.

**This file is only what is live.** History belongs in `packages/*/CHANGES.md`, open defects in `ISSUES.md`, settled arguments in `DECISIONS.md`. A line here earns its place by changing what someone does in the next hour.

## Invariants

Don't violate without an explicit decision; record it in `DECISIONS.md` if you do.

1. **Dependency direction** — `Litestone ← Junction ← Sierra`, never reverse.
2. **Model names are PascalCase singular** (`model Lead` → `db.lead`); `@@external` exempt. Three resolvers depend on this agreeing.
3. **App layout** — `db/` at the root and each SURFACE a directory beside it: `api/`, `web/`, `site/` (the public prerendered site), `widgets/` (embeddable scripts) and `extension/` (a jetty browser extension). Most sub-projects carry `config/ src/ public/ test/ dist/ deploy/` (db/ doesn't). Configuration lives in `config/`, `vite.config.js` included. Which surfaces an app has is the app's business — api-only, web-only, **site-only**, **widgets-only** and **extension-only** are all whole projects — but a surface inside another one is not: folded into `web/`, it inherits the SPA's build, port and release. A surface earns its own directory when its config, its tests and its release are all different answers, which is what `site/`, `widgets/` and `extension/` are. **`site/` has a fourth and it is the decisive one — OUTPUT**: one Vite root is one `dist/`, and `vite build` empties `outDir`, so a `target: 'static'` site living inside `web/` is deleted by the next SPA build with nothing said (`FJS-D127`, `FJS-449`). `fli check`'s `app-layout` reports a static config found inside another surface. Canonical: root `README.md` §Project Structure. Never *derive* a config path from where `vite.config.js` sits — probe, or be told.
4. **One owner per translation.** Exactly one place turns a thrown value into an HTTP status, one wraps/unwraps the result envelope, one parses `$`-params into `ctx.directives`, one announces a mutation, one startup phase list every caller runs. Implementations are in §Bridge index. Add to the owner, never beside it.
5. **One owner per `app.<thing>`.** Claim it with `app.claim(name, value)`; type it by augmenting an exported interface, never by redeclaring the property — declaration merging requires identical types, so a redeclaration silently loses. The verb is `claim` and not `provide` because **a Provider is a third party the app speaks to** (`FJS-D06`) — `/metrics` contributions go through `app.registerMetricsSource(name, fn)` for the same reason.
6. **Access is declared in the schema, not in hooks.** Gates, `@encrypted`, `@guarded`, `@@transitions` are enforced at the Data boundary. `x-gate` on the client is a UI affordance only — unknown answers are permissive and the server enforces regardless. No exceptions.
7. **Protected fields are redacted in the audit trail.** `@encrypted`/`@guarded`/`@secret` log as `[redacted]` in field entries and in `before`/`after` snapshots.
8. **Caller-supplied names never enter a SQL pattern.**
9. **Patch semantics: an explicit `null` clears.** Test key presence (`key in updates`), not `??`.
10. **A `$`-PREFIXED KEY is transport syntax only.** `$limit`, `$offset`, `$orderBy`, `$select` are how a directive travels on a wire; `ctx.query` is filters, `ctx.directives` is `{limit, offset, orderBy, select}`, and no `$`-prefixed KEY survives the bridge. The rule is about the prefix on a parameter name and about nothing else — junction's ambient `$`, the service call in progress, is a different thing that happens to share a character (Bridge index § API internals). **Two boundaries read the convention** — junction's bridge off a request, sierra's router off a URL onto `page.query` + `page.directives` — and the table they read it by is one module, `@frontierjs/toolbelt/directives`, one row per directive so a Data-realm feature that grows a per-call option cannot arrive half wired. **What the VALUES mean is the sibling module, `@frontierjs/toolbelt/query`** (`FJS-D125`) — a string is a number only if `String(Number(v)) === v`, `true`/`false`/`null` are themselves, structure is bracket notation, and `?code="5"` is the escape. Three readers: junction's transport, junction's client writing one, sierra's router. **Not a WS frame**, which is JSON and already carries its types.
11. **The nearest delegation root owns an event.** Roots nest; a handler must fire once.
12. **Mesa compiler output is reproducible** — scope ids are content-addressed, which is what makes CSS dedupe work across the two compilers a static build runs.
13. **`@frontierjs/css` is the styling language.** Style with a tone (`danger`) and a treatment (`outlined`), never a colour. UnoCSS is supported *alongside* it as an opt-in layer a consuming app configures (`packages/css/README.md` §Using it with UnoCSS). A package in this repo ships no utility classes — a component needing Uno to look right is unusable by an app that does not run it.
14. **Typecheck baselines ratchet down only.** `scripts/typecheck-baselines.json`, one number per package; absent means 0. `bun run typecheck -- --update` writes an improvement back.
15. **A clean compile is not proof of valid JS.** Compiler tests parse their output.
16. **Runnable examples are verified, not sketches.** A broken one is a bug.
17. **Four markdown files at a package root is the standard** — `README.md`, `CLAUDE.md`, `PROJECT_STATE.md`, `CHANGES.md`; everything else in `<pkg>/docs/`. **A fifth is a question, not a refusal**: `package-root-md` warns and names it, because the rule cannot tell a stray design note from the next thing everyone needs at the root. Answer it — move the file, or record an allowance saying why it stays. Generated `*.snapshot.md` is exempt; it is gated output, not documentation.
18. **In a Sierra app, `src/resources/` holds `.mesa` files, and a resource file carries its model's default form.** A Resource is a UI-realm noun, written in the UI-realm language. The data half is `<script module>` — `createResource` and the model's own verbs — which runs once at import and is what every other module imports (Mesa VISION §11, rule 30); that half is required. **The markup half is the form and it is optional**: with it, a create or edit page is `<Order />` and nothing else, and a page wanting a different form passes children, which `<Form>` already lets win. A file with no `<script module>` is a component in the wrong folder (`FJS-D112`).
19. **A resource file is named for its noun — PascalCase, singular — one Resource per file.** `App.mesa` exporting `export const apps`; the same split the Data realm makes between `model App` and `db.app`. Where a model exists the filename IS the model name, so an irregular is visible (`AlertRule.mesa` exporting `alerts` says `model:` must be stated). A resource over no model takes its service noun, singularised.

**Always `cd` into the package and run its own script.** Runners differ per package and a wrong runner produces failures that belong to nothing. `bun run --filter '*' test` from the root runs them all, one each. `bun test` instead of `bun run test` runs bun's own runner over whatever it finds — in mesa that is ~35 failures that are runner artifacts.

**`bun run ci` is the whole of CI and it is not a GitHub feature.** One node script runs twelve phases — hygiene, structure, registers, snapshots, access, coverage, registry, advisories, scaffold, typecheck, deploy, tests — and `.github/workflows/ci.yml` does nothing but call it, so it runs identically on a laptop. It fails a package with no `test` script, a source file `.gitignore` hides, a *raised* typecheck baseline, a committed snapshot that no longer matches its source, **a dependency or a clock inside the substrate package** (`hygiene` — `@frontierjs/toolbelt` may be imported by litestone and mesa only because it depends on nothing, so a non-relative import under its `src/` fails the build), an **id the register issued twice** (`registers` — `packages/cli/core/register-check.js`, the same engine `fli register:check` gives a client app; `ISSUES.md` says an id is never reused and nothing held it up, so three ids each named two different defects), and an **architecture rule broken in this repo's own apps** — `structure` runs `packages/cli/core/checks.js`, the same engine `fli check` gives a client app, because two implementations of one rule is how a framework ends up breaking rules it publishes. **`snapshots` carries no list of what exists, and it is not implemented here**: it runs `packages/cli/core/snapshots.js`, the same module `fli test:snapshots` gives a client app — every committed `*.snapshot.*` names the command that wrote it in its own header (`generated by: litestone ddl --schema schema.lite`), and that command is rerun with `--check` from the file's own directory, so a new KIND of snapshot costs a generator and never a CI edit. The command comes out of a file in the repo, so it is restricted to a known binary and a shell-free argv, and a snapshot naming no generator fails rather than being skipped. **Discovery alone fails open**, so the expectation comes from the BASE REF: a snapshot tracked where the branch left main and absent now is a failure, because a generated artefact that stops existing takes its check with it in green. A deliberate removal is a named entry under `removedSnapshots` in `scripts/ci-allowances.json`. **`access` is the one phase that reports rather than judges** — *what did this branch do to who may do what*, printed per app against the base ref, and never a failure, because a branch that widens access is usually a branch doing its job and a red that fires on every feature trains everyone to skip the phase. The gate is `fli test:access --from <ref> --strict`, which belongs on the branch that deploys. It runs the same `litestone access --from` a client app runs, and **it is not `release:check` with a different word**: the two grade one comparison on axes that disagree by construction — removing a `@@gate` is an *expand* for the deploy and the widest thing a schema change can do, and on a real five-part widening every single finding was an expand. **`registry` asks the cheap half of the published-framework question**: every `@frontierjs` package `fli new` writes into an app's `package.json` is looked up on npm, and a name the registry has never heard of fails by name — because the register cannot see this class at all (every id in it is a statement about the WORKING TREE, and a user's experience is the tree AND the registry, which drift independently). It reads the list from `packages/cli/core/app-config.js`, the module `fli new` itself reads, so there is no second answer to *which packages does an app get*. A version gap between tree and registry is a NOTE rather than a failure — being ahead is the normal state between releases — and an unpublished package is allowed by name under `knownUnpublished`, which fails once it IS published. No network, no failure: it reports a named skip and `FJS_CI_REQUIRE_REGISTRY=1` makes that skip fatal. **`advisories` is dependency posture, and it is a COMPARISON rather than a scan** — the decision `IDEAS/tooling-decisions.md` §5 left open, settled the way everything else here is: a phase, not a bot, because an external bot would be this project's first check that cannot run on a laptop. `bun audit` answers what is advised against; almost all of it is dev tooling, and a vitest advisory is not something an app installing this framework can be hurt by. What FAILS is an advised package **reachable from a PUBLISHED package's runtime `dependencies`**, since that is the set every app installs — walked from each package's own directory and resolved the way node resolves, because bun installs into `.bun/` with symlinks and a path guess finds nothing and would report every advisory as dev-only. The **resolved version is printed beside the advisory's range and the two are never compared**: a range parser here would be a security judgement made by a regex, and one line showing `vite@8.2.0` against `<=6.4.2` settles the two-copies case for a reader. Its first run found `packages/mesa` shipping `happy-dom@14.12.3` — two criticals — to every app that installs mesa (`FJS-475`). No network is a named skip and `FJS_CI_REQUIRE_AUDIT=1` makes it fatal; a known one is a named entry with a reason under `knownAdvisories`. **`scaffold` is the phase no suite can replace**: it runs `bun pm pack` over every publishable package, scaffolds an app against the tarballs, installs it, builds it, **runs that app's own `bun run check`**, then **scaffolds a model into it and builds again** (`scripts/scaffold-build.mjs`). The check is there because a default whose first use is red is worse than no default: `fli check` from an INSTALLED cli (it had never run at all — a free `resolve` the parse sweep cannot see, `FJS-269`), Biome against a config resolved out of `node_modules`, and `fli typecheck` against packages that ship `.ts`. An app in this repo resolves sierra to `packages/sierra/` and never to a node_modules path, so the code that only runs for an *installed* app runs nowhere else here — which is how `FJS-251` broke every npm install past 836 green sierra tests. It grades each package's `files:` field for free, and **its per-run `--cache-dir` is load-bearing**: bun caches a tarball by name *and* version, so a shared cache serves the previous run's bytes and the phase passes against a broken tree. **`deploy` runs the same pipeline twice, once per package source** — `fli new` → `make:deploy` → `deploy:local`, an image built, a health answer, and then a **register + login through the prefix the app's own `web/config/sierra.config.js` names**, because a health answer says the process is up and not that the app works: a scaffold template written against behaviour only the tree has installs cleanly, builds, answers health and cannot log in, and nothing else here can see that (`FJS-252`). `/manifest` is not asked — `manifestPlugin` is `devOnly` and the container runs `NODE_ENV=production`. `--source npm` is the only thing here testing the PUBLISHED framework, which drifts from the tree independently (`FJS-252`); `--source local` is the working tree containerised, which was impossible until the build started packing the tree into its own build context, since a Docker build can see neither a `link:` spec nor a `file:` tarball outside that context (`FJS-241`). **`packages/cli/core/vendor.js` is the one owner of that pack** — `fli deploy:vendor` is the command, `deploy:local` and the pipeline's build step run it first, and `basecamp`'s image builder calls it rather than carrying the copy it used to be. It needs a daemon that can read the build context: a shell with a private `/tmp` gets `unable to prepare context` about a directory that is plainly there, and `FJS_CI_WORKDIR` is the way out. **Without a daemon it reports a named note and passes** — requiring Docker for `bun run ci` on a laptop is too much — and `FJS_CI_REQUIRE_DOCKER=1` turns that skip into a failure, which the workflow sets, because a check that quietly stops running is worse than one nobody wrote. A suite known to fail is named so a NEW failure is loud, and **so is a deploy source** — `knownDeployFailures` exists for publish order, where the scaffold gives an app a package this repo has written and nobody has published, so `npm` cannot resolve it while `local` passes. **The `deploy` phase has a second half and it is the only thing here that runs `fli deploy`** — `deployJournalCycle` in `scripts/scaffold-build.mjs`: deploy → deploy → crash → resume → revert, against a machine, with a journal on it and a container serving from it. `deploy:local` is a different command — it builds an image and runs it and never touches `_steps-docker/`, the journal, the swap, the health poll or the revert — so the pipeline an app actually deploys with had run **zero times**, and every defect that implies was sitting in it: **nine of its ten multi-line shell commands were shell syntax errors on the target** (`.replace(/\n\s*/g, '; ')` makes `then;` and `do;`, and an interpolated `ssh host "…"` is parsed by the local shell first, so `$(curl …)` in the health check ran on the OPERATOR'S machine), `deploy:setup` wrote an nginx config with every `$remote_addr` stripped, `fli deploy:revert` restored the bytes it was reverting FROM and reported success, and a resumed deploy started `undefined`. What makes it runnable is that a deploy machine can be **`localhost`**: `packages/cli/core/machine.js` is the one owner of *(host, script) → the argv that runs it there*, and the script travels on **stdin** to `sh -s`, so the same script reaches the same shell with or without an ssh prefix. Not a simulation — real docker, real journal, real revert; the only thing it does not exercise is ssh itself. **Its sharpest assertion is that an unchanged redeploy mints the SAME Release** — trivially true while every Release had a null digest, and the thing 2.3f is about now that `04c-journal` opens the transition after the artefact exists. It failed on its first run, and the reason was that the container writes `db/app.db-wal` into the mounted volume, the volume is inside the build context, and the scaffold's `.dockerignore` said `db/*.db`, which never matches a sidecar: **every deploy after the first copied the running app's write-ahead log into the image**. ~4 minutes and six image builds, so it is full-tier only, and it skips with the same `FJS_CI_REQUIRE_DOCKER=1` escalation as the rest of the phase. Every allowance is a named entry with a reason in `scripts/ci-allowances.json`. `bun run hooks:install` points `core.hooksPath` at `scripts/hooks`, whose `pre-push` runs the fast tier (~40s); the suites (~3 min) belong in the workflow, because a pre-push costing minutes teaches everyone `--no-verify`. `--only <pkg>` narrows typecheck and tests.

**The browser drives need their servers started by hand, first.** They exit 1 naming the missing process. All need Chrome. **The *Start first* column is READ** — `packages/cli/core/preflight.js` parses it, `runnables.js` puts the resolved steps on the drive's row, and `fli gui` walks them behind one button, skipping anything already answering. So the order in a cell is the order they are run in, `nothing` is the explicit empty answer rather than a blank, prose after the em-dash is not read, and a step whose script has been renamed is a `fli check` error (`drive-preamble`) rather than advice somebody notices is wrong. What it cannot see is the drive's own check, which is the half `--preflight` would close.

## House style

Match the file you are in first; this is what the repo does when there is no local precedent.

- **Comments explain the failure, not the mechanism.** `// increment the counter` is noise; `// vite hops ports silently, so the drive would talk to the other app` is the house voice.
- **A comment must be load-bearing. Delete it otherwise.** Test: if it vanished, could someone editing this file make a mistake it would have prevented?
  - **No edit history in code** ("used to be", "this replaced X", "merged 2026-08-08"). That is `CHANGES.md`, `DECISIONS.md` and git. Narrow exception: a past bug stated because the shape still invites it (`--ring` in `tokens.css`), where the history IS the warning.
  - **No dates in code comments.** If the comment needs one, it belongs in a decision record the code points at.
  - **No persuasion** — "the whole point", "deliberately", "which is exactly why", italics for emphasis. State the constraint flatly; if it needs selling, it needs a ruling.
  - **Never narrate your own edit.** The reader does not know a change happened.
- **Every non-trivial file opens with a header block** — what it is, and what it is for. Test harnesses document their own traps at the top (`example/web/test/verify.mjs`).
- **Section dividers inside a file**: `// ─── name ──────` (box-drawing, padded to a consistent width). Not `// ---`, not banner boxes.
- **Aligned columns** where a run of lines is parallel — imports, object literals, `const` blocks. See `example/api/src/app.ts`.
- **Prose in the docs is sentence-shaped, not bullet-shrapnel.** Bold the claim, then say what it cost. Numbers earn their place by being measured.
- **British spelling** in prose (`behaviour`, `serialise`). Identifiers stay US (`color`, `serialize`) where a web API or CSS property already chose.
- **No semicolons**, single quotes, 2-space indent, in TS and JS alike (`packages/css`'s own build/test scripts are the one holdout). TypeScript in junction, auth, caravan, conduit, notifications; plain ESM JavaScript in litestone, mesa, sierra, ui, css, jetty. Do not introduce TS into a JS package.
- **Fake clients hide real bugs.** Cross-package behaviour is tested against the real dependency — `{ post: {…} }` passed every test and failed every real Litestone client.
- **A new `on*` states its tier** (`FJS-D06` §1) — **Hook** may mutate the arguments or halt the operation, **Guard** answers allow/deny, **Observer** receives and cannot act. The word goes on the option that holds it: conduit's callbacks are `observers:` because a throw in one is swallowed, and `management.hooks` beside it keeps *hook* because that pipeline can refuse the call.
- **A new defect gets an `FJS-###` in `ISSUES.md`**, not a paragraph in a package file. A ruling closes an `FJS-D##` and moves to `DECISIONS.md`. Check a new `.gitignore` rule against `git status --porcelain` — an ignore glob hid 20 source files once.

## Live hazards

**Correct behaviour you have to know about.** Things that are *wrong* live in `ISSUES.md`, one id each; things that are *fixed* live in `CHANGES.md`. If a rule here is pinned by a test that cannot be deleted quietly, it does not need to be here.

**Data**

- **A composite `@@unique` naming a NULLABLE column is a parse error, and single-column `@unique` over one is not.** Two NULLs never compare equal, so the index admitted `(1, NULL, NULL)` twice while refusing the same pair with values — the constraint held exactly where nobody doubted it. `@@unique([a, b], nullsDistinct: true)` is how a schema says it meant that: SQL's own word for what SQLite does, emitting identical DDL, so it is a statement rather than a knob. The asymmetry is the ruling (`FJS-D130`) — on one optional column *unique when present* has a single reading, and on a tuple the reading is the tuple. A `@from` is on the same page for the same reason: it correlates on **every** column of its relation's key, in three places (the subquery, the policied `first`/`last` repick, and the correlation columns injected for a `select`), because a join on the first column alone answers a count of real rows to a question nobody asked. A write naming a `@from` field refuses by name like the other five virtual kinds.
- **A drive that cleans up through the API cannot free a `@unique` on a soft-deleting model, so a fixed fixture key makes it single-use.** `verify:notify` used a literal `ORD-NOTIFY-1`, deleted it over HTTP — which SOFT-deletes — and the kept reference refused the next run's create with a 409 the drive did not check, so the order id was `undefined` and `pay` answered **500** about a collision three steps upstream. It passed once per seed for its whole life, and `db:seed` being in its own preamble is why nobody saw it (`FJS-530`). **Two ways out and they are not interchangeable.** Mint the key per run, as `verify:money` does for a discount code and `verify:ui` now does — and check the two things that bit that fix: a `@upper` column stores a lowercase id uppercased, so a later search for it silently misses, and `@length(3, 20)` refuses a prefix plus a run id. Or RELEASE the value in the sweep, which is what to reach for when the drive's own expectations name the literal: read with `?$withDeleted=true`, `PATCH /{service}/{id}?$withDeleted=true` the reference aside, and delete only a row that is still live — a second DELETE is a no-op against something already gone. **`FJS-530` fixed one drive and nothing looked for the rest**: `verify:ui` (twice in one file), `verify:pay` and `verify:jobs` all had it, and two of them had never been run twice, so a race in each was sitting behind a create that could not succeed (`FJS-546`, `FJS-547`).
- **A soft-deleted row keeps its `@unique` values, and `restore()` is why.** Freeing the slot would make `@unique` false for every read that includes deleted rows — `findUnique(withDeleted)` legitimately matching two — and would make the way back fail whenever a stranger took the value first. So a write naming a value a deleted row holds is refused by name (`SoftDeletedUniqueError`, 409) rather than by SQLite, and releasing a slot is a decision the app makes: `update({ …, withDeleted: true })` moves the value, `delete({ …, withDeleted: true })` stops keeping the row. **A LIVE holder is the other half and it is a different error** — `UniqueConflictError`, also 409, naming the field with the value redacted where the column is protected, and carrying `errors` so a form marks the box rather than showing a banner. Two classes because the ways out differ: restore-or-release, against send another value. Every create AND update path translates; SQLite's own sentence, which names a physical table, reaches nobody (`FJS-441`). **Membership now has a spelling**: `@@allow('read', auth().id in memberIds)`, the list always the RIGHT operand, so an audience held on the row no longer has to become a service where-clause. `DECISIONS.md` § Query & write semantics.
- **A soft-deleted parent's children have THREE fates and each has a spelling.** `@@softDelete(cascade)` stamps them, `@hardDelete` on the relation field destroys them, and **`@keep` leaves them live on purpose** — the third, which for its whole life could be produced and not said: it is what a plain `@@softDelete` already does, and the parser warns about it because forgetting the cascade and meaning it look identical. *The customer goes, the receipts stay* is that shape and it is not rare — `example`'s `Customer.orders` is `@keep`, and without it removing a customer either destroyed every order they had placed (`onDelete: Cascade`) or hid them, neither of which is what a shop means. It covers the whole subtree beneath that child, and says nothing about removing the child directly. The footgun warning names all three ways out, so the third is discoverable from the thing that complains about it.
- **A `@@gate` refuses, a `@@allow` filters — so a wrong policy is an empty screen, not an error.** The two rules underneath that, and the order every layer reads in, are `packages/litestone/docs/access-control.md` § *Combining them*: **a refusal must never confirm a row exists** (which is why create is the one policy that throws — the payload IS the row), and **whose mistake is it** — `@guarded`/`@system` throw because no caller was ever meant to send that column, a field `@allow('write')` drops because the same form body is legitimate one level up. A gate throws naming the model and the level; a policy compiles silently into the WHERE. Every read that legitimately crosses a policy's scope must be `asSystem()`, or it returns nothing with a 200. Declare one model at a time and run the app's drive between them. **`fli test:access` writes the whole declared surface to a committed `db/access.snapshot.md`** — gates, policy predicates, protected fields, transition gates — and the `snapshots` CI phase fails a stale one, so a gate that moved is a diff rather than a production refusal. **`--from <ref>` asks the other question and writes nothing**: what this branch did to who may do what, graded `widens` / `narrows` / `undecidable` / `new`. The comparison is `classifyPivot`'s own walk read on a second axis, because *can N-1 still serve* and *who may now do more* disagree by construction — a removed `@@gate` is an expand and the widest change there is. What no comparison can answer is a predicate whose text moved, and that is reported rather than guessed — **an allow→deny inversion is the same answer for the same reason**, because `@@allow(X)` replaced by `@@deny(!X)` over the same operations admits the same rows and adopting declared tenancy desugars to exactly that (`FJS-D131`). **`new` is a model the baseline never had**: it has no counterpart, so it is listed with the gate and policies it DECLARES and graded on neither axis, ranked below `narrows` so `--strict` keeps its meaning. **A baseline is graded by its own era** — a validation rule invented after that ref is a named note rather than *no baseline*, since every rule this parser learns is retroactive and `--strict` fails on no baseline by design; a SYNTAX error there still refuses. `--strict` is the gate; the `access` CI phase only prints. **`fli test:ddl` is the sibling for the opposite problem** — `db/ddl.snapshot.sql` is the emitted DDL, and the names in it are what every hand-written statement binds to while the app's own tests go through the client that changed with the emitter.
- **A schema change is a deploy question before it is a migration**, and `fli release:check` is the one that asks it: can the release still serving and the release starting share one database? Expand — N-1 keeps working, so the deploy can be taken back. Contract — it cannot, and that deploy is the **pivot**, after which only forward. Unknown counts as contract. `db/release.snapshot.md` is the surface it diffs, `--from <ref>` is the question a deploy asks, `--strict` fails a branch on anything but expand *including no baseline at all*. **Access is in the comparison, which is the half no generic deployer can reach**: raising a `@@gate` takes reads away from a release still serving them, and adding an `@@allow` empties a screen with a 200. A required column with no default is the one contract handed back as a plan — expand, backfill, contract — rather than a refusal.
- **You cannot run without gates.** A schema declaring any `@@gate` auto-installs `GatePlugin({ getLevel: FrontierGateGetLevel })` — a declared-but-unenforced gate is fail-open. Installing your own replaces it; installing none does not disable it. Contract: **absent = the app does not model this stage; only `null` grades down**, and standing (`isSystemAdmin`/`isOwner`/`isAdmin`) is checked before the lifecycle.
- **Under `strategy database` four seams are the tenant path's, not the single-client path's, and all four were missing.** A session is verified at the TRANSPORT, before any hook — so `IAuth.verifySession(token, from?)` carries the request's host and headers, which is the only way an app whose people live per tenant can authenticate anybody (`FJS-487`). A raw route (`app.get`/`app.post`) now runs inside the request scope, so `requestMeta()` works inside `/auth/login` and inside a webhook (`FJS-488`). `announceDataWrites` taps each TENANT's client on first open rather than one app-wide client (`FJS-489`). And the per-request principal resolver runs for an ANONYMOUS caller, exactly as `withLitestoneDb` does — a claim is what a caller with no session carries, and skipping them made every guest basket a 404 (`FJS-490`). A `jsonl`/`logger` database stays schema-global and is written by every tenant's client, so its index is idempotent by primary key (`FJS-491`).
- **Tenancy is declared in the seed and there are two strategies.** `tenancy { }` at the top of `schema.lite` — `strategy database` is one SQLite file per tenant plus a registry that indexes them, `strategy row` is one database and a tenant column. Every reader asks one resolution (`db.$tenancy` / `registry.tenancy` / `resolveTenancy`), and precedence is **option → declaration → default**, which is what stops `litestone tenant create` and the running app disagreeing about where a tenant lives. **Row tenancy desugars into `@@deny`, never `@@allow`** — allows are OR'd within an operation, so an allow would widen every read to the whole tenant — plus a `@default(auth().<claim>)` stamp, and it is two rules because `checkCreatePolicy` runs BEFORE the stamp: an absent column is legitimate on create and belongs to nobody on read. A model with no tenant column is reported by name at parse; `@@tenant(none)` says it spans tenants on purpose. `asSystem()` is the only way across, which is what a cross-tenant tier is built on. `packages/litestone/docs/multi-tenancy.md`.
- **A CRUD method written on a `createBaseService` definition WINS over the generated one** — it used to be dropped in silence, and what answered instead was the generated row-by-id, which is a plausible wrong SHAPE rather than an error (`FJS-426`). The derived hooks are unaffected: `gateAuth` and `autoFilter` attach by method name, so an override keeps the model's `@@gate`.
- **`$setAuth(user)` RETURNS a scoped client, it does not mutate.** `db.$setAuth(u)` then `db.thing.create(…)` grades as anonymous, with no warning. It is `const userDb = db.$setAuth(u)`.
- **A Litestone client THROWS on an unknown property** — never `undefined`, so a typo'd accessor is loud. The cost: feature-detection is itself a throwing expression. `typeof db.$maybe === 'function'` explodes; use `'$maybe' in db` or a `try`. A capability that depends only on the schema belongs on **every** flavour of client — root, `$setAuth`, `asSystem`, `$scopedBy`.
- **A CAPABILITY is a grid beside the ladder, and a finer grant REPLACES the coarse one rather than adding to it.** `@@capabilities` on a model grades its writes and its named moves (`(all)` adds read); `@capability` on a column grades that column's write; both are ANDed with the `@@gate`, which stays the floor (`FJS-D146`). The rule that makes the fine tiers worth having is what an update's payload is partitioned BY: a key carrying `@capability` is graded by that column's grant, a key that is the transitions field is graded by the MOVE it resolves to, and everything else is what `Model.update` is for — so `Environment.variables` can be handed to somebody who holds no other edit on the environment, and `Server.reboot` alone reboots. It shipped the other way round and no unit test could see it, because no fixture had ever held one grant and not the other. **A CREATE keeps both**, since `Model.create` is the grant for the row existing at all. **A move the ENGINE makes is nobody's grant** — `@system`, or a gate of 8 or 9 — so it is out of the derived set and out of any picker; a `@system` move is refused AS `@system`, never as a missing grant that would not have helped. **A verifier has to take the grid out of the way to grade anything else**: `atLevel`, `verifyRowPolicies` and `verifyTenantIsolation` hand their synthetic caller every declared capability, or a policy that filters correctly is reported as *the call threw*, which is true and is about the grid (`FJS-351`). **The caller's set is `auth().capabilities`** (`FJS-D151`) — one name the framework fixes rather than the app, because litestone's grid reads it; what an app chooses is which COLUMN it comes out of, and under tenancy that column is on the membership row, so the same person holds a different set per tenant (`FJS-D149`). **A `Capability[]` column carries its own escalation guard** — subset, never a rank — and that guard is undefined under `asSystem()`, which has no principal: an app whose membership writes go through one still needs the rule said in a hook, and needs BOTH axes there, since two roles can hold the same grid and differ on the ladder (basecamp's `admin` and `owner`).
- **`asSystem()` does not bypass a `@check`, a `@@check` or an `@@arc`, and it bypasses everything else.** The gate, every row policy, `@guarded`, `@system` and every field `@allow` are this package's rules and the system client drops all of them (`FJS-519`); a CHECK is in the TABLE, so SQLite refuses a system write exactly as it refuses anybody's. That is the reason to reach for one: a rule that must hold against a job on `db.`, a migration, a seed and `fli tinker` cannot be declared any other way — a validator runs here and a service hook is not on the path. The cost is the other side of the same fact: it cannot be evaluated in a browser, so it arrives as a refusal rather than as an affordance, and the refusal is a `ValidationError` (400) whose sentence comes from the attribute's own message argument — without one the person reads `is not valid` and the expression goes to `err.constraint`. `packages/litestone/docs/schema.md` § Constraints the database enforces. **`@@arc([orderId, productId])` is the third and the one with a shape rather than an expression** — several optional foreign keys of which exactly one is set, which is *this row points at an Order OR a Product* keeping a real FK, a real cascade and a real `include`, where the polymorphic `subjectType`/`subjectId` pair keeps none of the three and needs a job to sweep what the database will not. Adding one is a **contract** for `release:check`, like any row invariant. One column per member and it stops scaling around six — which is the signal the target set is OPEN, and an open set is the case no relation can serve (`IDEAS/polymorphic-relations.md` prices the real thing: 69 single-valued `.targetModel` reads are the cheap half, and the expensive half is that `policy.js` compiles the TARGET's own policy into a subquery, so N targets is N gates and a caller who reads one model and not another sees half a list as a 200).
- **Raw SQL requires `asSystem()` once a schema declares access rules.** `db.sql` and `db.$setAuth(u).sql` throw; `db.asSystem().sql` is the bypass, and it can write. Raw statements enforce no `@@gate`/`@@allow`/`@guarded`/`@scoped`/`@@softDelete`. Coarse per schema on purpose — deciding per statement means parsing it, and a wrong validator grants a *false* guarantee. `where: { $raw: sql\`…\` }` keeps every policy and is the hatch to reach for. A JS migration is exempt: the runner hands it the system client.
- **A field `@allow` is a PREDICATE and it is compiled into SQL, both ways** (`FJS-D129`). Not a strip and not a JS check against the payload, because both of those were holes. A READ predicate is AND-ed into the caller's arguments as a **sibling** of their `where` — sibling, because a conjunct inside it is complemented by their own `NOT` — so a column they may not read cannot be filtered or sorted on, and a value that used to come back by binary search in seventeen requests comes back as nothing. A row-dependent one therefore narrows to the rows it admits rather than refusing, which is the case the feature exists for; the cost is that an `OR` branch naming the column narrows the whole read. A WRITE predicate is the WHEN of `SET col = CASE WHEN … THEN ? ELSE col END`, so it reads the STORED row — grading it against the payload let a caller write a column on somebody else's row by stating `ownerId: me` in the same payload. **CREATE is the exception and keeps the JS evaluation**: there is no stored row and the payload IS the row. Through a relation both refuse by name.
- **`@guarded` is not a level** — a system-context lock taking only `(all)`; `@guarded(5)` does not parse. Per-role column access is field-level `@allow('read', auth().role == 'admin')`. It locks **both directions**: a non-system write naming a guarded column is refused with an `AccessDeniedError` naming the field, where it used to land silently while the read strip made it look refused. `@encrypted` alone is not a guard — it hides a value from a reader and stays writable, which is what a caller submitting a secret needs. The two are not exclusive — `@secret` expands into exactly `@encrypted @guarded(all)` — but writing both by hand is `@secret` spelled out, and the choice worth making is which ONE you want: `@allow('write', …)` for a column some callers may set, `@guarded` for one only `asSystem()` touches. A **required** `@guarded` column makes its model uncreatable below level 8.
- **A column your `getLevel` reads must not be writable by the caller being graded.** A gate is per MODEL, so `@@gate("4.4.4.5")` on an identity table says *any signed-in caller may write any other person's row* — `role`, `isAdmin`, a status, whatever the ladder is graded from. `@frontierjs/auth`'s `User` ships the shape: a level for what kind of caller, `@@allow('update', id == auth().id || auth().isAdmin)` for whose row, `@allow('write', auth().isAdmin)` for which columns. **`8` is not a stronger `5`** — it means nothing outside `asSystem()` has anything to say to this model, which is true of credential material and false of the table an app's own screens list; raising the gate just moves the surface into the bypass. `DECISIONS.md` § Access control.
- **`encryptionKey` is parsed as hex**, so 64 *characters* is not necessarily 32 bytes. Non-hex padding decodes short and is rejected with `must be 32 bytes (got 1)`.
- **A relative `database { path }` resolves against the process CWD, and a schema can be told otherwise.** The same schema then means a different file depending on which directory the command was typed in, and nothing fails — SQLite creates the file, litestone creates the directory above it, and every tool reports on the new empty database (`FJS-449`: studio served an empty `db/db/shop.db` for nineteen hours; a `vite build` from a surface root prerendered twelve product pages as **zero products, exit 0**). `resolveFrom: 'schema'` anchors to the APP ROOT — the schema file's directory, or its parent when that directory is `db` — which is what every litestone CLI call site does. **A schema assembled in memory says where it would have lived**: `path:` beside `schema:` when the app read a file and appended to it, or `resolveFrom: '<dir>'` (a directory or a `file:` URL) when there is no file at all, which THROWS on an anchor that is not a directory. `createTenantRegistry` takes `path` the same way, and there it matters twice: `tenancy { dir }` and `tenancy { registry }` are written against the SCHEMA FILE's own directory, not the app root — the one place the two bases differ. An override (`db`, `databases: { … }`) is unaffected and must be: code is written against the process. **The default stays the CWD**, because isolation-by-CWD is a real contract a seed test depends on. **Creating the DIRECTORY for a database is announced** — creating the file is ordinary, the directory is the signal every instance of this had in common, and the message names the cwd because `db/shop.db` from two different directories prints the same string.
- **`createClient({ db })` names MAIN's path and nothing else.** It overrides a declared `database main`, so `db: ':memory:'` is the in-memory test client; a SECOND declared database keeps its declared path regardless. `databases: ':memory:'` is the shorthand that moves them all, jsonl and logger included. Precedence: `databases: ':memory:'` > `databases: { main: { path } }` > `db` > the declaration.
- **Litestone emits columns verbatim camelCase and `DateTime` as ISO-8601 TEXT.** Hand-written SQL assuming snake_case or epoch-ms will not match.
- **Every timestamp litestone writes comes from the CLIENT's clock, and a raw `UPDATE` therefore stamps nothing.** `@default(now())`, `@updatedAt` on create and on update, `@@softDelete`'s stamp, `now()` in a policy and the retention cutoff all read `createClient({ now })` — which is what makes `advance('100d')` then `$retain()` a test anybody can write. `@updatedAt` was an AFTER UPDATE trigger and is not any more (`FJS-531`): a trigger reads SQLite's clock and nothing else, so a frozen clock stamped today and the one crossing a frozen clock exists to stage could not be staged. **Retiring it is also what closed `FJS-396` at the root** — RETURNING is evaluated before an AFTER trigger, so naming the column in the SET clause had only ever helped while the two values DIFFERED, and they are equal whenever the clock has not moved between two writes to one row. The column DEFAULT stays as the floor, so a raw INSERT still stamps; a hand-written UPDATE owns its own. An existing database takes one generated `DROP TRIGGER IF EXISTS` and no rebuild. What no clock reaches is a raw statement and a `@derived` expression reading `now()`, which is compiled once at startup.
- **The audit logger defers one event-loop tick**, so a read in the same tick sees 0 rows. `fireLog()` schedules with `setImmediate` and the jsonl driver appends synchronously — anything after an `await` sees the row. Yield once; do not wait.
- **`@@log(audit)` records a WRITE; `db.$audit()` records an EVENT — and the second one throws.** A sign-in is not a write to `User`, and a *failed* one is not a write at all, so nothing the logger can see names the actor or the attempt. `$audit({ operation, model?, records?, actorId?, meta? })` is the one way to put a row there by hand — an unknown key is refused by name, `actorId` defaults to the calling client's principal (a system context has none), and a stated value beats `onLog`'s. **It awaits and throws where `fireLog` is fire-and-forget**, because there the record is a side effect of a write that already succeeded and here it is the point. `meta` is NOT redacted — it is yours, so do not put a secret in it. On every flavour of client.
- **A per-call flag the model cannot SATISFY is refused by name, and so is a method.** `onlyDeleted` on a model with no `@@softDelete` used to answer the LIVE rows — the opposite of the question, with nothing saying the flag had not applied — and `search()` below `@@fts` threw a bare `Error` that reached a caller as a 500. Both are `CapabilityNotDeclaredError` now: **400**, naming the model and the attribute that would make the request legal — `onlyDeleted`/`onlyTemplates` on every read and write, plus `search()`, `optimizeFts()`, `restore()` and `transition()`. **`withDeleted`/`withTemplates` do not refuse**: they ask to widen, and a model that hides nothing already answers everything, which is what generic tooling (Studio's row browser, a *show deleted* toggle) is asking for.
- **A cursor and an offset never combine, and `$after` wins.** A caller sending both has named no position either one of them means. Growing a window is also not a chance to ask a different question — `more()` reuses the last `load()`'s query and directives, because a cursor minted under one ordering names no position in another, so a new filter or a new sort is a `load()`. And **a list is a set of ids in an order**: one row cannot be in it twice, which is what stops a row that arrived on the socket mid-scan from being in both the list and the next slice.

**A `where` typo below the boundary warns to stderr and returns no rows.** Over HTTP an unknown key is a 400 naming it (`autoFilter`), but a service building its own filter gets silence. `client.service('x').find({ limit: 100 })` is the trap: the FIRST argument is the filter, `limit` belongs in the second. `find()` answers the list envelope; `findData()` is the rows.

**API**

- **`ctx.params` does not exist anywhere in Junction, and `ctx.route` is not it.** A `ServiceContext` splits into `auth` (the principal) / `client` (`ip`, `userAgent`, `headers`) / `route` (path captures alone) / `locals` (per-call scratch, where `withLitestoneDb` puts `db`); a `TransportContext` carries the same `route` and puts headers at `ctx.headers`. **The four have four different rules and that is the substance** — `auth` is frozen and PROPAGATES to a nested call at any depth, `client` propagates, `route` is router-only (`{}` internally), `locals` is fresh per call and does NOT propagate. `packages/junction/CLAUDE.md` § The two contexts is the reference and `tests/context-contract.test.ts` runs it. Stale Feathers idioms survive in old notes; reading `ctx.params.user` yields `undefined`, so a role check silently passes for everyone. Also: `before: { all: [...] }` applies to *every* method, machine-facing endpoints included.
- **Absent is not null on `auth`.** A call naming no `auth` inherits the principal in scope; `{ auth: { user: null } }` means *as nobody, deliberately* and stays anonymous. Same distinction Invariant 9 makes about a patch, and it is the only way to ask what a stranger would see.
- **The gate runs before anything an app wrote, and `validated:` is the phase after the derived layer.** `gateAuth` is a service-level AROUND hook, so it wraps every before hook at either scope; the validators (`autoValidate`, `autoFilter`, `autoSort`) still trail the app's, because a before hook shapes `ctx.data` and it is the shaped payload that must satisfy them. It used to be one appended layer, so an app rule that read the database read it for strangers — on `example`, an unauthenticated POST naming a customer that does not exist answered 400 and the same request naming a real one answered 401, an existence oracle over a gated table (`FJS-403`). Leading the per-method list would not have closed it: `resolvePipelines` runs `before.all` ahead of `before.<method>`. The order is **`around(gateAuth) → before → validated → method → after`**, and `validated:` is where a rule that reads the database off `ctx.data` belongs — it needs a caller the gate has graded and a payload the validator has coerced, and until `FJS-D124` there was nowhere in a service to say it. An APP-level `around` hook is still ahead of the gate, and must be: `withLitestoneDb` establishes the client it grades against.
- **A query string is PARSED, and the schema still wins.** `?qty=5&live=true&qty[gte]=3` reaches a service as numbers, booleans and structure — `@frontierjs/toolbelt/query`, one module for junction's transport, junction's client and sierra's router. Before it the two TRANSPORTS disagreed and the socket was the correct one: it spreads filters into a JSON frame, while HTTP `String()`d every scalar, `JSON.stringify`d every operator object and dropped `null` outright, so an app worked until its socket dropped and then silently filtered on text (`FJS-450`). **A string is a number only if it round-trips** — `'007'`, `'+1'`, `'1.50'`, `'1e5'` and a snowflake id all stay text — and `?code="5"` is the escape for the rest. **Where a model exists it has the last word**: `id String` filtered by `?id=5` reads 5 and Litestone converts it back to `'5'`. Stated gotcha, not a defect.
- **Raw routes (`app.get`/`app.post`) take `{id}`, not `:id`** — `:id` registers as a literal segment and 404s silently forever.
- **A plugin reads `junction.config.js` in `boot()`, never in `register()`.** `configure()` runs `register()` synchronously and junction does not load the config file until the `load-config` start phase, so a block read in `register()` is the config as it was *before* the file. Every app configures its plugins at module scope, which made caravan's whole `caravan:` section unreachable — `admin: true` in a config file mounted nothing, and the only app it appeared to work for was one that hand-loaded the config and passed it to `createApp` (`FJS-431`). `boot-plugins` runs after `load-config` and before `service-routes` and `listen`, so routes mounted there are still served.
- **A missing config DIRECTORY is not a missing config file.** An absent file is an optional miss and stays silent — an app may declare nothing. An absent directory is a path that resolves nowhere, and `loadConfig` now warns naming it: `basecamp` read `api/config` for its whole life without that directory existing and took junction's defaults every boot, with its CORS `*` for everyone (`FJS-430`). `fli check`'s `surface-config` is the static half.
- **`apiPrefix` moves EVERY route the app registers**, auth's `/auth/login` and caravan's `/jobs` included, because the `app.get`/`app.post` shortcuts are its one owner. A path that must not move is registered on `app.http.router` directly. An app that sets a prefix proxies one path, not one per plugin.
- **An `Idempotency-Key` on a mutating request now executes once and replays the first answer** — claimed in `callService`, so it holds over HTTP and the socket alike. The replay runs **no hooks**, so an app effect living in one does not happen twice *and does not happen on the replay at all*. Keyed by `(service, method, principal, key)`; a failed call releases the key, an in-flight duplicate is a retryable 409.
- **Every READ carries `$withDeleted`; on a WRITE only `update`/`patch` by id do.** That is the escape hatch a `SoftDeletedUniqueError` points at — a deleted row keeps its `@unique` values, so *move the value aside* is `PATCH /{service}/{id}?$withDeleted=true`, and without it there is no request an app can make that frees the slot. The default is fail-closed: the same request with no directive is a 404. **A bulk patch does not read it** — `bulkByRow` selects its targets through litestone's own filter, so a widened WHERE would match nothing. **`remove` declines it by NAME**: against an already-deleted row the only action left is to destroy it, the one write that defeats `@@softDelete`, and a directive on the ordinary DELETE would hand that to every caller who may remove a row with no separate permission to grade. It always refused; it refused with a 404 about a row that is plainly there, which reads as the row being gone rather than as the flag being declined. Graded on the REQUEST rather than the row's state, and silent on a model that hides nothing (`FJS-523`).
- **`hasRoute()` is a matching question, not an existence one** — every app registers `GET /{service}`, which matches almost anything. Use `hasExactRoute(method, path)` for "is this mounted", `routePaths(method)` for what landed where.
- **Where an app's services are is PROBED, not derived** — `./services` then `./src/services` beside the ENTRY file, first one that exists, and `resolveServicesDir` is the one owner of that list. It used to be `./services` alone, which is the flat layout; the layout this repo documents and scaffolds puts the entry at `api/index.ts` and the services at `api/src/services`, so the default named a directory that is not there — and a missing directory is a silent no-op, so the app boots, `/health` answers, and every route those services would have mounted is a 404 (`FJS-458`). The miss is now on the boot banner: `autoload=` names the directory or the candidates that were looked at. **A DECLARED directory is never probed around** — `services: { dir }` or `createApp({ autoload })` that is absent is reported by name rather than replaced, because a relative path resolved against the wrong working directory lands on nothing and looks exactly like an app with no services. **Under a test runner the entry is the TEST FILE**, so an app that needs its services in a test states an absolute path.
- **What the API answers is not readable in a service file, so it is committed too.** `junction surface --app <module> [--services <dir>]` writes `surface.snapshot.md` at the app root — methods after the policy, custom methods as `collectCustomMethods` resolved them at construction, the hook chain in RUN order with the derived hooks (`gateAuth`, `autoValidate`) leading it, every mounted path with `apiPrefix` applied, plugins in configure order. Read off a BUILT app, so the module must expose one **without listening**, which is what the `api/index.ts` / `api/src/app.ts` split is for — the entry starts the app, the module it imports assembles one and exports it unstarted (`fli check`'s `surface-src`). An app that made them one file guards `app.start()` with `import.meta.main`.  The `snapshots` CI phase fails a stale one.
- **What an app runs with no caller is committed too.** `junction jobs --app <module> [--services <dir>]` writes `jobs.snapshot.md` at the app root — every registered handler's declaration (queue, cron, zone, attempts, retry delay) and every in-process `app.scheduler` timer with the expression as written. Read off a BUILT app, because a job file registers itself by being autoloaded. **The two registries are separate sections and that is the substance** (`FJS-D36`): `app.jobs` survives a restart, `app.scheduler` does not and runs in every replica. **No queue installed reads differently from a queue with no handlers.** Live state is absent by design — a next run or a queue depth moves between two boots and takes the file's value with it. The failure it exists for is silent by construction: a schedule that stops being registered is *nothing happening* (`FJS-327`, `FJS-328`). The `snapshots` CI phase fails a stale one.
- **Who a caller BECOMES is committed too, and it is the input every tenancy predicate compares against.** `db/access.snapshot.md` holds `workspaceId != auth().workspaceId` and the `snapshots` phase fails a stale one; nothing held *who emits that claim, off which request, verified against which model*, so a resolver emitting the WRONG tenant left every artefact byte-identical and CI green (`FJS-514`). `junction principal --app <module> [--services <dir>]` writes `principal.snapshot.md` at the app root — read off a BUILT app, because a resolver is wired in application code and no file tree can answer which one an app ended up with. Seven sections: tenancy · resolver · claims · standing · what the rules reach · the three refusals · **per-tenant configuration, empty until `FJS-D126` is ruled** — that one exists before the feature on purpose, so *which keys a tenant may override* arrives as a diff in a file people read rather than as a new face. **Names, never values**: a claim's name is a fact about the app, a claim's value is a caller — so `membershipClaim()` carries a `describe()` and `tenantFrom` (a function) is out while `namedBy` (a constant) is in. The **value→level mapping is deliberately absent**: `getLevel` is a function handed to `GatePlugin` and a client answers plugin names rather than instances, so the column and its enum values are committed (a value added to the ladder and not to `getLevel` is a caller silently graded at the default) and the mapping is executed by `verifyGateLadder`. Under `createApp({ tenants })` the declaration is on the REGISTRY and not on `app.db`, which does not exist there. Whether the rules HOLD is the sibling question with an executed answer — litestone's `verifyTenantIsolation()`.
- **An irreversible effect belongs in `ctx.afterCommit(fn)`, not in an `after` hook.** `after` is after the METHOD: hooks run in sequence, so an email sent from one goes out and a later one throwing still fails the call — and under `transactional:` the row is rolled back with the email already gone. What is queued runs once, on the success path, after the announcement, and after the commit where there was one. **Observer tier** — a throw is logged and emitted, never reported as the call failing, because the write is committed and the broadcast is out. **Not durability**: a crash between the two loses the effect, and `ctx.enqueue` is the verb that survives it
- **`ctx.enqueue(job, payload)` is the durable half, and it is a second VERB because a closure cannot be persisted.** It writes a row into the app's OWN database inside the calling method's transaction, so the intent commits with the write or rolls back with it; `app.configure(outbox())` is the relay that hands it to `app.jobs` and marks it delivered (`FJS-D35`). **The row can be in no other database** — litestone opens one connection per declared `database` block and holds one transaction manager, over main's, so a row in a second block survives the rollback that was supposed to take it (measured). The queue stays a separate file, which is what makes the handoff **at-least-once**: the relay dispatches under the OUTBOX ROW's id and caravan's `dispatch({ id })` treats a taken primary key as work already queued, so a crash between the two replays into a no-op. Refuses by name outside a transaction, without the model, and with no relay — a row nothing delivers is worse than a refusal. `fli outbox:install` writes the import line, and `/metrics` answers `outbox: { pending, delivered, failed, lastPassAt }` — contributed through `app.registerMetricsSource`, whose sources must be SYNCHRONOUS (the body takes `fn()` directly), so the count is refreshed once per relay pass rather than once per scrape
- **A payload key that is not a column is declared `@transient`, and it arrives at `ctx.transients` — never at `ctx.data`.** The mirror of `@computed`: no column, written by the caller, never read back (`FJS-D23`). `autoValidate` validates it with the model's own rules and then LIFTS it off the payload, because the Data boundary refuses a transient key by name — a service passing `ctx.data` on whole fails the write rather than the field. Fresh `{}` per call, does not propagate, `{}` on a model that declares none. **A bulk write carrying one is refused**: the rows a service receives are the ones that passed validation, so an index-aligned array would pair one row's value with another row. Undeclared is still deleted in silence, which is what the declaration is for.
- **The METHOD decides list vs single.** `find` must answer a list or it throws `ResultShapeError`; an array is a list; the bulk `{data,errors}` protocol is a list on any method; everything else is a single and travels whole. A service answering one thing names it and calls it as a custom method; a summary alongside rows is its own named method.
- **A header the caller varies per call must be DECLARED, or it works until the socket connects.** `config.http.callHeaders: ['x-cart-token']`; the client sets it with `setCallHeader`. A WebSocket frame has no headers of its own, so the value rides `meta.headers` and the server merges only declared names — undeclared, the header is simply absent and whatever reads it sees nothing, which for a token-scoped row policy is an empty result with a 200 or a 404. The same declaration is what gets it past a cross-origin preflight. What may NOT travel this way is the identity: it belongs to the upgrade.
- **A socket stays alive because the SERVER pings it, and an app calls nothing.** The channels plugin pings an idle connection every 15s and evicts one silent for 40s; any frame counts, and the browser client answers from its message handler rather than a timer — a timer is throttled to ~1/min in a hidden tab, slower than the eviction window. `client.startHeartbeat()` is for a client whose server predates this and is otherwise the wrong reach; nothing called it for as long as it was the only half that existed, so every app flapped on a ~35s cycle with a reconnect hiding it (`FJS-366`).
- **Never call `ws.send()` directly.** Bun answers `-1` for buffered and **`0` for discarded** past ~16.9MB of unacknowledged data on one socket (`maxBackpressureLimit` is accepted and ignored). `transport/send-queue.ts` is the one owner of a send: it holds a dropped frame, flushes on `drain`, preserves order, and past `http.wsMaxQueued` (8MB) closes with 1013 so the client reconnects.
- **Caravan owns the clock; `app.scheduler` is in-process only** (`FJS-D36`). Two timers exist and they are not the same feature — `app.scheduler` has no persistence, no retry and no principal, and is gone with the process; `app.jobs` is durable work. **A timer that dispatches into a queue is the QUEUE's schedule**, registered with `app.jobs.schedule(name, expr, fn)`: firing `app.jobs.dispatch(…)` off `app.scheduler` buys a clock with none of the queue's durability while looking like it has it. **Caravan's clock is safe to run in two processes and junction's is not** — a cron fire is dispatched under `cron:<job>:<epoch-minute>`, so a second replica's fire is a no-op rather than a second row, and a `running` row is owned by a heartbeating instance so recovery reclaims only what a crashed one left (`FJS-294`). A schedule that came from a database ROW also needs `app.jobs.unschedule(name)` when the row stops being true, and re-registering at boot — neither registry survives a restart, which cost basecamp every scheduled job it had (`FJS-327`, `FJS-328`). `app.scheduler` is for work with no row behind it: a cache sweep, a metrics tick.
- **A background job runs as whoever asked for it, and a job nobody asked for runs as the app.** Caravan records the principal in scope at `dispatch()` and Junction re-resolves them when the job runs (`app.runAs`), so `ctx.app.service('x').patch(…)` from a handler names no `auth` and inherits one. **An id is stored, never a session** — a caller demoted between asking and running is graded at the standing they hold *now*, where a replayed snapshot is a privilege outliving its own revocation. No enqueuer (a cron fire, boot) resolves to `createApp({ system })`, the one place an app says who it is acting on its own behalf; declaring none is valid and gives `null`. `example/api/gate.ts` is the pattern. Still true: `db.asSystem()` is the wrong fix, because it writes at the Data boundary where nothing announces and every open tab keeps the stale row.
- **`IAuth.sessionFor(userId)` is how a principal is rebuilt without a credential**, and it must never be wired to anything a request can name — it proves nothing. Optional; a provider lacking it makes `runAs(userId, …)` throw by name rather than quietly downgrade.
- **Junction resolves every Bearer token through `IAuth.verifySession()` and calls `verifyApiKey` nowhere** (`transport/http.ts`). One door: a key is only verified if the *provider* falls through to its own `verifyApiKey`. A third provider inherits that job.
- **A job attempt has no bound unless one is declared, and `oldestRunningMs` is how you see the ones that do not.** `timeout` on a handler, a job file or a queue; absent means no bound, honestly, because a default would kill every legitimately long job in every app that upgraded. A timeout is an ordinary failure — it counts as an attempt and retries on the same ladder as a throw — and **it does not stop the handler**, since nothing in JavaScript cancels a promise: the abandoned invocation may still be writing while the retry runs, so it is announced (`caravan.job.orphan`, and a `console.warn`) rather than swallowed. A handler that never yields is unreachable either way; the timer needs the event loop. For the jobs nobody bounded, `stats().queues.<q>.oldestRunningMs` is the number that separates a stalled queue from a busy one — `running: 1` reads identically for both — and it is asked of the database, so another replica's stuck job is in the answer (`FJS-295`). `drainTimeout` bounds `stop()`.
- **Caravan's `unique` is a lock on work IN FLIGHT, not an idempotency key.** Once a job is terminal the key is free. A key built from a row id is not one either — SQLite reuses ids.
- **A job in `jobsDir` is named by its file and declares its own schedule.** `send-email.job.ts` is `send-email`; a `defineJob` naming anything else is refused at load rather than registered, because a handler answering to `send-emial` is a dispatch that silently never runs. `cron` is a `handle()` option — a `*.job.ts` file carrying one is scheduled by being autoloaded, and `schedule()` is sugar over the same registration. The definition is also the dispatch handle: `dispatch(sendEmail, data)` states no name and types the payload. **The queue's database opens on first use**, which is what lets every key of `junction.config.js`'s caravan section apply — and means a dispatch before `app.configure(…)` opens it at the DEFAULT path.

**UI**

- **The route table is a naming convention over a file tree, so it is committed too.** `sierra routes --config config/sierra.config.js`, run from the app's **web root**, writes `routes.snapshot.md` — every URL with its file, the layout the scanner resolved (none where a page declared `reset`), the meta a layout pushed down onto every page under it, and what each `_module.mesa` wraps. On a `static` target **`publishes:` leads the file** in its own section: it is the one line that turns off the fail-closed publish check, and it lives in one page's frontmatter. One config is one target and its name carries — `sierra.static.config.js` → `routes.static.snapshot.md`. The `snapshots` CI phase fails a stale one.
- **A node is the synced truth for a row; a view remembers what it READ.** `resource.record(id)` is live, so a push moves the value on screen — and it does not move the `@version` this screen holds, which is the whole of why the two are separate (`FJS-341`, `FJS-D138`). A draft belongs to the form and enters neither. Two more that are less obvious than they look: a node write with the **same object** does not notify, because a push writes the node on arrival and the list it lands in writes it back through while assembling itself; and **removal is the record view's own state, never the node's** — clearing the shared node would shorten every list holding the row before that list ran its own removal accounting, and two resources over one service share a proxy. **Optimism cannot be asserted in a browser here**: every in-flight marker a page offers — the loading toast, the move buttons — is also true for a moment AFTER the call answers, because the WS push lands before the `await`'s continuation runs, so *the status moved while the toast was spinning* passes with the optimistic write taken out. It is asserted where it can be negative-controlled, in `junction/tests/nodes.test.ts` and `sierra/tests/resource-record.test.js`.
- **A live store holds what its last `load(query)` asked for, so a patch can take a row OUT of it.** A row moved out of the filter is removed rather than updated in place — there is no other event for leaving a filter. A record the schema cannot judge (a `select` dropped the filtered column, the filter names a relation, `$search`) triggers a reload instead of a guess. The row is also PLACED — `orderBy` decides where, and the first page trims what falls past `limit` — but **past page 1 a new row is refused**, because nothing in a browser knows whether it belongs on an earlier page. That, and a gap a removal leaves, count on `resource.stale`, which `load()` clears and a view renders as *3 new — refresh*. **`changed` is the event that names no row** — what a bulk write or a `select: false` write announces — and the store's answer to it is the reload it already gives an undecidable record, coalesced per burst. Not `stale`: a counter describes a gap the list knows the shape of, and *some unknown rows moved* is not one.
- **`@version` is the revision a screen READ, and a push does not move it.** `createResource` records a version off every call result and off a load that was not superseded — never off the store, because a WS push reaches the store as an upsert, moves the number, and moves nothing the person is looking at. Remembering it off the store made a save from a screen holding a DRAFT carry a revision nobody there had read, which won the race the column exists to lose: measured in basecamp, the other person's write erased with the guard in place and no error anywhere (`FJS-341`). The cost is a 409 where a silent success used to be, and that 409 is the right answer — a caller who has genuinely read the newer revision states it, which `<Form record={row}>` already does by editing the row whole. **The 409 says which two revisions disagreed**: `VersionConflictError` declares `data = { model, field, expected, actual }`, junction's error boundary carries a declared plain-object payload, and `resource.conflict(err)` answers the numbers where `fieldErrors()` answers the sentence — the half a status and `retryable` cannot express, which is what a *reload* against *overwrite* prompt needs. **The API-side sibling**: junction derived ONE create-mode JSON Schema and compiled the patch validator from it, so `autoValidate` stripped the version off every patch and `@version` did not work through a service at all (`FJS-335`).
- **A write drops the columns the SERVER owns, and the version column is the one exception.** `@system`, `@generated`, `@computed`, `@from`, `@version` and a tenancy stamp all reach the client as `readOnly`; a create is safe because `make()` never seeds one, and an EDIT form is not, because it is handed a row the server wrote and sends the whole thing back. The Data boundary refuses `@system` BY NAME, so the person sees a 403 about a column that is not on their screen (`FJS-526`). `stripReadOnly` runs first in the resource's create/patch pipeline — ahead of coerce, blank and validate, so nothing judges a value that will not be sent — and it takes a KEEP list rather than dropping everything read-only, because `@version` is marked read-only and is the one the server requires back. A key with no field rule behind it is left alone: a `@transient` is legitimate, and guessing there is how a strip breaks a working app.
- **A `File` column's control sends the bytes WITH the record, and there is no upload step.** A `File` anywhere in a payload turns the create or patch into `multipart/form-data` at the client, the bridge merges it back into `ctx.data`, and `FileStorage` stores it — so submitting the form IS the upload, on the one route carrying the gate, the row policies and `@accept` (`FJS-409`). What the field holds until then is the browser `File` itself; the resource's write pipeline passes one through untouched. **The value has three shapes and only one of them is ever sent**: `undefined` where nothing is set, the URL a READ resolved the stored reference into, or the `File` just chosen. `undefined` back from the control means *leave the stored file alone* and `null` means *clear the column* — a form that conflates them drops a photograph on every edit that did not touch it.
- **`createResource` coerces, blank-strips and validates by default.** A bad create throws `ResourceValidationError` in the browser with the request never made, and an untouched text box writes NULL rather than `''`. A resource whose service accepts a shape the model does not describe needs `{ validate: false }` — the symptom otherwise is "the button does nothing" unless something renders the throw. `<Form>` renders it.
- **`@system` is the column an application writes and its caller does not** — readable by anyone, refused on write by name. The orthogonal sibling of `@guarded`, which locks both directions. It reaches the client as `readOnly`, so a generated form does not offer it and `make()` does not seed it; it is **out of create-mode `required`**, because listing a server-written column there refuses every create in the browser naming fields the caller was never meant to send (`FJS-095`). The app fills it by naming the column on the write — `db.order.update({ where, data, system: ['trackingCode'] })` — which keeps the gate, the row policies and the audit actor, where `asSystem()` drops all three to write one value. A required `@system` column that nobody filled fails at the write, saying which side is missing.
- **`<Form {resource} />` with no children IS the form** — every writable column in schema order, each with the control its type implies, over the one table in `field-rules.js`. Children win (the caller is writing it); `only` narrows and orders, `except` removes, `auto` forces either way. **DEFAULT children, and only those** — `_auto` is `auto ?? !$slots.default`, so `slot="actions"` composes with the generated list rather than replacing it, which is what lets a Resource's own default form (Invariant 18) supply a button row without turning generation off for every page under it. A `{#snippet actions()}` beats the slot where both are given, because a prop is the more specific statement — which is how a page states a different row (Save beside Delete) without restating the fields. A column the table cannot place is **warned about by name** rather than dropped. Beware the shape that found the mesa bug: a slot whose only child is an HTML comment used to count as children, so one comment inside a `<Form>` turned generation off in silence.
- **Everything a component reaches for is on `$`, and `$` is legal only as the object of a member expression** (`FJS-D132`). `$.onMount`, `$.emit`, `$.tick` — the bare `$onMount` spelling is gone and refused by name, pointing at its replacement. **Five members are the exception and the bare spelling is the CANONICAL one there** (`FJS-D135`): `$props`, `$attributes`, `$slots`, `$context` and `$async` — the ones read as a bag and a key rather than called — because `{...$attributes}` is 81 of this repo's 82 uses of that member and it sits in markup, where `$.` is JavaScript punctuation in the middle of HTML. Both spellings are one binding aliased at emit, and the bare names stay RESERVED, so declaring one at script top is refused rather than shadowing it. `$` may not be destructured, aliased, shadowed, passed or defaulted-to: several members are COMPILED rather than read — `$context.k = v` becomes a provide call, `$.inspect` is stripped when `debug` is off, `$.mounted` is counted for its one-per-component rule — so through a copy each one compiles, parses and silently does nothing. It does not exist in `<script module>`, which runs outside any instance; import from the runtime there, where `$onMount` and `$onDestroy` keep the bare spelling because they are module exports rather than the door. **Four prefixes and each is a different KIND** (`FJS-D137`) — `$` the door, `$:` the label (a JavaScript label, a namespace of its own, so no rule above touches it), `$$` the compiler's own locals, and `__` the CALLING CONVENTION: `__anchor`/`__props`/`__block` are the component function's parameters and `__prev` is the render callback's. `__` does not converge on `$$` because three of the four are read BY NAME out of compiled output by jetty's build plugin, which is `FJS-D134`'s class; all four are reserved, so declaring one is refused rather than shadowing a parameter and failing at mount. **Two names wear a single `$` and are protocol rather than either tier**: `$class`, the prop `{class}` travels under, and `$dom`, the key a block factory answers with — the only single-`$` names correct in compiled output.
- **A Mesa instance `<script>` exports exactly two things.** `export let` is a prop, `export function` is a method on the component's instance API; every other export form is refused by name. **`bind:this` means two things** — on a COMPONENT it gives that instance API (props read through the child's own signals, so `ref.count` is live and writable), on an ELEMENT it gives the node.
- **On an ELEMENT `bind:` means the DOM writes back, so it is `value`, `checked`, `files` — plus `group` and `this` — and every other `bind:x` there is refused, naming `x={expr}`** (`FJS-D136`). Nothing changes `readonly` or `colspan` but you, so there is no second direction; and for the eight attributes whose DOM property is spelled differently (`for`/`htmlFor`, `class`/`className`, `readonly`/`readOnly`, …) there was no FIRST direction either — `bindInput`'s generic branch is `el[name] = v`, which writes a JS expando the DOM never reads. `bind:class` was the measured one (`FJS-478`). **On a COMPONENT `bind:x` is an ordinary two-way prop and is unaffected**, which is every non-form `bind:` in this repo.
- **Mesa's scoped styles do not reach into child components.** Use `:global(...)`; the selector subject carries the hash (`button` → `button.mHASH`). A dynamic `class` MERGES, never replaces — all dynamic classes route through `bindClassPassthrough`.
- **An overlay that is present is not an overlay that is visible.** Kit overlays fade in with `el.animate(…, { fill: 'forwards' })`; an assertion that only asks `querySelector` passes against a fully invisible full-screen backdrop. Assert computed opacity and hit-testing.
- **Headless Chrome delivers almost no rendering lifecycle after load.** Anything behind `IntersectionObserver` must be set up before it; `requestAnimationFrame` hangs. Working pattern: `packages/sierra/tests/fixtures/island-site/verify.mjs`. **`getComputedStyle` goes stale after a class change** — `el.matches()` and `document.styleSheets` report the new state while computed styles stay frozen, and forcing layout does not help. To check a post-click style change, read the rules that match the element.
- **A component rendered at BUILD time may import a sibling by relative path, and that had never worked.** `renderComponent` writes the compiled module to a temp directory, so `'./money.js'` resolved against the temp directory and was not there — a bare specifier survives (Node walks up to a `node_modules`) and an absolute one survives, so the only casualty was the ordinary case of a page or an island importing its own neighbour. Rewritten to an absolute PATH now, not a `file://` URL: Node takes either and Vite's import-analysis refuses the URL (`FJS-438`).
- **On a static target, dev is an SPA and the build is files, and only the build checks anything.** A `render: static` route's `load()` runs in Node at build time and its companion may never enter the browser graph (`FJS-543`) — so the client route table has no import for it, and for a long time that meant the dev server rendered every page with `data: null`, which is indistinguishable from a query that found nothing. **It runs on the DEV SERVER now**, which is a Node process: `/__sierra/static-data` executes the loader and the browser gets JSON, so `vite dev` shows the site with its data. What the table emits is a **fetch shim and never an import**, which is what keeps `FJS-543` closed. Two consequences worth knowing: it imports the companion the way the BUILD does — a plain `import()` keyed on mtime, not `ssrLoadModule`, which rewrites the module and withholds Bun's `import.meta.dir` — and the dev server must therefore be `bun --bun vite`, exactly as `build:site` always has been. `dev: { staticData: false }` restores the old behaviour. A route on a static target that is NOT prerendered keeps its loader and runs it in the browser like any client-routed page. `target: 'static'` is the SPA's Vite config plus a prerender pass in `closeBundle`, so `vite dev` on a `site/` surface serves the routes client-routed — and the publish check, the island chunks, one HTML file per route and the refusal when a `render: static` route emitted nothing all live in the build. A page that works in dev and fails in the build is the normal case. **A companion is build-time only and the static build now says so**: its loaders are dropped from the client route table, because rolldown otherwise followed every `.meta.js` into the browser graph and a storefront's companion imports the app's own Litestone client — the published directory carried `db.js`, the DDL emitter and the migration engine as fetchable files, linked by nothing, on a public origin.
- **A static route whose render THREW used to be a warning and a green build.** Every reason a route produced no page went on one list — *not found*, *no paths*, `load() threw`, `render failed` — and two of those are a page opting out while two are a broken build. The failing kinds throw now, naming the route; before, the build printed one line among the bundler's own, exited 0, and said *no route declares `render: static`* about a page that plainly declares it (`FJS-439`).
- **Vite injects the built `<script>` at the first textual match for the body tag and does not skip comments.** Mention it inside a comment in a hand-written `index.html` and the build succeeds, `dist/index.html` looks right, and the page loads no JavaScript. Never write the body tag in a comment.
- **A `var()` naming a token nothing defines drops the whole DECLARATION, so a design system can be linked, matched and ignored line by line.** An undefined custom property is invalid at computed-value time — `gap: var(--space-4)` is not a wrong gap, it is no `gap` property at all, and `border: 1px solid var(--border)` is no border. Nothing reports it: the stylesheet is in the bundle, every selector matches, and a browser drive asserts what a page SAYS. `example/site/` shipped its whole public storefront that way — thirteen of the fifteen tokens it used were invented, a Tailwind-shaped `--space-4`/`--radius`/`--border` against the ladder this package actually ships (`--space-2xl`, `--card-radius`, `--rule`) — with `verify:site` green at 39/39 throughout (`FJS-545`). The ladder is **named, not numbered**: `3xs 2xs xs sm md lg xl 2xl 3xl 4xl 5xl 6xl`, each rung `calc(base × var(--density))`. `fli check`'s `css-token-undefined` is the guard and it reads the table off the CSS the app installs. **A fallback is the opt-out and it means something** — `var(--knob, var(--color-primary))` is a knob a caller may set, and nothing is dropped.
- **A class name is not checked by anything**, which is the same failure one layer up and has no guard: `.list` where the vocabulary says `.rows divided`, `.input` for `.field`, `.button` for `.btn`, `.stack-sm` for a rhythm the package does not ship. `@frontierjs/css`'s `vocabulary.json` is the list — 55 terms with their classes, plus `anatomy`, whose entry for a term carries the one canonical markup block. Read it rather than guessing; a class nothing defines is markup that looks styled and is not.
- **A code sample highlighted with `prefix: true` loses its first character.** `glow()` strips a leading `+`, `-` or `>` as a diff/callout marker, and all three are legal first characters in CSS (`> .child`, `+ .sibling`). `--` is disambiguated; the combinators cannot be, so **a CSS caller passes `prefix: false`**.

**Repo**

- **`bun install` resolves `workspace:*` to a COPY under `node_modules/.bun/`, not a symlink.** An edit to `packages/mesa/src/compiler.js` is invisible to importers until reinstall, so a suite can go green against a stale snapshot. In-repo tests import workspace source by relative path. `packages/ui`'s hand-made symlink will not survive a reinstall.
- **Nested directories are invisible to the `packages/*` glob** — uninstalled, untested, unrunnable. Four cases, all deliberate and named in `scripts/ci-allowances.json` § nonMembers: `mesa/mesa-bench`, `oracle/mockup`, `orion/mockup/api-engine`, `toolbelt/mockup/datetime`. **A fifth is a CI note naming the path**, so the way this goes wrong is by someone reading the note as noise, not by silence.
- **Publishing a package silences every loose peer range that names it.** While a sibling is unpublished a peer of `"*"` fails at install with the name in the error; the moment it exists, the same range resolves from the registry without a word. **Below 1.0 a caret pins the MINOR** — `^0.1.0` is `>=0.1.0 <0.2.0` — which is both the behaviour wanted for a pre-alpha peer and the trap in the other direction, where a stale caret excludes the only published copies. Nothing catches either shape from inside the workspace: a `workspace:*` devDep answers first and the range is never consulted. **`fli ws:exports` commits the published surface** — `exports.snapshot.md` at the root, one section per publishable package: the top-level entries its tarball actually contains (asked of `bun pm pack --dry-run`, never derived from the globs), every `exports`/`bin`/`main`/`types` target marked with whether that tarball holds it, and the peer ranges naming a sibling. It is the cheap half of what `scaffold` proves end to end: a declared entry point `files:` does not publish is a broken install, decidable from the listing alone. The `snapshots` CI phase fails a stale one.

## Bridge index — the named cross-package handoffs

The current seams. Reach for them before grepping. They may move, merge, or change signature as long as ownership and dependency direction hold.

**Data → API**
- `$setAuth(user)` / `asSystem()` — the Data-boundary checkpoint / bypass — `litestone/src/core/client.js`
- `$tapEvents(fn)` — every write, announced. `event` is `create` · `update` · `remove` · `transition`, and a transition carries `transition` (the move's name) and `record` where the others carry `result`. **Two shapes and the write says which**: `scope: 'row'` (one row; `result` is it, or `null` where `select: false` skipped the RETURNING) or `scope: 'collection'` (`count` rows matching `where`, never built). Stated, never read off `result` — that is two facts. A bulk write's shape is the per-call `announce` — `collection` (default) · `rows` · `none`, floor at `createClient({ announce })` — because the batch size is a property of the call, not the model (`FJS-D34`)
- `withLitestoneDb(db)` — per-request scoped client on `ctx.locals.db`; auto-installed by `createApp({ db })` — `junction/src/core/litestone.ts`
- `gateAuth()` + `autoValidate()` — schema-derived 401s/400s for model services — `junction/src/core/litestone.ts` + `core/service.ts`
- `validateInput(type)` — **the same 400 for a method no model describes.** `autoValidate` derives from a MODEL and covers create/patch on a model service; every other method a service answers took `ctx.data` on trust. A `methods:` entry may be `{ method, input }`, and `input` names a `type T { … }` in the app's own seed — so the seed stays the one owner of what a shape is, and the payload compiles through the same `jsonSchemaToJunctionSchema` → `createSchema` pair, carrying `@label` and the author's `x-messages` into a 400 that renders in `<Form>` like a CRUD one. A CRUD name may carry one, replacing the model-derived validator. **A named type that is not there THROWS** where a missing model warns: an absent model definition is a config that used to work, an `input:` is a statement the author just made. **Declaring an input also declares the SURFACE** — `{ method: 'pay' }` narrows exactly as `'pay'` does, so a service gaining its first `methods:` answers 405 to every verb it did not name; `surface.snapshot.md` carries the policy-applied list AND the inputs, so that is a CI diff rather than a production 405. Transforms do NOT cross (`FJS-401`) — `@trim` is a Data-boundary rule, and the two boundaries apply transforms on opposite sides of validation, so they would disagree about what is *valid*
- `sessionGateLevel(user)` — `SessionContext` → litestone's 0–7 scale; pass to `GatePlugin({ getLevel })`. Litestone cannot import Junction, so this is **a hand copy on both sides — change one, change both**

Without it every row policy compares against `undefined` and matches nothing, silently. **Two functions, one boundary**: change either and ask whether the other needs it too
- `resolveTenancy(schema)` / `registry.tenantFor({host, headers, principal})` — **the one reading of `tenancy { }`**. The declaration is a Data-realm fact and *which tenant is this request for* is an API-realm question, so the API asks rather than re-deriving; `createApp({ tenants })` installs `withTenantDb`, which assigns the same `ctx.locals.db` that `withLitestoneDb` does and therefore replaces it. - `accessorCandidates()` — `model Post` ⇄ service `posts` ⇄ `db.post`; shared by query, gate and validation so a naming slip cannot disable just one
- `db.$checkWhere(accessor, where)` → `[{key, suggestion, allowed}]` — the one definition of "is this a valid filter key", asked rather than copied; junction's `autoFilter` calls it. An unknown accessor answers `[]` — *I cannot judge this* is not *this is wrong*

Strength picks the control and the two weak ones pick the SAME one — `required` a picker, `open`/`suggested` a combobox with `allowNew` — because what separates them is what the server does with a new value, not what a caller may type; a bound array is a multiselect where an unbound one is still `json`. **Every narrowing travels as a NAME** — `$checkWhere` validates a `$scope`, so it survives junction's `autoFilter`, which is what makes the offered list the list the Data boundary will accept. A declared `where` is SQL and a browser may never send SQL, so it **mints a `@@scope` on the source named after the set** and crosses the same way; the predicate itself never leaves the server (`FJS-430`). The enforcement is litestone's, through the CALLER'S own accessor — `x-values` is an affordance here exactly as `x-gate` is

- `$context.form` — the UI-side form seam, provided by `ui/components/forms/Form.mesa` as `{ errors, submitting, disabled, fields, submitted, optionsFor, reportInvalid }`. A stated prop always wins, including `required={false}`. **`reportInvalid(name, message)` is the one channel that goes the other way** (`FJS-404`) — a control saying *the value I am showing is not one I can hand over*, which nothing else in a form can know: a control whose element cannot hold every value the field may take writes only what it could convert, so the record keeps the last good value and every check on it passes while the screen shows something else. - `x-version` — names the `@version` column an update must carry back, `readOnly` in the update schema and absent from the create schema. `createResource` remembers the version of every record it reads and puts it on the next patch. `resource.version(id)` / `.versionField` expose it
- `retryable` on a thrown error — the one thing a status cannot carry. A 409 is either a race (`VersionConflictError`, `TransitionConflictError` — re-read and re-apply) or a domain refusal (`TransitionViolationError`, `UniqueConflictError`, `SoftDeletedUniqueError` — show its message). Set it on any error class you own; `toFrameworkError` adopts it and it lands at `err.data.retryable`. `isStaleWrite(err)` reads it. **`junction errors` commits what a thrown value actually becomes** — `packages/junction/errors.snapshot.md`, every row executed through the boundary, Litestone's own classes constructed and run through it. - `buildTransitions()` / `transitionsAt()` — `@@transitions` reaches the client as **`x-transitions` on the model, keyed by field**, never on the enum `$def`, because only a model can carry a per-transition `@gate`. **It is the GATE half of `db.<model>.transitions(row)` and only that half** (`FJS-495`): a move is an update, so a row policy refuses one exactly as a gate does, and the server grades both — the `update` policy against the row as it IS (one evaluation per call) and `post-update` against the row as it WOULD BE (one per target, the half that varies between moves). `x-transitions` carries a gate and not a predicate and a browser has no policy engine, so a move a policy refuses reads `allowed: true` there and 403s when pressed. **`refusedBy` is what keeps the two one shape** — `'gate'` · `'policy'` · `null` — because a screen renders *you are not senior enough* and *not this record* differently, and neither a status nor a non-null `gate` separates them: the gate is null for every ungated move a policy refuses. Permissive-when-unknown is the affordance contract, and a screen needing the graded list asks the SERVER
- `modelNameFor()` / `schemaFor()` — `sierra/src/junction/schema-registry.js`, over `@frontierjs/toolbelt/inflect`. **The inflection rules are one module and five callers** — litestone's table name and its introspection, junction's `deriveModelName`, sierra's registry and `createResource` — because a table name and the model name derived back from it are the same rules run twice (Invariant 2). A miss warns and degrades to a bare `make()`

- `extend model X { … }` — **what an app says about a model it did not write**, and the reason the machinery half is imported rather than pasted. A package owns its columns; where those rows sit in the installing app — the relation back to its own `User`, `@@log(audit)`, `@@tenant(none)` under row tenancy — is three facts the shipped file cannot know. Adds only: an extend naming no model, a field the model already declares, and a second answer to a single-valued attribute (`@@gate` twice) are each refused by name; `@@allow`/`@@deny`/`@@index`/`@@unique`/`@@check`/`@@trait` are repeatable. Collected across the whole import tree and applied once it is merged, so a file may extend a model it is imported BY, and applied before traits. **The opposite direction of `@@trait`**, which is opted INTO by the model and therefore needs its author to have known. basecamp carried hand copies of four of these for its whole life and one had `@guarded(all)` where auth writes `@secret`, with 137 green tests either side of the divergence — a copy is the failure this removes (`packages/litestone/docs/traits.md`)

- `signRequest()` / `verifyRequest()` — `@frontierjs/toolbelt/signature`, **the one definition of what a signed machine-to-machine request is**: method, path, timestamp, nonce and a hash of the body, joined with newlines. It exists because signing with no verifier reads as a scheme being enforced: basecamp's three machine endpoints took no credential at all behind a comment saying the transport had checked one, and an unsigned POST could point every fleet command at an address the caller named (`FJS-349`). - `matchesQuery(fields, record, query)` → `resource(name, idField, { match })` — **is this pushed record still in the list `load()` asked for?** Junction owns the store and holds no schema, so the decision comes from `sierra/src/junction/field-rules.js`, over the same operators `parseWhere`/`translateOps` accept and with SQL's null semantics. `true` upserts, `false` REMOVES, `null` is *undecidable from this record* and reloads. A caller passing no `match` gets the old apply-everything behaviour
- `$after` / `endCursor` / `resource.more()` — **a live list grows a window; it does not step through pages** (`FJS-D145`). One row in `@frontierjs/toolbelt/directives`, so both transports carry it. A caller sending `$after` is on the keyset path: no OFFSET, no COUNT, and `total` is `null` rather than guessed. An ORDINARY page carries the edge too — `endCursor`/`hasMore` on the list envelope, minted from the last row it already holds, so growing costs no extra query and a caller that never grows one pays nothing. **The tiebreaker is the schema's and litestone owns it**: `cursorFor(row, orderBy)` and `findManyCursor` derive the same sort keys, appending the model's id where the ordering is not total, because an ordering with no unique column serves a row twice and skips another *in silence* — and refusing only where there is nothing to append. `offset` is untouched: **offset is what you ASK for, the window is what a live resource GETS**. **`findWindow(table, args, after, label)` is the server half and it is exported**, because the derived find is not the only find — a service that assembles its own query answers the same two paths, and a restatement is how the tiebreaker and the absent `total` end up with two answers (basecamp's audit trail is the first caller outside junction). The page is run in **`table.orderTotal()`**'s ordering rather than the caller's: the two differ exactly on a tie, so the page stopped where SQLite stopped while the edge named where the total order says it stopped, and the rows between were lost once per tie (`FJS-535`). A list whose ties cannot be broken carries **no edge rather than a wrong one**
- `comparatorFor(orderBy)` — `junction/src/core/sort.ts`, **the one reading of `orderBy`**: `parseSort` IS `normalizeOrderBy`, so the SQL the server compiles and the position the browser gives a pushed row come from one parse of `-createdAt`. `compareValues` follows SQLite (NULLs first ascending, numbers before text, a Boolean as its stored 0/1) and states where it cannot be exact. What no client can answer is paging — past page 1 a pushed row is refused and counted on `resource.stale`

**UI**
- `page.query` / `page.directives` — the URL's search string, split by `@frontierjs/toolbelt/directives` exactly as the bridge splits a request's. `resource.load(page.query, page.directives)` is a filtered, sorted, paged list that lives in its URL. `page.params` is path captures alone
- `watchProxy()` / `createSignal()` / `createRoot(fn)` — the reactive seam and lifetime ownership — `mesa/runtime.js`
- `mount(label, Component, {props, root})` — page entry. Registers the delegation root; a component called directly renders but handles no events
- `renderComponent(src, opts)` — UI → HTML at build time; Sierra's `static` target composes route + layout chain through it. Children must be supplied **both** ways (`children={s}` and element children) — the two slot protocols do not bridge
- `appSrcDir(root)` / `appAliasPlugin()` → `renderComponent({ alias })` — **`@` is the SURFACE's own `src/`, and two resolvers have to agree about it.** A surface is a Vite root, so `@/api.js` means a different file in `web/` than in `site/`; the base is that root and never `process.cwd()`, which is the same directory only when the command was typed inside the surface. A prerender is the second resolver and knows nothing about Vite — it compiles a page and imports it under Node, where `@/api.js` is a package specifier — so `prerenderRoutes` passes the table it is already using. It shipped for its whole life resolved against the cwd, and no app had ever written a `@/` import, so nothing could see it: a missing alias TARGET is not an error, it falls through to Node and reports `Cannot find package '@'`. `@` is rooted at `src`, so a sibling of it (`config/`) stays relative
- `swapInstances(entries, newFn, newSetMark, label)` — **the DOM a hot update replaces**, `mesa/mesa-vite/swap.js`. Two callers: mesa's own HMR client and jetty's `__jettyMesa.hot_update`, which used to hold a hand copy of it (`FJS-259`). **No `import.meta` and no imports**, because jetty bundles it into an MV3 content script and those are CLASSIC scripts. The client that wraps it is two files, so a plugin serving it at a virtual id must ask `client-source.js` for them joined — a virtual id resolves no relative import, and `client.js` alone is a 200 that dies in the browser
- `island(anchor, Comp, props, block, meta)` — the island seam, off by default. Markers are **comments, not an element** (an element is foster-parented out of `<tbody>` and joins `>` selectors). Sierra collects them at prerender, bundles one chunk per island, and mounts via `@frontierjs/sierra/islands`. **A mounted ancestor is authoritative** — test a marker with `isConnected`, not `parentNode`
- **The theme is a class on `<html>` and Sierra owns the switch** (`FJS-308`). `@frontierjs/css` owns the vocabulary — eleven `theme-*` classes, each a block of inheriting custom properties — and ships no JavaScript, so it cannot own a switch; beating first paint needs a `<head>` script only the build can write, so the kit cannot either. `theme: { themes, default, system, persist, key, apply }` in `sierra.config.js`; `setTheme` refuses a name the app did not declare. **The element is not a knob** — `<body>` does not exist when a `<head>` script runs, so a `target: 'body'` would only bring the flash back. Before this, sierra wrote `data-theme` and the kit wrote `.dark`, and **the design system read neither**, so both apps hand-wrote a third applier
- **There is no cross-package reactivity registry.** Sierra exports no module-level signal — `page`, `status`, `theme` are plain objects a component makes reactive with a `$:` path watch — so `sierra/src/build/mesa-plugin.js` passes mesa no `externalSignals` map, only `externalReactivityHints: 'strict'`. The map survives in mesa as an escape hatch for a third-party package that does export a signal. **Strict is the end state, not a migration aid**: the default tier is silent for a component that watches nothing, which is the shape that shipped the original bug

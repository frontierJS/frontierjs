# FrontierJS — Map

Bun-workspace monorepo: a schema-seeded fullstack framework. One mental model — three realms, three nouns:
**Data (Model) → API (Service) → UI (Resource)**, plus Deployment (Release) and Testing (Suite).
Everything derives from `db/schema.lite`; growth happens outward and traces back.

`ARCHITECT.md` §2 is the default vocabulary for design discussion. Depart from it when a different word is materially clearer — then fold the clearer word back in rather than keeping two.

## Evolution policy

FrontierJS is pre-alpha. **Prefer evolving existing designs over preserving them.** Existing behaviour is evidence, not a constraint.

Only two things are binding: the **Invariants** below, and rulings in `DECISIONS.md`. Everything else may change — prefer simplifying, removing duplication, and improving consistency over reproducing what is there. **Preserve the mental model, not the mechanism.**

Where docs disagree, assume different stages of a pre-alpha design and reconcile, rather than treating either as wrong.

**This file is only what is live.** History belongs in `packages/*/CHANGES.md`, open defects in `ISSUES.md`, settled arguments in `DECISIONS.md`. A line here earns its place by changing what someone does in the next hour.

## Invariants

Don't violate without an explicit decision; record it in `DECISIONS.md` if you do.

1. **Dependency direction** — `Litestone ← Junction ← Sierra`, never reverse.
2. **Model names are PascalCase singular** (`model Lead` → `db.lead`); `@@external` exempt. Three resolvers depend on this agreeing.
3. **App layout** — `db/` at the root and each SURFACE a directory beside it: `api/`, `web/`, `widgets/` (embeddable scripts) and `extension/` (a jetty browser extension). Most sub-projects carry `config/ src/ public/ test/ dist/ deploy/` (db/ doesn't). Configuration lives in `config/`, `vite.config.js` included. Which surfaces an app has is the app's business — api-only, web-only, **widgets-only** and **extension-only** are all whole projects — but a surface inside another one is not: folded into `web/`, it inherits the SPA's build, port and release. A surface earns its own directory when its config, its tests and its release are all different answers, which is what `widgets/` and `extension/` are. Canonical: root `README.md` §Project Structure. Never *derive* a config path from where `vite.config.js` sits — probe, or be told.
4. **One owner per translation.** Exactly one place turns a thrown value into an HTTP status, one wraps/unwraps the result envelope, one parses `$`-params into `ctx.directives`, one announces a mutation, one startup phase list every caller runs. Implementations are in §Bridge index. Add to the owner, never beside it.
5. **One owner per `app.<thing>`.** Claim it with `app.claim(name, value)`; type it by augmenting an exported interface, never by redeclaring the property — declaration merging requires identical types, so a redeclaration silently loses. The verb is `claim` and not `provide` because **a Provider is a third party the app speaks to** (`FJS-D06`) — `/metrics` contributions go through `app.registerMetricsSource(name, fn)` for the same reason.
6. **Access is declared in the schema, not in hooks.** Gates, `@encrypted`, `@guarded`, `@@transitions` are enforced at the Data boundary. `x-gate` on the client is a UI affordance only — unknown answers are permissive and the server enforces regardless. No exceptions.
7. **Protected fields are redacted in the audit trail.** `@encrypted`/`@guarded`/`@secret` log as `[redacted]` in field entries and in `before`/`after` snapshots.
8. **Caller-supplied names never enter a SQL pattern.**
9. **Patch semantics: an explicit `null` clears.** Test key presence (`key in updates`), not `??`.
10. **`$` is transport syntax only.** `ctx.query` is filters, `ctx.directives` is `{limit, offset, orderBy, select}`; nothing past the bridge sees a `$`. **Two boundaries read the convention** — junction's bridge off a request, sierra's router off a URL onto `page.query` + `page.directives` — and the table they read it by is one module, `@frontierjs/toolbelt/directives`, one row per directive so a Data-realm feature that grows a per-call option cannot arrive half wired.
11. **The nearest delegation root owns an event.** Roots nest; a handler must fire once.
12. **Mesa compiler output is reproducible** — scope ids are content-addressed, which is what makes CSS dedupe work across the two compilers a static build runs.
13. **`@frontierjs/css` is the styling language.** Style with a tone (`danger`) and a treatment (`outlined`), never a colour. UnoCSS is supported *alongside* it as an opt-in layer a consuming app configures (`packages/css/README.md` §Using it with UnoCSS). A package in this repo ships no utility classes — a component needing Uno to look right is unusable by an app that does not run it.
14. **Typecheck baselines ratchet down only.** `scripts/typecheck-baselines.json`, one number per package; absent means 0. `bun run typecheck -- --update` writes an improvement back.
15. **A clean compile is not proof of valid JS.** Compiler tests parse their output.
16. **Runnable examples are verified, not sketches.** A broken one is a bug.
17. **Four markdown files at a package root is the standard** — `README.md`, `CLAUDE.md`, `PROJECT_STATE.md`, `CHANGES.md`; everything else in `<pkg>/docs/`. **A fifth is a question, not a refusal**: `package-root-md` warns and names it, because the rule cannot tell a stray design note from the next thing everyone needs at the root. Answer it — move the file, or record an allowance saying why it stays. Generated `*.snapshot.md` is exempt; it is gated output, not documentation.
18. **In a Sierra app, `src/resources/` holds `.mesa` files.** A Resource is a UI-realm noun, written in the UI-realm language. A resource file has no markup; its code goes in `<script module>` (Mesa VISION §11, rule 30).
19. **A resource file is named for its noun — PascalCase, singular — one Resource per file.** `App.mesa` exporting `export const apps`; the same split the Data realm makes between `model App` and `db.app`. Where a model exists the filename IS the model name, so an irregular is visible (`AlertRule.mesa` exporting `alerts` says `model:` must be stated). A resource over no model takes its service noun, singularised.

**Always `cd` into the package and run its own script.** Runners differ per package and a wrong runner produces failures that belong to nothing. `bun run --filter '*' test` from the root runs them all, one each. `bun test` instead of `bun run test` runs bun's own runner over whatever it finds — in mesa that is ~35 failures that are runner artifacts.

**`bun run ci` is the whole of CI and it is not a GitHub feature.** One node script runs ten phases — hygiene, structure, snapshots, access, coverage, registry, scaffold, typecheck, deploy, tests — and `.github/workflows/ci.yml` does nothing but call it, so it runs identically on a laptop. It fails a package with no `test` script, a source file `.gitignore` hides, a *raised* typecheck baseline, a committed snapshot that no longer matches its source, **a dependency or a clock inside the substrate package** (`hygiene` — `@frontierjs/toolbelt` may be imported by litestone and mesa only because it depends on nothing, so a non-relative import under its `src/` fails the build), and an **architecture rule broken in this repo's own apps** — `structure` runs `packages/cli/core/checks.js`, the same engine `fli check` gives a client app, because two implementations of one rule is how a framework ends up breaking rules it publishes. **`snapshots` carries no list of what exists, and it is not implemented here**: it runs `packages/cli/core/snapshots.js`, the same module `fli test:snapshots` gives a client app — every committed `*.snapshot.*` names the command that wrote it in its own header (`generated by: litestone ddl --schema schema.lite`), and that command is rerun with `--check` from the file's own directory, so a new KIND of snapshot costs a generator and never a CI edit. The command comes out of a file in the repo, so it is restricted to a known binary and a shell-free argv, and a snapshot naming no generator fails rather than being skipped. **Discovery alone fails open**, so the expectation comes from the BASE REF: a snapshot tracked where the branch left main and absent now is a failure, because a generated artefact that stops existing takes its check with it in green. A deliberate removal is a named entry under `removedSnapshots` in `scripts/ci-allowances.json`. **`access` is the one phase that reports rather than judges** — *what did this branch do to who may do what*, printed per app against the base ref, and never a failure, because a branch that widens access is usually a branch doing its job and a red that fires on every feature trains everyone to skip the phase. The gate is `fli test:access --from <ref> --strict`, which belongs on the branch that deploys. It runs the same `litestone access --from` a client app runs, and **it is not `release:check` with a different word**: the two grade one comparison on axes that disagree by construction — removing a `@@gate` is an *expand* for the deploy and the widest thing a schema change can do, and on a real five-part widening every single finding was an expand. **`registry` asks the cheap half of the published-framework question**: every `@frontierjs` package `fli new` writes into an app's `package.json` is looked up on npm, and a name the registry has never heard of fails by name — because the register cannot see this class at all (every id in it is a statement about the WORKING TREE, and a user's experience is the tree AND the registry, which drift independently). It reads the list from `packages/cli/core/app-config.js`, the module `fli new` itself reads, so there is no second answer to *which packages does an app get*. A version gap between tree and registry is a NOTE rather than a failure — being ahead is the normal state between releases — and an unpublished package is allowed by name under `knownUnpublished`, which fails once it IS published. No network, no failure: it reports a named skip and `FJS_CI_REQUIRE_REGISTRY=1` makes that skip fatal. **`scaffold` is the phase no suite can replace**: it runs `bun pm pack` over every publishable package, scaffolds an app against the tarballs, installs it, builds it, **runs that app's own `bun run check`**, then **scaffolds a model into it and builds again** (`scripts/scaffold-build.mjs`). The check is there because a default whose first use is red is worse than no default: `fli check` from an INSTALLED cli (it had never run at all — a free `resolve` the parse sweep cannot see, `FJS-269`), Biome against a config resolved out of `node_modules`, and `fli typecheck` against packages that ship `.ts`. An app in this repo resolves sierra to `packages/sierra/` and never to a node_modules path, so the code that only runs for an *installed* app runs nowhere else here — which is how `FJS-251` broke every npm install past 836 green sierra tests. It grades each package's `files:` field for free, and **its per-run `--cache-dir` is load-bearing**: bun caches a tarball by name *and* version, so a shared cache serves the previous run's bytes and the phase passes against a broken tree. **`deploy` runs the same pipeline twice, once per package source** — `fli new` → `make:deploy` → `deploy:local`, an image built, a health answer, and then a **register + login through the prefix the app's own `web/config/sierra.config.js` names**, because a health answer says the process is up and not that the app works: a scaffold template written against behaviour only the tree has installs cleanly, builds, answers health and cannot log in, and nothing else here can see that (`FJS-252`). `/manifest` is not asked — `manifestPlugin` is `devOnly` and the container runs `NODE_ENV=production`. `--source npm` is the only thing here testing the PUBLISHED framework, which drifts from the tree independently (`FJS-252`); `--source local` is the working tree containerised, which was impossible until the build started packing the tree into its own build context, since a Docker build can see neither a `link:` spec nor a `file:` tarball outside that context (`FJS-241`). **`packages/cli/core/vendor.js` is the one owner of that pack** — `fli deploy:vendor` is the command, `deploy:local` and the pipeline's build step run it first, and `basecamp`'s image builder calls it rather than carrying the copy it used to be. It needs a daemon that can read the build context: a shell with a private `/tmp` gets `unable to prepare context` about a directory that is plainly there, and `FJS_CI_WORKDIR` is the way out. **Without a daemon it reports a named note and passes** — requiring Docker for `bun run ci` on a laptop is too much — and `FJS_CI_REQUIRE_DOCKER=1` turns that skip into a failure, which the workflow sets, because a check that quietly stops running is worse than one nobody wrote. A suite known to fail is named so a NEW failure is loud, and **so is a deploy source** — `knownDeployFailures` exists for publish order, where the scaffold gives an app a package this repo has written and nobody has published, so `npm` cannot resolve it while `local` passes. Every allowance is a named entry with a reason in `scripts/ci-allowances.json`. `bun run hooks:install` points `core.hooksPath` at `scripts/hooks`, whose `pre-push` runs the fast tier (~40s); the suites (~3 min) belong in the workflow, because a pre-push costing minutes teaches everyone `--no-verify`. `--only <pkg>` narrows typecheck and tests.

**A dev server serves the code it started with.** A `.mesa` module is transformed once and cached for the life of the process, so editing the compiler invalidates nothing and the app fails exactly as it did before the fix. ## House style

Match the file you are in first; this is what the repo does when there is no local precedent.

- **Comments explain the failure, not the mechanism.** `// increment the counter` is noise; `// vite hops ports silently, so the drive would talk to the other app` is the house voice.
- **A comment must be load-bearing. Delete it otherwise.** Test: if it vanished, could someone editing this file make a mistake it would have prevented?
  - **No edit history in code** ("used to be", "this replaced X", "merged 2026-08-08"). That is `CHANGES.md`, `DECISIONS.md` and git. Narrow exception: a past bug stated because the shape still invites it (`--ring` in `tokens.css`), where the history IS the warning.
  - **No dates in code comments.** If the comment needs one, it belongs in a decision record the code points at.
  - **No persuasion** — "the whole point", "deliberately", "which is exactly why", italics for emphasis. State the constraint flatly; if it needs selling, it needs a ruling.
  - **Never narrate your own edit.** The reader does not know a change happened.
- **Every non-trivial file opens with a header block** — what it is, and what it is for. Test harnesses document their own traps at the top (`example/web/test/verify.mjs`).
- **Section dividers inside a file**: `// ─── name ──────` (box-drawing, padded to a consistent width). Not `// ---`, not banner boxes.
- **Aligned columns** where a run of lines is parallel — imports, object literals, `const` blocks. See `example/api/app.ts`.
- **Prose in the docs is sentence-shaped, not bullet-shrapnel.** Bold the claim, then say what it cost. Numbers earn their place by being measured.
- **British spelling** in prose (`behaviour`, `serialise`). Identifiers stay US (`color`, `serialize`) where a web API or CSS property already chose.
- **No semicolons**, single quotes, 2-space indent, in TS and JS alike (`packages/css`'s own build/test scripts are the one holdout). TypeScript in junction, auth, caravan, conduit, notifications; plain ESM JavaScript in litestone, mesa, sierra, ui, css, jetty. Do not introduce TS into a JS package.
- **Fake clients hide real bugs.** Cross-package behaviour is tested against the real dependency — `{ post: {…} }` passed every test and failed every real Litestone client.
- **A new `on*` states its tier** (`FJS-D06` §1) — **Hook** may mutate the arguments or halt the operation, **Guard** answers allow/deny, **Observer** receives and cannot act. The word goes on the option that holds it: conduit's callbacks are `observers:` because a throw in one is swallowed, and `management.hooks` beside it keeps *hook* because that pipeline can refuse the call.
- **A new defect gets an `FJS-###` in `ISSUES.md`**, not a paragraph in a package file. A ruling closes an `FJS-D##` and moves to `DECISIONS.md`. Check a new `.gitignore` rule against `git status --porcelain` — an ignore glob hid 20 source files once.

## Live hazards

**Correct behaviour you have to know about.** Things that are *wrong* live in `ISSUES.md`, one id each; things that are *fixed* live in `CHANGES.md`. If a rule here is pinned by a test that cannot be deleted quietly, it does not need to be here.

**Data**

- **A soft-deleted row keeps its `@unique` values, and `restore()` is why.** Freeing the slot would make `@unique` false for every read that includes deleted rows — `findUnique(withDeleted)` legitimately matching two — and would make the way back fail whenever a stranger took the value first. So a write naming a value a deleted row holds is refused by name (`SoftDeletedUniqueError`, 409) rather than by SQLite, and releasing a slot is a decision the app makes: `update({ …, withDeleted: true })` moves the value, `delete({ …, withDeleted: true })` stops keeping the row. **Membership now has a spelling**: `@@allow('read', auth().id in memberIds)`, the list always the RIGHT operand, so an audience held on the row no longer has to become a service where-clause. `DECISIONS.md` § Query & write semantics.
- **A `@@gate` refuses, a `@@allow` filters — so a wrong policy is an empty screen, not an error.** A gate throws naming the model and the level; a policy compiles silently into the WHERE. Every read that legitimately crosses a policy's scope must be `asSystem()`, or it returns nothing with a 200. Declare one model at a time and run the app's drive between them. **`fli test:access` writes the whole declared surface to a committed `db/access.snapshot.md`** — gates, policy predicates, protected fields, transition gates — and the `snapshots` CI phase fails a stale one, so a gate that moved is a diff rather than a production refusal. **`--from <ref>` asks the other question and writes nothing**: what this branch did to who may do what, graded `widens` / `narrows` / `undecidable`. The comparison is `classifyPivot`'s own walk read on a second axis, because *can N-1 still serve* and *who may now do more* disagree by construction — a removed `@@gate` is an expand and the widest change there is. What no comparison can answer is a predicate whose text moved, and that is reported rather than guessed. `--strict` is the gate; the `access` CI phase only prints. **`fli test:ddl` is the sibling for the opposite problem** — `db/ddl.snapshot.sql` is the emitted DDL, and the names in it are what every hand-written statement binds to while the app's own tests go through the client that changed with the emitter.
- **A schema change is a deploy question before it is a migration**, and `fli release:check` is the one that asks it: can the release still serving and the release starting share one database? Expand — N-1 keeps working, so the deploy can be taken back. Contract — it cannot, and that deploy is the **pivot**, after which only forward. Unknown counts as contract. `db/release.snapshot.md` is the surface it diffs, `--from <ref>` is the question a deploy asks, `--strict` fails a branch on anything but expand *including no baseline at all*. **Access is in the comparison, which is the half no generic deployer can reach**: raising a `@@gate` takes reads away from a release still serving them, and adding an `@@allow` empties a screen with a 200. A required column with no default is the one contract handed back as a plan — expand, backfill, contract — rather than a refusal.
- **You cannot run without gates.** A schema declaring any `@@gate` auto-installs `GatePlugin({ getLevel: FrontierGateGetLevel })` — a declared-but-unenforced gate is fail-open. Installing your own replaces it; installing none does not disable it. Contract: **absent = the app does not model this stage; only `null` grades down**, and standing (`isSystemAdmin`/`isOwner`/`isAdmin`) is checked before the lifecycle.
- **Tenancy is declared in the seed and there are two strategies.** `tenancy { }` at the top of `schema.lite` — `strategy database` is one SQLite file per tenant plus a registry that indexes them, `strategy row` is one database and a tenant column. Every reader asks one resolution (`db.$tenancy` / `registry.tenancy` / `resolveTenancy`), and precedence is **option → declaration → default**, which is what stops `litestone tenant create` and the running app disagreeing about where a tenant lives. **Row tenancy desugars into `@@deny`, never `@@allow`** — allows are OR'd within an operation, so an allow would widen every read to the whole tenant — plus a `@default(auth().<claim>)` stamp, and it is two rules because `checkCreatePolicy` runs BEFORE the stamp: an absent column is legitimate on create and belongs to nobody on read. A model with no tenant column is reported by name at parse; `@@tenant(none)` says it spans tenants on purpose. `asSystem()` is the only way across, which is what a cross-tenant tier is built on. `packages/litestone/docs/multi-tenancy.md`.
- **`$setAuth(user)` RETURNS a scoped client, it does not mutate.** `db.$setAuth(u)` then `db.thing.create(…)` grades as anonymous, with no warning. It is `const userDb = db.$setAuth(u)`.
- **A Litestone client THROWS on an unknown property** — never `undefined`, so a typo'd accessor is loud. The cost: feature-detection is itself a throwing expression. `typeof db.$maybe === 'function'` explodes; use `'$maybe' in db` or a `try`. A capability that depends only on the schema belongs on **every** flavour of client — root, `$setAuth`, `asSystem`, `$scopedBy`.
- **Raw SQL requires `asSystem()` once a schema declares access rules.** `db.sql` and `db.$setAuth(u).sql` throw; `db.asSystem().sql` is the bypass, and it can write. Raw statements enforce no `@@gate`/`@@allow`/`@guarded`/`@scoped`/`@@softDelete`. Coarse per schema on purpose — deciding per statement means parsing it, and a wrong validator grants a *false* guarantee. `where: { $raw: sql\`…\` }` keeps every policy and is the hatch to reach for. A JS migration is exempt: the runner hands it the system client.
- **`@guarded` is not a level** — a system-context lock taking only `(all)`; `@guarded(5)` does not parse. Per-role column access is field-level `@allow('read', auth().role == 'admin')`. It locks **both directions**: a non-system write naming a guarded column is refused with an `AccessDeniedError` naming the field, where it used to land silently while the read strip made it look refused. `@encrypted` alone is not a guard — it hides a value from a reader and stays writable, which is what a caller submitting a secret needs. The two cannot sit on one field, and that is the choice: `@allow('write', …)` for a column some callers may set, `@guarded` for one only `asSystem()` touches. A **required** `@guarded` column makes its model uncreatable below level 8.
- **A column your `getLevel` reads must not be writable by the caller being graded.** A gate is per MODEL, so `@@gate("4.4.4.5")` on an identity table says *any signed-in caller may write any other person's row* — `role`, `isAdmin`, a status, whatever the ladder is graded from. `@frontierjs/auth`'s `User` ships the shape: a level for what kind of caller, `@@allow('update', id == auth().id || auth().isAdmin)` for whose row, `@allow('write', auth().isAdmin)` for which columns. **`8` is not a stronger `5`** — it means nothing outside `asSystem()` has anything to say to this model, which is true of credential material and false of the table an app's own screens list; raising the gate just moves the surface into the bypass. `DECISIONS.md` § Access control.
- **`encryptionKey` is parsed as hex**, so 64 *characters* is not necessarily 32 bytes. Non-hex padding decodes short and is rejected with `must be 32 bytes (got 1)`.
- **`createClient({ db })` names MAIN's path and nothing else.** It overrides a declared `database main`, so `db: ':memory:'` is the in-memory test client; a SECOND declared database keeps its declared path regardless. `databases: ':memory:'` is the shorthand that moves them all, jsonl and logger included. Precedence: `databases: ':memory:'` > `databases: { main: { path } }` > `db` > the declaration.
- **Litestone emits columns verbatim camelCase and `DateTime` as ISO-8601 TEXT.** Hand-written SQL assuming snake_case or epoch-ms will not match.
- **The audit logger defers one event-loop tick**, so a read in the same tick sees 0 rows. `fireLog()` schedules with `setImmediate` and the jsonl driver appends synchronously — anything after an `await` sees the row. Yield once; do not wait.
- **`@@log(audit)` records a WRITE; `db.$audit()` records an EVENT — and the second one throws.** A sign-in is not a write to `User`, and a *failed* one is not a write at all, so nothing the logger can see names the actor or the attempt. `$audit({ operation, model?, records?, actorId?, meta? })` is the one way to put a row there by hand — an unknown key is refused by name, `actorId` defaults to the calling client's principal (a system context has none), and a stated value beats `onLog`'s. **It awaits and throws where `fireLog` is fire-and-forget**, because there the record is a side effect of a write that already succeeded and here it is the point. `meta` is NOT redacted — it is yours, so do not put a secret in it. On every flavour of client.
- **A per-call flag the model cannot SATISFY is refused by name, and so is a method.** `onlyDeleted` on a model with no `@@softDelete` used to answer the LIVE rows — the opposite of the question, with nothing saying the flag had not applied — and `search()` below `@@fts` threw a bare `Error` that reached a caller as a 500. Both are `CapabilityNotDeclaredError` now: **400**, naming the model and the attribute that would make the request legal — `onlyDeleted`/`onlyTemplates` on every read and write, plus `search()`, `optimizeFts()`, `restore()` and `transition()`. **`withDeleted`/`withTemplates` do not refuse**: they ask to widen, and a model that hides nothing already answers everything, which is what generic tooling (Studio's row browser, a *show deleted* toggle) is asking for.
- **A `where` typo below the boundary warns to stderr and returns no rows.** Over HTTP an unknown key is a 400 naming it (`autoFilter`), but a service building its own filter gets silence. `client.service('x').find({ limit: 100 })` is the trap: the FIRST argument is the filter, `limit` belongs in the second. `find()` answers the list envelope; `findData()` is the rows.

**API**

- **`ctx.params` does not exist anywhere in Junction, and `ctx.route` is not it.** A `ServiceContext` splits into `auth` (the principal) / `client` (`ip`, `userAgent`, `headers`) / `route` (path captures alone) / `locals` (per-call scratch, where `withLitestoneDb` puts `db`); a `TransportContext` carries the same `route` and puts headers at `ctx.headers`. **The four have four different rules and that is the substance** — `auth` is frozen and PROPAGATES to a nested call at any depth, `client` propagates, `route` is router-only (`{}` internally), `locals` is fresh per call and does NOT propagate. `packages/junction/CLAUDE.md` § The two contexts is the reference and `tests/context-contract.test.ts` runs it. Stale Feathers idioms survive in old notes; reading `ctx.params.user` yields `undefined`, so a role check silently passes for everyone. Also: `before: { all: [...] }` applies to *every* method, machine-facing endpoints included.
- **Absent is not null on `auth`.** A call naming no `auth` inherits the principal in scope; `{ auth: { user: null } }` means *as nobody, deliberately* and stays anonymous. Same distinction Invariant 9 makes about a patch, and it is the only way to ask what a stranger would see.
- **Raw routes (`app.get`/`app.post`) take `{id}`, not `:id`** — `:id` registers as a literal segment and 404s silently forever.
- **`apiPrefix` moves EVERY route the app registers**, auth's `/auth/login` and caravan's `/jobs` included, because the `app.get`/`app.post` shortcuts are its one owner. A path that must not move is registered on `app.http.router` directly. An app that sets a prefix proxies one path, not one per plugin.
- **An `Idempotency-Key` on a mutating request now executes once and replays the first answer** — claimed in `callService`, so it holds over HTTP and the socket alike. The replay runs **no hooks**, so an app effect living in one does not happen twice *and does not happen on the replay at all*. Keyed by `(service, method, principal, key)`; a failed call releases the key, an in-flight duplicate is a retryable 409.
- **`hasRoute()` is a matching question, not an existence one** — every app registers `GET /{service}`, which matches almost anything. Use `hasExactRoute(method, path)` for "is this mounted", `routePaths(method)` for what landed where.
- **What the API answers is not readable in a service file, so it is committed too.** `junction surface --app <module> [--services <dir>]` writes `surface.snapshot.md` at the app root — methods after the policy, custom methods as `collectCustomMethods` resolved them at construction, the hook chain in RUN order with the derived hooks (`gateAuth`, `autoValidate`) leading it, every mounted path with `apiPrefix` applied, plugins in configure order. Read off a BUILT app, so the module must expose one **without listening** (guard an entry's `app.start()` with `import.meta.main`) and autoloaded services need `--services`. The `snapshots` CI phase fails a stale one.
- **An irreversible effect belongs in `ctx.afterCommit(fn)`, not in an `after` hook.** `after` is after the METHOD: hooks run in sequence, so an email sent from one goes out and a later one throwing still fails the call — and under `transactional:` the row is rolled back with the email already gone. What is queued runs once, on the success path, after the announcement, and after the commit where there was one. **Observer tier** — a throw is logged and emitted, never reported as the call failing, because the write is committed and the broadcast is out. **Not durability**: a crash between the two loses the effect, and `ctx.enqueue` is the verb that survives it
- **`ctx.enqueue(job, payload)` is the durable half, and it is a second VERB because a closure cannot be persisted.** It writes a row into the app's OWN database inside the calling method's transaction, so the intent commits with the write or rolls back with it; `app.configure(outbox())` is the relay that hands it to `app.jobs` and marks it delivered (`FJS-D35`). **The row can be in no other database** — litestone opens one connection per declared `database` block and holds one transaction manager, over main's, so a row in a second block survives the rollback that was supposed to take it (measured). The queue stays a separate file, which is what makes the handoff **at-least-once**: the relay dispatches under the OUTBOX ROW's id and caravan's `dispatch({ id })` treats a taken primary key as work already queued, so a crash between the two replays into a no-op. Refuses by name outside a transaction, without the model, and with no relay — a row nothing delivers is worse than a refusal. `fli outbox:install` writes the import line, and `/metrics` answers `outbox: { pending, delivered, failed, lastPassAt }` — contributed through `app.registerMetricsSource`, whose sources must be SYNCHRONOUS (the body takes `fn()` directly), so the count is refreshed once per relay pass rather than once per scrape
- **A payload key that is not a column is declared `@transient`, and it arrives at `ctx.transients` — never at `ctx.data`.** The mirror of `@computed`: no column, written by the caller, never read back (`FJS-D23`). `autoValidate` validates it with the model's own rules and then LIFTS it off the payload, because the Data boundary refuses a transient key by name — a service passing `ctx.data` on whole fails the write rather than the field. Fresh `{}` per call, does not propagate, `{}` on a model that declares none. **A bulk write carrying one is refused**: the rows a service receives are the ones that passed validation, so an index-aligned array would pair one row's value with another row. Undeclared is still deleted in silence, which is what the declaration is for.
- **The METHOD decides list vs single.** `find` must answer a list or it throws `ResultShapeError`; an array is a list; the bulk `{data,errors}` protocol is a list on any method; everything else is a single and travels whole. A service answering one thing names it and calls it as a custom method; a summary alongside rows is its own named method.
- **Never call `ws.send()` directly.** Bun answers `-1` for buffered and **`0` for discarded** past ~16.9MB of unacknowledged data on one socket (`maxBackpressureLimit` is accepted and ignored). `transport/send-queue.ts` is the one owner of a send: it holds a dropped frame, flushes on `drain`, preserves order, and past `http.wsMaxQueued` (8MB) closes with 1013 so the client reconnects.
- **Caravan owns the clock; `app.scheduler` is in-process only** (`FJS-D36`). Two timers exist and they are not the same feature — `app.scheduler` has no persistence, no retry and no principal, and is gone with the process; `app.jobs` is durable work. **A timer that dispatches into a queue is the QUEUE's schedule**, registered with `app.jobs.schedule(name, expr, fn)`: firing `app.jobs.dispatch(…)` off `app.scheduler` buys a clock with none of the queue's durability while looking like it has it. **Caravan's clock is safe to run in two processes and junction's is not** — a cron fire is dispatched under `cron:<job>:<epoch-minute>`, so a second replica's fire is a no-op rather than a second row, and a `running` row is owned by a heartbeating instance so recovery reclaims only what a crashed one left (`FJS-294`). A schedule that came from a database ROW also needs `app.jobs.unschedule(name)` when the row stops being true, and re-registering at boot — neither registry survives a restart, which cost basecamp every scheduled job it had (`FJS-327`, `FJS-328`). `app.scheduler` is for work with no row behind it: a cache sweep, a metrics tick.
- **A background job runs as whoever asked for it, and a job nobody asked for runs as the app.** Caravan records the principal in scope at `dispatch()` and Junction re-resolves them when the job runs (`app.runAs`), so `ctx.app.service('x').patch(…)` from a handler names no `auth` and inherits one. **An id is stored, never a session** — a caller demoted between asking and running is graded at the standing they hold *now*, where a replayed snapshot is a privilege outliving its own revocation. No enqueuer (a cron fire, boot) resolves to `createApp({ system })`, the one place an app says who it is acting on its own behalf; declaring none is valid and gives `null`. `example/api/gate.ts` is the pattern. Still true: `db.asSystem()` is the wrong fix, because it writes at the Data boundary where nothing announces and every open tab keeps the stale row.
- **`IAuth.sessionFor(userId)` is how a principal is rebuilt without a credential**, and it must never be wired to anything a request can name — it proves nothing. Optional; a provider lacking it makes `runAs(userId, …)` throw by name rather than quietly downgrade.
- **Junction resolves every Bearer token through `IAuth.verifySession()` and calls `verifyApiKey` nowhere** (`transport/http.ts`). One door: a key is only verified if the *provider* falls through to its own `verifyApiKey`. A third provider inherits that job.
- **Caravan's `unique` is a lock on work IN FLIGHT, not an idempotency key.** Once a job is terminal the key is free. A key built from a row id is not one either — SQLite reuses ids.
- **A job in `jobsDir` is named by its file and declares its own schedule.** `send-email.job.ts` is `send-email`; a `defineJob` naming anything else is refused at load rather than registered, because a handler answering to `send-emial` is a dispatch that silently never runs. `cron` is a `handle()` option — a `*.job.ts` file carrying one is scheduled by being autoloaded, and `schedule()` is sugar over the same registration. The definition is also the dispatch handle: `dispatch(sendEmail, data)` states no name and types the payload. **The queue's database opens on first use**, which is what lets every key of `junction.config.js`'s caravan section apply — and means a dispatch before `app.configure(…)` opens it at the DEFAULT path.

**UI**

- **The route table is a naming convention over a file tree, so it is committed too.** `sierra routes --config config/sierra.config.js`, run from the app's **web root**, writes `routes.snapshot.md` — every URL with its file, the layout the scanner resolved (none where a page declared `reset`), the meta a layout pushed down onto every page under it, and what each `_module.mesa` wraps. On a `static` target **`publishes:` leads the file** in its own section: it is the one line that turns off the fail-closed publish check, and it lives in one page's frontmatter. One config is one target and its name carries — `sierra.static.config.js` → `routes.static.snapshot.md`. The `snapshots` CI phase fails a stale one.
- **A live store holds what its last `load(query)` asked for, so a patch can take a row OUT of it.** A row moved out of the filter is removed rather than updated in place — there is no other event for leaving a filter. A record the schema cannot judge (a `select` dropped the filtered column, the filter names a relation, `$search`) triggers a reload instead of a guess. The row is also PLACED — `orderBy` decides where, and the first page trims what falls past `limit` — but **past page 1 a new row is refused**, because nothing in a browser knows whether it belongs on an earlier page. That, and a gap a removal leaves, count on `resource.stale`, which `load()` clears and a view renders as *3 new — refresh*. **`changed` is the event that names no row** — what a bulk write or a `select: false` write announces — and the store's answer to it is the reload it already gives an undecidable record, coalesced per burst. Not `stale`: a counter describes a gap the list knows the shape of, and *some unknown rows moved* is not one.
- **A live store defeats `@version` on any screen holding a draft.** `createResource` remembers a version off the STORE — deliberately, because a WS push reaches it as an upsert and never passes through a call result, and without that the row a second tab patched left a pre-patch number behind and the next patch 409'd on something nobody read. The other side of it is that a DRAFT does not move with the push but its version does, so the save carries a number nobody on that screen read and wins the race the column exists to lose: measured in basecamp, the other person's write erased with the guard in place and no error anywhere. Put the version in the draft — a stated one beats the remembered one, which is the documented escape. `<Form record={row}>` is already right, because it edits the row whole. **The API-side sibling**: junction derived ONE create-mode JSON Schema and compiled the patch validator from it, so `autoValidate` stripped the version off every patch and `@version` did not work through a service at all (`FJS-335`).
- **`createResource` coerces, blank-strips and validates by default.** A bad create throws `ResourceValidationError` in the browser with the request never made, and an untouched text box writes NULL rather than `''`. A resource whose service accepts a shape the model does not describe needs `{ validate: false }` — the symptom otherwise is "the button does nothing" unless something renders the throw. `<Form>` renders it.
- **`@system` is the column an application writes and its caller does not** — readable by anyone, refused on write by name. The orthogonal sibling of `@guarded`, which locks both directions. It reaches the client as `readOnly`, so a generated form does not offer it and `make()` does not seed it; it is **out of create-mode `required`**, because listing a server-written column there refuses every create in the browser naming fields the caller was never meant to send (`FJS-095`). The app fills it by naming the column on the write — `db.order.update({ where, data, system: ['trackingCode'] })` — which keeps the gate, the row policies and the audit actor, where `asSystem()` drops all three to write one value. A required `@system` column that nobody filled fails at the write, saying which side is missing.
- **`<Form {resource} />` with no children IS the form** — every writable column in schema order, each with the control its type implies, over the one table in `field-rules.js`. Children win (the caller is writing it); `only` narrows and orders, `except` removes, `auto` forces either way. A column the table cannot place is **warned about by name** rather than dropped. Beware the shape that found the mesa bug: a slot whose only child is an HTML comment used to count as children, so one comment inside a `<Form>` turned generation off in silence.
- **A Mesa instance `<script>` exports exactly two things.** `export let` is a prop, `export function` is a method on the component's instance API; every other export form is refused by name. **`bind:this` means two things** — on a COMPONENT it gives that instance API (props read through the child's own signals, so `ref.count` is live and writable), on an ELEMENT it gives the node.
- **Mesa's scoped styles do not reach into child components.** Use `:global(...)`; the selector subject carries the hash (`button` → `button.mHASH`). A dynamic `class` MERGES, never replaces — all dynamic classes route through `bindClassPassthrough`.
- **An overlay that is present is not an overlay that is visible.** Kit overlays fade in with `el.animate(…, { fill: 'forwards' })`; an assertion that only asks `querySelector` passes against a fully invisible full-screen backdrop. Assert computed opacity and hit-testing.
- **Headless Chrome delivers almost no rendering lifecycle after load.** Anything behind `IntersectionObserver` must be set up before it; `requestAnimationFrame` hangs. Working pattern: `packages/sierra/tests/fixtures/island-site/verify.mjs`. **`getComputedStyle` goes stale after a class change** — `el.matches()` and `document.styleSheets` report the new state while computed styles stay frozen, and forcing layout does not help. To check a post-click style change, read the rules that match the element.
- **Vite injects the built `<script>` at the first textual match for the body tag and does not skip comments.** Mention it inside a comment in a hand-written `index.html` and the build succeeds, `dist/index.html` looks right, and the page loads no JavaScript. Never write the body tag in a comment.
- **A code sample highlighted with `prefix: true` loses its first character.** `glow()` strips a leading `+`, `-` or `>` as a diff/callout marker, and all three are legal first characters in CSS (`> .child`, `+ .sibling`). `--` is disambiguated; the combinators cannot be, so **a CSS caller passes `prefix: false`**.

**Repo**

- **`bun install` resolves `workspace:*` to a COPY under `node_modules/.bun/`, not a symlink.** An edit to `packages/mesa/src/compiler.js` is invisible to importers until reinstall, so a suite can go green against a stale snapshot. In-repo tests import workspace source by relative path. `packages/ui`'s hand-made symlink will not survive a reinstall.
- **Nested directories are invisible to the `packages/*` glob** — uninstalled, untested, unrunnable. Four cases, all deliberate and named in `scripts/ci-allowances.json` § nonMembers: `mesa/mesa-bench`, `oracle/mockup`, `orion/mockup/api-engine`, `toolbelt/mockup/datetime`. **A fifth is a CI note naming the path**, so the way this goes wrong is by someone reading the note as noise, not by silence.
- **Publishing a package silences every loose peer range that names it.** While a sibling is unpublished a peer of `"*"` fails at install with the name in the error; the moment it exists, the same range resolves from the registry without a word. **Below 1.0 a caret pins the MINOR** — `^0.1.0` is `>=0.1.0 <0.2.0` — which is both the behaviour wanted for a pre-alpha peer and the trap in the other direction, where a stale caret excludes the only published copies. Nothing catches either shape from inside the workspace: a `workspace:*` devDep answers first and the range is never consulted. **`fli ws:exports` commits the published surface** — `exports.snapshot.md` at the root, one section per publishable package: the top-level entries its tarball actually contains (asked of `bun pm pack --dry-run`, never derived from the globs), every `exports`/`bin`/`main`/`types` target marked with whether that tarball holds it, and the peer ranges naming a sibling. It is the cheap half of what `scaffold` proves end to end: a declared entry point `files:` does not publish is a broken install, decidable from the listing alone. The `snapshots` CI phase fails a stale one.

## Bridge index — the named cross-package handoffs

The current seams. Reach for them before grepping. They may move, merge, or change signature as long as ownership and dependency direction hold.

**Data → API**
- `$setAuth(user)` / `asSystem()` — the Data-boundary checkpoint / bypass — `litestone/src/core/client.js`
- `$tapEvents(fn)` — every write, announced. **Two shapes and the write says which**: `scope: 'row'` (one row; `result` is it, or `null` where `select: false` skipped the RETURNING) or `scope: 'collection'` (`count` rows matching `where`, never built). Stated, never read off `result` — that is two facts. A bulk write's shape is the per-call `announce` — `collection` (default) · `rows` · `none`, floor at `createClient({ announce })` — because the batch size is a property of the call, not the model (`FJS-D34`)
- `withLitestoneDb(db)` — per-request scoped client on `ctx.locals.db`; auto-installed by `createApp({ db })` — `junction/src/core/litestone.ts`
- `gateAuth()` + `autoValidate()` — schema-derived 401s/400s for model services — `junction/src/core/litestone.ts` + `core/service.ts`
- `sessionGateLevel(user)` — `SessionContext` → litestone's 0–7 scale; pass to `GatePlugin({ getLevel })`. Litestone cannot import Junction, so this is **a hand copy on both sides — change one, change both**
- `toDataPrincipal(user)` — the other half of the same translation: `SessionContext` → the principal `auth()` reads (`userId` → `id`). Applied at both `$setAuth` call sites. Without it every row policy compares against `undefined` and matches nothing, silently. **Two functions, one boundary**: change either and ask whether the other needs it too
- `resolveTenancy(schema)` / `registry.tenantFor({host, headers, principal})` — **the one reading of `tenancy { }`**. The declaration is a Data-realm fact and *which tenant is this request for* is an API-realm question, so the API asks rather than re-deriving; `createApp({ tenants })` installs `withTenantDb`, which assigns the same `ctx.locals.db` that `withLitestoneDb` does and therefore replaces it. Under `strategy row` nothing is swapped and `tenantClaimGuard` refuses a signed-in principal with no claim, because the alternative is an empty list with a 200 on every screen
- `accessorCandidates()` — `model Post` ⇄ service `posts` ⇄ `db.post`; shared by query, gate and validation so a naming slip cannot disable just one
- `db.$checkWhere(accessor, where)` → `[{key, suggestion, allowed}]` — the one definition of "is this a valid filter key", asked rather than copied; junction's `autoFilter` calls it. An unknown accessor answers `[]` — *I cannot judge this* is not *this is wrong*
- `db.$checkOrderBy(accessor, orderBy)` → `[{key, reason, suggestion, sortable, message}]` — the sibling, identical contract; junction's `autoSort` calls it. **Both halves throw** (a bad sort key returns the right rows in the wrong order, which nothing can see). `reason` separates *no such field* from *`@computed`, so SQLite can neither sort nor paginate by it* and from *`opaque`* — an array, a `Json`, a `File` or an encrypted column, whose stored TEXT is a serialisation rather than the value, so ordering by it is always plausible and never what was asked. A `@from` field sorts

Both `$check*` live on **every flavour of client** — root, `$setAuth`, `asSystem`, `$scopedBy`. Filterability is a fact about the schema; auth has no bearing on it.

**Schema → API/UI**
- `generateJsonSchema(schema)` — consumed by junction validation and sierra's `build/schema-plugin.js` → `registerSchemas(defs, modelNames)`. **`$defs` is the whole definition table** (models, enums, `type T`, FileRef) and must stay whole — enum fields emit `{"$ref":"#/$defs/Plan"}` and both sides resolve it. Model names travel separately. Full key reference: `packages/litestone/docs/jsonschema.md`. **Three readers and no build that breaks when it changes shape** — a keyword that stops being emitted makes a form stop validating, silently — so `litestone jsonschema --snapshot` commits `db/jsonschema.snapshot.md`: `$defs`, enum values, per model the gate/relations/transitions and one row per field (type + default, required, label, keywords, which rules `x-messages` answers for), then what CREATE mode accepts. The `snapshots` CI phase fails a stale one
- `ctx.transients` — **the `@transient` half of a payload, lifted off `ctx.data`.** Declared in the seed, emitted `writeOnly` into the create/update JSON Schema and absent from the read modes, so a generated form offers a control for a value no read answers. `liftTransient` in junction's `autoValidate` is the one place it moves; `isStoredField` in litestone's `ddl.js` is the one answer to whether a field is a column at all
- `ServiceTypes` — **the schema's TYPES on the far side of the wire**, where JSON Schema is its rules. `litestone types --augment junction` emits `service name → row` plus the module augmentation that registers it with `@frontierjs/junction/client`, so `client.service('posts')` and `resource('posts')` infer with no type argument and an undeclared column is a compile error in the browser. Keyed by the plural through `@frontierjs/toolbelt/inflect`, like every other name that crosses (Invariant 2), and **audience-split**: the API generates the system row, the browser the client row, because one file for both tells browser code a `@guarded` column exists that every response strips. An app that generates nothing has an empty registry, which is `never`, so every call keeps the open shape it had
- `@label` → `title`, validator messages → **`x-messages`**, keyed by rule name *and* by the JSON Schema keyword it compiles to. Litestone owns the keyword table (`jsonschema.js`); Junction's `schema.ts` and Sierra's `field-rules.js` look up the keyword they failed. A field's label is read off the field's OWN schema, never a `$ref` target
- `buildFieldRules()` / `validateAgainstFields()` / `coerceToSchema()` / `normalizeBlanks()` — `sierra/src/junction/field-rules.js`, a **leaf module** with no Junction-client import so it runs in plain Node and can be compared against junction's server rules rather than copied. Order: **coerce → blankToNull → validate**. All three on by default (`{ validate: false }` opts out; the test is `!== false`, so a threaded-through `undefined` does not disarm it)
- `controlFor(rule, {field, model})` / `formFieldList(fields, {only, except, model})` / `labelFieldFor(fields)` — same module, **the one place a field becomes a control**, so a generated form and a hand-written one cannot disagree about what a `Float` is. Reached through the resource (`resource.formFields()`, `resource.options(fk)`) rather than imported, because `@frontierjs/ui` peers only on mesa and css and importing sierra would invert the dependency. A field it has no control for answers `control: null` **with a reason** — dropping it would make a new column absent from a form with nothing saying so. **`registerControl(name, resolve)` is the way in**, and it is HALF of a contributed control: this side answers a name, `@frontierjs/ui/controls` binds that name to a component, and a name is the only thing that can cross a boundary where one side must run in plain Node and the other may not import sierra (`FJS-D17`). Last registered is asked first, so an app beats the kit it imported; a `readOnly` column is not offered to the registry at all; `defaultControlFor(rule)` is the built-in table alone, for a resolver that extends rather than restates
- `toFieldErrors(err)` — same module, also `resource.fieldErrors(err)`. **The one owner of "a thrown value → per-field messages."** Three shapes reach it because each hop wraps once: `err.errors`, `err.data.data` (a server 400 through the browser client — the double `data` is real), `err.data`. Returns `{ fields, message }`
- `$context.form` — the UI-side form seam, provided by `ui/components/forms/Form.mesa` as `{ errors, submitting, disabled, fields, submitted }`. Nine controls resolve their own label, constraints, `aria-invalid` and message from it; an absent form reads `undefined` and every fallback is what the control did standing alone. A stated prop always wins, including `required={false}`
- `buildRelations()` / `buildGate()` / `canAtLevel()` — same module. **`x-relations` is the only place a relation exists on the client**; `x-gate` is an affordance, never a boundary
- `x-version` — names the `@version` column an update must carry back, `readOnly` in the update schema and absent from the create schema. `createResource` remembers the version of every record it reads and puts it on the next patch. `resource.version(id)` / `.versionField` expose it
- `retryable` on a thrown error — the one thing a status cannot carry. A 409 is either a race (`VersionConflictError`, `TransitionConflictError` — re-read and re-apply) or a domain refusal (`TransitionViolationError` — show its message). Set it on any error class you own; `toFrameworkError` adopts it and it lands at `err.data.retryable`. `isStaleWrite(err)` reads it. **`junction errors` commits what a thrown value actually becomes** — `packages/junction/errors.snapshot.md`, every row executed through the boundary, Litestone's own classes constructed and run through it. Nothing above `toFrameworkError` reads anything but the result, so a class gaining or lacking a `status` changes a category with no test to fail; `FJS-255` is what the first run found
- `buildTransitions()` / `transitionsAt()` — `@@transitions` reaches the client as **`x-transitions` on the model, keyed by field**, never on the enum `$def`, because only a model can carry a per-transition `@gate`. Mirrors `db.<model>.transitions(row)`
- `modelNameFor()` / `schemaFor()` — `sierra/src/junction/schema-registry.js`, over `@frontierjs/toolbelt/inflect`. **The inflection rules are one module and five callers** — litestone's table name and its introspection, junction's `deriveModelName`, sierra's registry and `createResource` — because a table name and the model name derived back from it are the same rules run twice (Invariant 2). Regular English plus a fixed irregular table, so `people` resolves `Person` unaided; genuine ambiguity (`lens`/`len`) cannot be reached by any rule and is said by hand — `createResource('lenses', { model: 'Lens' })`. A miss warns and degrades to a bare `make()`
- `authUserModel(db)` / `authMachineryModels(db)` — auth contributes INTO the seed, as two `.lite` files it ships (`auth/db/user.lite`, `auth/db/auth.lite`); `schema.ts` reads them and `authSchemaFragments(db)` is both, for a caller assembling one string in memory. **Split by owner**: `User` is `@@gate("4.4.4.5")` with policies an app changes, so `fli auth:install` appends it into the app's own `schema.lite`; the three `@@gate("8")` models go to `db/auth.lite` and are imported, so an upgrade reaches an installed app. The CLI reads the same bytes through auth's `exports` — it cannot import `schema.ts`, because `fli` runs on node and that file is TypeScript

**API internals**
- `bridge.toContext()` / `toResponse()` — the transport↔service boundary — `junction/src/transport/bridge.ts`
- `toFrameworkError()` — the error boundary. Order: `FrameworkError` → `registerErrorMapper(fn)` → numeric `status`/`statusCode`/`code` in 400–599 → `err.name` → 500. **If you own the error class, give it a `status`**; `registerErrorMapper` is for errors you cannot modify
- `wrapResult(raw, service, method)` / `unwrapResult()` / `isServiceResult()` — the result envelope. `kind:'single'|'list'` discriminates; a list keeps its envelope, a single unwraps. The same function runs on both sides of the wire, so the browser client asks it rather than carrying a copy of the rule
- `ctx.directives` — parsed from `$`-params by the bridge and nothing else. The GRAMMAR is `@frontierjs/toolbelt/directives` (`splitParams` → `{query, directives}`), because sierra's router applies the same one to a URL; the bridge is still the only thing that produces a `ctx`
- `collectCustomMethods(def, name, methods?)` → `svc._customMethods` — **the one place "is this key an option or a method" is decided**, at construction. `methods:` DECLARES (a non-CRUD name in it is a custom method, resolved off the definition, and is the only way to name one after an option key); absent, function keys are scanned for as before. Dispatch, `/manifest`, OpenAPI and `/metrics` read the table rather than re-applying the rule — `junction/src/core/service.ts`
- `svc.pipelines(appHooks)` — **the one owner of the hook chain.** Memoised on the app map's IDENTITY and a version `hooks()` bumps, so both inputs are in the key and a stale answer is unreachable. `app.hooks()` reassigns rather than mutates, which is what makes identity sound — mutate it in place and the memo goes stale silently
- `svc.describe()` → `ServiceDescription` — **the one answer to "what is this service"**, read by `/manifest`, the OpenAPI generator and `/metrics` instead of reaching into `_meta`/`_schemas`/`_hookMap`
- `isBuiltService(v)` / `Symbol.for('junction.service')` — has `createService` already built this? Non-enumerable, so a spread copy is correctly NOT built; the autoloader tests it rather than sniffing whether `hooks` is a function
- `normalizePrefix()` + the `app.get`/`post`/… shortcuts — **the one owner of `apiPrefix`**, `junction/src/core/app.ts`. Every route the app registers is mounted under it; `app.http.router` is the layer beneath and applies nothing. The browser client's `apiPrefix`/`authPrefix` compose the same way
- `ctx.enqueue(job, payload)` / `deliverOutbox(app)` — **the durable effect**, `junction/src/core/outbox.ts`. The enqueue writes an `OutboxMessage` row through `asSystem()` on `ctx.locals.db`, which the transaction hook has already reassigned to the tx client — so the intent is inside the call's own transaction. The relay claims with a compare-and-set, dispatches into `app.jobs` under the ROW's id, and marks it delivered; `app.configure(outbox())` owns the timer. The model ships as `junction/db/outbox.lite` and reaches an app two ways, both the same bytes: `fli outbox:install` writes an `import` line, `outboxSchemaFragment(db)` is for an app assembling one schema string.
- `claimIdempotency(ctx, key, config)` — `junction/src/core/idempotency.ts`, claimed once in `callService` so both transports are covered. The replay bypasses the hook pipeline by design; `requestMeta()` is where the key comes from, and the WS path now populates that store too
- Plugin protocol `{ name, register, boot, ready, shutdown, requires }` — `junction/src/core/app.ts`. **`register` is sync** (`configure()` never awaits it); async setup goes in `boot()`. `requires: ['mailer']` is checked once at startup against presence *and* configure order
- `runStartPhases(bindHost)` — the one startup list; `needsHost` phases are skipped by the test path
- `IAuth.verifySession(token)` — inbound auth — declared `junction/src/auth/types.ts`, implemented `auth/auth.ts`. **What junction ACCEPTS is `SessionVerifier`, not `IAuth`** — `Pick<IAuth,'verifySession'> & Partial<IAuth>`, because the interface declares six required methods and junction calls two of them (`FJS-D10`). Derived rather than declared beside it so it cannot drift, and `Partial` is what keeps a fuller provider assignable past the excess-property check
- `app.principal()` / `app.runAs(userId, fn)` — **the seam deferred work runs through**, `junction/src/core/app.ts`. `principal()` is the request-wide principal asked from somewhere holding no `ctx`; `runAs` re-resolves an id through `IAuth.sessionFor` and opens the ALS scope, so a service call inside `fn` inherits it. `null` means `createApp({ system })`. Caravan is the first caller and reaches both **duck-typed off `CaravanApp`** — it takes junction as an optional peer, so nothing here is imported at runtime
- `createLitestoneAuth(db, { sessionFields })` — **the one place an app's own `User` columns reach the session.** Called from `toContext()`, the single point every issued session is built, so one hook covers login, `verifySession`, an API key and `createUser`. Two kinds of thing belong in it: the standing `sessionGateLevel()` grades on (`isAdmin`/`isOwner`/`isSystemAdmin`/`activatedAt`/`verifiedAt`), and the app's own keys, which travel untouched. Spread LAST — a stated field wins
- `manifestPlugin()` + litestone `status()` — migration state into `/manifest`

**API → UI**
- `wsSend()` / `flushSendQueue()` — `junction/src/transport/send-queue.ts`. **The one owner of "put this frame on that socket"**, for replies and broadcasts alike
- `publish()` hook + `app.channel(name)` — real-time — `junction/src/transport/channels.ts`. Services declare `channel: 'posts'`; `callService` is the single announcement point for both the bus (`svc:created`) and channels (`svc created`). **A custom method announces too, under its own name** (`orders pay`); only `find`/`get` are excluded, and a read-shaped one opts out with `ctx.dispatch = false`. **An app-level `app.channels.publishDefault(fn)` is the catch-all Feathers spells `app.publish`** — consulted only where a service declares nothing, so it composes with `channel:` instead of racing it; function-only, because one channel name for a whole app is the shape that hands a subscriber rows no `@@allow` would have let them read, and the plugin reports at boot which services fall through to it (`FJS-334`). **A write that came through no service announces too** — `announceDataWrites` taps litestone's `$tapEvents` and routes it into the same fan-out (`FJS-010`) — and it announces in one of two shapes, which litestone decides (`scope`): a write holding its row broadcasts `created`/`updated`/`removed` with that row, one holding only a count broadcasts **`changed`**, `{model, operation, count}`. The caller's `where` reaches the in-process bus and never the wire. Open: jetty hardcodes Feathers-style names
- **Transport: WebSocket when one is connected, HTTP as the fallback.** Every service call — CRUD and custom methods — checks `_wsReady` first; over WS it is a `service_call` frame naming the method, over HTTP the REST verb (a custom method: `POST /{service}/{id}` + `X-Service-Method`). The one exception is a payload carrying a File. **A custom method may address the COLLECTION** — `invoke(name, null, data, query)` posts to `/{service}`. The two paths share almost nothing and drift silently; `env.verifyTransportParity()` (`@frontierjs/testing`) is what asks whether they still agree
- `createJunctionClient()` / `client.resource(name)` — `junction/src/client/index.ts`, consumed at `sierra/src/junction/index.js`
- `client.auth.*` — the browser half of `@frontierjs/auth`: `signIn`/`signUp`/`signOut`/`me`/`changePassword`/`sessions`/`apiKeys`/reset/verify. It lives on the CLIENT because the client holds the token, opens the socket and knows both prefixes; an app writing its own sign-in reproduced all three. It speaks the server's own split — the routes that establish a session, the services for what the caller does next
- `tokenStorage` on the client + `session` in sierra — **the token has one owner and the session has one shape.** `setToken` persists, clears and emits `token`; `@frontierjs/sierra/junction`'s `session` is the reactive object over it, with `ready` for the navigation guard. `login(token)`/`logout()` are gone
- `matchesQuery(fields, record, query)` → `resource(name, idField, { match })` — **is this pushed record still in the list `load()` asked for?** Junction owns the store and holds no schema, so the decision comes from `sierra/src/junction/field-rules.js`, over the same operators `parseWhere`/`translateOps` accept and with SQL's null semantics. `true` upserts, `false` REMOVES, `null` is *undecidable from this record* and reloads. A caller passing no `match` gets the old apply-everything behaviour
- `comparatorFor(orderBy)` — `junction/src/core/sort.ts`, **the one reading of `orderBy`**: `parseSort` IS `normalizeOrderBy`, so the SQL the server compiles and the position the browser gives a pushed row come from one parse of `-createdAt`. `compareValues` follows SQLite (NULLs first ascending, numbers before text, a Boolean as its stored 0/1) and states where it cannot be exact. What no client can answer is paging — past page 1 a pushed row is refused and counted on `resource.stale`

**UI**
- `page.query` / `page.directives` — the URL's search string, split by `@frontierjs/toolbelt/directives` exactly as the bridge splits a request's. `resource.load(page.query, page.directives)` is a filtered, sorted, paged list that lives in its URL. `page.params` is path captures alone
- `watchProxy()` / `createSignal()` / `createRoot(fn)` — the reactive seam and lifetime ownership — `mesa/runtime.js`
- `mount(label, Component, {props, root})` — page entry. Registers the delegation root; a component called directly renders but handles no events
- `renderComponent(src, opts)` — UI → HTML at build time; Sierra's `static` target composes route + layout chain through it. Children must be supplied **both** ways (`children={s}` and element children) — the two slot protocols do not bridge
- `swapInstances(entries, newFn, newSetMark, label)` — **the DOM a hot update replaces**, `mesa/mesa-vite/swap.js`. Two callers: mesa's own HMR client and jetty's `__jettyMesa.hot_update`, which used to hold a hand copy of it (`FJS-259`). **No `import.meta` and no imports**, because jetty bundles it into an MV3 content script and those are CLASSIC scripts. The client that wraps it is two files, so a plugin serving it at a virtual id must ask `client-source.js` for them joined — a virtual id resolves no relative import, and `client.js` alone is a 200 that dies in the browser
- `island(anchor, Comp, props, block, meta)` — the island seam, off by default. Markers are **comments, not an element** (an element is foster-parented out of `<tbody>` and joins `>` selectors). Sierra collects them at prerender, bundles one chunk per island, and mounts via `@frontierjs/sierra/islands`. **A mounted ancestor is authoritative** — test a marker with `isConnected`, not `parentNode`
- **The theme is a class on `<html>` and Sierra owns the switch** (`FJS-308`). `@frontierjs/css` owns the vocabulary — eleven `theme-*` classes, each a block of inheriting custom properties — and ships no JavaScript, so it cannot own a switch; beating first paint needs a `<head>` script only the build can write, so the kit cannot either. `theme: { themes, default, system, persist, key, apply }` in `sierra.config.js`; `setTheme` refuses a name the app did not declare. **The element is not a knob** — `<body>` does not exist when a `<head>` script runs, so a `target: 'body'` would only bring the flash back. Before this, sierra wrote `data-theme` and the kit wrote `.dark`, and **the design system read neither**, so both apps hand-wrote a third applier
- **There is no cross-package reactivity registry.** Sierra exports no module-level signal — `page`, `status`, `theme` are plain objects a component makes reactive with a `$:` path watch — so `sierra/src/build/mesa-plugin.js` passes mesa no `externalSignals` map, only `externalReactivityHints: 'strict'`. The map survives in mesa as an escape hatch for a third-party package that does export a signal. **Strict is the end state, not a migration aid**: the default tier is silent for a component that watches nothing, which is the shape that shipped the original bug

# Testing — which runner, and what it needs

Reference for running a suite or a drive in this workspace. The root `CLAUDE.md` carries the rule (cd into the package, `bun run test`); this file carries the per-package detail. `fli ws:atlas --as=report` derives the runner column from each `package.json`, so when the two disagree the report is right and this table is stale.

**Always `cd` into the package and run its own script.** Runners differ per package and a wrong runner produces failures that belong to nothing. `bun run --filter '*' test` from the root runs them all, one each. `bun test` instead of `bun run test` runs bun's own runner over whatever it finds — in mesa that is ~35 failures that are runner artifacts.

**A test file's directory says whose test it is; its extension says what runs it.** A package is not an app — it has one `src/`, so its suite is `test/`, and `tests/` stays reserved for the app-level surface Invariant 3 names. Inside it, **`*.test.*` is COLLECTED and `*.spec.*` is DRIVEN**: a `.test` file declares a suite that bun or vitest finds by globbing, while a `.spec` file exports a `run` function, sits in a `specs/` directory, and is imported by the `run.mjs` beside it that owns the browser or the harness. Vitest's default glob takes `{test,spec}` both, so a `.spec` left where vitest looks is collected as a suite declaring nothing and fails a dozen times saying nothing — which is why `packages/mesa/vitest.config.js` excludes `test/browser/` by hand. **A collected test is hermetic**: one that asks for its checkout's port block, binds a literal port or launches Chrome runs beside every other suite and fails as environment, so `fli check`'s `test-not-hermetic` reds it. `port: 0` read back is the fix; Chrome means a spec. **A package's test timeout has one place once it has any**: `--timeout N` in a bun package's `test` script (bun 1.4.2 reads no timeout from `bunfig.toml`), `testTimeout` in a vitest config. Where one is set, `test-timeout-inline` warns on a test that sets its own; a package with none keeps its inline timeouts on known-slow tests.

**Every `test` script runs inside `scripts/tmp-run.mjs`** — `node ../../scripts/tmp-run.mjs '<command>'`, the command as ONE quoted argument so a `&&` chain stays one run. It points `$TMPDIR` at `fjs-run-<pid>` for the whole script, removes it on the way out, and on the way in kills and removes what a SIGKILLed run left: a temp dir a test never removed, a template, a Chrome and its profile. Before it, a week of runs filled the disk (`FJS-2762`). CI's `coverage` phase fails a `test` script outside it. A runner started directly (`bun test`, `npx vitest`) writes to the real `/tmp`.

**A deadline bounds failure; it does not establish completion.** A test that waits a fixed time and then asserts has proved only that the time passed: on a loaded machine the thing it waited for has not happened yet and the assertion fails naming nothing, and on a fast one it passes by luck. Poll for the condition and let the deadline be the failure, worded as what was waited for — `example/web/test/lib/preflight.mjs` is the shape.

## Dev servers

**A dev server serves the code it started with.** A `.mesa` module is transformed once and cached for the life of the process, so editing the compiler invalidates nothing and the app fails exactly as it did before the fix. Start the server the run will test, and refuse a port that already answers. Backgrounding a server from a tool call is unreliable here (`nohup`/`setsid` both drop it); what works is a script that spawns it, polls until it answers, asserts, and kills it — `example/web/test/verify-build.mjs` is the shape. **And a port that answers is not evidence the right process is on it**: `bun run api` spawns a CHILD, so killing the wrapper leaves the app holding its ports, the next start exits `EADDRINUSE` into a log nobody reads, and the readiness poll is answered by the process that never went away — a drive then reports on code that is not in the tree, green or red (`FJS-740`). `example/web/test/lib/preflight.mjs` asks reachability and FRESHNESS together, because separating them is how the second stops being asked: `/health`'s `uptime` against the newest mtime under `api/` and `db/`, since dev has no build stamp and mtime is the only fact both sides can see.

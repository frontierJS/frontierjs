# CI — the phases and what fails each one

`bun run ci -- --help` prints the phase list and every flag, derived from the phase table in `scripts/ci.mjs`. This file is what each phase FAILS ON, which the help text points at.

**`bun run ci` is the whole of CI and it is not a GitHub feature.** One node script runs thirteen phases and `.github/workflows/ci.yml` does nothing but call it, so it runs identically on a laptop. `ci:fast` skips the suites, `--only <pkg>` narrows typecheck and tests, `--phase <name>` runs one by name (repeatable, and always in the table's order — `scaffold` packs what `deploy` installs), and `bun run hooks:install` points `core.hooksPath` at `scripts/hooks`, whose `pre-push` runs the fast tier — the suites belong in the workflow, because a pre-push costing minutes teaches everyone `--no-verify`. Every allowance is a named entry with a reason in `scripts/ci-allowances.json`. **`fli ci` is the same call from anywhere in the workspace** and forwards its argv untouched, so there is one flag set and one owner (`FJS-D255`); `fli ci -- --help` and `bun run ci -- --help` print the phase list and every flag, derived from the phase table rather than written out. In an APP there is no `scripts/ci.mjs` and `fli ci` says so, naming `bun run check`. **Every run writes its closing summary — notes, failures and each failure's output — to `.cache/ci-last.txt`**, headed with the time, commit and argv, so a pre-push that blocked can be read back instead of pasted. **Every run also logs itself as it goes to `.cache/ci-runs/<id>.jsonl`** — phases, a `begin` before each suite, each result with its time and test counts — through `packages/cli/core/ci-log.js`, the one owner of that format. `fli gui`'s `ci` panel reads it: the run going now against its usual time, each phase and suite's own latest result (a `--only` rerun answers one row, never the whole run), and a rerun or stop button. A log write that fails is a warning and never changes the verdict.

| Phase | What fails it |
| ----- | -------------- |
| `hygiene` | a source file `.gitignore` hides, and **a dependency or a clock inside the substrate package** — `@frontierjs/toolbelt` may be imported by litestone and mesa only because it depends on nothing, so a non-relative import under its `src/` fails the build |
| `structure` | an architecture rule broken in this repo's own apps. It runs `packages/cli/core/checks.js`, the same engine `fli check` gives a client app, because two implementations of one rule is how a framework ends up breaking rules it publishes |
| `registers` | an id a register issued twice, a citation pointing at nothing, a ruling nobody named — `packages/cli/core/register-check.js`, the engine behind `fli register:check` |
| `snapshots` | a committed `*.snapshot.*` that no longer matches its source. It carries **no list of what exists**: every snapshot names the command that wrote it in its own header, and that command is rerun with `--check` from the file's own directory, so a new KIND of snapshot costs a generator and never a CI edit. The command comes out of a file in the repo, so it is restricted to a known binary and a shell-free argv, and a snapshot naming no generator fails rather than being skipped. **Discovery alone fails open**, so the expectation comes from the BASE REF — a snapshot tracked where the branch left main and absent now is a failure, because a generated artifact that stops existing takes its check with it in green. A deliberate removal is a named entry under `removedSnapshots` |
| `access` | nothing, by design. **The one phase that reports rather than judges** — *what did this branch do to who may do what*, printed per app against the base ref — because a branch that widens access is usually a branch doing its job, and a red that fires on every feature trains everyone to skip the phase. The gate is `fli test:access --from <ref> --strict`, which belongs on the branch that deploys |
| `coverage` | a package with no `test` script that `exemptPackages` does not name |
| `registry` | a `@frontierjs` package `fli new` writes into an app's `package.json` that npm has never heard of. **It asks the half the register cannot see**: every id there is a statement about the WORKING TREE, and a user's experience is the tree AND the registry, which drift independently. The list is read from `core/app-config.js`, the module `fli new` itself reads. A version gap is a NOTE; an unpublished package is allowed by name under `knownUnpublished`, which fails once it IS published; no network is a named skip that `FJS_CI_REQUIRE_REGISTRY=1` makes fatal. **It also asks whether what a package SHIPS still works**, for the one artifact executed at boot: every `.lite` a published `exports` map offers is unpacked and parsed with the tree's own parser, because `@frontierjs/auth@1.0.3` shipped an argument the language had deleted and no app in this workspace could see it — each one resolves auth to `packages/auth/` and never reads the published bytes (`FJS-921`). The candidate list comes from the REGISTRY's exports rather than from the tree, so it grades exactly what a consumer can import; `knownPublishedSchemas` is the allowance and is keyed `name@version`, so it goes stale on the release that fixes it |
| `advisories` | an advised package **reachable from a PUBLISHED package's runtime `dependencies`**, since that is the set every app installs — walked from each package's own directory and resolved the way node resolves, because bun installs into `.bun/` with symlinks and a path guess reports every advisory as dev-only. A **comparison rather than a scan**: a vitest advisory is not something an app installing this framework can be hurt by. The resolved version is printed beside the advisory's range and **the two are never compared**, because a range parser here would be a security judgement made by a regex. `knownAdvisories` is the named allowance; `FJS_CI_REQUIRE_AUDIT=1` makes a no-network skip fatal |
| `scaffold` | **the phase no suite can replace.** It packs every publishable package, scaffolds an app against the tarballs, installs it, builds it, runs that app's own `bun run check`, then scaffolds a model into it and builds again, asks whether the app NAMES every framework package its own source imports, and finally writes a `site/` surface into it and builds THAT (`scripts/scaffold-build.mjs`) — a second Vite root with its own config, its own entry and its own prerender pass, none of which the SPA build reaches, and every file of which was broken for as long as nothing ran one (`FJS-758`). An app in this repo resolves sierra to `packages/sierra/` and never to a node_modules path, so the code that only runs for an *installed* app runs nowhere else here. It grades each package's `files:` field for free, and **its per-run `--cache-dir` is load-bearing**: bun caches a tarball by name *and* version, so a shared cache serves the previous run's bytes and the phase passes against a broken tree. **The import check is the same hazard through resolution rather than the cache** (`FJS-1048`): the packed `overrides` reach every package — they have to, or the framework packages' dependencies on each other resolve from npm — so bun installs and hoists every publishable package and an app resolves what it never declared, which a real `fli new` does not. Its own control is the COUNT of packages the walk saw, because *nothing is wrong* and *nothing was read* are one answer otherwise |
| `typecheck` | a *raised* baseline (Invariant 14) |
| `deploy` | the pipeline an app actually deploys with, in four parts. `fli new` → `make:deploy` → `deploy:local` **once per package source**, each ending in a **register and login through the prefix the app's own `web/config/sierra.config.js` names**, because a health answer says the process is up and not that the app works. `--source npm` is the only thing here testing the PUBLISHED framework; `--source local` is the working tree containerized, which needs `core/vendor.js` to pack the tree into the build context, since a Docker build can see neither a `link:` spec nor a tarball outside it. The second half is **`deployJournalCycle`, the only thing that runs `fli deploy`** — deploy → deploy → crash → resume → revert, an unbound attachment, a declared configuration key nothing carries, and the build a browser compares against, all against `localhost` as a real deploy machine with real docker, a real journal and a real revert. `core/machine.js` is the one owner of *(host, script) → the argv that runs it there*, and the script travels on **stdin** to `sh -s`, so the same script reaches the same shell with or without an ssh prefix; the only thing it does not exercise is ssh itself. Its sharpest assertion is that an unchanged redeploy mints the SAME Release. The third is `pauseEdgeCycle`, which is seconds rather than minutes and builds no image: the pause guard in front of a real `nginx:alpine`, because a vhost built from a template is a claim about nginx and a test over its TEXT passes against a config nginx refuses — and the file `deploy:setup` writes, loaded verbatim in both shapes (one origin, and `deploy.api.domain` as a second), against an upstream that answers with the path it received, since a URI on `proxy_pass` stripped `/api` from every call for as long as nothing loaded it (`FJS-1100`). The fourth is `pauseQueueCycle`, the other half of a pause (`FJS-D262`): the script `_steps-pause` sends, run against a real Caravan worker in an `oven/bun` container with the source mounted, which is the only place Caravan's bin finds the app's database through `/proc` with nothing narrowing the search, and the only place its answer crosses two shells before the verdict reads it. Full tier only. Without a daemon it reports a named note and passes, and `FJS_CI_REQUIRE_DOCKER=1` turns that skip into a failure, which the workflow sets; `knownDeployFailures` exists for publish order, where the scaffold gives an app a package nobody has published |
| `tutor` | a command renamed out from under a lesson, a scaffold whose default gate moved, an answer the framework changed. It **executes the tutorial** — thirteen lessons, `--tmp --yes`, on test-tier ports, each lesson a command whose every step ends in a probe against the running world rather than an exit code: a port that answers, a table in `sqlite_master`, a row read back out of the file the app wrote, the same POST answered 201 with a token and 401 without. It is the phase for the one document that had no compiler behind it. A port already held is a SKIP rather than a finding, because the lessons refuse a busy port rather than moving to the next one; `knownTutorFailures` is the ratcheting allowance |
| `tests` | a suite. A suite known to fail is named, so a NEW failure is loud |

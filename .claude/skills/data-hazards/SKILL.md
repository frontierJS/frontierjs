# Data-realm live hazards

**Correct behavior you have to know about.** Things that are *wrong* live in `ISSUES.md`, one id each; things that are *fixed* live in `CHANGES.md`. If a rule here is pinned by a test that cannot be deleted quietly, it does not need to be here.

## Schema and parse

- **Two owners decide whether a schema is legal, and the line between them is what CAN be expressed.** The parser refuses what cannot work at all — `@unique`/`@@unique`/`@@index` over a field with no column (a `@computed` in a `@@unique` makes a table SQLite refuses at boot, naming nothing the author wrote), a fractional `@default` on `@scale`/`@money` (an INTEGER of minor units takes `DEFAULT 12.99` and the first defaulted row is refused at runtime), a `@relation` across two `database` blocks (a foreign key resolving nowhere, `no such table` on every create). These are derived from one FACET — *what does the column physically hold* — rather than ruled pair by pair over a hundred-word surface, which is how three of them stayed open while their sibling `@unique` × `@encrypted` had a good message (`FJS-721`); `@generated` is outside the set, being a real column. **What is merely legal and WRONG is `litestone advise`**, whose own contract is that every rule in it parses — `@@fts` over an encrypted column is one of those, and adding it to the parser too made that rule unreachable and broke its own test. Reach for the parser when the schema cannot be built, and for `advise` when it can be built and should not be.
- **A composite `@@unique` naming a NULLABLE column is a parse error, and single-column `@unique` over one is not** (`FJS-D130`). Two NULLs never compare equal, so the tuple index admits `(1, NULL, NULL)` twice while refusing the same pair with values — the constraint holds exactly where nobody doubted it. `@@unique([a, b], nullsDistinct: true)` is how a schema says it meant that, emitting identical DDL. **`@@unique([a], where: <expr>)` is the other answer and usually the one wanted** (`FJS-603`) — *at most one OPEN row per parent*, which is what effective dating is built on, and getting there means moving the nullable column OUT of the tuple and into the predicate. A predicate cannot ride a table constraint, so it emits a standalone `CREATE UNIQUE INDEX … WHERE`, migrates by one DROP and one CREATE, and does NOT make a relation one-to-one. Its literals are inlined, because SQLite prohibits a bound parameter in a partial index predicate. **`@@softDelete`'s clause is not ANDed in**: on a unique index the predicate IS the constraint, so ANDing it would free the slot a deleted row holds. A `@from` correlates on **every** column of its relation's key, in three places, or a join on the first column alone answers a count of real rows to a question nobody asked; a write naming a `@from` field refuses by name.
- **`litestone introspect` output must PARSE, and the property that holds it is a FIXED POINT** (`FJS-594`). It is the adoption door — a database you already have into a `.lite` — and also what `fli db:pull` runs. Reading a database built from the output must give the same output, asserted over the seven corpus schemas and the 188-model `openmrp` fixture. No substring assertion can see what that catches: a SQL expression default emitted as a string LITERAL, whose quotes `ddl.js` doubles on every pass; an `@@index(where:)` re-emitting the clause `createIndexes` ANDs on for `@@softDelete`, nesting a level deeper each time; a **relation field named for the table it points at**, which takes a real COLUMN's name and deletes it, since the parser keeps one field per name; and an **enum name colliding with a MODEL name**, which makes that model's own relations resolve as enums and become TEXT columns. **Anything here that writes `.lite` owes the same property.** The output is graded as well — `src/import/tiers.js` is one table for both converters, `--report` writes the list and `--strict` fails on `changed`.
- **A Litestone client THROWS on an unknown property, and `createClient` refuses an unknown OPTION by name** — never `undefined`, so a typo'd accessor is loud, and a typo'd capability no longer quietly fails to apply (`FJS-579`: `autoMigrate: true` is not an option, does nothing, and was passed by five of litestone's own test files, every one of which opens a fresh database where creating and migrating are the same thing). The refusal comes off a rest capture, so what counts as unknown is whatever the destructure did not bind; `autoMigrate` is answered rather than suggested at, naming `autoMigrate(client)` and why it stays a call. The cost: feature-detection is itself a throwing expression. `typeof db.$maybe === 'function'` explodes; use `'$maybe' in db` or a `try`. A capability that depends only on the schema belongs on **every** flavor of client — root, `$setAuth`, `asSystem`, `$scopedBy`.
- **A relative `database { path }` resolves against the process CWD, and a schema can be told otherwise.** The same schema then means a different file depending on which directory the command was typed in, and nothing fails — SQLite creates the file, litestone creates the directory above it, and every tool reports on the new empty database (`FJS-449`: studio served an empty `db/db/shop.db` for nineteen hours; a `vite build` from a surface root prerendered twelve product pages as **zero products, exit 0**). `resolveFrom: 'schema'` anchors to the APP ROOT — the schema file's directory, or its parent when that directory is `db` — which is what every litestone CLI call site does. **A schema assembled in memory says where it would have lived**: `path:` beside `schema:` when the app read a file and appended to it, or `resolveFrom: '<dir>'` (a directory or a `file:` URL) when there is no file at all, which THROWS on an anchor that is not a directory. `createTenantRegistry` takes `path` the same way, and there it matters twice: `tenancy { dir }` and `tenancy { registry }` are written against the SCHEMA FILE's own directory, not the app root — the one place the two bases differ. An override (`db`, `databases: { … }`) is unaffected and must be: code is written against the process. **The default stays the CWD**, because isolation-by-CWD is a real contract a seed test depends on. **Creating the DIRECTORY for a database is announced** — creating the file is ordinary, the directory is the signal every instance of this had in common, and the message names the cwd because `db/shop.db` from two different directories prints the same string.
- **`@map` renames the COLUMN and nothing a caller touches**, and the write side fails loudly while the read side does not. `fieldToColumnName` is the one owner — the field-level counterpart of `modelToTableName` — and `columnMapFor` holds only the names that DIFFER, so a schema with no `@map` translates on no path. A payload key, a row, a policy's own text, an error message and an index NAME all stay the field's; the index name particularly, because the migrator matches by shape and deriving it from the column would rename every index the day a schema adds a `@map`. **A missed identifier in a WHERE is silent**, and that is the trap: SQLite reads an unknown `"ident"` as a STRING LITERAL, so the clause matches nothing and answers `[]` with a 200 — `@@allow('read', auth().id == ownerId)` compiled against the text `'ownerId'`, and `{ pages: { increment: 5 } }` evaluated `'pages' + 5` and stored 5 (`FJS-761`). An INSERT column list is the loud half. So **anything asserted about a mapped model is asserted as a PAIR against the same schema unmapped**: a mechanism answering `[]` for both spellings passes any test that only asks the mapped one. The read direction is the STATEMENT's, `mappedDb` beside `wideDb` for the same written reason — a count, an aggregate and an existence probe reach a caller without passing either row reader — and it wraps rather than unwraps, so a wide-AND-mapped model keeps both. **An author-written expression is translated by `mapExprCols`** (`@@check`, a compiled `@@index(where:)`), sharing the importer's `mapIdentifiers`, which leaves a word inside `'…'` alone because it is a value. Its mapped identifiers are emitted **bare** where the name allows: SQLite reports an unnamed CHECK by its source text, and one opening with a quoted identifier arrives truncated, which sends every violation on that model to the generic sentence — a column named for a SQL keyword is quoted and does lose the message, the same as an author who quotes their own column.
- **`createClient({ db })` names MAIN's path and nothing else.** It overrides a declared `database main`, so `db: ':memory:'` is the in-memory test client; a SECOND declared database keeps its declared path regardless. `databases: ':memory:'` is the shorthand that moves them all, jsonl and logger included. Precedence: `databases: ':memory:'` > `databases: { main: { path } }` > `db` > the declaration.
- **A scaled column is bounded at 2^53 and a plain `Int` is not.** `Int @scale(n)`/`@money` promise an exact round trip, and the round trip goes through a JS `number` at both ends — `bun:sqlite` answers a `number` on every path, a column read and an aggregate alike, so past 2^53 the rounded double is stored and a DIFFERENT number is read back in silence, two minor-unit values collapsing into one (`FJS-583`). Nine places therefore leaves **seven** figures in front of the point rather than the nine that reasoning from the 64-bit column gives. Both ends refuse it — the boundary by name, in a different sentence from the fraction refusal because they are different mistakes, and the column with a `CHECK`, because a migration, a seed, a raw statement and `asSystem()` never reach the boundary. **The column whose values genuinely go past 2^53 is `Int @big`** (`FJS-D174`): it uses the whole 64 bits and the price is that values cross as a **string of digits**, since a `BigInt` is exact and `JSON.stringify` throws on one — which is every response, every frame and every audit snapshot, and node-postgres answers `int8` the same way. Storage stays `INTEGER`, so ordering, a range filter, an index and `AUTOINCREMENT` are all still numeric. **It emits no `CHECK` and `@scale` does**, which is a measurement rather than an inconsistency: `STRICT` already refuses all three ways a wide value stops being exact, so `@scale`'s bound is the narrower one and only a CHECK can hold it, while `@big`'s IS the column's own. `@@noStrict` is the one shape that earns it. `litestone import` maps a foreign `BIGINT` onto it, keys and foreign keys exempt. **`@scale` stops at 9 and `FJS-575` closed rather than raising it** (`FJS-D154`): a precise accumulated total fits no 64-bit integer at any scale and belongs to rounding and allocation.

## Soft delete and `@unique`

- **A drive that cleans up through the API cannot free a `@unique` on a soft-deleting model, so a fixed fixture key makes it single-use** (`FJS-530`, `FJS-546`, `FJS-547`). A DELETE over HTTP soft-deletes, the kept row still holds the value, and the next run's create is a 409 the drive does not check — so the id is `undefined` and the failure surfaces three steps downstream, in a drive that passes once per seed. **Two ways out and they are not interchangeable.** Mint the key per run — and check the two things that bite that fix: a `@upper` column stores a lowercase id uppercased, so a later search for it silently misses, and `@length(3, 20)` refuses a prefix plus a run id. Or RELEASE the value in the sweep, which is what to reach for when the drive's own expectations name the literal: read with `?$withDeleted=true`, `PATCH /{service}/{id}?$withDeleted=true` the reference aside, and delete only a row that is still live — a second DELETE is a no-op against something already gone.
- **A soft-deleted row keeps its `@unique` values, and `restore()` is why.** Freeing the slot would make `@unique` false for every read that includes deleted rows — `findUnique(withDeleted)` legitimately matching two — and would make the way back fail whenever a stranger took the value first. So a write naming a value a deleted row holds is refused by name (`SoftDeletedUniqueError`, 409) rather than by SQLite, and releasing a slot is a decision the app makes: `update({ …, withDeleted: true })` moves the value, `delete({ …, withDeleted: true })` stops keeping the row. **A LIVE holder is the other half and it is a different error** — `UniqueConflictError`, also 409, naming the field with the value redacted where the column is protected, and carrying `errors` so a form marks the box rather than showing a banner. Two classes because the ways out differ: restore-or-release, against send another value. Every create AND update path translates, since SQLite's own sentence names a physical table and reaches nobody (`FJS-441`). Membership is spelled `@@allow('read', auth().id in memberIds)`, the list always the RIGHT operand, so an audience held on the row does not have to become a service where-clause.
- **A soft-deleted parent's children have THREE fates and each has a spelling.** `@@softDelete(cascade)` stamps them, `@hardDelete` on the relation field destroys them, and **`@keep` leaves them live on purpose** — which is what a plain `@@softDelete` already does, and the parser warns about it because forgetting the cascade and meaning it look identical. *The customer goes, the receipts stay* is that shape and it is not rare: `example`'s `Customer.orders` is `@keep`, and without it removing a customer either destroys every order they placed (`onDelete: Cascade`) or hides them, neither of which is what a shop means. It covers the whole subtree beneath that child, and says nothing about removing the child directly. The warning names all three ways out, so the third is discoverable from the thing that complains about it.
- **A per-call flag the model cannot SATISFY is refused by name, and so is a method.** `onlyDeleted` on a model with no `@@softDelete` used to answer the LIVE rows — the opposite of the question, with nothing saying the flag had not applied — and `search()` below `@@fts` threw a bare `Error` that reached a caller as a 500. Both are `CapabilityNotDeclaredError` now: **400**, naming the model and the attribute that would make the request legal — `onlyDeleted`/`onlyTemplates` on every read and write, plus `search()`, `optimizeFts()`, `restore()` and `transition()`. **`withDeleted`/`withTemplates` do not refuse**: they ask to widen, and a model that hides nothing already answers everything, which is what generic tooling (Studio's row browser, a *show deleted* toggle) is asking for.

## Gates, policies and claims

- **`auth().x` is graded against a DECLARED set, and only where there is one** (`FJS-666`, `FJS-667`, `FJS-668`). An absent claim is `NULL`, so `NOT (NULL = 1)` excludes EVERY caller while the create path's `null === true` excludes none: one misspelling is a lockout on read and an open door on create, and the side that refuses reads exactly like a policy doing its job. The set has **four sources** — the eight names litestone reads itself (`id`, `capabilities`, and the six `FrontierGateGetLevel` grades a caller by, none of which is a column), the `@@auth` model's own columns, the `tenancy { claim }`, and **`createClient({ claims: [...] })`** for a claim resolved per request, which is on no row and in no schema. That last is a client option rather than a `.lite` keyword because junction already declares the list and generates `principal.snapshot.md` § Claims from the resolver's own `describe()` (`FJS-D181`). **A schema with no `@@auth` and no `claims:` is ungraded and says so**, once per distinct set of names; `claims: []` is a statement where absent is silence. **A field-level `@allow` runs the same walk**, and a typo there fails CLOSED, stripping the column from every row, so the schema, the build and every assertion on the refused side agree with the mistake. **An absent claim means one thing rather than two**: `evalJs` propagates NULL the way SQLite does, an `@@allow` holds only on TRUE and an `@@deny` fires on TRUE and UNKNOWN alike. `x == null` keeps its own branch and answers a boolean, because that is how this language spells `IS NULL`.
- **A `@@gate` refuses, a `@@allow` filters — so a wrong policy is an empty screen, not an error.** The two rules underneath, and the order every layer reads in, are `packages/litestone/docs/access-control.md` § *Combining them*: **a refusal must never confirm a row exists** (which is why create is the one policy that throws — the payload IS the row), and **whose mistake is it** — `@guarded`/`@system` throw because no caller was ever meant to send that column, a field `@allow('write')` drops because the same form body is legitimate one level up. A gate throws naming the model and the level; a policy compiles silently into the WHERE. Every read that legitimately crosses a policy's scope must be `asSystem()`, or it returns nothing with a 200. Declare one model at a time and run the app's drive between them. **`fli test:access` writes the whole declared surface to a committed `db/access.snapshot.md`** — gates, policy predicates, protected fields, and per declared move its gate AND its `@system`, which stay separate columns because they compose: `@system @gate(5)` is both, and folding one into the other renders the widest narrowing a state machine can express identically to an ungated move (`FJS-613`). The `snapshots` CI phase fails a stale one, so a gate that moved is a diff rather than a production refusal. **`--from <ref>` asks the other question and writes nothing**: what this branch did to who may do what, graded `widens` / `narrows` / `undecidable` / `new`. It is not `release:check` with a different word — *can N-1 still serve* and *who may now do more* disagree by construction, and a removed `@@gate` is an expand and the widest change there is. A predicate whose text moved is reported rather than guessed, and an allow→deny inversion is the same answer for the same reason (`FJS-D131`). `--strict` is the gate; the `access` CI phase only prints.
- **A freeze that depends on STATE is not expressible, and `@@gate` is where you notice.** A gate is per MODEL, so *a payslip under a draft run may be removed and one under a paid run may not* has nowhere to live: `example`'s `Payslip` had `9` on delete, which made `revert: calculated -> draft` strand its own payslips and collide on the next calculation, and `8` lets the system remove one and says nothing about when. The rule ends up in application code beside the aggregate ones — `revertPayRun` reads the PARENT's state before touching a child, which is a different shape from *the lines sum to the total* and is worth counting separately when the cross-row spelling is ruled (`FJS-D162`'s open DELETE question, met from a direction it did not anticipate).
- **`asSystem()` grades at 8, and `9` is LOCKED — not reachable through the ORM by any client.** So `@@gate("…9")` on a write is not *only the application may* — it is *nothing may*, the system context included, and a module that posts through `asSystem()` gets an `AccessDeniedError` naming the model and `required: 9, got: 8`. The two are a real pair rather than a fencepost: `8` is *the application acting on its own behalf* and `9` is *there is no code path at all*, which is what makes an append-only table declarable — `example`'s `JournalEntry` is `@@gate("5.8.9.9")`, read by staff, posted by `api/src/domain/ledger.ts`, amended by nothing. Reading the ladder does not separate them; writing `9` where `8` was meant produces a table that migrates, snapshots and passes every check, and refuses the first write the application makes.
- **A cache keyed on the ctx OBJECT is shared across principals** (`FJS-722`). One table object per model serves every flavor of client, so the ctx its method bodies close over is a single object with `auth`, `isSystem`, `scopedBy` and `tables` as getters over the call in progress. Three caches predated that and were keyed on the ctx because the ctx used to BE per flavor — the gate plugin's level resolver, external-ref's stash, the hoisted field-read answer — and each then answered the first caller's value to everybody. **The gate one is the shape to fear**: an `isSystemAdmin` reader graded at whatever level the process saw first, which is a wrong ANSWER and not an error. Key on `ctx._flavor ?? ctx`, and write to the flavor rather than onto the ctx. **Reading one of those four outside a call THROWS** — falling back to the unscoped root would let an escaped read run as nobody and answer `[]` with a 200 — and it is not junction's ENDED marker: AsyncLocalStorage propagates into anything scheduled inside a call, so what it catches is a stored ctx read later.
- **You cannot run without gates.** A schema declaring any `@@gate` auto-installs `GatePlugin({ getLevel: FrontierGateGetLevel })` — a declared-but-unenforced gate is fail-open. Installing your own replaces it; installing none does not disable it. Contract: **absent = the app does not model this stage; only `null` grades down**, and standing (`isSystemAdmin`/`isOwner`/`isAdmin`) is checked before the lifecycle. **`role` is the exception and is read for PRESENCE** — no role is CREATOR(3), any role is USER(4), because the ladder cannot rank what an app puts in that column; `@frontierjs/auth`'s `User` defaults it, so a stock app grades USER and this branch is reached by a session some other path built. The scale, the comparison and the grader are all `@frontierjs/toolbelt/gate` — junction's `sessionGateLevel` and sierra's `canAtLevel` are the same bindings, after four hand copies drifted (`FJS-D197`).
- **`$setAuth(user)` RETURNS a scoped client, it does not mutate.** `db.$setAuth(u)` then `db.thing.create(…)` grades as anonymous, with no warning. It is `const userDb = db.$setAuth(u)`.
- **A CAPABILITY is a grid beside the ladder, and a finer grant REPLACES the coarse one rather than adding to it** (`FJS-D146`). `@@capabilities` on a model grades its writes and its named moves (`(all)` adds read); `@capability` on a column grades that column's write; both are ANDed with the `@@gate`, which stays the floor. What makes the fine tiers worth having is what an update's payload is partitioned BY: a key carrying `@capability` is graded by that column's grant, a key that is the transitions field is graded by the MOVE it resolves to, and everything else is what `Model.update` is for — so `Environment.variables` can be handed to somebody who holds no other edit on the environment, and `Server.reboot` alone reboots. **A CREATE keeps both**, since `Model.create` is the grant for the row existing at all. **A move the ENGINE makes is nobody's grant** — `@system`, or a gate of 8 or 9 — so it is out of the derived set and out of any picker, and is refused AS `@system` rather than as a missing grant that would not have helped. **A verifier hands its synthetic caller every declared capability** (`atLevel`, `verifyRowPolicies`, `verifyTenantIsolation`), or a policy that filters correctly is reported as *the call threw*, which is true and is about the grid (`FJS-351`). **The caller's set is `auth().capabilities`** (`FJS-D151`) — one name the framework fixes rather than the app, because litestone's grid reads it; what an app chooses is which COLUMN it comes out of, and under tenancy that column is on the membership row, so the same person holds a different set per tenant (`FJS-D149`). **A `Capability[]` column carries its own escalation guard** — subset, never a rank — and that guard is undefined under `asSystem()`, which has no principal: an app whose membership writes go through one still needs the rule said in a hook, and needs BOTH axes there, since two roles can hold the same grid and differ on the ladder.
- **`asSystem()` does not bypass a `@check`, a `@@check` or an `@@arc`, and it bypasses everything else.** The gate, every row policy, `@guarded`, `@system` and every field `@allow` are this package's rules and the system client drops all of them (`FJS-519`); a CHECK is in the TABLE, so SQLite refuses a system write exactly as it refuses anybody's. That is the reason to reach for one: a rule that must hold against a job on `db.`, a migration, a seed and `fli tinker` cannot be declared any other way — a validator runs here and a service hook is not on the path. The cost is the other side of the same fact: it cannot be evaluated in a browser, so it arrives as a refusal rather than as an affordance, and the refusal is a `ValidationError` (400) whose sentence comes from the attribute's own message argument — without one the person reads `is not valid` and the expression goes to `err.constraint`. `packages/litestone/docs/schema.md` § Constraints the database enforces. **`@@arc([orderId, productId])` is the third and the one with a shape rather than an expression** — several optional foreign keys of which exactly one is set, which is *this row points at an Order OR a Product* keeping a real FK, a real cascade and a real `include`, where the polymorphic `subjectType`/`subjectId` pair keeps none of the three and needs a job to sweep what the database will not. Adding one is a **contract** for `release:check`, like any row invariant. One column per member and it stops scaling around six — the signal that the target set is OPEN, which is the case no relation can serve and the one `FJS-D189` refuses rather than solves (`IDEAS/polymorphic-relations.md` prices the real thing: 69 single-valued `.targetModel` reads are the cheap half, and the expensive half is that `policy.js` compiles the TARGET's own policy into a subquery, so N targets is N gates and a caller who reads one model and not another sees half a list as a 200).
- **Raw SQL requires `asSystem()` once a schema declares access rules.** `db.sql` and `db.$setAuth(u).sql` throw; `db.asSystem().sql` is the bypass, and it can write. Raw statements enforce no `@@gate`/`@@allow`/`@guarded`/`@scoped`/`@@softDelete`. Coarse per schema on purpose — deciding per statement means parsing it, and a wrong validator grants a *false* guarantee. `where: { $raw: sql\`…\` }` keeps every policy and is the hatch to reach for. A JS migration is exempt: the runner hands it the system client.
- **A field `@allow` is a PREDICATE and it is compiled into SQL, both ways** (`FJS-D129`). Not a strip and not a JS check against the payload, because both of those were holes. A READ predicate is AND-ed into the caller's arguments as a **sibling** of their `where` — sibling, because a conjunct inside it is complemented by their own `NOT` — so a column they may not read cannot be filtered or sorted on, and a value that used to come back by binary search in seventeen requests comes back as nothing. A row-dependent one therefore narrows to the rows it admits rather than refusing, which is the case the feature exists for; the cost is that an `OR` branch naming the column narrows the whole read. A WRITE predicate is the WHEN of `SET col = CASE WHEN … THEN ? ELSE col END`, so it reads the STORED row — grading it against the payload lets a caller write a column on somebody else's row by stating `ownerId: me` in the same payload. **CREATE is the exception and keeps the JS evaluation**: there is no stored row and the payload IS the row. Through a relation both refuse by name.
- **`@guarded` is not a level** — a system-context lock taking only `(all)`; `@guarded(5)` does not parse. Per-role column access is field-level `@allow('read', auth().role == 'admin')`. It locks **both directions**: a non-system write naming a guarded column is refused with an `AccessDeniedError` naming the field, where it used to land silently while the read strip made it look refused. `@encrypted` alone is not a guard — it hides a value from a reader and stays writable, which is what a caller submitting a secret needs. The two are not exclusive — `@secret` expands into exactly `@encrypted @guarded` — but writing both by hand is `@secret` spelled out, and the choice worth making is which ONE you want: `@allow('write', …)` for a column some callers may set, `@guarded` for one only `asSystem()` touches. A **required** `@guarded` column makes its model uncreatable below level 8.
- **A column your `getLevel` reads must not be writable by the caller being graded.** A gate is per MODEL, so `@@gate("4.4.4.5")` on an identity table says *any signed-in caller may write any other person's row* — `role`, `isAdmin`, a status, whatever the ladder is graded from. `@frontierjs/auth`'s `User` ships the shape: a level for what kind of caller, `@@allow('update', id == auth().id || auth().isAdmin)` for whose row, `@allow('write', auth().isAdmin)` for which columns. **`8` is not a stronger `5`** — it means nothing outside `asSystem()` has anything to say to this model, which is true of credential material and false of the table an app's own screens list; raising the gate just moves the surface into the bypass. `DECISIONS.md` § Access control.
- **A `9`-gated table cannot be tidied up, by anything** — `asSystem()` grades 8, so a test or a drive that writes to an append-only model cannot remove its own fixtures through any client, and every row held by a foreign key from one is stuck with it. `example`'s `verify:retro` is the case: leaving the rows was not an option either, because a backdated employee goes on producing arrears and `verify:payrun` sweeps every employee there is. The way out is `asSystem().sql`, which enforces no gate and no policy and binds to TABLE names — worth budgeting for when a `9` goes on a model a fixture writes to.

## `@@transitions`

- **A BULK write may not name a transitions field** (`FJS-D182`). `updateMany` matches rows with a WHERE and never reads them, so there is no `from` to grade — and skipping that check took the whole ladder with it: a `@gate(5)` move, a `@system` move and a move the schema does not declare were each allowed through it (`FJS-671`). Not reachable over HTTP, since junction's `bulkByRow` selects its targets and writes them one at a time through `update()`; what is reachable is a hand-written service, job or script. The refusal is the **KEY and not the verb** — `BulkTransitionError`, **400** rather than 403, because no level and no grant answers it, the verb is wrong rather than the caller — and `upsertMany`'s `update:` half refuses with it while its insert half, being a create with no from-state, does not. **Every other column stays bulk-writable in the same call.** `asSystem()` still writes it and says so, because `update()` announces its bypass through `emitTransitionEvent` and a bulk write reaches none.
- **A move asked for BY NAME is not the same question as an update carrying the column** (`FJS-611`). `transition(id, name)` desugars into `update()`, and carrying the value a row ALREADY holds is legitimate there, because a form round-trips the whole row — so the check returned early and enforced nothing. Asked for by NAME the same row state means the opposite: the move did not happen here. The early return took the gate, the capability and `@system` with it. The compare-and-swap was never the missing half — the UPDATE has always carried `AND status = <from>` — and `$transaction` made it WORSE, since serializing the callers means each re-reads after the winner committed, which is precisely the state the early return called a no-op. A move onto the state the row already holds is a `TransitionConflictError` carrying `actual` and `retryable: false`, where losing a race to a DIFFERENT move stays `retryable: true`: two opposite races under one class, and `isStaleWrite()` reads the flag. **The caller is graded before the row's state** — a gate is about the caller and the declared move, so somebody who could never make it is told that rather than being told where the row is. That ordering applies to a named move and to nothing else: an ordinary update matching no `(from, to)` pair has identified no move, so **naming the move is what makes its gate askable**. `asSystem()` bypasses all of it, so a job moving a row through one is still guarded by its own read.

## `@immutable` and encryption

- **`@immutable` is a column written once, and `asSystem()` cannot drop it either.** It refuses the KEY rather than comparing the value — the same number sent back is refused too — because nothing in the language can see the stored row beside the incoming one, and a form that round-trips a frozen column is one that would have overwritten it the day somebody changed the box. So it reaches the client as `readOnly` **in the update schema alone**: the one column kind whose answer differs by mode, since a create form must still offer the box. It is what a DOCUMENT is (`FJS-D162`) — an invoice's number, the instant it was issued, the total it was issued for — and the correction is a new row beside it. It says nothing about DELETE and nothing about the row: to freeze a row when it reaches a state, freeze its columns and let `@@transitions` own the state column. Refused at parse beside `@version` and `@updatedAt`, which the engine writes on every update.
- **A stored value names the KEY that wrote it** (`FJS-D183`). The envelope is `v2.<kid>.<payload>`, the kid a domain-separated HMAC of the key truncated to eight hex characters — it identifies a key without being one, so it is safe in a column, a log line and an error. `$rotateKey` runs **one transaction per DATABASE**, so a crash between two commits leaves each database saying which key wrote it and the rotation resumable. **An unknown kid still tries the ring**: GCM's tag is the authority and the kid is only the ORDER. `createClient({ previousEncryptionKeys })` is read-only, the old key STAYS on the ring after a rotation, and re-running one finishes it. **A half-rotated schema is not supported**, and that is a consequence rather than a limit: a deterministic encoding is a function of the key, the operand is widened across the whole ring at all four spellings of equality, and every equality filter over a not-yet-rotated row would answer nothing. **A caller may not send a ciphertext-shaped value** (`FJS-715`) — the same check gates the HASH path, so a `v1.`-shaped value used to skip hashing entirely. **A decrypt that fails is RAISED** (`FJS-716`), naming the kid wanted and the kids held; the one column that still degrades is `@secret(rotate: false)`, because that loss is declared and raising would make the whole row unreadable to punish a column the app already gave up.

## Tenancy

- **Under `strategy database` four seams belong to the tenant path rather than the single-client path.** A session is verified at the TRANSPORT, before any hook — so `IAuth.verifySession(token, from?)` carries the request's host and headers, which is the only way an app whose people live per tenant can authenticate anybody (`FJS-487`). A raw route (`app.get`/`app.post`) runs inside the request scope, so `requestMeta()` works inside `/auth/login` and inside a webhook (`FJS-488`). `announceDataWrites` taps each TENANT's client on first open rather than one app-wide client (`FJS-489`). And the per-request principal resolver runs for an ANONYMOUS caller, exactly as `withLitestoneDb` does — a claim is what a caller with no session carries, and skipping them makes every guest basket a 404 (`FJS-490`). A `jsonl`/`logger` database stays schema-global and is written by every tenant's client, so its index is idempotent by primary key (`FJS-491`).
- **Tenancy is declared in the seed and there are two strategies.** `tenancy { }` at the top of `schema.lite` — `strategy database` is one SQLite file per tenant plus a registry that indexes them, `strategy row` is one database and a tenant column. Every reader asks one resolution (`db.$tenancy` / `registry.tenancy` / `resolveTenancy`), and precedence is **option → declaration → default**, which is what stops `litestone tenant create` and the running app disagreeing about where a tenant lives. **Row tenancy desugars into `@@deny`, never `@@allow`** — allows are OR'd within an operation, so an allow would widen every read to the whole tenant — plus a `@default(auth().<claim>)` stamp, and it is two rules because `checkCreatePolicy` runs BEFORE the stamp: an absent column is legitimate on create and belongs to nobody on read. A model with no tenant column is reported by name at parse; `@@tenant(none)` says it spans tenants on purpose. `asSystem()` is the only way across, which is what a cross-tenant tier is built on. `packages/litestone/docs/multi-tenancy.md`.

## Migrations and release

- **A schema change is a deploy question before it is a migration**, and `fli release:check` is the one that asks it: can the release still serving and the release starting share one database? Expand — N-1 keeps working, so the deploy can be taken back. Contract — it cannot, and that deploy is the **pivot**, after which only forward. Unknown counts as contract. `db/release.snapshot.md` is the surface it diffs, `--from <ref>` is the question a deploy asks, `--strict` fails a branch on anything but expand *including no baseline at all*. **Access is in the comparison, which is the half no generic deployer can reach**: raising a `@@gate` takes reads away from a release still serving them, and adding an `@@allow` empties a screen with a 200. A required column with no default is the one contract handed back as a plan — expand, backfill, contract — rather than a refusal.
- **The migration differ compares an ENUMERATED list of dimensions, so *in sync* means *in sync on every dimension it reads*.** Six issues of litestone's history are one dimension arriving in the DDL emitter and not in `diffSchemas` — generated columns, CHECK, table uniques, index order, index sorts, index predicates — each reading as a green tick over a database that is not the declared one. There is a catch-all under it (`FJS-D186`): once the enumeration has spoken, the two `sqlite_master`s are compared whole and the leftovers are `diff.residue`, announced by `autoMigrate` and printed by `db push` and `db diff`. It is **not part of `hasChanges`**, because nothing there can write a migration for a dimension it cannot see and a change that never resolves would migrate on every boot for ever; and it does not block, because the commonest cause is the **adoption door** rather than a defect — a real database has a `COLLATE NOCASE` on its email column or a hand-written index, which this language cannot say. `{ acceptResidue: true }` is the caller stating it, beside the `acceptDataLoss` it is modeled on, and it clears the record rather than filtering the output. **Adding the missing dimension is what makes it go quiet**: a residue is a question about the differ, and the answer is usually a comparison it is not making yet.
- **A new column with an EXPRESSION default costs a table rebuild, and one with no default at all is refused.** SQLite takes an expression default in `CREATE TABLE` and refuses one in `ALTER TABLE ADD COLUMN`, where it wants a constant — so `@default(now())` on a new column is a rebuild, and a rebuild is itself refused where the app made its own index or trigger over that table, which has to be moved into the schema first. A `NOT NULL` column with no default is **blocked whether or not the table holds rows**, deliberately: migrating an empty table and refusing a populated one migrates on every developer's machine and blocks at the deploy. `autoMigrate` answers `{ state: 'blocked', reason }` and prints it — it used to answer `migrated` with the reason inside a SQL comment, so the app ran against a table missing a column its own seed declares and every write of it was silently stripped (`FJS-604`, `FJS-605`).

## Columns and clocks

- **Litestone emits columns verbatim camelCase and `DateTime` as ISO-8601 TEXT.** Hand-written SQL assuming snake_case or epoch-ms will not match.
- **Every timestamp litestone writes comes from the CLIENT's clock, and a raw `UPDATE` therefore stamps nothing.** `@default(now())`, `@updatedAt` on create and on update, `@@softDelete`'s stamp, `now()` in a policy and the retention cutoff all read `createClient({ now })` — which is what makes `advance('100d')` then `$retain()` a test anybody can write. **`@updatedAt` is not a trigger** (`FJS-531`): a trigger reads SQLite's clock and nothing else, so a frozen clock cannot be staged — and RETURNING is evaluated before an AFTER trigger anyway, so naming the column in the SET clause only ever helped while the two values differed (`FJS-396`). The column DEFAULT stays as the floor, so a raw INSERT still stamps; a hand-written UPDATE owns its own. What no clock reaches is a raw statement and a `@derived` expression reading `now()`, which is compiled once at startup.

## The audit trail and the log

- **An audit row says WHERE the write came from, and junction is what tells it.** `correlationId` · `source` (the call, `orders.pay`) · `origin` · `ip` · `userAgent` · `tenant`, filled from `db.$logContext(fn)` — a function the client is handed and calls when it builds an entry, the same shape as `now` and for the same reason. The direction is forced: litestone must not learn that a request exists (Invariant 1), so junction installs a closure over its own store, in `createApp({ db })` and on the per-tenant tap. A throw in it costs the columns and never the write. `correlationId` is the one no audit package in the field carries and it is the join `$.log` exists for on the other side; `source` stands where laravel-auditing puts `url`, because the same write arrives over HTTP, over a socket frame with no URL, and from a job with no request at all. **`db.$logStats()`** answers `{ written, dropped, lastError, lastWrittenAt, lastDroppedAt, lastRetainAt }` and junction puts it on `/metrics` as `audit`, because `fireLog` is fire-and-forget and a trail that stopped recording reads exactly like an app doing no work.
- **A `driver logger` trail is written by every process, and the index database's write transaction is what serialises them** (`FJS-D180`). A byte offset cannot be computed before an append or recovered after it — `statSync(f).size` then `appendFileSync` is two syscalls — so `create`/`createMany` hold `BEGIN IMMEDIATE` on the companion index across the pair, and the index row naming the offset commits with it. A transaction rather than a lockfile, because a lockfile has no answer for a writer that dies holding it. **The sidecar is in WAL and compaction must never unlink it**: an unlink leaves `-wal`/`-shm` behind and a live process's next write then answers `ok` while writing into an inode with no directory entry, where a rollback journal answers `SQLITE_READONLY_DBMOVED` — WAL turns a crash into a lie, so the two are one decision. **Compaction holds the same lock across its READ**, not just its write-back: locking the write alone leaves the window and widens it, because compaction then waits while the writer appends. So an append waits for a compaction, which is the correct trade — the alternative is a destroyed audit row. `packages/litestone/src/drivers/jsonl-index.js` is the one owner.
- **An audit row names the TABLE, not the model** — `model: 'pay_window'` for `model PayWindow`, where every other name that crosses a boundary is the model's. So `auditLogs.findMany({ where: { model: 'payWindow' } })` is a 200 with no rows, which reads as *this model is not logged* and is indistinguishable from a missing `@@log(audit)`. `before` and `after` are JSON STRINGS and `records` is a stringified array of ids, so nothing in a JSONL trail joins to anything: it is a record and not a dimension. **`@@log` may name a SQLite database instead**, which is what makes it one — `database main { … model AuditRow }` with `model` REQUIRED there (there is nothing to synthesise into, and a table the app never declared carries no gate, no policy, no index and no migration). A declared trail is an ordinary model: its `Json` columns come back parsed, it joins to `User`, a row policy scopes it, a cursor pages it, litestream replicates it, and `@@gate("5.8.9.9")` makes it append-only at the Data boundary — the engine's own write still lands, because it goes through a system context at 8. Writing `9` for create instead gives a trail that migrates, snapshots, passes every check and refuses the first row the engine writes.
- **An effective-dated write BACKWARDS overwrites the prior belief, and only the log holds it.** A window is closed by moving `effectiveTo`, so backdating a correction moves it to an earlier instant in place — after which the row cannot say what it once ran on, and an as-at read at a PAST date answers differently than it did before. That is correct, and it is the opposite of what a forward raise does, which is why the two are worth knowing together: `effectiveFrom`/`effectiveTo` holds VALID time and nothing holds *when we learnt it*, so **anything that must reprint as it was issued has to have FROZEN it** — `example`'s `Payslip` names the `PayWindow` it was computed under and copies every figure, which is the only reason a backdate cannot reprint history. A report that re-derives from the terms table instead is correct until the first correction and wrong silently afterwards (`example`: `verify:retro`).
- **`@@log(audit)` records a WRITE; `db.$audit()` records an EVENT — and the second one throws.** A sign-in is not a write to `User`, and a *failed* one is not a write at all, so nothing the logger can see names the actor or the attempt. `$audit({ operation, model?, records?, actorId?, meta? })` is the one way to put a row there by hand — an unknown key is refused by name, `actorId` defaults to the calling client's principal (a system context has none), and a stated value beats `onLog`'s. **It awaits and throws where `fireLog` is fire-and-forget**, because there the record is a side effect of a write that already succeeded and here it is the point. `meta` is NOT redacted — it is yours, so do not put a secret in it. On every flavor of client.

## Reads and windows

- **A `where` refusal is a `ValidationError` — including an operator that does not exist** (`FJS-892`). `$checkWhere` grades the KEY (`?statuz=paid` is a 400 naming the field with a did-you-mean) and the compiler grades the OPERATOR; the second was a bare `Error` and therefore a **500 blaming the server**, on a fully modelled service as readily as a modelless one. The message names the valid operators off `WHERE_OPS` — the set the typed-JSON walk already reads, asserted equal to `buildWhere`'s cases, so an operator added to one and not the other fails rather than producing a refusal that omits a real answer. **Still not refused: a text operator on a NUMBER.** `TEXT_OP_REFUSALS` covers array/json/file/boolean, so `contains` on an `Int` substring-matches the number's text.

- **A modelless service's filters cannot be graded and do not need to be.** There is no schema, by construction. What protects the only dangerous shape is that a query handed to litestone is graded BY litestone — a typo'd column is a 400, not a wide read — so the ungraded half is the author reading keys in their own code. All four modelless services in this repo (`hub`, `portal`, `infra`, `shopfront`) read `ctx.query` on no path.

- **An `include` is a SEPARATE statement, and `$tapQuery` reports it as one** (`FJS-891`). Includes are batched — `WHERE fk IN (…)`, never N+1 — so a hundred-row populate is two statements and a nested or sibling pair is three, arriving as `include` / `include:count` events naming the relation TARGET as `model` and that target's own `database`. Before that they were reported nowhere: `fireQuery` runs BEFORE `withIncludes`, so neither the count nor the parent's `duration` covered them, and telemetry read a populate as one statement. **The vocabulary is closed in the GENERATED type**, so a new `operation` costs a row in `index.d.ts` and in `typegen.js` — `test/query-tap.test.ts` greps the call sites and fails on one that is emitted and not declared, which is how four operations the client had always emitted (`aggregate`, `exists`, `groupBy`, `upsert`) turned out to be missing from it. **Anything measuring statements must count EXECUTIONS**: a statement is cached after its first prepare, so instrumenting `prepare` after a seed has run misses every SQL already compiled and undercounts.

- **A cursor and an offset never combine, and `$after` wins.** A caller sending both has named no position either one of them means. Growing a window is also not a chance to ask a different question — `more()` reuses the last `load()`'s query and directives, because a cursor minted under one ordering names no position in another, so a new filter or a new sort is a `load()`. And **a list is a set of ids in an order**: one row cannot be in it twice, which is what stops a row that arrived on the socket mid-scan from being in both the list and the next slice.
  - **A cursor is caller-supplied text and is GRADED against the ordering using it** (`FJS-779`). The columns compared come from the server's own `orderBy`, so only the VALUES are read out of the token — which is why there is no signature and why adding one would buy nothing. What that leaves is a token whose keys are for another sort: ungraded, every value read `undefined`, bound NULL, and the list answered **0 rows with a 200**, while `null` answered the whole table by paging from the start. `decodeCursor(token, fields)` compares against the key set `cursorFields` computed for this query — the same function `cursorFor` minted it with — and refuses with a `ValidationError` on `['$after']`, a 400. **`fields` includes the tiebreaker litestone appended**, so a cursor hand-built out of the caller's own `orderBy` is correctly not one this list mints.
  - **A sort key carries WHERE ITS NULLS SIT, and a cursor compares against that** (`FJS-780`). `"col" > NULL` is NULL and matches nothing, so a window over a nullable column used to serve the null rows and then stop — `hasMore: true`, then an empty page, both 200. Each field contributes an EQUAL and an AFTER predicate now, read against SQLite's own positions (first ascending, last descending, measured) or whatever `orderBy` stated. **`nulls` has to survive every hop**: `normaliseOrderBy` dropped it, `findManyCursor`'s ORDER BY dropped it where `findMany` emitted it, and `orderTotal` dropped it on the way back to junction — so the scan walked one arrangement and the cursor was compared against another. **`nullable` is on the field for a reason**: the NULL-aware form costs an `OR`, which is what stops SQLite using the index a keyset scan exists for, so a `NOT NULL` column compiles exactly what it always did.
  - **`buildCursorWhere` never answers `''` when it was given a cursor.** An empty string reaches the caller as *no cursor clause*, which is the whole table from the start — the shape a `null` token used to take. A position nothing can follow answers `0`.

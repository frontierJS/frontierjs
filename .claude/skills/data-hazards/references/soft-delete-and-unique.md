# Soft delete and `@unique`

The full entries behind this section of the `data-hazards` skill's index.

- **A drive that cleans up through the API cannot free a `@unique` on a soft-deleting model, so a fixed fixture key makes it single-use** (`FJS-530`, `FJS-546`, `FJS-547`). A DELETE over HTTP soft-deletes, the kept row still holds the value, and the next run's create is a 409 the drive does not check — so the id is `undefined` and the failure surfaces three steps downstream, in a drive that passes once per seed. **Two ways out and they are not interchangeable.** Mint the key per run — and check the two things that bite that fix: a `@upper` column stores a lowercase id uppercased, so a later search for it silently misses, and `@length(3, 20)` refuses a prefix plus a run id. Or RELEASE the value in the sweep, when the drive's own expectations name the literal: read with `?$withDeleted=true`, `PATCH /{service}/{id}?$withDeleted=true` the reference aside, and delete only a row that is still live — a second DELETE is a no-op against something already gone.
- **A soft-deleted row keeps its `@unique` values, and `restore()` is why.** Freeing the slot would make `@unique` false for every read that includes deleted rows and would make the way back fail whenever a stranger took the value first (`FJS-D65`). So a write naming a value a deleted row holds is refused by name (`SoftDeletedUniqueError`, 409) rather than by SQLite, and releasing a slot is a decision the app makes: `update({ …, withDeleted: true })` moves the value, `delete({ …, withDeleted: true })` stops keeping the row. **A LIVE holder is the other half and it is a different error** — `UniqueConflictError`, also 409, naming the field with the value redacted where the column is protected, and carrying `errors` so a form marks the box rather than showing a banner. Two classes because the ways out differ: restore-or-release, against send another value. Every create AND update path translates, since SQLite's own sentence names a physical table and reaches nobody (`FJS-441`). Membership is spelled `@@allow('read', auth().id in memberIds)`, the list always the RIGHT operand, so an audience held on the row does not have to become a service where-clause. Ruled: `FJS-D424`.
- **A soft-deleted parent's children have THREE fates and each has a spelling.** `@@softDelete(cascade)` stamps them, `@hardDelete` on the relation field destroys them, and **`@keep` leaves them live on purpose** — which is what a plain `@@softDelete` already does, and the parser warns about it because forgetting the cascade and meaning it look identical. *The customer goes, the receipts stay* is that shape: `example`'s `Customer.orders` is `@keep`, where `onDelete: Cascade` would destroy every order and a cascade would hide them. It covers the whole subtree beneath that child, and says nothing about removing the child directly. The warning names all three ways out.
- **A per-call flag the model cannot SATISFY is refused by name, and so is a method.** It is `CapabilityNotDeclaredError`: **400**, naming the model and the attribute that would make the request legal — `onlyDeleted`/`onlyTemplates` on every read and write, plus `search()`, `optimizeFts()`, `restore()` and `transition()`. **`withDeleted`/`withTemplates` do not refuse**: they ask to widen, and a model that hides nothing already answers everything, which is what generic tooling (Litestone Studio's row browser, a *show deleted* toggle) is asking for. Ruled: `FJS-D425`.

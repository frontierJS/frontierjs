# The audit trail and the log

The full entries behind this section of the `data-hazards` skill's index.

- **An audit row says WHERE the write came from, and junction is what tells it.** `correlationId` · `source` (the call, `orders.pay`) · `origin` · `ip` · `userAgent` · `tenant`, filled from `db.$logContext(fn)` — a function the client is handed and calls when it builds an entry, the same injected shape as `now`. The direction is forced: litestone must not learn that a request exists (Invariant 1), so junction installs a closure over its own store, in `createApp({ db })` and on the per-tenant tap. A throw in it costs the columns and never the write. `correlationId` is the join to `$.log`; `source` names the call rather than a URL, because the same write arrives over HTTP, over a socket frame with no URL, and from a job with no request at all. **`db.$logStats()`** answers `{ written, dropped, lastError, lastWrittenAt, lastDroppedAt, lastRetainAt }` and junction puts it on `/metrics` as `audit`, because `fireLog` is fire-and-forget and a trail that stopped recording reads exactly like an app doing no work. Ruled: `FJS-D433`.
- **A `driver logger` trail is written by every process, and the index database's write transaction is what serializes them** (`FJS-D180`). A byte offset cannot be computed before an append or recovered after it — `statSync(f).size` then `appendFileSync` is two syscalls — so `create`/`createMany` hold `BEGIN IMMEDIATE` on the companion index across the pair, and the index row naming the offset commits with it. It is a transaction and not a lockfile, since a lockfile has no answer for a writer that dies holding it. **The sidecar is in WAL and compaction must never unlink it**: an unlink leaves `-wal`/`-shm` behind and a live process's next write then answers `ok` while writing into an inode with no directory entry. **Compaction holds the same lock across its READ**, not just its write-back, or the window stays open and widens. So an append waits for a compaction; the alternative is a destroyed audit row. `packages/litestone/src/drivers/jsonl-index.js` is the one owner.
- **An audit row names the TABLE, not the model** — `model: 'pay_window'` for `model PayWindow`, where every other name that crosses a boundary is the model's. So `auditLogs.findMany({ where: { model: 'payWindow' } })` is a 200 with no rows, which reads as *this model is not logged* and is indistinguishable from a missing `@@log(audit)`. `before` and `after` are JSON STRINGS and `records` is a stringified array of ids, so nothing in a JSONL trail joins to anything: it is a record and not a dimension. **`@@log` may name a SQLite database instead**, which is what makes it one — `database main { … model AuditRow }` with `model` REQUIRED there, since there is nothing to synthesize into and a table the app never declared carries no gate, no policy, no index and no migration. A declared trail is an ordinary model: its `Json` columns come back parsed, it joins to `User`, a row policy scopes it, a cursor pages it, litestream replicates it, and `@@gate("5.8.9.9")` makes it append-only at the Data boundary — the engine's own write still lands, because it goes through a system context at 8. Writing `9` for create instead gives a trail that migrates, snapshots, passes every check and refuses the first row the engine writes. Ruled: `FJS-D434`.
- **An effective-dated write BACKWARDS overwrites the prior belief, and only the log holds it.** A window is closed by moving `effectiveTo`, so backdating a correction moves it to an earlier instant in place — after which the row cannot say what it once ran on, and an as-at read at a PAST date answers differently than it did before. A forward raise does not. `effectiveFrom`/`effectiveTo` holds VALID time and nothing holds *when we learnt it*, so **anything that must reprint as it was issued has to have FROZEN it** (`FJS-D164`) — `example`'s `Payslip` names the `PayWindow` it was computed under and copies every figure. A report that re-derives from the terms table instead is correct until the first correction and wrong silently afterwards (`example`: `verify:retro`).
- **`@@log(audit)` records a WRITE; `db.$audit()` records an EVENT — and the second one throws.** A sign-in is not a write to `User`, and a *failed* one is not a write at all, so nothing the logger can see names the actor or the attempt. `$audit({ operation, model?, records?, actorId?, meta? })` is the one way to put a row there by hand — an unknown key is refused by name, `actorId` defaults to the calling client's principal (a system context has none), and a stated value beats `onLog`'s. **It awaits and throws where `fireLog` is fire-and-forget**, because there the record is a side effect of a write that already succeeded and here it is the point. `meta` is NOT redacted — do not put a secret in it. On every flavor of client. Ruled: `FJS-D435`.

# Schema and parse

The full entries behind this section of the `data-hazards` skill's index.

- **Two owners decide whether a schema is legal, and the line between them is what CAN be expressed.** The parser refuses what cannot work at all — `@unique`/`@@unique`/`@@index` over a field with no column (a `@computed` in a `@@unique` makes a table SQLite refuses at boot, naming nothing the author wrote), a fractional `@default` on `@scale`/`@money` (an INTEGER of minor units takes `DEFAULT 12.99` and the first defaulted row is refused at runtime), a `@relation` across two `database` blocks (a foreign key resolving nowhere, `no such table` on every create). These derive from one FACET — *what does the column physically hold* — rather than a rule per attribute pair (`FJS-721`); `@generated` is outside the set, being a real column. **What is merely legal and WRONG is `litestone advise`**, whose own contract is that every rule in it parses — `@@fts` over an encrypted column is one, and putting a rule in the parser too makes its `advise` rule unreachable. Reach for the parser when the schema cannot be built, and for `advise` when it can be built and should not be. Ruled: `FJS-D420`.
- **A composite `@@unique` naming a NULLABLE column is a parse error, and single-column `@unique` over one is not** (`FJS-D130`). Two NULLs never compare equal, so the tuple index admits `(1, NULL, NULL)` twice while refusing the same pair with values. `@@unique([a, b], nullsDistinct: true)` is how a schema says it meant that, emitting identical DDL. **`@@unique([a], where: <expr>)` is the other answer and usually the one wanted** (`FJS-603`) — *at most one OPEN row per parent*, which effective dating is built on, reached by moving the nullable column OUT of the tuple and into the predicate. A predicate cannot ride a table constraint, so it emits a standalone `CREATE UNIQUE INDEX … WHERE`, migrates by one DROP and one CREATE, and does NOT make a relation one-to-one. Its literals are inlined, because SQLite prohibits a bound parameter in a partial index predicate. **`@@softDelete`'s clause is not ANDed in**: on a unique index the predicate IS the constraint, so ANDing it would free the slot a deleted row holds (`FJS-D65`). A `@from` correlates on **every** column of its relation's key, in three places, or a join on the first column alone answers a count of real rows to a question nobody asked; a write naming a `@from` field refuses by name.
- **`litestone introspect` output must PARSE, and the property that holds it is a FIXED POINT** (`FJS-594`). It is the adoption door — a database you already have into a `.lite` — and also what `fli db:pull` runs. Reading a database built from the output must give the same output, asserted over the seven corpus schemas and the 188-model `openmrp` fixture. It catches what no substring assertion sees: a SQL expression default emitted as a string LITERAL, whose quotes `ddl.js` doubles on every pass; an `@@index(where:)` re-emitting the clause `createIndexes` ANDs on for `@@softDelete`, nesting a level deeper each time; a **relation field named for the table it points at**, which takes a real COLUMN's name and deletes it, since the parser keeps one field per name; and an **enum name colliding with a MODEL name**, which makes that model's own relations resolve as enums and become TEXT columns. **Anything here that writes `.lite` owes the same property.** The output is graded as well — `src/import/tiers.js` is one table for both converters, `--report` writes the list and `--strict` fails on `changed`.
- **A Litestone client THROWS on an unknown property, and `createClient` refuses an unknown OPTION by name** — never `undefined`, so a typo'd accessor is loud and a typo'd capability does not quietly fail to apply (`FJS-579`: `autoMigrate: true` is not an option). The refusal comes off a rest capture, so what counts as unknown is whatever the destructure did not bind; `autoMigrate` is answered rather than suggested at, naming `autoMigrate(client)` and why it stays a call. The cost: feature-detection is itself a throwing expression. `typeof db.$maybe === 'function'` explodes; use `'$maybe' in db` or a `try`. A capability that depends only on the schema belongs on **every** flavor of client — root, `$setAuth`, `asSystem`, `$scopedBy`. Ruled: `FJS-D421`.
- **A relative `database { path }` resolves against the process CWD, and a schema can be told otherwise.** The same schema then means a different file depending on which directory the command was typed in, and nothing fails — SQLite creates the file, litestone creates the directory above it, and every tool reports on the new empty database (`FJS-449`). `resolveFrom: 'schema'` anchors to the APP ROOT — the schema file's directory, or its parent when that directory is `db` — which is what every litestone CLI call site does. **A schema assembled in memory says where it would have lived**: `path:` beside `schema:` when the app read a file and appended to it, or `resolveFrom: '<dir>'` (a directory or a `file:` URL) when there is no file at all, which THROWS on an anchor that is not a directory. `createTenantRegistry` takes `path` the same way, and there it matters twice: `tenancy { dir }` and `tenancy { registry }` are written against the SCHEMA FILE's own directory, not the app root — the one place the two bases differ. An override (`db`, `databases: { … }`) is unaffected: code is written against the process. **The default stays the CWD**, because a seed test depends on isolation-by-CWD. **Creating the DIRECTORY for a database is announced**, naming the cwd, since `db/shop.db` from two different directories prints the same string. Ruled: `FJS-D422`.
- **`@map` renames the COLUMN and nothing a caller touches**, and the write side fails loudly while the read side does not. `fieldToColumnName` is the one owner — the field-level counterpart of `modelToTableName` — and `columnMapFor` holds only the names that DIFFER, so a schema with no `@map` translates on no path. A payload key, a row, a policy's own text, an error message and an index NAME all stay the field's; the index name because the migrator matches by shape, and deriving it from the column would rename every index the day a schema adds a `@map`. **A missed identifier in a WHERE is silent**: SQLite reads an unknown `"ident"` as a STRING LITERAL, so the clause matches nothing and answers `[]` with a 200 — a policy compares against the text `'ownerId'`, and `{ pages: { increment: 5 } }` stores 5 (`FJS-761`). An INSERT column list is the loud half. So **anything asserted about a mapped model is asserted as a PAIR against the same schema unmapped**: a mechanism answering `[]` for both spellings passes any test that only asks the mapped one. **The pairing has to reach the FAST PATHS** (`FJS-969`): `_fastFindManySql` and `_fastFindUniqueSql` are SQL strings precomputed once per table, outside the builder everything else goes through, so a naming change that misses them leaves a mapped model answering nothing to `findMany` and to `findUnique` by id while `count`, `findFirst`, `orderBy`, `select`, `aggregate` and `groupBy` answer correctly. `test/column-mapping.test.ts` is the oracle: one model declared twice, 28 operations, compared. The read direction is the STATEMENT's, `mappedDb` beside `wideDb` for the same reason — a count, an aggregate and an existence probe reach a caller without passing either row reader — and it wraps rather than unwraps, so a wide-AND-mapped model keeps both. **An author-written expression is translated by `mapExprCols`** (`@@check`, a compiled `@@index(where:)`), sharing the importer's `mapIdentifiers`, which leaves a word inside `'…'` alone because it is a value. Its mapped identifiers are emitted **bare** where the name allows: SQLite reports an unnamed CHECK by its source text, and one opening with a quoted identifier arrives truncated, sending every violation on that model to the generic sentence — a column named for a SQL keyword is quoted and does lose the message, the same as an author who quotes their own column. Ruled: `FJS-D423`.
- **`createClient({ db })` names MAIN's path and nothing else.** It overrides a declared `database main`, so `db: ':memory:'` is the in-memory test client; a SECOND declared database keeps its declared path regardless. `databases: ':memory:'` is the shorthand that moves them all, jsonl and logger included. Precedence: `databases: ':memory:'` > `databases: { main: { path } }` > `db` > the declaration. **Under `strategy database` a second database keeps nothing**: the registry redirects every sqlite database into the tenant's own file, so its declared `path` is unread and the two names are one file, which the registry says at open. **The unit is the FILE, so a `$transaction` spanning two declared databases is atomic under tenancy and is not atomic outside it** (`FJS-D232`). Outside tenancy the second declaration is a second connection and `FJS-D35`'s split stands, which is why the outbox row goes in main.
- **A scaled column is bounded at 2^53 and a plain `Int` is not.** `Int @scale(n)`/`@money` promise an exact round trip, and the round trip goes through a JS `number` at both ends — `bun:sqlite` answers a `number` on every path, a column read and an aggregate alike, so past 2^53 the rounded double is stored and a DIFFERENT number is read back in silence (`FJS-583`). Nine places therefore leaves **seven** figures in front of the point, not the nine the 64-bit column suggests. Both ends refuse it — the boundary by name, in a different sentence from the fraction refusal, and the column with a `CHECK`, because a migration, a seed, a raw statement and `asSystem()` never reach the boundary. **The column whose values genuinely go past 2^53 is `Int @big`** (`FJS-D174`): it uses the whole 64 bits and its values cross as a **string of digits**, since `JSON.stringify` throws on a `BigInt` — every response, every frame and every audit snapshot. Storage stays `INTEGER`, so ordering, a range filter, an index and `AUTOINCREMENT` are all still numeric. **It emits no `CHECK` and `@scale` does** (`FJS-D174`): `STRICT` already refuses every way a wide value stops being exact, so only `@scale`'s narrower bound needs one; `@@noStrict` is the one shape that earns it. `litestone import` maps a foreign `BIGINT` onto it, keys and foreign keys exempt. **`@scale` stops at 9 and `FJS-575` closed rather than raising it** (`FJS-D154`): a precise accumulated total fits no 64-bit integer at any scale and belongs to rounding and allocation.

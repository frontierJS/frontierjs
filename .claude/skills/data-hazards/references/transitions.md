# `@@transitions`

The full entries behind this section of the `data-hazards` skill's index.

- **A BULK write may not name a transitions field** (`FJS-D182`). `updateMany` matches rows with a WHERE and never reads them, so there is no `from` to grade, and without the check a `@gate(5)` move, a `@system` move and an undeclared move all pass (`FJS-671`). Not reachable over HTTP, since junction's `bulkByRow` selects its targets and writes them one at a time through `update()`; what is reachable is a hand-written service, job or script. The refusal is the **KEY and not the verb** — `BulkTransitionError`, **400** rather than 403, since no level and no grant answers it — and `upsertMany`'s `update:` half refuses with it while its insert half, being a create with no from-state, does not. **Every other column stays bulk-writable in the same call.** `asSystem()` is refused it too (`FJS-D502`).
- **A move asked for BY NAME is not the same question as an update carrying the column** (`FJS-611`). `transition(id, name)` desugars into `update()`, where carrying the value a row ALREADY holds is legitimate — a form round-trips the whole row — and enforces nothing. Asked for by NAME, the same row state means the move did not happen here, so a move onto the state the row already holds is a `TransitionConflictError` carrying `actual` and `retryable: false`, where losing a race to a DIFFERENT move stays `retryable: true`; `isStaleWrite()` reads the flag (`FJS-D171`). The compare-and-swap is the UPDATE's `AND status = <from>`, and wrapping callers in a `$transaction` does not help, since each re-reads after the winner committed. **The caller is graded before the row's state** — a gate is about the caller and the declared move, so somebody who could never make it is told that rather than where the row is. That ordering applies to a named move and to nothing else: an ordinary update matching no `(from, to)` pair has identified no move, so **naming the move is what makes its gate askable**. `asSystem()` bypasses all of it, so a job moving a row through one is guarded only by its own read. Ruled: `FJS-D432`.
- **A row that stops counting at a date and is also MOVED at that date has two answers until the move fires, and the date is the one to read** (`FJS-D353`). A window (`@@expires`, `@@effective`) changes what counts the instant the clock passes and writes nothing; a `@@commitment` makes its transition when its fire runs — up to a minute after the due time, later while the queue is down, never while `while:` holds it. So *is this still live* filters on the date, and the status column is the record that catches up: `status == 'active'` answers yes for a row whose window has closed and whose move has not fired. `db.<model>.due()` and sierra's commitment date read the same `@frontierjs/toolbelt/datetime` function, so the date a screen prints is the one the fire uses. **The declaration is the only owner of the move.** A job still making it turns whichever runs second into a quiet no-op, and its own cron, cutoff and zone decide when rows move; `fli check`'s `commitment-swept` reports one, including a job spelling it as a different move into the same state.
- **`asSystem()` holds the machine, and a row starts at its `@default`** (`FJS-D502`, `FJS-D470`). System lifts a move's `@gate` and `@system` and nothing else: a system write is a declared move from the row's current state, under the compare-and-swap, and a create naming any state but the default is refused for every principal. A fixture or seed that wants a row further along creates it at the default and walks the moves; one that puts a row where no move leads (a reset from `shipped`, a revive from `cancelled`) writes `sys.sql`. Compensation after a failed side effect is a transaction around the move, not a write back — orion's `activate` is the shape.
- **A `@@commitment`'s fire is graded as `createApp({ system })`, so the model's read policy must admit that principal by name** (`FJS-2231`). The fire reads as system and MOVES as the app's own principal, which a member-shaped policy (`auth().memberRole != null`) does not reach — serpgrid's `Scan` declared its timeout, swept it as due, and failed every fire until the policy said `|| auth().isSystemAdmin`. Under `strategy row` the fire runs inside the ROW's tenant, which `due()` answers off the model's tenancy column; a model scoped through its parent has no column to answer from and still cannot fire (`FJS-2284`).
- **`@zoned` is read by `due()` alone — a window over the same day is still read in the call's zone** (`FJS-2170`, `FJS-D512`). A `@@commitment` on a `String @date @zoned(customer.timeZone)` is owed at midnight in each row's own zone, and the row's zone beats `due({ timeZone })`, which then reads only a row whose zone is null. Nothing else reads the binding: an `@@expires` or `@@effective` over the same `@date` still takes one zone per call, and a `where` on the column compares text. The SQL filter is the latest day any zone is on (`Pacific/Kiritimati`, UTC+14) and each candidate is graded in its own zone in JavaScript, so a sweep reads up to a day of rows it then discards — bounded, but not the per-zone lowering `FJS-D908` rules for a `where`.
- **What a `@seals` commitment's move owes is written in `before`; a write its from-state contends with, in `after`** (`FJS-2163`, `FJS-D1022`). `commitments({ hooks })` takes `defineCommitment({ before, after, around })`, the service pipeline's tiers in its order, all in the move's transaction. After a sealing move the row refuses the number and the draft's refresh with `SealedDocumentError`, and a hook that looks the draft up by `status: 'draft'` finds none and writes a second one, which owes its own seal. A renewal is the other way round: the closing period holds `@@unique([subscriptionId], where: status == 'open')` until it has moved, so opening the next one in `before` is refused. `record` is the from-state row in `before` and the moved row in `after`.
- **A machine only some rows enter needs a state that means "none", not a nullable column** (`FJS-3047`, `FJS-D470`). `status S?` has no `@default`, and a move cannot leave null, so `@@transitions(status, …)` over it is refused at parse. Add the resting state to the enum (`none`, `unpackaged`), make it the `@default`, and drop the `?`; the rows that never enter the machine sit there, and the first move is the one that enters it. The refusal's message says this when the column is nullable.

# Gates, policies and claims

The full entries behind this section of the `data-hazards` skill's index.

- **`auth().x` is graded against a DECLARED set, and only where there is one** (`FJS-666`, `FJS-667`, `FJS-668`). An absent claim is `NULL`, so `NOT (NULL = 1)` excludes EVERY caller while the create path's `null === true` excludes none: one misspelling is a lockout on read and an open door on create, and the refusing side reads exactly like a policy doing its job. The set has **four sources** — the nine names litestone reads itself (`id`, `capabilities`, the six `FrontierGateGetLevel` grades a caller by, none of which is a column, and `level` — the grade itself, asked of the gate per model and carried by no principal, `FJS-D296`), the `@@auth` model's own columns, the `tenancy { claim }`, and **`createClient({ claims: [...] })`** for a claim resolved per request, which is on no row and in no schema — a client option rather than a `.lite` keyword (`FJS-D181`). **A schema with no `@@auth` and no `claims:` is ungraded and says so**, once per distinct set of names; `claims: []` is a statement where absent is silence. **A field-level `@allow` runs the same walk**, and a typo there fails CLOSED, stripping the column from every row, so the schema, the build and every assertion on the refused side agree with the mistake. **An absent claim means one thing rather than two**: `evalJs` propagates NULL the way SQLite does, an `@@allow` holds only on TRUE and an `@@deny` fires on TRUE and UNKNOWN alike. `x == null` keeps its own branch and answers a boolean, since that is how this language spells `IS NULL`.
- **A `@@gate` refuses, a `@@allow` filters — so a wrong policy is an empty screen, not an error.** The two rules underneath, and the order every layer reads in, are `packages/litestone/docs/access-control.md` § *Combining them*: **a refusal must never confirm a row exists** (so create is the one policy that throws — the payload IS the row), and **whose mistake is it** — `@guarded`/`@system` throw because no caller was ever meant to send that column, a field `@allow('write')` drops because the same form body is legitimate one level up. A gate throws naming the model and the level; a policy compiles silently into the WHERE. Every read that legitimately crosses a policy's scope must be `asSystem()`, or it returns nothing with a 200. Declare one model at a time and run the app's drive between them. **`fli test:access` writes the whole declared surface to a committed `db/access.snapshot.md`** — gates, policy predicates, protected fields, and per declared move its gate AND its `@system`, kept as separate columns because they compose: `@system @gate(5)` is both, and folding one into the other renders the widest narrowing a state machine can express identically to an ungated move (`FJS-613`). The `snapshots` CI phase fails a stale one, so a gate that moved is a diff rather than a production refusal. **`--from <ref>` asks the other question and writes nothing**: what this branch did to who may do what, graded `widens` / `narrows` / `undecidable` / `new`. It is a different question from `release:check`'s — a removed `@@gate` is an expand there and the widest change here. A predicate whose text moved is reported rather than guessed, and so is an allow→deny inversion (`FJS-D131`). `--strict` is the gate; the `access` CI phase only prints. Ruled: `FJS-D427`.
- **A freeze that depends on STATE is not expressible, and `@@gate` is where you notice.** A gate is per MODEL, so *a payslip under a draft run may be removed and one under a paid run may not* has nowhere to live: `9` on delete strands the rows a revert must remove, and `8` lets the system remove one and says nothing about when. The rule goes in application code beside the aggregate ones — `example`'s `revertPayRun` reads the PARENT's state before touching a child. It is `FJS-D162`'s open DELETE question.
- **`asSystem()` grades at 8, and `9` is LOCKED — not reachable through the ORM by any client.** So `@@gate("…9")` on a write means *nothing may*, the system context included, and a module that posts through `asSystem()` gets an `AccessDeniedError` naming the model and `required: 9, got: 8` (`FJS-D53`). `8` is *the application acting on its own behalf* and `9` is *there is no code path at all*, which is how an append-only table is declared — `example`'s `JournalEntry` is `@@gate("5.8.9.9")`, read by staff, posted by `api/src/domain/ledger.ts`, amended by nothing. Writing `9` where `8` was meant produces a table that migrates, snapshots and passes every check, and refuses the first write the application makes.
- **A cache keyed on the ctx OBJECT is shared across principals** (`FJS-722`). One table object per model serves every flavor of client, so the ctx its method bodies close over is a single object with `auth`, `isSystem`, `scopedBy` and `tables` as getters over the call in progress. A cache keyed on it answers the first caller's value to everybody; in the gate plugin's level resolver that is an `isSystemAdmin` reader graded at whatever level the process saw first — a wrong ANSWER, not an error. Key on `ctx._flavor ?? ctx`, and write to the flavor rather than onto the ctx. **Reading one of those four outside a call THROWS**, since falling back to the unscoped root would let an escaped read run as nobody and answer `[]` with a 200. It is not junction's ENDED marker: AsyncLocalStorage propagates into anything scheduled inside a call, so what it catches is a stored ctx read later. Ruled: `FJS-D426`.
- **You cannot run without gates.** A schema declaring any `@@gate` auto-installs `GatePlugin({ getLevel: FrontierGateGetLevel })`, because a declared-but-unenforced gate is fail-open (`FJS-D53`). Installing your own replaces it; installing none does not disable it. Contract: **absent = the app does not model this stage; only `null` grades down**, and standing (`isSystemAdmin`/`isOwner`/`isAdmin`) is checked before the lifecycle. **`role` is the exception and is read for PRESENCE** — no role is CREATOR(3), any role is USER(4) (`FJS-D197`); `@frontierjs/auth`'s `User` defaults it, so a stock app grades USER and the no-role branch is reached only by a session some other path built. The scale, the comparison and the grader are all `@frontierjs/toolbelt/gate`; junction's `sessionGateLevel` and sierra's `canAtLevel` are the same bindings.
- **`$setAuth(user)` RETURNS a scoped client, it does not mutate.** `db.$setAuth(u)` then `db.thing.create(…)` grades as anonymous, with no warning. It is `const userDb = db.$setAuth(u)`.
- **A CAPABILITY is a grid beside the ladder, and a finer grant REPLACES the coarse one rather than adding to it** (`FJS-D146`). `@@capabilities` on a model grades its writes and its named moves (`(all)` adds read); `@capability` on a column grades that column's write; both are ANDed with the `@@gate`, which stays the floor. An update's payload is partitioned: a key carrying `@capability` is graded by that column's grant, a key that is the transitions field is graded by the MOVE it resolves to, and everything else by `Model.update` — so `Environment.variables` can be handed to somebody who holds no other edit on the environment, and `Server.reboot` alone reboots. **A CREATE keeps both**, since `Model.create` is the grant for the row existing at all. **A move the ENGINE makes is nobody's grant** — `@system`, or a gate of 8 or 9 — so it is out of the derived set and out of any picker, and is refused AS `@system` rather than as a missing grant. **A verifier hands its synthetic caller every declared capability** (`atLevel`, `verifyRowPolicies`, `verifyTenantIsolation`), or a policy that filters correctly is reported as *the call threw* (`FJS-351`). **The caller's set is `auth().capabilities`** (`FJS-D151`); what an app chooses is which COLUMN it comes out of, and under tenancy that column is on the membership row, so the same person holds a different set per tenant (`FJS-D149`). **A `Capability[]` column carries its own escalation guard** — subset, never a rank — and that guard is undefined under `asSystem()`, which has no principal: an app whose membership writes go through one still needs the rule said in a hook, on BOTH axes, since two roles can hold the same grid and differ on the ladder.
- **A `CHECK` fails only on FALSE, so a NULL passes it** — three-valued logic, and the way a declared constraint most often holds nothing. `@@check("price > 0")` on `price Int?` emits `CHECK (price > 0)`, and a row with no price is accepted. It bites hardest where the expression reaches through a function that answers NULL for a missing input — `json_type(site,'$.lat') IN ('integer','real')` admits every object with no `lat` at all, so the constraint refuses only the wrong VALUE and never the wrong shape. Two ways out, and they are different rules: say the null case out loud (`price IS NULL OR price > 0`) when absent is legitimate, or `coalesce()` the unknown to something outside the admitted set (`coalesce(json_type(site,'$.lat'),'-') IN (…)`) when it is not. Assert the NULL row alongside the bad one, since a check that admits everything passes any test that only offers it values.
- **`asSystem()` does not bypass a `@check`, a `@@check` or an `@@arc`, and it bypasses everything else.** The gate, every row policy, `@guarded`, `@system` and every field `@allow` are this package's rules and the system client drops all of them (`FJS-519`); a CHECK is in the TABLE, so SQLite refuses a system write exactly as it refuses anybody's. Reach for one when a rule must hold against a job on `db.`, a migration, a seed and `fli tinker` — a validator runs here and a service hook is not on the path. The cost: it cannot be evaluated in a browser, so it arrives as a refusal rather than as an affordance — a `ValidationError` (400) whose sentence comes from the attribute's own message argument; without one the person reads `is not valid` and the expression goes to `err.constraint`. `packages/litestone/docs/schema.md` § Constraints the database enforces. **`@@arc([orderId, productId])` is the third and the one with a shape rather than an expression** — several optional foreign keys of which exactly one is set, so *this row points at an Order OR a Product* keeps a real FK, a real cascade and a real `include`, where a polymorphic `subjectType`/`subjectId` pair keeps none of the three. Adding one is a **contract** for `release:check`, like any row invariant. One column per member stops scaling around six — the signal that the target set is OPEN, which no relation can serve and `FJS-D189` refuses; `IDEAS/polymorphic-relations.md` prices the open case.
- **Raw SQL requires `asSystem()` once a schema declares access rules.** `db.sql` and `db.$setAuth(u).sql` throw; `db.asSystem().sql` is the bypass, and it can write. Raw statements enforce no `@@gate`/`@@allow`/`@guarded`/`@scoped`/`@@softDelete`. The rule is per schema, not per statement, since deciding per statement means parsing it (`FJS-D52`). `where: { $raw: sql\`…\` }` keeps every policy and is the hatch to reach for. A JS migration is exempt: the runner hands it the system client.
- **A field `@allow` is a PREDICATE and it is compiled into SQL, both ways** (`FJS-D129`). A READ predicate is AND-ed into the caller's arguments as a **sibling** of their `where` — a sibling, because a conjunct inside it is complemented by their own `NOT` — so a column they may not read cannot be filtered or sorted on. A row-dependent one therefore narrows to the rows it admits rather than refusing; the cost is that an `OR` branch naming the column narrows the whole read. A WRITE predicate is the WHEN of `SET col = CASE WHEN … THEN ? ELSE col END`, so it reads the STORED row — grading it against the payload would let a caller write a column on somebody else's row by stating `ownerId: me` in the same payload. **CREATE is the exception and keeps the JS evaluation**: there is no stored row and the payload IS the row. Through a relation both refuse by name.
- **`@guarded` is not a level** — a system-context lock taking only `(all)`; `@guarded(5)` does not parse. Per-role column access is field-level `@allow('read', auth().role == 'admin')`. It locks **both directions**: a non-system write naming a guarded column is refused with an `AccessDeniedError` naming the field. `@encrypted` alone is not a guard — it hides a value from a reader and stays writable, which is what a caller submitting a secret needs. `@secret` expands into exactly `@encrypted @guarded`, so writing both by hand is `@secret` spelled out; the choice to make is which ONE you want: `@allow('write', …)` for a column some callers may set, `@guarded` for one only `asSystem()` touches. A **required** `@guarded` column makes its model uncreatable below level 8.
- **A column your `getLevel` reads must not be writable by the caller being graded.** A gate is per MODEL, so `@@gate("4.4.4.5")` on an identity table says *any signed-in caller may write any other person's row* — `role`, `isAdmin`, a status, whatever the ladder is graded from. `@frontierjs/auth`'s `User` ships the shape: a level for what kind of caller, `@@allow('update', id == auth().id || auth().isAdmin)` for whose row, `@allow('write', auth().isAdmin)` for which columns. **`8` is not a stronger `5`** — it means nothing outside `asSystem()` has anything to say to this model, which is true of credential material and false of a table an app's own screens list; raising the gate moves the surface into the bypass. `DECISIONS.md` § Access control.
- **A `9`-gated table cannot be tidied up, by anything** — `asSystem()` grades 8, so a test or a drive that writes to an append-only model cannot remove its own fixtures through any client, and every row held by a foreign key from one is stuck with it (`example`'s `verify:retro`). The way out is `asSystem().sql`, which enforces no gate and no policy and binds to TABLE names — budget for it when a `9` goes on a model a fixture writes to.

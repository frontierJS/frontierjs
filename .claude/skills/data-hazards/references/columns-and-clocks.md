# Columns and clocks

The full entries behind this section of the `data-hazards` skill's index.

- **Litestone emits columns verbatim camelCase and `DateTime` as ISO-8601 TEXT.** Hand-written SQL assuming snake_case or epoch-ms will not match.
- **Every timestamp litestone writes comes from the CLIENT's clock, and a raw `UPDATE` therefore stamps nothing.** `@default(now())`, `@updatedAt` on create and on update, `@@softDelete`'s stamp, `now()` in a policy and the retention cutoff all read `createClient({ now })`, so `advance('100d')` then `$retain()` is a test anybody can write. **`@updatedAt` is not a trigger** (`FJS-531`, `FJS-396`, `FJS-D152`), since a trigger reads SQLite's clock and a frozen clock could not be staged. **A create reads the clock after it holds the transaction lock**, so its stamp is no earlier than the transaction it queued behind — but `now()` is still not commit order across clients, and a column that must order by commit is a `@sequence` (`FJS-2153`). The column DEFAULT stays as the floor, so a raw INSERT still stamps; a hand-written UPDATE sets its own. No clock reaches a raw statement or a `@derived` expression reading `now()`, which is compiled once at startup. **A deadline the CALLER computes is minted from `db.$now()`, never `Date.now()`**: `@@expires` grades it on the client's clock, so a `Date.now() + ttl` mint lapses early or never in exactly the test that moves the clock.
- **A `@derived` reads the client's clock too, but only when the client was GIVEN one** (`FJS-2629`). Its SQL is compiled before any client exists, so `now()` is a marker on SQLite's clock that `clockedDb` swaps for `createClient({ now })` as each statement is prepared; a client with no `now` runs it on the wall clock. A new site that builds SQL from a derived expression needs nothing, but SQL built from `NOW_SQL` or `now()` in a raw clause is still SQLite's own clock.
- **A `DateTime @zoned(date, time, zone)` is a stored column nobody but litestone writes** (`FJS-D963`, `FJS-D1434`). The caller is refused by name, system included; a write naming a source re-derives it from the payload laid over the stored row, and an update reaching several rows must move them all to one instant or is refused. A write to the zone recomputes every child in the parent's unit and `@@exclude` grades the new instants, so a zone correction can be refused as an overlap. A gap time takes the later side. Each moved child is a write of its own, as an `onDelete: SetNull` child is: stamped `@updatedAt`, announced as a row `update` after the parent's own event, and trailed with its before and after under the parent's actor (`FJS-4480`). An overnight end must name its start — `@zoned(onDate, endLocal, site.timeZone, after: startsAt)` (`FJS-D2294`); without `after:` a `22:00`–`06:00` end still resolves on `onDate`, before its start, and `@@exclude` reads the inverted range. `test/zoned-instant.test.ts`.
- **A `File` column's stored object is its row's own, so the same bytes on two rows are two objects** (`FJS-D1293`, `FJS-3050`). Every upload is keyed by a fresh `:uuid` (`resolveKey` in `src/storage/file-storage.js`) and `cleanup` deletes the key when its row's ref goes, so no schema word says "two rows, one copy, freed when the last goes". Dedupe within an owner is app modeling: `file File @digest(sha256)` with `sha256 String` and `@@unique([ownerId, sha256])`, and a second upload of the same bytes finds the existing row instead of creating one. Do not model a `Blob` keyed on the hash and shared across owners: it has no owner a row policy can name, so behind `@@gate("8")` an ownership row's caller reads it as missing (`FJS-D576`) and the app ends up in `asSystem()`. Cross-owner dedup is also a leak, since a digest lookup tells a caller someone else holds the bytes.
- **A folding `@@retention(…, into:)` writes its rollup in raw SQL, so the rollup's trail, write events and plugins never hear the fold** (`FJS-D1297`, `FJS-3030`). Each batch is an `INSERT … SELECT … ON CONFLICT DO UPDATE` and a `DELETE`, committed together, so a reader adding both tables never counts a row twice. That reader still has to be told which rollup rows are final: a rollup the app also writes and publishes can sit beside raw rows of its day, and the sweep reaching a sealed one (`@immutable(after:)`) keeps those rows and reports an `error` line rather than adding to the sealed number. The fold stamps the rollup's `@default(now())` and `@updatedAt` from the client's clock, its day is the UTC day of the clock column, and the cutoff is the start of a UTC day, so a day folds whole. A create for a folded day is refused with `FoldedSpanError`, and so is an `update`, `updateMany` or `upsert` whose key or clock moves a row into one (`FJS-4541`). `upsertMany` cannot read the row it conflicts with, so an `update:` naming some of the fold's `by:` keys and clock but not all is refused by name, even toward a day nobody folded.
- **A `@stale` flag is set by a trigger, so the mark is in no audit trail, stamps no clock, and climbs one level per write** (`FJS-D2307`, `FJS-3023`). Every insert, update and delete of a listed source sets the flag on the live declaring rows that reach it, a raw `UPDATE` included. The update trigger leaves out the flag column and SQLite's `recursive_triggers` is off, so the job's successor row marks the parent above and nothing higher. A row the job has not created yet is never marked, and the old row of an `@@effective` pair keeps `stale: true` after its successor lands, so read `where: { stale: true, <to>: null }`. Owner: `src/core/stale.js`.

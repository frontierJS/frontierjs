# Tenancy

The full entries behind this section of the `data-hazards` skill's index.

- **Under `strategy database` four seams belong to the tenant path rather than the single-client path.** A session is verified at the TRANSPORT, before any hook — so `IAuth.verifySession(token, from?)` carries the request's host and headers, without which an app whose people live per tenant can authenticate nobody (`FJS-487`). A raw route (`app.get`/`app.post`) runs inside the request scope, so `requestMeta()` works inside `/auth/login` and inside a webhook (`FJS-488`). `announceDataWrites` taps each TENANT's client on first open rather than one app-wide client (`FJS-489`). And the per-request principal resolver runs for an ANONYMOUS caller, exactly as `withLitestoneDb` does, since a claim is what a caller with no session carries — skipping it makes every guest basket a 404 (`FJS-490`). A `jsonl`/`logger` database stays schema-global and is written by every tenant's client, so its index is idempotent by primary key (`FJS-491`).
- **Tenancy is declared in the schema and there are two strategies.** `tenancy { }` at the top of `schema.lite` — `strategy database` is one SQLite file per tenant plus a registry that indexes them, `strategy row` is one database and a tenant column. Every reader asks one resolution (`db.$tenancy` / `registry.tenancy` / `resolveTenancy`), and precedence is **option → declaration → default**, so `litestone tenant create` and the running app agree on where a tenant lives (`FJS-D05`). **Row tenancy desugars into `@@deny`, never `@@allow`** — allows are OR'd within an operation, so an allow would widen every read to the whole tenant — plus a `@default(auth().<claim>)` stamp; two rules, because `checkCreatePolicy` runs BEFORE the stamp and an absent column is legitimate on create and belongs to nobody on read (`FJS-D05`). A model with no tenant column is reported by name at parse; `@@tenant(none)` says it spans tenants on purpose. `asSystem()` is the only way across, which is what a cross-tenant tier is built on. `packages/litestone/docs/multi-tenancy.md`.
- **Admitted is not a member** (`FJS-D1100`). The row-tenancy deny passes a principal carrying the tenant claim OR its twin `<claim>Admitted`, and `workspaceId == auth().workspaceId` reads only the first. A `membershipClaim({ guests })` row and every `bearerClaim` grant naming the tenant claim emit the twin, so a guest or link holder passes the deny and is nobody to the common policy until the app writes them a narrower rule. A create by one must state the tenant column; the stamp is the member claim's. `packages/litestone/docs/multi-tenancy.md` § Admitted is not a member.
- **A row scoped through a parent that names NO parent is `asSystem()`'s alone** (`FJS-D481`). Where every scoping relation is optional, the desugar adds `rel1 == null && rel2 == null` as one more deny, so a tenant cannot read, create or detach into such a row. A null in ONE of several scoping relations still passes, since the row is anchored through another (`FJS-382`). A row meant for every tenant belongs in a `@@tenant(none)` model. A null claim column answers the same way (`FJS-D141`). `packages/litestone/test/tenancy-delegation.test.ts` § FJS-D481.
- **A `@@tenant(none)` row that names a tenant-owned parent is written `asSystem()`, with the actor carried in a column.** The FK is a read (`FJS-D576`) and the caller's context cannot see a parent in a workspace they are not in, so a caller-context create is refused as a hidden parent even when the parent exists. basecamp's `backups.create` writes the row at system and keeps `requestedBy: actor()`; the trail's actor then reads `system` and the column answers *who*.
- **A tenant read of a `@@tenant` view runs `@@sql` over the reader's rows only** (`FJS-D1149`). The read inlines `@@sql` under CTEs that shadow each row-tenanted table on the view's database with `WHERE <column> = ?`, bound to the reader's tenant; a table scoped through a parent keeps the rows whose parent is in the parent's shadow (`narrowedDb`, `databases.js`; `tenantShadowsFor`, `client.js`). So a view that aggregates across tenants on purpose, a benchmark, answers each tenant over its own rows, and `asSystem()` with no tenant in scope is the one reader of the whole. A `@@materialized` view is not shadowed: its rows were computed at refresh. `onQuery` reports the statement the table built, before the shadows; the bytes SQLite ran start `WITH "<table>" AS (`. Without it a window or a GROUP BY over a CTE kept SQLite from pushing the tenant term down, and the smallest tenant paid a full-table read (`FJS-3140`, `test/view-access.test.ts`).

# Reads and windows

The full entries behind this section of the `data-hazards` skill's index.

- **A `where` refusal is a `ValidationError` — including an operator that does not exist** (`FJS-892`). `$checkWhere` grades the KEY (`?statuz=paid` is a 400 naming the field with a did-you-mean) and the compiler grades the OPERATOR, on a modelled and a modelless service alike. The message names the valid operators off `WHERE_OPS` — the set the typed-JSON walk already reads, asserted equal to `buildWhere`'s cases, so an operator added to one and not the other fails the suite.

- **A modelless service's filters cannot be graded and do not need to be.** There is no schema, by construction. A query handed to litestone is graded BY litestone — a typo'd column is a 400, not a wide read — so the ungraded half is the author reading keys in their own code.

- **An `include` is a SEPARATE statement, and `$tapQuery` reports it as one** (`FJS-891`). Includes are batched — `WHERE fk IN (…)`, never N+1 — so a hundred-row populate is two statements and a nested or sibling pair is three, arriving as `include` / `include:count` events naming the relation TARGET as `model` and that target's own `database`. `fireQuery` runs BEFORE `withIncludes`, so the parent's event and its `duration` cover none of its includes. **The vocabulary is closed in the GENERATED type**, so a new `operation` costs a row in `index.d.ts` and in `typegen.js` — `test/query-tap.test.ts` greps the call sites and fails on one that is emitted and not declared. **Anything measuring statements must count EXECUTIONS**: a statement is cached after its first prepare, so instrumenting `prepare` after a seed has run misses every SQL already compiled and undercounts.

- **A cursor and an offset never combine, and `$after` wins.** A caller sending both has named no position either one of them means. `more()` reuses the last `load()`'s query and directives, because a cursor minted under one ordering names no position in another, so a new filter or a new sort is a `load()` (`FJS-D145`). **A list is a set of ids in an order**: one row cannot be in it twice, so a row that arrived on the socket mid-scan is not in both the list and the next slice. Ruled: `FJS-D429`.
  - **A cursor is caller-supplied text and is GRADED against the ordering using it** (`FJS-779`). The columns compared come from the server's own `orderBy`, so only the VALUES are read out of the token; that is why it carries no signature, and one would buy nothing. What grading catches is a token whose keys are for another sort: every value would read `undefined`, bind NULL, and answer **0 rows with a 200**. `decodeCursor(token, fields)` compares against the key set `cursorFields` computed for this query — the same function `cursorFor` minted it with — and refuses with a `ValidationError` on `['$after']`, a 400. **`fields` includes the tiebreaker litestone appended**, so a cursor hand-built out of the caller's own `orderBy` is correctly not one this list mints. Ruled: `FJS-D430`.
  - **A sort key carries WHERE ITS NULLS SIT, and a cursor compares against that** (`FJS-780`). `"col" > NULL` is NULL and matches nothing, so a window over a nullable column would serve the null rows and then stop — `hasMore: true`, then an empty page, both 200. Each field contributes an EQUAL and an AFTER predicate, read against SQLite's own positions (first ascending, last descending) or whatever `orderBy` stated. **`nulls` has to survive every hop** — `normalizeOrderBy`, `findManyCursor`'s ORDER BY, and `orderTotal` on the way back to junction — or the scan walks one arrangement and the cursor is compared against another. **`nullable` is on the field** because the NULL-aware form costs an `OR`, which stops SQLite using the index a keyset scan exists for, so a `NOT NULL` column compiles the plain comparison. Ruled: `FJS-D431`.
  - **`buildCursorWhere` never answers `''` when it was given a cursor.** An empty string reaches the caller as *no cursor clause*, which is the whole table from the start. A position nothing can follow answers `0`.

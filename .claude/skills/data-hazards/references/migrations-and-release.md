# Migrations and release

The full entries behind this section of the `data-hazards` skill's index.

- **A schema change is a deploy question before it is a migration**, and `fli release:check` is the one that asks it: can the release still serving and the release starting share one database? Expand — N-1 keeps working, so the deploy can be taken back. Contract — it cannot, and that deploy is the **pivot**, after which only forward. Unknown counts as contract. `db/release.snapshot.md` is the surface it diffs, `--from <ref>` is the question a deploy asks, `--strict` fails a branch on anything but expand *including no baseline at all*. **Access is in the comparison**: raising a `@@gate` takes reads away from a release still serving them, and adding an `@@allow` empties a screen with a 200. A required column with no default is the one contract handed back as a plan — expand, backfill, contract — rather than a refusal.
- **The migration differ compares an ENUMERATED list of dimensions, so *in sync* means *in sync on every dimension it reads*.** A dimension that reaches the DDL emitter and not `diffSchemas` reads as a green tick over a database that is not the declared one — generated columns, CHECK, table uniques, index order, index sorts and index predicates each did. Under the enumeration is a catch-all (`FJS-D186`): the two `sqlite_master`s are compared whole and the leftovers are `diff.residue`, announced by `autoMigrate` and printed by `db push` and `db diff`. It is **not part of `hasChanges`**, since nothing can write a migration for a dimension it cannot see, and it does not block, since its commonest cause is the **adoption door** — a real database with a `COLLATE NOCASE` on its email column or a hand-written index, which this language cannot say. `{ acceptResidue: true }` is the caller stating it, beside the `acceptDataLoss` it is modeled on, and it clears the record rather than filtering the output. **Adding the missing dimension is what makes it go quiet**: a residue is a question about the differ, and the answer is usually a comparison it is not making yet.
- **A new column with an EXPRESSION default costs a table rebuild, and one with no default at all is refused.** SQLite takes an expression default in `CREATE TABLE` and refuses one in `ALTER TABLE ADD COLUMN`, where it wants a constant — so `@default(now())` on a new column is a rebuild, and a rebuild is itself refused where the app made its own index or trigger over that table, which has to be moved into the schema first (`FJS-D66`). A `NOT NULL` column with no default is **blocked whether or not the table holds rows** (`FJS-D68`), since migrating an empty table and refusing a populated one migrates on every developer's machine and blocks at the deploy. `autoMigrate` answers `{ state: 'blocked', reason }` and prints it (`FJS-604`, `FJS-605`). Ruled: `FJS-D428`.
- **A rename is a statement, never an inference** (`FJS-D603`). The differ sees a column leave and another arrive, and the rebuild copies only the columns the two tables share, so the values go with the old name. `migrate create` takes the rename as `--rename Model.old=new`, as `--operations <document>`, or as a yes at a prompt (default no, terminal only), and writes `ALTER TABLE … RENAME COLUMN` first in the file, then diffs against the history *as renamed*. It refuses a `from` the schema still declares or the history lacks. Oracle's `was` on a field emits the document. A guess (`guessRenames`) only ever asks.

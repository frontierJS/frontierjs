# Mesa

The full entries behind this section of the `ui-hazards` skill's index.

- **Everything a component reaches for is on `$`, and `$` is legal only as the object of a member expression** (`FJS-D132`). `$.onMount`, `$.emit`, `$.tick` — the bare `$onMount` spelling is refused by name, pointing at its replacement. **Five members are the exception and the bare spelling is the CANONICAL one there** (`FJS-D135`): `$props`, `$attributes`, `$slots`, `$context` and `$async`, the ones read as data rather than called, whose spelling sits in markup. Both spellings are one binding aliased at emit, and the bare names stay RESERVED, so declaring one at script top is refused rather than shadowing it. **`$` may not be destructured, aliased, shadowed, passed or defaulted-to**: several members are COMPILED rather than read — `$context.k = v` becomes a provide call, `$.inspect` is stripped when `debug` is off, `$.mounted` is counted for its one-per-component rule — so through a copy each one compiles, parses and silently does nothing. `$` does not exist in `<script module>`, which runs outside any instance; import from the runtime there, where `$onMount` and `$onDestroy` keep the bare spelling as module exports. **Four prefixes and each is a different KIND** (`FJS-D137`) — `$` the door, `$:` the label (a JavaScript label, untouched by the rules above), `$$` the compiler's own locals, and `__` the CALLING CONVENTION: `__anchor`/`__props`/`__block` are the component function's parameters and `__prev` is the render callback's, and three of the four are read by name out of compiled output by jetty's build plugin (`FJS-D134`). All four are reserved, so declaring one is refused rather than shadowing a parameter and failing at mount. **Two names wear a single `$` and are protocol rather than either tier**: `$class`, the prop `{class}` travels under, and `$dom`, the key a block factory answers with.
- **A Mesa instance `<script>` exports two kinds of thing: a prop and a method.** A prop and a method, in four forms (`FJS-D211`): `export let` is a prop, `export const` a prop the child may not write (`FJS-D209`), `export var` a prop snapshotted at mount that ignores the parent's later values, and `export function` a method on the component's instance API. `export default`, `export *` and every other export form are refused by name; module-scope exports go in `<script module>`. **`bind:this` means two things** — on a COMPONENT it gives that instance API (props read through the child's own signals, so `ref.count` is live and writable), on an ELEMENT it gives the node.
- **On an ELEMENT `bind:` means the DOM writes back, so it is `value`, `checked`, `files` — plus `group` and `this` — and every other `bind:x` there is refused, naming `x={expr}`** (`FJS-D136`). Nothing but you changes `readonly` or `colspan`, so there is no second direction, and for the eight attributes whose DOM property is spelled differently (`for`/`htmlFor`, `class`/`className`, `readonly`/`readOnly`, …) the generic `el[name] = v` path writes a JS expando the DOM never reads (`FJS-478`). **On a COMPONENT `bind:x` is an ordinary two-way prop and is unaffected.**
- **Mesa's scoped styles do not reach into child components.** Use `:global(...)`; the selector subject carries the hash (`button` → `button.mHASH`). A dynamic `class` MERGES, never replaces — all dynamic classes route through `bindClassPassthrough`.
- **A block that reads a `const` derived from another `const` can mount a STALE value.** Two derived layers (`entry = chain[depth]`, `Component = entry?.component`) under one block that also reads the upper one: when both move in one flush the block runs between the layers and mounts the old `Component` with the new inputs. `ChainRenderer` mounted the screen being LEFT with the next route's id this way (`FJS-1684`) — `apps.get` asked for a deployment. Read the same source directly in both places, one layer; a hand-written commit of the same writes does not reproduce it, only the mounted router does.
- **A `const` read off a getter is a constant, whatever the getter reads.** `const rows = list.rows` takes one value at setup: the compiler derives from what it can see in the expression, and a signal behind a getter is out of its sight. Probed 2026-10-13 over a signal getter: `{rows}` stayed `1` while `{list.rows}` in the template and a braced `$: { r = list.rows }` both moved to `5`. On an IMPORTED handle the template read is inert as well (the import entry below), so `let` plus a braced `$:` is the form that works in both places. Three apps each carried a comment rediscovering this.
- **A `const` that CALLS something with a `let` in its arguments is made again on every write to that `let`.** The call is a derivation like `count * 2` (VISION RULE 2), so a HANDLE made that way is replaced, not updated: `const here = presence(channel, { meta: { x, y } })` joined the channel afresh on each step a figure took, sent a second subscribe, showed an empty roster until the new sync, and left a `subscribe` hung on the first handle hearing nothing — Haven's square, `packages/haven/web/src/components/Scene.mesa`. Seed a handle from something that does not change (`scene.spawn`) and move it with its own verb (`updateMeta`).
- **Replacing a value notifies; mutating one does not — and `o = o` is the deliberate exception** (VISION RULE 43, RULE 49). `o.n = 2` on a local `let` object fires nothing unless a `$:` path watch covers it, while `o = { ...o, n: 2 }` does. Writing `o = o` after a mutation forces the notify — it reads as a no-op and is the idiom, the same on a local and a watched import. `Date`, `Map`, `Set` and the other slot-holding types pass through the proxy untouched, so `st.tags.add('x')` under a `$: st` still renders nothing; reassign the property that holds one. Probed 2026-10-08: mutate leaves `{u.s}` at 0, `u = u` moves it. An `x = x` carries a one-line comment naming why, or the next edit deletes it as a no-op.
- **An import is inert in a component with no `$:` of its own on it, and the default hint level says nothing about that** (RULE 44, RULE 47). `{store.count}` with no `$: store.count` in THIS file compiles to a value read once at mount, even when another component watches `store` — that cover only reaches reads made through the proxy, and the proxy is only emitted where this file has a `$:` on the import. An imported primitive (`export let count`) is a constant no watch can name; state that moves is a field on an exported object. The default `externalReactivityHints` level warns only when the file already watches some other path on that import, so a component watching nothing gets no warning; `'strict'` warns on every uncovered read (Sierra sets it, a bare `@frontierjs/mesa/vite` config does not). Every uncovered read is on `analysis.staticReads` and in the devtools panel either way. **A `$: x = store.y` derivation is not that watch**: probed 2026-10-13, `$: open = st.rows.filter(…)` alone left both `{open.length}` and `{st.rows.length}` stale, and adding a bare `$: st.rows` moved both. A module store is `export const s = watchProxy({ … })` with every read and write going through `s` — a write to the raw object behind it notifies nothing, and a hand-kept callback `Set` is a second reactivity runtime beside this one.
- **A function hides its reads from the compiler, which costs a subscription and an ordering.** A template call to a LOCAL function that reads an import's field does not re-run when the field moves, even with `$: page.route` in the file; name the path in the expression — `aria-current={(page.route, isActive(href)) ? 'page' : null}` — and the leading read is the subscription. A call to an IMPORTED function does re-run under a watch (VISION RULE 64). The compiler also orders `$:` derivations by the reads it can see, so a `$:` that reaches a `let` through a function sits BELOW that `let`; above it, mount throws `Cannot access '$$sig_recent' before initialization` — basecamp's `routes/_module.mesa` says so above its *Recent* block. Probed 2026-10-13: the local call stayed `N` under the watch and the imported one moved; a direct read of a later `let` worked and the same read through a function threw. **Inside an `{#each}` row the local call does re-run**: the row's attributes are one effect over the item, and it tracks whatever the call reads at run time — probed 2026-10-13 in the kit's `Shell.mesa`, where removing the leading `(path, query)` read left `shell.spec.mjs` green. The leading read is owed only where the expression names nothing reactive.
- **A `$: dep, handler` does not run at mount, and its `prev` is the same object when the change was a mutation.** The handler form is change-triggered: it subscribes on the first run and withholds the handler, so `$: userId, () => load()` does not load on mount — call it once above the watch, `load()` then `$: userId, () => load()`, two lines kept together, or make the value a `const` derivation. `$.onMount(load)` is not that first call: a dep that moves between setup and mount fires the handler AND the mount hook, so one id loads twice (probed 2026-10-13: `[2, 2]` where the two-line form gives `[1, 2]`). The handler receives `(value, prev)` (arrays of each for several deps); a replaced object gives a real previous value, a mutated one hands the same reference twice. A braced `$: { … }` block is the opposite: it runs at once, before the template exists, because it discovers its dependencies by running.
- **A watched object cannot be cloned or spread out of its proxy — `unproxy()` it.** `{...state}` copies through the get trap, so a nested object comes back as a proxy and `structuredClone({...state})` throws `DataCloneError` (probed 2026-10-08). `unproxy(state)` from the runtime returns a plain deep copy; it is also what to log and what to send over the wire. VISION § 4, beside RULE 48.
- **An unkeyed `{#each}` is keyed by INDEX, so a row's DOM state stays with the position after a reorder** (`FJS-325`). It can never collide, which the item-keyed default it replaced could, and a moved item is rebound into the node already at that position: focus, an uncontrolled input or a running animation stays where it was while the data moves. State a key — `{#each rows as row (row.id)}` — wherever a row owns DOM state. **A row holding a control is that case**: an `<Input>`, a `<Textarea>` or a per-row button, so deleting row 2 hands row 3's draft to row 2's box — basecamp's per-file textarea on `apps/[id]` was index-keyed this way. A column loop inside a `<Table>` snippet owns no state and stays unkeyed. `each-unkeyed.spec.mjs` pins the trade.
- **`null` renders as nothing, but `false` means three different things depending on where it lands** (`FJS-D208`). In a text hole `null`/`undefined` render as the empty string; a deep path through one still throws, on purpose, so a misspelling is not silently blank. On an attribute `null` removes and `false` removes too — except `aria-expanded`, `aria-selected`, `aria-checked` and `aria-pressed`, where `false` is WRITTEN as `"false"`, because absent there announces a different kind of control. `style:x={null}` removes the property. Probed 2026-10-08: `title={null}` gone, `aria-expanded={false}` → `"false"`, `aria-label={false}` gone.
- **A `type="number"` or `"range"` input binds a NUMBER, and an empty box binds `undefined`** (`FJS-857`). No modifier: the control's own `type` decides, through `valueAsNumber`. An empty or half-typed box (`-`) gives `undefined` rather than `0` or `null`, so a required-field check that tests `== null` passes and one that tests `=== ''` never fires. Probed 2026-10-08: `12` → `number:12`, cleared → `undefined`.
- **In a `.md` file `{…}` interpolates a bare path only; anything else stays literal text, with no error** (`FJS-D213`). Prose is template source, so the rule exists to keep `{1, 2, 3}` from rendering as `3`. `{page.title}` interpolates; `{a + b}` or `{fn()}` is printed as written. `\{` is the escape for a brace that should never interpolate. Put an expression in a `<script>` `const` and interpolate the name.
- **A compiled component called directly instead of through `mount()` renders and never answers a click.** Delegated handlers dispatch from a root that `mount()` registers; `Comp(anchor, props, null)` builds correct markup with no root, so every `on:click` in it is dead and nothing reports. An island, a test harness or a hand-mounted fixture goes through `mount(label, Comp, { props })` — the runtime's island comment says the same.
- **A parent sends a prop only when ITS value changed, so re-sending the same value does not reset a child's own edit** (`FJS-2589`). A child may write an unbound `export let` locally, and that copy stands until the parent's expression yields a different value — `pushProps` compares against what the parent last sent, not against what the child holds. Before that, the push re-ran with every other prop and put the parent's unchanged value back, which is how `<Form record={row} bind:dirty>` lost the keystroke that flipped `dirty`. A parent that means *start over* hands a NEW value (`row = { ...row }`), or binds the prop. `test/prop-push-unchanged.test.js` and the kit's `form-pushed-record` spec pin it.
- **A component reaches the DOM through nodes it owns.** A read after a write is `await $.tick()` and then the `bind:this` node; on an `{#each}` row, which carries no `bind:this` of its own, query beneath the list's bound root — `root.querySelector('[data-id="…"]')` — so a second mounted instance's matching node is never the one found. `$.tick()` is enough: probed 2026-10-13, a keyed list grown by one row counted one `li` before the tick and two after. A `window` or `document` listener is `<mesa:window on:keydown={fn}>`, which comes off with the component (probed: no call after destroy); a hand `addEventListener` needs its `$.onDestroy` removal written beside it, or it outlives the screen.

- **A prop a component does not declare is not an error: it is the component's `$attributes`, spread onto its root element** (`FJS-1648`). `<EmptyState title="…" sub="Pick another currency…">` wrote `sub` by analogy with `SectionHeader` and `StatCard`, and `EmptyState`'s text is its children, so the div carried `sub="…"` and the sentence never rendered — through a browser drive that asserted the title. Neither the compiler (it cannot see across the import) nor the browser objects. `fli check`'s `kit-prop-unknown` reads each `@frontierjs/ui/components/…` import, takes the component's `export let`/`export var` list as the authority and reports a lowercase name that is neither declared nor a known HTML attribute (`data-*`, `aria-*`, `on*` and `bind:` are the transport's). A component reading `$$props` consumes undeclared names itself and is not judged.

# Live stores and records

The full entries behind this section of the `ui-hazards` skill's index.

- **A node is the synced truth for a row; a view remembers what it READ.** `resource.record(id)` is live, so a push moves the value on screen without moving the `@version` this screen holds (`FJS-341`, `FJS-D138`). A draft belongs to the form and enters neither. A node write with the **same object** does not notify, because a push writes the node on arrival and the list it lands in writes it back while assembling itself. **Removal is the record view's own state, never the node's**: clearing the shared node would shorten every list holding the row before that list ran its own removal accounting, and two resources over one service share a proxy. **Optimism cannot be asserted in a browser**: every in-flight marker a page offers is still true for a moment after the call answers, because the WS push lands before the `await`'s continuation runs, so a drive passes with the optimistic write taken out. Assert it where it can be negative-controlled, in `junction/test/nodes.test.ts` and `sierra/test/resource-record.test.js`.
- **A comparison between two independent `record()` views has THREE states, and drawing two of them is a screen that lies.** The two reads land milliseconds apart, so *the values agree* and *we have not finished asking* are one branch unless the undecided case is rendered (`FJS-632`). Key it on whether each read has **ANSWERED** rather than on whether it produced a value — a refused or missing row has answered, and keying on the value spins forever on a row the caller may not read. The drawn undecided state is also the only thing a drive can wait for; waiting on either half is the bug.
- **A `@from` column moves when a CHILD row is written, and nothing announces the parent.** `Plan.currentPrice` is `@from(PlanVersion, max: price, where: "effectiveTo IS NULL")`, so repricing writes a `PlanVersion` and the `Plan` row does not move — no broadcast names it, and a record view watching the plan holds the old price. The screen that made the change is the one place that knows, so it calls `record().refresh()`. Same shape for every aggregate a parent carries.
- **A live store holds what its last `load(query)` asked for, so a patch can take a row OUT of it.** A row moved out of the filter is removed rather than updated in place. A record the schema cannot judge (a `select` dropped the filtered column, the filter names a relation, `$search`) triggers a reload instead of a guess. The row is also PLACED — `orderBy` decides where, and the first page trims what falls past `limit` — but on an `offset`-paged list **past page 1 a new row is refused**, because nothing in a browser knows whether it belongs on an earlier page (`FJS-D145`). **A list with a `limit` and NO `orderBy` is in that same position**, so at the page size a new row is counted rather than appended (`FJS-766`). That bounds growth alone: a patch to a row already on the page still applies, and a page not yet full still appends. A refused row and a gap a removal leaves count on `resource.stale`, which `load()` clears and a view renders as *3 new — refresh*. **`changed` is the event that names no row** — what a bulk write or a `select: false` write announces — and the store answers it with the reload it gives an undecidable record, coalesced per burst, never a `stale` count: a counter describes a gap whose shape the list knows, and *some unknown rows moved* is not one. Ruled: `FJS-D465`, `FJS-D466`.
- **`@version` is the revision a screen READ, and a push does not move it.** `createResource` records a version off every call result and off a load that was not superseded — never off the store, where a WS push upserts a number nobody on this screen read; a save from a screen holding a DRAFT would carry it and erase the other person's write with the guard in place (`FJS-341`, `FJS-D138`). The result is a 409, which is the right answer: a caller who has read the newer revision states it, which `<Form record={row}>` does by editing the row whole. **The 409 says which two revisions disagreed**: `VersionConflictError` declares `data = { model, field, expected, actual }`, junction's error boundary carries a declared plain-object payload, and `resource.conflict(err)` answers the numbers where `fieldErrors()` answers the sentence — what a *reload* against *overwrite* prompt needs. **The API-side sibling**: a patch validator compiled from the create-mode JSON Schema makes `autoValidate` strip the version off every patch, so `@version` stops working through a service (`FJS-335`).
- **A watched record empties itself on its own delete, before the handler's next line.** The removal's push reaches the `record()` view before the `await` on `service.remove()` resumes, so a toast reading `job.name` throws on `null`, and the `goto` after it never runs: the row is gone and the screen stays where it was, with no banner, because the page is rendering `NoRecord`. Destructure what the handler needs from the row BEFORE the write. basecamp's job, app and environment screens all had this shape; `verify:screens` § *the edit surfaces* deletes through two of them.

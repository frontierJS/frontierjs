# The hook pipeline

The full entries behind this section of the `api-hazards` skill's index.

- **A custom method takes the model's READ gate as a floor, and declares anything above it** (`FJS-826`). `OP_FOR_METHOD` names the six CRUD verbs; a method it does not name is graded against the model's read gate as a presence check, because the Data boundary refuses a write only after the method body — and its side effect — has already run. The floor needs no declaration; `methods: [{ method, gate }]` is what sits above it, and a declared level grades the caller (401 stranger / 403 too junior) where the floor is a presence check. Ruled: `FJS-D436`.
  - **A method authenticated by something that is NOT a session states `gate: 0`** — a signed machine-to-machine call, an invitation opened by somebody with no account; basecamp has both. The refusal warns once per method on the SERVER's log with that sentence; the 401 body stays generic.
  - **Declaring one gate means naming the whole surface**, because a `methods:` list is the whole surface or it is a narrowing — the same sharp edge `input:` has. A method defined as an arrow property rather than `async name()` is the one a hand-written list most often misses.
- **The gate runs before anything an app wrote, and `validated:` is the phase after the derived layer.** `gateAuth` is a service-level AROUND hook, so it wraps every before hook at either scope; the validators (`autoValidate`, `autoFilter`, `autoSort`) still trail the app's, because a before hook shapes `ctx.data` and it is the shaped payload that must satisfy them. An app rule that reads the database before the gate answers strangers — a 400 for a customer that does not exist and a 401 for one that does is an existence oracle over a gated table (`FJS-403`). The order is **`around(gateAuth) → before → validated → method → after`**, and `validated:` is where a rule that reads the database off `ctx.data` belongs — it needs a caller the gate has graded and a payload the validator has coerced (`FJS-D124`). An APP-level `around` hook is still ahead of the gate, and must be: `withLitestoneDb` establishes the client it grades against.
- **An `Idempotency-Key` on a mutating request executes once and replays the first answer** — claimed in `callService`, so it holds over HTTP and the socket alike. The replay runs **no hooks**, so an app effect living in one does not happen twice and does not happen on the replay at all. Keyed by `(service, method, principal, key)`; a failed call releases the key, an in-flight duplicate is a retryable 409. Ruled: `FJS-D451`.
- **An irreversible effect belongs in `ctx.afterCommit(fn)`, not in an `after` hook.** `after` is after the METHOD: hooks run in sequence, so an email sent from one goes out and a later one throwing still fails the call — and under `transactional:` the row is rolled back with the email already gone. What is queued runs once, on the success path, after the announcement, and after the commit where there was one. **Observer tier** — a throw is logged and emitted, never reported as the call failing, because the write is committed and the broadcast is out. **Not durability**: a crash between the two loses the effect, and `ctx.enqueue` is the verb that survives it.
- **A `mailer.send()` that answers `sent` sends everything the message declared — including `cc`, `bcc`, `attachments` and `headers`** (`FJS-895`), on the SMTP driver and the Resend adapter alike. **`bcc` is in the envelope and in NO header**, which is what makes it blind — mirroring `Cc` would leak it. A caller's own headers are graded for injection at the ADAPTER as well as the transport, because a refusal raised while building the MIME body fires with a socket open mid-transaction and reads as a hang. The conversation is bounded by `timeoutMs` (default 30s) at every read AND at the connect, and **`SmtpError.retryable` is the reply code's first digit** — 4yz transient, 5yz permanent, no code (a refused connection, a timeout) transient.
- **A recurring `app.scheduler` job does not overlap itself, and the tick it dropped is COUNTED** (`FJS-896`). A tick arriving mid-run is dropped rather than queued, because a backlog fails later and further from the cause, and `stats.skipped` counts it. `every()` refuses an interval that is not one; `parseTtlOrNull` is the strict entry point, and `parseTtl` keeps a five-minute fallback for every other caller, so scheduling through it turns `'nonsense'` into a schedule nobody wrote. The cron driver re-aligns to the minute on every tick rather than using a fixed 60s interval, and remembers the minute each job fired for. Ruled: `FJS-D444`.
- **The log level is a CELL shared down the whole tree, and `setLevel` moves all of it** (`FJS-897`). Setting it on a child moves the root — the level belongs to the logger, not to a namespace. Ruled: `FJS-D445`.
- **A job records the request that queued it** (`FJS-897`): `correlation_id`, the third of caravan's dispatch-time columns beside `actor_id` and `tenant_id`, filled from `app.correlationId()` and read back as `ctx.correlationId`. Same absent-is-not-null rule as the other two — `correlationId: null` is a caller saying this work belongs to no request. Request-wide where the TENANT is per-call, because a service re-resolving a tenant mid-request is still inside one request. Ruled: `FJS-D446`.
- **`ctx.enqueue(job, payload)` is the durable half, and it is a second VERB because a closure cannot be persisted** (`FJS-D35`). It writes a row into the app's OWN database inside the calling method's transaction, so the intent commits with the write or rolls back with it; `app.configure(outbox())` is the relay that hands it to `app.jobs` and marks it delivered. **The row can be in no other database** — litestone opens one connection per FILE and holds one transaction manager over main's, so a row in a second block survives the rollback that was supposed to take it; under `strategy database` that second block IS main's file (`FJS-D232`), and the outbox is written where it works in both. The queue stays a separate file, which makes the handoff **at-least-once**: the relay dispatches under the OUTBOX ROW's id and caravan's `dispatch({ id })` treats a taken primary key as work already queued, so a crash between the two replays into a no-op. Refuses by name outside a transaction, without the model, and with no relay. `fli outbox:install` writes the import line, and `/metrics` answers `outbox: { pending, dead, delivered, failed, lastPassAt }`.
  - **A row that keeps failing is given up on, and `dead` is the only thing that says so** (`FJS-778`). `maxAttempts` (default 10) with a doubling backoff on `nextAttemptAt`; past the cap the row is not deleted and not stamped — it stops matching the relay's query, counts as `dead` rather than `pending`, and fails the readiness check. Dead is DERIVED from `attempts`, so **raising the cap is the way back** for a handler that has since been fixed, and `maxAttempts: 0` never gives up. The two counts stay split because a dead row is owed forever, and counted as pending it would keep that number off zero for the life of the app. Ruled: `FJS-D447`.
  - **The relay's walk is COLD, and a tick is ONE walk.** Under `strategy database` the rows are one file per tenant, and `registry.get(id)` — the request path's verb — promotes into litestone's LRU, so an idle pass would evict the tenants being served. The walk goes through `registry.query`, and `outboxPass` is the tick. **The post-commit kick names its own database** and walks nothing, which leaves the timer as pure crash recovery. Anything new here that needs the database set goes through `forEachOutboxDatabase`, never a `list()` + `get()` loop.

# Sockets

The full entries behind this section of the `api-hazards` skill's index.

- **A socket stays alive because the SERVER pings it, and an app calls nothing.** The channels plugin pings an idle connection every 15s and evicts one silent for 40s; any frame counts, and the browser client answers from its message handler rather than a timer, because a timer is throttled to ~1/min in a hidden tab, slower than the eviction window (`FJS-366`). `client.startHeartbeat()` is only for a server that does not ping. Ruled: `FJS-D450`.
- **Never call `ws.send()` directly.** Bun answers `-1` for buffered and **`0` for discarded** past ~16.9MB of unacknowledged data on one socket (`maxBackpressureLimit` is accepted and ignored). `transport/send-queue.ts` is the one owner of a send: it holds a dropped frame, flushes on `drain`, preserves order, and past `http.wsMaxQueued` (8MB) closes with 1013 so the client reconnects.
- **`app.ws` is the raw door: junction's `connected` and `{type:'error'}` frames belong to the handler set carrying `SESSION_SOCKET`, and a route has neither.** A frame past a route's bound closes `1008` with the code as the reason, because a peer that speaks its own protocol cannot read a frame it did not define and a silent drop is a gap in its stream. The path takes `apiPrefix` (`app.http.ws` does not); `limits` lays over `config.http.ws` field by field, `maxPayloadLength` excepted, which is Bun's and one for the server; per-socket state is `ctx.locals` (`FJS-1829`, `FJS-D688`, `test/ws-raw-route.test.ts`).
- **A `removed` frame goes only to a reader the row's BEFORE-image admitted, and a write with no before-image sends none.** Litestone's single-row `update` event carries `before` (the shaped pre-write row, in-process only) while an `onEvent` listener or a `$tapEvents` tap exists; `gradeRecipients` reads it through `src.before` and owes a removal to a cohort the new row refuses AND the old one admitted. A covering service call announces without a before-image, so the tap sends that call's removals itself (`removalsOnly`). A bulk `updateMany` (even `announce: 'rows'`), a cross-process write, a restore and `select: false` carry none, so a narrowing made that way no longer removes the row from an open store; the reader re-reads on `reconnected` or a `changed` (`FJS-1742`, `FJS-D1199`, pinned by `test/realtime-grading.test.ts` § *a removal goes only to a reader who could read the row before*).

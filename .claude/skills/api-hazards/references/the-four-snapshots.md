# The four snapshots

The full entries behind this section of the `api-hazards` skill's index.

- **What an app ANSWERS, what it RUNS with no caller, what it can TELL somebody, and who a caller BECOMES are each committed beside the API, in `api/`.** Four snapshots, each written by `junction <cmd> --app <module> [--services <dir>]` and each read off a BUILT app, because none of the four is a fact a file tree can answer: a hook chain resolves at construction, a job file registers itself by being autoloaded, a notification takes its type from its own FILE NAME, and a principal resolver is wired in application code. So the module must expose an app **without listening** — the `api/index.ts` / `api/src/app.ts` split (`FJS-D128`, `fli check`'s `surface-src`); an app that made them one file guards `app.start()` with `import.meta.main`. They sit in the surface they describe, and the `snapshots` CI phase fails a stale one.

| Snapshot | Command | Holds | The silence it breaks |
| --- | --- | --- | --- |
| `surface.snapshot.md` | `junction surface` | methods after the policy, custom methods as `collectCustomMethods` resolved them, the hook chain in RUN order with the derived hooks leading it, every mounted path with `apiPrefix` applied, plugins in configure order | a 405 in production for a verb a `methods:` list stopped naming |
| `jobs.snapshot.md` | `junction jobs` | every registered handler's declaration — queue, cron, zone, attempts, retry delay — and every `app.scheduler` timer, expression as written | a schedule that stops being registered is *nothing happening* (`FJS-327`, `FJS-328`) |
| `notifications.snapshot.md` | `junction notifications` | every declared type and the transports it can format for | a type that stops being registered THROWS at send time, usually inside a job, hours after the deploy |
| `principal.snapshot.md` | `junction principal` | tenancy · resolver · claims · standing · what the rules reach · the three refusals · per-tenant configuration | a resolver emitting the WRONG tenant leaves every other artifact byte-identical and CI green (`FJS-514`) |

Four rules cut across them. **The two job registries are separate sections** — `app.jobs` survives a restart, `app.scheduler` does not and runs in every replica (`FJS-D36`) — and *no queue installed* reads differently from *a queue with no handlers*. **Names, never values, and no live state**: a claim's name is a fact about the app and its value is a caller, and a next run or a queue depth moves between two boots. **A duck-typed registry that is absent is a stated absence**, a different fact from one that found nothing. And **a notification's type is PERSISTED** (`notifications.type`, read by the browser to pick a renderer), so a type that moves here orphans every row written under the old string. **The app must boot from `api/`**: the `snapshots` phase reruns each generator from the snapshot's own directory, and junction's `configPath` defaults to `./api/config` against the CWD, so an app that does not state it describes an app booted on junction's defaults. An app that moves them states `configPath` anchored to its own module, as it states `autoload`, and anchors any relative path its config carries.

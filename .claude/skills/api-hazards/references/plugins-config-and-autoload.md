# Plugins, config and autoload

The full entries behind this section of the `api-hazards` skill's index.

- **A plugin reads `junction.config.js` in `boot()`, never in `register()`.** `configure()` runs `register()` synchronously and junction does not load the config file until the `load-config` start phase, so a block read in `register()` is the config as it was before the file, and a config-file key silently does nothing (`FJS-431`). `boot-plugins` runs after `load-config` and before `service-routes` and `listen`, so routes mounted there are still served.
- **A missing config DIRECTORY is not a missing config file.** An absent file is an optional miss and stays silent — an app may declare nothing. An absent directory is a path that resolves nowhere, and the app would boot on junction's defaults (CORS `*` included), so `loadConfig` warns naming it (`FJS-430`). `fli check`'s `surface-config` is the static half.
- **Where an app's services are is PROBED, not derived** — `./services` then `./src/services` beside the ENTRY file, first one that exists, and `resolveServicesDir` is the one owner of that list. A missing directory is a silent no-op, so the app boots, `/health` answers, and every route those services would have mounted is a 404 (`FJS-458`). The miss is on the boot banner: `autoload=` names the directory or the candidates that were looked at. **A DECLARED directory is never probed around** — `services: { dir }` or `createApp({ autoload })` that is absent is reported by name rather than replaced, because a relative path resolved against the wrong working directory lands on nothing and looks exactly like an app with no services. **Under a test runner the entry is the TEST FILE**, so an app that needs its services in a test states an absolute path.

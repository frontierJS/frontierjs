# Secrets and the log line

The full entries behind this section of the `api-hazards` skill's index.

- **The logger redacts a credential by NAME, on both paths, and it is a floor rather than a proof** (`FJS-775`). `authorization`, `cookie`, `password`, `x-api-key` and their spellings become `[redacted]` in the JSON line and in the pretty one, nested included, in a `JSON.stringify` replacer. **It cannot see a secret stored under `note`**, and must not be read as *everything else is safe to log*. The name set is `@frontierjs/toolbelt/redact` and is shared with `defineEnv` and conduit; add a name there, never to a list in a call site. `redactProtected` in `core/errors.ts` runs the SAME walk with the SCHEMA's protected set — two predicates, one walker, two separate questions: a key the schema does not name survives the schema predicate.
- **`defineEnv` will not quote a value it must not, and infers that from the NAME.** `STRIPE_SECRET_KEY` prints `[redacted]`; `SORT_KEY` and `PARTITION_KEY` print their value, because `key` alone does not qualify a name and a redaction that ate those would be turned off wholesale. A `DATABASE_URL` keeps its user and host and loses its password — including when the value is MALFORMED, which is the only time the message quotes it. State `secret: true` where a name does not say so.

- **An adapter cache is keyed on `$schema`, never on the client** (`FJS-777`). Junction makes a client per request — `withLitestoneDb` calls `$setAuth(user)` and the principal is a fresh object each time — so a `WeakMap` keyed on the client misses on every call. Everything cached there is schema-derived, and litestone shares the parsed schema BY REFERENCE across root, `$setAuth`, `asSystem` and `$scopedBy`, so two clients over one schema correctly share the entries. **A new cache in `packages/junction/src/core/litestone.ts` goes through `schemaKey(client)`** — and anything that depends on the caller does not belong in one of these at all.

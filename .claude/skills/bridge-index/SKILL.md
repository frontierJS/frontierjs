# Bridge index — the named cross-package handoffs

The current seams. Reach for them before grepping. They may move, merge, or change signature as long as ownership and dependency direction hold.

`CLAUDE.md` § Bridge index keeps the key list — every seam by name — and points here for what each one says. Invariant 4 (*one owner per translation*) is enforced from this file.

**Data → API**
- `$setAuth(user)` / `asSystem()` — the Data-boundary checkpoint / bypass — `litestone/src/core/client.js`
- `$tapEvents(fn)` — every write, announced. `event` is `create` · `update` · `remove` · `transition`, and a transition carries `transition` (the move's name) and `record` where the others carry `result`. **Two shapes and the write says which**: `scope: 'row'` (one row; `result` is it, or `null` where `select: false` skipped the RETURNING) or `scope: 'collection'` (`count` rows matching `where`, never built). Stated, never read off `result` — that is two facts. A bulk write's shape is the per-call `announce` — `collection` (default) · `rows` · `none`, floor at `createClient({ announce })` — because the batch size is a property of the call, not the model (`FJS-D34`)
- `withLitestoneDb(db)` — per-request scoped client on `ctx.locals.db`; auto-installed by `createApp({ db })` — `junction/src/core/litestone.ts`
- `gateAuth()` + `autoValidate()` — schema-derived 401s/400s for model services — `junction/src/core/litestone.ts` + `core/service.ts`
- `validateInput(type)` — **the same 400 for a method no model describes.** `autoValidate` derives from a MODEL and covers create/patch on a model service; every other method a service answers took `ctx.data` on trust. A `methods:` entry may be `{ method, input }`, and `input` names a `type T { … }` in the app's own seed — so the seed stays the one owner of what a shape is, and the payload compiles through the same `jsonSchemaToJunctionSchema` → `createSchema` pair, carrying `@label` and the author's `x-messages` into a 400 that renders in `<Form>` like a CRUD one. A CRUD name may carry one, replacing the model-derived validator. **A named type that is not there THROWS** where a missing model warns: an absent model definition is a config that used to work, an `input:` is a statement the author just made. **Declaring an input also declares the SURFACE** — `{ method: 'pay' }` narrows exactly as `'pay'` does, so a service gaining its first `methods:` answers 405 to every verb it did not name; `surface.snapshot.md` carries the policy-applied list AND the inputs, so that is a CI diff rather than a production 405. Transforms do NOT cross (`FJS-401`) — `@trim` is a Data-boundary rule, and the two boundaries apply transforms on opposite sides of validation, so they would disagree about what is *valid*
- `needsBackfill` on a release finding → `fli release:check` — **the middle step of a split, made checkable.** `classifyPivot` refuses a contract on a required column and hands back *expand → backfill → contract*; it grades the two deploys and stops after naming the COLUMN, because which mechanism fills it is a question about the running application and litestone sits below the package that answers it. So the finding carries `{model, field}` and `packages/cli/core/backfills.js` reads the app's own source for a `defineBackfill` naming that pair — SOURCE rather than a directory convention, the way the thirteen source-reading `fli check` rules work, because a rule keyed on a path reports a correct app as missing one. What no command can answer is whether it has RUN: that is a row in the deployed database, and it says so (`FJS-D157`)
- `sessionGateLevel(user)` — `SessionContext` → the 0–7 scale; pass to `GatePlugin({ getLevel })`. It was **a hand copy on both sides** — Litestone cannot import Junction — and it drifted on the one branch neither side's test could see, so both are now `gradeStanding` from **`@frontierjs/toolbelt/gate`**, which also owns `LEVELS`, `LEVEL_NAMES` and `levelPasses` (`FJS-D197`). Sierra's `canAtLevel` and `transitionsAt` read the same `levelPasses`, which is what makes a screen's verdict and the boundary's the same function rather than two spellings of `>=`
- `toDataPrincipal(user)` — the other half of the same translation: `SessionContext` → the principal `auth()` reads (`userId` → `id`). Applied at both `$setAuth` call sites. Without it every row policy compares against `undefined` and matches nothing, silently. **Two functions, one boundary**: change either and ask whether the other needs it too
- `resolveTenancy(schema)` / `registry.tenantFor({host, headers, principal})` — **the one reading of `tenancy { }`**. The declaration is a Data-realm fact and *which tenant is this request for* is an API-realm question, so the API asks rather than re-deriving; `createApp({ tenants })` installs `withTenantDb`, which assigns the same `ctx.locals.db` that `withLitestoneDb` does and therefore replaces it. Under `strategy row` nothing is swapped and `tenantClaimGuard` refuses a signed-in principal with no claim, because the alternative is an empty list with a 200 on every screen
- `accessorCandidates()` — `model Post` ⇄ service `posts` ⇄ `db.post`; shared by query, gate and validation so a naming slip cannot disable just one
- `db.$checkWhere(accessor, where)` → `[{key, suggestion, allowed}]` — the one definition of "is this a valid filter key", asked rather than copied; junction's `autoFilter` calls it. An unknown accessor answers `[]` — *I cannot judge this* is not *this is wrong*
- `db.$checkOrderBy(accessor, orderBy)` → `[{key, reason, suggestion, sortable, message}]` — the sibling, identical contract; junction's `autoSort` calls it. **Both halves throw** (a bad sort key returns the right rows in the wrong order, which nothing can see). `reason` separates *no such field* from *`@computed`, so SQLite can neither sort nor paginate by it* and from *`opaque`* — an array, a `Json`, a `File` or an encrypted column, whose stored TEXT is a serialization rather than the value, so ordering by it is always plausible and never what was asked. A `@from` field sorts

- `db.$readAs(accessor, row, principal)` → the row as that principal would have read it, or `null` — **the fifth sibling, and the one that exists because a BROADCAST IS NOT A SELECT.** `@@allow` compiles into a WHERE, so a row reaching a caller through a query is filtered by construction and one reaching them through a WebSocket frame was filtered by nothing: an anonymous socket received whole `Order` rows the same caller was answered 401 for (`FJS-631`). Takes its subject as an ARGUMENT for `$capabilitiesFor`'s reason — the asker holds one client and is answering about somebody else. Three questions in the order every layer here reads them: the **gate** (about the caller alone, an integer comparison, and the whole answer for a stranger), the **row policy** (`policyVerdict`, in JS against the row in hand — no query), then the **field policies**. Shaping a row that has already been read is safe because every protection STRIPS for a non-system reader and a recipient is never system, so no decrypt branch runs; what it gives up is that the row is not re-read, so a `@from`/`@computed` is the writer's. **Fails closed** — an undecidable policy throws and a throw refuses. **Two readers now**: the broadcast fan-out, and a webhook delivery, which grades as the principal that REGISTERED it (`FJS-D193`) — deferred work runs as whoever asked for it, and a registration is deferred work with a longer fuse. `db.$readGrading(accessor)` → `'open' | 'graded'` is the half that keeps it cheap, and an unknown accessor is `graded`, the opposite of the other siblings' `{}`: there uncertainty means *I cannot judge this*, here it is a permission
- `db.$primaryKey(accessor)` → the key's columns, **in key order**; `[]` for an unknown accessor. The sixth sibling, same contract on every flavor of client. It exists because the layer above has to know whether a row can be named by ONE value: `expandCompositeId` stamps `@id` on every member of an `@@id([a, b])`, so asking the FIELDS answers all of them and in declaration order, while the key's own order — the order its implicit index is prefix-matched on — is stated only on the model attribute. Junction's derived `get` reads it to refuse a one-value id by name, because a URL segment is one value and the key is several (`FJS-694`)
- `db.$protectedFields(accessor)` → `{ field: 'guarded' | 'encrypted' | 'hashed' }` — **which columns must never be written down in plain text.** The third sibling, same contract: unknown accessor answers `{}`, every flavor of client answers the same. `@@log(audit)` redacts these in litestone's own JSONL (Invariant 7); an application keeping an audit table of its own had nothing to ask and could only hand-copy the names, which go stale the first time somebody adds a `@secret`. The value names WHICH protection because the three are not interchangeable

Both `$check*` live on **every flavor of client** — root, `$setAuth`, `asSystem`, `$scopedBy`. Filterability is a fact about the schema; auth has no bearing on it.

**Schema → API/UI**
- `generateJsonSchema(schema)` — consumed by junction validation and sierra's `build/schema-plugin.js` → `registerSchemas(defs, modelNames)`. **`$defs` is the whole definition table** (models, enums, `type T`, FileRef) and must stay whole — enum fields emit `{"$ref":"#/$defs/Plan"}` and both sides resolve it. Model names travel separately. Full key reference: `packages/litestone/docs/jsonschema.md`. **Three readers and no build that breaks when it changes shape** — a keyword that stops being emitted makes a form stop validating, silently — so `litestone jsonschema --snapshot` commits `db/jsonschema.snapshot.md`: `$defs`, enum values, per model the gate/relations/transitions and one row per field (type + default, required, label, keywords, which rules `x-messages` answers for), then what CREATE mode accepts. The `snapshots` CI phase fails a stale one
- `ctx.system` — **the `@system` columns THIS CALL is supplying**, `junction/src/core/context.ts`. A `@system` column is written by the application and refused when a caller's payload names it; litestone's hatch is `system: ['col']` on the call, which keeps the gate, the row policies, `@@softDelete` and the audit actor where `asSystem()` drops all four. A hook that DERIVES such a column could not reach it — a hook shapes `ctx.data` and the write happens downstream on the caller's own client, so the derived value arrived at the boundary indistinguishable from one the caller sent, and every customer create over HTTP in `example` was a 403 (`FJS-644`). `ctx.system.add('slots')` in a hook; `systemFields(ctx)` in `core/litestone.ts` is the one reader, called at each of the five derived write args. **A Set that hooks ADD to and `readonly`**, because `before.all` and `validated.create` each legitimately derive their own column and an assignment from the second silently drops the first's. Naming a column widens one CALL and never the model, and an empty set is not *all*. `$.system` reads it and `$.system =` is refused by name. `@guarded` gets no equivalent by design (`FJS-D178`)
- `ctx.transients` — **the `@transient` half of a payload, lifted off `ctx.data`.** Declared in the seed, emitted `writeOnly` into the create/update JSON Schema and absent from the read modes, so a generated form offers a control for a value no read answers. `liftTransient` in junction's `autoValidate` is the one place it moves; `isStoredField` in litestone's `ddl.js` is the one answer to whether a field is a column at all
- `ServiceTypes` — **the schema's TYPES on the far side of the wire**, where JSON Schema is its rules. `litestone types --augment junction` emits `service name → row` plus the module augmentation that registers it with `@frontierjs/junction/client`, so `client.service('posts')` and `resource('posts')` infer with no type argument and an undeclared column is a compile error in the browser. Keyed by the plural through `@frontierjs/toolbelt/inflect`, like every other name that crosses (Invariant 2), and **audience-split**: the API generates the system row, the browser the client row, because one file for both tells browser code a `@guarded` column exists that every response strips. An app that generates nothing has an empty registry, which is `never`, so every call keeps the open shape it had
- `@label` → `title`, validator messages → **`x-messages`**, keyed by rule name *and* by the JSON Schema keyword it compiles to. Litestone owns the keyword table (`jsonschema.js`); Junction's `schema.ts` and Sierra's `field-rules.js` look up the keyword they failed. A field's label is read off the field's OWN schema, never a `$ref` target
- `buildFieldRules()` / `validateAgainstFields()` / `coerceToSchema()` / `normalizeBlanks()` — `sierra/src/junction/field-rules.js`, a **leaf module** with no Junction-client import so it runs in plain Node and can be compared against junction's server rules rather than copied. Order: **coerce → blankToNull → validate**. All three on by default (`{ validate: false }` opts out; the test is `!== false`, so a threaded-through `undefined` does not disarm it)
- `controlFor(rule, {field, model})` / `formFieldList(fields, {only, except, model})` — same module, **the one place a field becomes a control**, so a generated form and a hand-written one cannot disagree about what a `Float` is. Reached through the resource (`resource.formFields()`, `resource.options(fk)`) rather than imported, because `@frontierjs/ui` peers only on mesa and css and importing sierra would invert the dependency. **A `Json` column answers `json`**, which the kit binds to `JsonInput`: it is the shape the schema stops describing, so there is no field list under it and the editor is the document's own syntax. **It is matched on the ABSENCE of a type, not on `type: 'object'`** — litestone emits `Json` as `{}`, since a document may be any of the seven things JSON can hold — and two shapes are carved back out of *no type* because neither is a document: a `File` column, which `$ref`s FileRef and derefs to an ordinary object (`x-litestone-file` is carried for exactly this), and a `$ref` nothing resolved, which `buildFieldRules` records as `unresolvedRef`. An array answers `json` too. A field it has no control for answers `control: null` **with a reason**, because dropping it would make a new column absent from a form with nothing saying so. **`registerControl(name, resolve)` is the way in**, and it is HALF of a contributed control: this side answers a name, `@frontierjs/ui/controls` binds that name to a component, and a name is the only thing that can cross a boundary where one side must run in plain Node and the other may not import sierra (`FJS-D17`). Last registered is asked first, so an app beats the kit it imported; a `readOnly` column is not offered to the registry at all
- `labelFieldInfo(fields, fallback, declared)` → `{field, source}` — **which column identifies a row to a person**, one owner, because a foreign key holds an id and nobody recognises an id. The declaration is `@@label(field)` in the seed, reaching the client as `x-label-field` and resolved once per resource onto `resource.labelField`; a picker asks the resource rather than scanning. **A declaration is not checked against the field rules and must not be** — the case it exists for is a `@generated` full name, which is `readOnly` (the scan skips those) and absent from a create-mode registry altogether, while the consumer reads it off a fetched row. Litestone refuses at parse every shape a picker cannot use, by name, because the options query SORTS by this column and searches it with `contains`. `source` is the other half: `declared` · `conventional` (one of eight names) · `scan` (the first plain string — a guess) · `fallback` (the id). Every step down used to be silent, and the two guessing tiers now say so once per field, naming the model and the fix — a `Person` with `firstName`/`lastName` labels every option *Ada, Ada, Ada* and looks like it worked (`FJS-392`)
- `x-values` → `rule.values` → `controlFor` / `resource.options()` — **a declared value set, from the seed to the request a picker sends** (`FJS-D120`). `valueset <Name> { source · value · scope · where }` in `.lite`, `@values(<Name>[, required|open|suggested])` on the column, BESIDE `@relation` rather than instead of it. **A bound column is asked before its foreign key**, because a bound FK is both and the set is the narrower answer — it names the scope the list is narrowed by and the column a person reads, where the relation names neither. Strength picks the control and the two weak ones pick the SAME one — `required` a picker, `open`/`suggested` a combobox with `allowNew` — because what separates them is what the server does with a new value, not what a caller may type; a bound array is a multiselect where an unbound one is still `json`. **Every narrowing travels as a NAME** — `$checkWhere` validates a `$scope`, so it survives junction's `autoFilter`, which is what makes the offered list the list the Data boundary will accept. A declared `where` is SQL and a browser may never send SQL, so it **mints a `@@scope` on the source named after the set** and crosses the same way; the predicate itself never leaves the server (`FJS-430`). The enforcement is litestone's, through the CALLER'S own accessor — `x-values` is an affordance here exactly as `x-gate` is
- `resource.options(field)` → `{ options, total, truncated, error }` — **what a picker OFFERS, and why it has nothing to offer.** `error` is what separates *there are none* from *I could not ask*: both used to answer an empty list, which a person reads as the first one, so a service no name resolved to looked like a shop with no variants in it (`FJS-570`). It is said where the COUNT is said — `optionsNote` beside `truncationNote` in `@frontierjs/ui/utils.js`, composed through one `withNote`, so `Select`, `Combobox` and `MultiSelect` cannot word it three ways — and it is a NOTE rather than a field error, because the value may be legitimately absent and marking the field invalid would refuse a submit on every optional relation whose rows happened not to arrive (`FJS-587`). `<Form>` keeps it beside `pickers` off the same prefetch and `defaultControlProps` carries it, so a contributed control gets it without restating the builder
- `toFieldErrors(err)` — same module, also `resource.fieldErrors(err)`. **The one owner of "a thrown value → per-field messages."** Three shapes reach it because each hop wraps once: `err.errors`, `err.data.data` (a server 400 through the browser client — the double `data` is real), `err.data`. Returns `{ fields, message }`. **`errors` is how a Data-realm refusal reaches a control**: junction's boundary adopts an error class's own `errors` array ahead of its `data`, so `ValidationError` and `UniqueConflictError` land under the box that caused them with nothing taught to either side. An error whose payload is an OBJECT (`VersionConflictError`'s two revisions) is a form-level answer by construction
- `$context.form` — the UI-side form seam, provided by `ui/components/forms/Form.mesa` as `{ errors, submitting, disabled, fields, submitted, optionsFor, reportInvalid }`. Nine controls resolve their own label, constraints, `aria-invalid` and message from it; an absent form reads `undefined` and every fallback is what the control did standing alone. A stated prop always wins, including `required={false}`. **`reportInvalid(name, message)` is the one channel that goes the other way** (`FJS-404`) — a control saying *the value I am showing is not one I can hand over*, which nothing else in a form can know: a control whose element cannot hold every value the field may take writes only what it could convert, so the record keeps the last good value and every check on it passes while the screen shows something else. It is the fourth error source and merges LAST, over a server message and a live one, because it alone describes what is on screen now; it refuses a submit even in a HAND-WRITTEN form, where `FJS-316` deliberately stops the record-level checks, because the control that reported is on screen by construction; and `clearErrors()` leaves it alone, since it is about text still in the box and only its own control can retract it
- `buildRelations()` / `buildGate()` / `canAtLevel()` — same module. **`x-relations` is the only place a relation exists on the client**; `x-gate` is an affordance, never a boundary
- `x-version` — names the `@version` column an update must carry back, `readOnly` in the update schema and absent from the create schema. `createResource` remembers the version of every record it reads and puts it on the next patch. `resource.version(id)` / `.versionField` expose it
- `retryable` on a thrown error — the one thing a status cannot carry. A 409 is either a race (`VersionConflictError`, `TransitionConflictError` — re-read and re-apply) or a domain refusal (`TransitionViolationError`, `UniqueConflictError`, `SoftDeletedUniqueError` — show its message). Set it on any error class you own; `toFrameworkError` adopts it and it lands at `err.data.retryable`. `isStaleWrite(err)` reads it. **`junction errors` commits what a thrown value actually becomes** — `packages/junction/errors.snapshot.md`, every row executed through the boundary, Litestone's own classes constructed and run through it. Nothing above `toFrameworkError` reads anything but the result, so a class gaining or lacking a `status` changes a category with no test to fail; `FJS-255` is what the first run found
- `buildTransitions()` / `transitionsAt()` — `@@transitions` reaches the client as **`x-transitions` on the model, keyed by field**, never on the enum `$def`, because only a model can carry a per-transition `@gate`. **It is the GATE half of `db.<model>.transitions(row)` and only that half** (`FJS-495`): a move is an update, so a row policy refuses one exactly as a gate does, and the server grades both — the `update` policy against the row as it IS (one evaluation per call) and `post-update` against the row as it WOULD BE (one per target, the half that varies between moves). `x-transitions` carries a gate and not a predicate and a browser has no policy engine, so a move a policy refuses reads `allowed: true` there and 403s when pressed. **`refusedBy` is what keeps the two one shape** — `'gate'` · `'policy'` · `null` — because a screen renders *you are not senior enough* and *not this record* differently, and neither a status nor a non-null `gate` separates them: the gate is null for every ungated move a policy refuses. Permissive-when-unknown is the affordance contract, and a screen needing the graded list asks the SERVER
- `modelNameFor()` / `schemaFor()` — `sierra/src/junction/schema-registry.js`, over `@frontierjs/toolbelt/inflect`. **The inflection rules are one module and five callers** — litestone's table name and its introspection, junction's `deriveModelName`, sierra's registry and `createResource` — because a table name and the model name derived back from it are the same rules run twice (Invariant 2). Regular English plus a fixed irregular table, so `people` resolves `Person` unaided; genuine ambiguity (`lens`/`len`) cannot be reached by any rule and is said by hand — `createResource('lenses', { model: 'Lens' })`. A miss warns and degrades to a bare `make()`
- `authUserModel(db)` / `authMachineryModels(db)` — auth contributes INTO the seed, as two `.lite` files it ships (`auth/db/user.lite`, `auth/db/auth.lite`); `schema.ts` reads them and `authSchemaFragments(db)` is both, for a caller assembling one string in memory. **Split by owner**: `User` is `@@gate("4.4.4.5")` with policies an app changes, so `fli auth:install` appends it into the app's own `schema.lite`; the four `@@gate("8")` models go to `db/auth.lite` and are imported, so an upgrade reaches an installed app. The CLI reads the same bytes through auth's `exports` — it cannot import `schema.ts`, because `fli` runs on node and that file is TypeScript
- `extend model X { … }` — **what an app says about a model it did not write**, and the reason the machinery half is imported rather than pasted. A package owns its columns; where those rows sit in the installing app — the relation back to its own `User`, `@@log(audit)`, `@@tenant(none)` under row tenancy — is three facts the shipped file cannot know. Adds only: an extend naming no model, a field the model already declares, and a second answer to a single-valued attribute (`@@gate` twice) are each refused by name; `@@allow`/`@@deny`/`@@index`/`@@unique`/`@@check`/`@@trait` are repeatable. Collected across the whole import tree and applied once it is merged, so a file may extend a model it is imported BY, and applied before traits. **The opposite direction of `@@trait`**, which is opted INTO by the model and therefore needs its author to have known. basecamp carried hand copies of four of these for its whole life and one had `@guarded` where auth writes `@secret`, with 137 green tests either side of the divergence — a copy is the failure this removes (`packages/litestone/docs/traits.md`)

- `attachments` → `checkAttachments(config.attachments)` → the `check-attachments` start phase — **what this app needs and does not own, and whether this environment binds it** (`FJS-D158`). The app DECLARES in `junction.config.js`; the environment BINDS, and the check reads `process.env`, not `fli deploy`'s recorded binding set, which goes into the Release for identity and revert and is applied by nobody (`FJS-585`) — so it is true however the variables arrived. **Not a second `defineEnv`**: `checkEnvField` is extracted from it and called by both, so *present, non-empty, a URL, long enough* has one owner. What an attachment adds is the three things a flat spec cannot say — these keys are ONE SERVICE, so a refusal names the service rather than a variable; ALL OR NOTHING, so `optional: true` forgives a service nobody bound and still refuses one **bound halfway**, which is the shape that reaches production and the one a per-variable check cannot see; and a DEFAULTED key is not evidence, or an unbound service with one default looks half-bound. **The refusal is at startup and `fli` is what makes it visible**: `showContainerTail` tails the container on a failed health check, on the revert path too, or the app's own clear sentence dies in `docker logs`

**Machine ↔ control plane**
- `signRequest()` / `verifyRequest()` — `@frontierjs/toolbelt/signature`, **the one definition of what a signed machine-to-machine request is**: method, path, timestamp, nonce and a hash of the body, joined with newlines. Three readers — conduit's transport signs outbound with it, basecamp's `requireOutpostSignature` verifies inbound with it, and `@frontierjs/outpost` does both. It exists because signing with no verifier reads as a scheme being enforced: basecamp's three machine endpoints took no credential at all behind a comment saying the transport had checked one, and an unsigned POST could point every fleet command at an address the caller named (`FJS-349`). The replay check runs LAST, so a caller who never held a valid signature cannot fill a nonce store, and storing nonces stays the caller's because this package does no I/O
- `requestMeta().traceparent` / `.tracestate` → conduit's default `trace` — **the outbound call hangs off the inbound request.** Junction CARRIES the caller's W3C trace verbatim and emits nothing: it traces nothing itself, and a parse there would be a second reading of the spec beside whoever continues the trace. Conduit's junction plugin is the first reader and defaults `trace` **under** the app's own opts, so an app with its own tracer replaces it whole and `trace: () => null` turns it off. An upstream trace is continued; with none, the trace id is DERIVED from the correlation id rather than minted per call, or six calls in one request are six unrelated traces — and a uuid needs no derivation, since junction mints correlation ids with `crypto.randomUUID()` and a uuid with its dashes out IS a 32-hex trace id (`FJS-742`)
- `ctx.$raw.rawBody` — **the body as bytes**, junction's half of the same seam. A signature binds a hash of the body, so a hook handed only the parsed object would have to re-serialize and both ends would have to agree on key order forever. Kept for JSON, urlencoded, XML and text; absent for multipart, where there is no single string

**API internals**
- `$` / `enterCall(ctx, fn)` / `currentCall()` — **the service call in progress**, `junction/src/core/context.ts`. A second ALS store, opened around the whole of `_callService` — pipeline, announcement, `afterCommit` drain, outbox handoff — so `$.db`, `$.data`, `$.id`, `$.locals`, `$.enqueue` are the call a function is inside rather than a parameter threaded to reach it. Plus `$.db` (`ctx.locals.db`) and `$.me` (`ctx.auth.user`) as derived accessors. Resolved on every read, never snapshotted: `transactional:` reassigns `ctx.locals.db` before the method runs. **Only junction's own contract keys can be assigned** — `data · query · id · result · error · statusCode · dispatch` — so `$.dispatch = false` works and an invented key is refused: what makes an ambient object dangerous is state nobody owns, not writes. **Outside a call it throws by name**, because an ambient dependency is an undeclared one and the whole of what makes that acceptable is a loud failure. NOT `runInServiceCall` below, whose narrower span the litestone write tap reads to suppress a double announcement. **`enterCall` is exported as the escape hatch** — `callService` opens the scope for every ordinary path, so this is for a hand-built context calling a method as a plain function (a unit test, an app invoking outside the pipeline); it nests and restores. Nothing shared with Invariant 10's `$`-prefixed keys but the character
- `$.config` / `app.configFor(tenant)` — **what this app is configured with, read at CALL scope**, `junction/src/core/config-scope.ts`.

# Bridge index — detail

The full entry for each seam the `bridge-index` skill lists. Reached from the index; the index line is the one `seams.js` parses, so an owner changes THERE.

## Machine ↔ control plane

- `signRequest()` / `verifyRequest()` — `@frontierjs/toolbelt/signature`, **the one definition of what a signed machine-to-machine request is**: method, path, timestamp, nonce and a hash of the body, joined with newlines. Three readers — conduit's transport signs outbound with it, basecamp's `requireOutpostSignature` verifies inbound with it, and `@frontierjs/outpost` does both. A signer with no verifier only looks like an enforced scheme, so every inbound machine endpoint verifies (`FJS-349`). The replay check runs LAST, so a caller who never held a valid signature cannot fill a nonce store; storing nonces is the caller's job, since this package does no I/O — `toolbelt/src/signature/signature.js`
- `requestMeta().traceparent` / `.tracestate` → conduit's default `trace` — **the outbound call hangs off the inbound request.** Junction CARRIES the caller's W3C trace verbatim and parses nothing; it traces nothing itself, and a parse there would be a second reading of the spec beside whoever continues the trace. Conduit's junction plugin is the first reader and defaults `trace` **under** the app's own opts, so an app with its own tracer replaces it whole and `trace: () => null` turns it off. An upstream trace is continued; with none, the trace id is DERIVED from the correlation id (junction mints a uuid, and a uuid with its dashes out is a 32-hex trace id) rather than minted per call, so the calls of one request share one trace (`FJS-742`) — `junction/src/core/context.ts` Ruled: `FJS-D459`.
- `ctx.$raw.rawBody` — **the body as bytes**, junction's half of the same seam. A signature binds a hash of the body, and re-serializing a parsed object would need both ends to agree on key order. Kept for JSON, urlencoded, XML and text; absent for multipart, where there is no single string — `junction/src/transport/http.ts`

## API internals

- `$` / `enterCall(ctx, fn)` / `currentCall()` — **the service call in progress**, `junction/src/core/context.ts`. A second ALS store, opened around the whole of `_callService` — pipeline, announcement, `afterCommit` drain, outbox handoff — so `$.data`, `$.id`, `$.locals`, `$.enqueue` are the call a function is inside rather than a parameter threaded to reach it. `$.db` (`ctx.locals.db`) and `$.me` (`ctx.auth.user`) are derived accessors, resolved on every read and never snapshotted: `transactional:` reassigns `ctx.locals.db` before the method runs. **Only junction's own contract keys can be assigned** — `data · query · id · result · error · statusCode · dispatch` — so `$.dispatch = false` works and an invented key is refused (`FJS-D200`). **Outside a call it throws by name.** Distinct from `runInServiceCall` below, whose narrower span the litestone write tap reads to suppress a double announcement. **`enterCall` is the escape hatch** for a hand-built context calling a method as a plain function (a unit test, an app invoking outside the pipeline); `callService` opens the scope for every ordinary path, and it nests and restores. Shares nothing with Invariant 10's `$`-prefixed keys but the character
- `$.config` / `app.configFor(tenant)` — **what this app is configured with, read at CALL scope**, `junction/src/core/config-scope.ts`. One owner, so a value that becomes per-tenant becomes per-tenant for every reader at once. **The source is `createApp({ tenantConfig, tenantConfigKeys })`** (`FJS-D126`) — a resolver answering a plain object per tenant, memoized as the PROMISE so two concurrent requests resolve once, with `invalidateTenantConfig(id?)` the explicit way out and a FAILED resolve not memoized. **The resolve happens where the tenant already is** — the around hook that sets `ctx.locals.tenantId`, and `runAs` — because a property read cannot await; a resolver that throws FAILS THE CALL rather than serving the floor, which would be one tenant's mail under another's name. **`tenantConfigKeys` is required and `RESERVED_CONFIG_PATHS` is refused at BOOT** (`port`, `host`, `database`, `http`, `auth`, `apiPrefix`, `logging`): a database path handed to a tenant is every other tenant's rows, and the rest are read at boot with no tenant in scope. A key the resolver answers that the list does not name is refused by name. The list is committed as `principal.snapshot.md` § Per-tenant configuration. **The view is read-only and deep**; `app.config` itself stays writable, since `loadConfig` merges into it at boot. A derived accessor like `$.db`, `$.me` and `$.log`, so it is absent from `ownKeys` and refuses outside a call; `app.configFor()` is the no-call half
- `$.log` — **the logger, already bound to the call**: `app.logger.child('orders.pay', { correlationId, userId, tenantId })`, memoized per call, so a line joins to its request the way the audit row's `correlationId` does from the Data side. The four derived accessors (`$.db`, `$.me`, `$.config`, `$.log`) are one `DERIVED` set, because three proxy traps must agree about the list; so it is absent from `ownKeys` (a spread must not EVALUATE it) and refuses outside a call. `app.logger` is the unbound logger for anything not inside one — `junction/src/core/context.ts`
- `bridge.toContext()` / `toResponse()` — the transport↔service boundary — `junction/src/transport/bridge.ts`
- `toFrameworkError()` — the error boundary. Order: `FrameworkError` → `registerErrorMapper(fn)` → numeric `status`/`statusCode`/`code` in 400–599 → `err.name` → 500. **If you own the error class, give it a `status`**; `registerErrorMapper` is for errors you cannot modify — `junction/src/core/errors.ts`
- `wrapResult(raw, service, method)` / `unwrapResult()` / `isServiceResult()` — the result envelope. `kind:'single'|'list'` discriminates; a list keeps its envelope, a single unwraps. The same function runs on both sides of the wire, so the browser client asks it rather than carrying a copy of the rule — `junction/src/core/envelope.ts`
- `enterRequest(src, fn)` / `reenterAs(user, fn)` — **the one owner of the request ALS store**, `junction/src/core/context.ts`. Five entry points establish a request (HTTP, a WS frame, `app.runAs`, a call arriving with no store, the test harness); each hands over what it holds and the `RequestMeta` is built here, including which headers carry a correlation id, an idempotency key and a locale. `reenterAs` is *the same request, someone else*: everything but the principal, opening nothing when the principal is already in scope
- `ctx.directives` — parsed from `$`-prefixed params by the bridge and nothing else. The GRAMMAR is `@frontierjs/toolbelt/directives` (`splitParams` → `{query, directives}`), because sierra's router applies the same one to a URL; the bridge is still the only thing that produces a `ctx` — `junction/src/transport/bridge.ts`
- `collectCustomMethods(def, name, methods?)` → `svc._customMethods` — **the one place "is this key an option or a method" is decided**, at construction. `methods:` DECLARES (a non-CRUD name in it is a custom method, resolved off the definition, and is the only way to name one after an option key); absent, function keys are scanned. Dispatch, `/manifest`, OpenAPI and `/metrics` read the table rather than re-applying the rule — `junction/src/core/service.ts`
- `CALL_OPTIONS_AT` — **which ARGUMENT of each `ServiceCaller` method holds `CallOptions`.** The signatures are not uniform — `find(query, opts)` is 1, `patch(id, data, opts)` is 2, and `call(name, id, data, opts)` is 3 — so anything binding a principal into a call by position reads the table; a guessed index puts the options where the DATA goes. Two packages outside junction read it: `@frontierjs/testing` binds `as(user).service(name)` through it, `@frontierjs/mcp` puts `{ auth: { user } }` there for a tool call. **A method absent from the table is a finding, never a default index** — both callers filter for one and name it, because a method whose options are dropped is an unauthenticated call that answers rows (`FJS-D258`). Declared beside the interface it describes, and graded against it by junction's own suite — `junction/src/core/app.ts`
- `svc.pipelines(appHooks)` — **the one owner of the hook chain.** Memoized on the app map's IDENTITY and a version `hooks()` bumps. `app.hooks()` reassigns rather than mutates, which is what keeps identity sound — mutating the map in place makes the memo stale silently — `junction/src/core/service.ts`
- `svc.describe()` → `ServiceDescription` — **the one answer to "what is this service"**, read by `/manifest`, the OpenAPI generator and `/metrics` instead of reaching into `_meta`/`_schemas`/`_hookMap` — `junction/src/core/service.ts`
- `isBuiltService(v)` / `Symbol.for('junction.service')` — has `createService` already built this? Non-enumerable, so a spread copy is correctly NOT built; the autoloader tests it rather than sniffing whether `hooks` is a function — `junction/src/core/service.ts`
- `normalizePrefix()` + the `app.get`/`post`/… shortcuts — **the one owner of `apiPrefix`**, `junction/src/core/app.ts`. Every route the app registers is mounted under it; `app.http.router` is the layer beneath and applies nothing. The browser client's `apiPrefix`/`authPrefix` compose the same way
- `ctx.enqueue(job, payload)` / `deliverOutbox(app)` — **the durable effect** (`FJS-D35`), `junction/src/plugins/outbox/engine.ts`. The enqueue writes an `OutboxMessage` row through `asSystem()` on `ctx.locals.db`, which the transaction hook has already reassigned to the tx client — so the intent is inside the call's own transaction. The relay claims with a compare-and-set, dispatches into `app.jobs` under the ROW's id, and marks it delivered; `app.configure(outbox())` owns the timer. The model ships as `junction/db/outbox.lite` and reaches an app two ways, both the same bytes: `fli outbox:install` writes an `import` line, `outboxSchemaFragment(db)` is for an app assembling one schema string
- `claimIdempotency(ctx, key, config)` — `junction/src/core/idempotency.ts`, claimed once in `callService` so both transports are covered. The replay bypasses the hook pipeline; `requestMeta()` is where the key comes from, and the WS path populates that store too
- Plugin protocol `{ name, register, boot, ready, shutdown, requires }` — `junction/src/core/app.ts`. **`register` is sync** (`configure()` never awaits it); async setup goes in `boot()`. `requires: ['mailer']` is checked once at startup against presence *and* configure order
- `runStartPhases(bindHost)` — the one startup list; `needsHost` phases are skipped by the test path — `junction/src/core/app.ts`
- `IAuth.verifySession(token)` — inbound auth — declared `junction/src/auth/types.ts`, implemented `auth/auth.ts`. **What junction ACCEPTS is `SessionVerifier`, not `IAuth`** — `Pick<IAuth,'verifySession'> & Partial<IAuth>`, because the interface declares six required methods and junction calls two of them (`FJS-D10`). Derived rather than declared beside it so it cannot drift, and `Partial` keeps a fuller provider assignable past the excess-property check
- `app.withDb(fn)` / `app.onTenantClient(observer)` — **`ctx.locals.db` for work that holds no ctx**, `junction/src/core/app.ts`. `withDb` runs the app's own data hook (`withTenantDb` or `withLitestoneDb`) around `fn`, so inside `runAs` it hands `fn` the principal's client in the tenant in scope with the resolver's claims applied — the two things a client scoped by hand from `principal()` misses. Its second argument is that principal, claims included, for a question the client answers about somebody's standing — `db.$readAs(accessor, row, toDataPrincipal(user))` — which `principal()` would answer without the claim and so refuse every tenant-scoped row. The client is leased for `fn`'s length and must not be kept. `onTenantClient` is an Observer called once per tenant client the app opens under `createApp({ tenants })`, which is how a plugin taps every tenant's writes when there is no one app client. Orion is the first caller of both (`FJS-D294`)
- `app.principal()` / `app.runAs(userId, fn)` — **the seam deferred work runs through**, `junction/src/core/app.ts`. `principal()` is the request-wide principal asked from somewhere holding no `ctx`; `runAs` re-resolves an id through `IAuth.sessionFor` and opens the ALS scope, so a service call inside `fn` inherits it. `null` means `createApp({ system })`. Caravan is the first caller and reaches both **duck-typed off `CaravanApp`** — it takes junction as an optional peer, so nothing here is imported at runtime
- `createLitestoneAuth(db, { sessionFields })` — **the one place an app's own `User` columns reach the session** (`FJS-D70`). Called from `toContext()`, the single point every issued session is built, so one hook covers login, `verifySession`, an API key and `createUser`. Two kinds of thing belong in it: the standing `sessionGateLevel()` grades on (`isAdmin`/`isOwner`/`isSystemAdmin`/`activatedAt`/`verifiedAt`), and the app's own keys, which travel untouched. Spread LAST — a stated field wins — `auth/auth.ts`
- `manifestPlugin()` + litestone `status()` — migration state into `/manifest` — `junction/src/plugins/manifest/index.ts`
- `app.registerMetricsSource(name, fn)` / `app.registerHealthCheck(name, fn)` — **what a plugin says about itself**, merged into `/metrics` and `/health`. A metrics source must be SYNCHRONOUS (the body takes `fn()` directly); a health check may be async, and `false` or a throw is a failure carrying its message. App-declared checks (`healthPlugin({ checks })`) apply LAST, so a name the app states beats the plugin's. **The bodies are `collectMetrics(app, startedAt)` / `collectHealth(app, startedAt, checks)`, not the routes**: the devtools console is a second reader on its own port, and a route is only one caller (`FJS-431`). Caravan grades a stall against the longest DECLARED timeout and the outbox against three missed passes; neither grades work nobody bounded — `junction/src/core/app.ts`
- `app.registerDevService({ name, url, note })` — **a second listener the app started, announced.** The banner is derived from mounted routes, and a sidecar — a dev mail catcher, a stand-in payment provider, an identity provider, each on its own port — has none, so it declares itself here. Two readers: one banner line each, after the app's own, and `devServices` in `/manifest`. **Announcing is all it does** — junction never starts, stops or health-checks the process, since the caller already holds the handle and a register implying otherwise is a supervisor. `_devtools` stays separate: it has a *refused* state carrying a reason, which an announcement cannot express — `junction/src/core/app.ts` Ruled: `FJS-D460`.
- `devtools({ port, auth })` — **the console those two feed**, default port **8503** (the global tooling block), `junction/src/plugins/devtools/index.ts`. Its own Bun server: the live call feed off `app.telemetry`, `/api/state` (the same metrics object `/metrics` answers), `/api/health`, and `/api/jobs*` read straight off `app.jobs` — caravan's own `admin:` routes are opt-in, sit behind the app's `apiPrefix` and are cross-origin from here, so the panel works with no app configuration. **It fails closed**: `NODE_ENV=production` with no `auth` refuses to bind rather than serving request params and a retry button unauthenticated. Acting on a job is POST-only, so a link preview cannot fire a retry Ruled: `FJS-D461`.

# Bridge index — detail

The full entry for each seam the `bridge-index` skill lists. Reached from the index; the index line is the one `seams.js` parses, so an owner changes THERE.

## API → UI

- `client.setCallHeader(name, value)` + `config.http.callHeaders` — **a value the CALLER varies per call, over either transport.** Over HTTP it is an ordinary header; over the socket the server sees only the UPGRADE request's headers, so the frame carries them under `meta.headers` and the server merges only the names the app declared. **One declaration, two readers** — the CORS allow-list and the frame merge list — since a header missing from the first never arrives cross-origin and one missing from the second is dropped on the frame. It is an ALLOW-LIST, and that is the security property: a frame that could name its own header could name `Authorization`, and the identity is established at upgrade. `setWorkspace` is one of these (`FJS-428`) — `junction/src/client/index.ts` Ruled: `FJS-D452`.
- `x-fjs-build` + the `connected` frame's `build` → `client.stale` — **which build this is, and which one the browser is on** (`FJS-D160`). The server STATES and the client COMPARES; nothing on the server reads a build off a request. It rides `connected`, sent once per socket, since a deploy restarts the container and the reconnect is when a stale client finds out. **It is the BUILD and not the Release**: two Releases share one web bundle on every API-only or schema-only deploy. `03-build-web` stamps `VITE_FJS_BUILD` (vite inlines it into the bundle) and `06-swap` passes `FJS_BUILD` to the container, so only a real deploy proves the two agree. Inert unless both sides know one; the response header is GATED so `_finalizeWithHeaders`'s no-op fast path survives; `stale` fires once — `junction/src/core/build-id.ts`
- `wsSend()` / `flushSendQueue()` — `junction/src/transport/send-queue.ts`. **The one owner of "put this frame on that socket"**, for replies and broadcasts alike
- **A broadcast is GRADED per recipient, in cohorts** (`FJS-D175`) — `gradeRecipients` in `junction/src/transport/channels.ts` asks `db.$readAs` once per PRINCIPAL and encodes one frame per cohort. The key is the principal's VALUE — a canonical serialization of the session, memoized on the object `verifySession` answered — so two tabs of one person are one verdict and one frame; object identity collapses nothing, because `verifySession` runs per socket and answers a fresh object each time (`FJS-764`). Serialization REFUSES anything carrying a prototype of its own and falls back to the object, since collapsing two principals that differ delivers a row to somebody who may not read it. **Joining a channel is a subscription, not a permission.** A model `$readGrading` calls `open` is skipped; a LIST payload is not graded (a bulk write announces a COUNT, which names no row); a call with no Data boundary is ungraded rather than refused, which differs from a boundary that was asked and threw. **Apply `toDataPrincipal` on the way in** — a `SessionContext` puts the id at `userId` and `auth()` reads `.id`, so skipping it makes `userId == auth().id` false for the recipient's own row and TRUE for a guest row whose `userId` is null
- `publish()` hook + `app.channel(name)` — real-time — `junction/src/transport/channels.ts`. Services declare `channel: 'posts'`; `callService` is the single announcement point for both the bus (`svc:created`) and channels (`svc created`). **A custom method announces too, under its own name** (`orders pay`); only `find`/`get` are excluded, and a read-shaped one opts out with `ctx.dispatch = false`. **`app.channels.publishDefault(fn)` is the catch-all**, consulted only where a service declares nothing, so it composes with `channel:`; function-only, and the plugin reports at boot which services fall through to it (`FJS-D80`, `FJS-334`). **A write that came through no service announces too** — `announceDataWrites` taps litestone's `$tapEvents` into the same fan-out — in one of THREE shapes litestone decides: a write holding its row broadcasts `created`/`updated`/`removed` with the row, one holding only a count broadcasts **`changed`**, and a **named move broadcasts under the move's own name**, the same event `callService` announces for that transition through the owning service (`FJS-463`). **A transition fires both an `update` and a `transition` event for one write**, so litestone stamps the update with the move's name — only when the transition event is really coming, since `asSystem()` suppresses it — and the tap skips the stamped one. **A model's services are found through `accessorCandidates`, every spelling indexed to a SET of services** (`FJS-765`, `FJS-464`), so every service over the model is told; a DECLARED `model:` is the only spelling that service claims, so one named `orders` over `model: 'Invoice'` receives no `Order` writes. The caller's `where` reaches the in-process bus and never the wire
- **Transport: WebSocket when one is connected, HTTP as the fallback.** Every service call — CRUD and custom methods — checks `_wsReady` first; over WS it is a `service_call` frame naming the method, over HTTP the REST verb (a custom method: `POST /{service}/{id}` + `X-Service-Method`). The one exception is a payload carrying a File. **A custom method may address the COLLECTION** — `invoke(name, null, data, query)` posts to `/{service}`. The two paths share almost nothing and can drift; `env.verifyTransportParity()` (`@frontierjs/testing`) checks they agree
- `createJunctionClient()` / `client.resource(name)` — `junction/src/client/index.ts`, consumed at `sierra/src/junction/index.js`
- `resource.save(data, { mode })` — **the one owner of "write this record"** (`FJS-D114`). `auto` creates when the model's OWN id field is absent and patches when it is present, `create`/`patch` force one, `upsert` is an alias of `auto`. `<Form>` calls it rather than choosing a service method, because the decision turns on the id field the schema names — the literal `id` on a model keyed otherwise creates a duplicate row that looks like an edit (`FJS-316`). It runs through `_call`, so coercion, blank-stripping, validation, the `@version` this screen read and the resource's own hooks all apply. The reads are declared beside it: `detailQuery` is what `get(id)` asks for when the caller states none, `optionsQuery` what a picker asks for, both `{ query, directives }` — `sierra/src/junction/resource.js`
- `client.auth.*` — the browser half of `@frontierjs/auth` (`FJS-D20`): `signIn`/`signUp`/`signOut`/`me`/`changePassword`/`sessions`/`apiKeys`/reset/verify. It lives on the CLIENT because the client holds the token, opens the socket and knows both prefixes. It speaks the server's own split — the routes that establish a session, the services for what the caller does next — `junction/src/client/index.ts`
- `signIn` → `completeSignIn(code)` — **the client holds the ticket, and a page never does** (`FJS-D261`). `signIn` answers a session or a challenge, told apart by the absence of a USER rather than the presence of a ticket: in cookie mode the transport strips `challenge` as it strips `token`, so a screen keyed on the ticket treats a real challenge as a session. A challenge stores nothing, opens no socket and **emits no `authenticated`**. The ticket is held on the client, as the token is, dropped before the next `signIn` and on `signOut`, and never persisted. Sierra's page-facing half is `submitCode(code)` + the reactive `session.awaitingCode`; jetty's is `auth.submitCode` through Harbor, which owns the storage and the broadcast. `retryable: false` is the server saying *start again from the password*, which closes the box. **The enrollment half is five `client.auth` methods named as the provider names them** — `totpStatus`, `setupTotp(currentPassword)`, `confirmTotp(code)`, `disableTotp`, `regenerateRecoveryCodes` — and a refusal there is 403 because the session is fine; `unauthorized` fires only for a request that presented its credential, so a wrong code does not close the box on a live ticket (`FJS-1088`) — `junction/src/client/index.ts`
- `client.auth.providers()` + `OAUTH_ERRORS` / `session.oauthMessage` — **the two things a sign-in screen cannot derive.** Which providers exist is asked of `GET /auth/oauth` rather than listed in the app, because the screen is a separate build from the API and a copy of `oauthProviders` drifts silently in both directions. What an `oauth_error` code MEANS is sierra's one table: the callback is a redirect, so the only channel back is a query parameter carrying a coarse token. `session.oauthError` is kept beside the sentence because **`link_required` is not a failure** — the next step is in the person's inbox — so a screen branches on the code and renders the words — `junction/src/client/index.ts`
- `tokenStorage` on the client + `session` in sierra — **the token has one owner and the session has one shape.** `setToken` persists, clears and emits `token`; `@frontierjs/sierra/junction`'s `session` is the reactive object over it, with `ready` for the navigation guard — `junction/src/client/index.ts`
- `client.nodes` / `resource.record(id)` — **one node per row, keyed by MODEL, and a list is a VIEW over it** (`FJS-D138`), `junction/src/client/nodes.ts`. Two `createResource('orders')` share rows, and a row read with `service.get(id)` is reached by announcements (`FJS-518`). The model name is passed in because junction holds no schema, as with `match`; **the id is normalized into the key**, because a list holds `{ id: 5 }` and a detail screen is reached by a URL carrying `'5'`. **Lifetime is a TTL** (`nodeTtlMs`), never a reference count an application maintains. `record(id)` is a view of one, and sierra's wraps it so the first read goes through the resource's own `_call('get')`. **`{ composed: true }` is the second mode** (`FJS-D161`): where a service's `get()` answers the row PLUS what hangs off it, a push carries the row alone, so the node is the TRIGGER, the view keeps its own value, and any move of that node re-runs the read, coalesced per burst. Declared, because nothing in a browser can see what a `get()` composes. **`changed` re-reads in both modes.** **A push moves the value and never the remembered `@version`**: the node is the synced truth, the view is what this screen READ, and a draft is in neither. **`resource.mutate(id, intent, run)`** stores the INTENT rather than the value it produced, settled against the MUTATION so a second writer moves the truth underneath; a create is refused by name, since there is no id and no row to show the change against
- `matchesQuery(fields, record, query)` → `resource(name, idField, { match })` — **is this pushed record still in the list `load()` asked for?** Junction owns the store and holds no schema, so the decision comes from `toolbelt/src/match/match.js` — substrate, so every side may import it — re-exported at `sierra/src/junction/field-rules.js` and imported directly by jetty's store, over the same operators `parseWhere`/`translateOps` accept and with SQL's null semantics. `true` upserts, `false` REMOVES, `null` is *undecidable from this record* and reloads. A caller passing no `match` gets apply-everything behavior
- `$after` / `endCursor` / `resource.more()` — **a live list grows a window; it does not step through pages** (`FJS-D145`). One row in `@frontierjs/toolbelt/directives`, so both transports carry it. A caller sending `$after` is on the keyset path: no OFFSET, no COUNT, and `total` is `null` rather than guessed. An ORDINARY page carries the edge too — `endCursor`/`hasMore` on the list envelope, minted from the last row it already holds, so growing costs no extra query. **The tiebreaker is the schema's and litestone owns it**: `cursorFor(row, orderBy)` and `findManyCursor` derive the same sort keys, appending the model's id where the ordering is not total — an ordering with no unique column serves a row twice and skips another silently — and refusing only where there is nothing to append. `offset` is untouched: **offset is what you ASK for, the window is what a live resource GETS**. **`findWindow(table, args, after, label)` is the server half and is exported** for a service that assembles its own query (basecamp's audit trail), so the tiebreaker and the absent `total` keep one answer. The page runs in **`table.orderTotal()`**'s ordering rather than the caller's, since the two differ on a tie and the edge must name where the page actually stopped (`FJS-535`). A list whose ties cannot be broken carries **no edge rather than a wrong one** — `toolbelt/src/directives/directives.js`
- `comparatorFor(orderBy)` — `junction/src/core/query-values.ts`, **the one reading of `orderBy` and of `select`**: `parseSort` IS `normalizeOrderBy` and `parseSelect` IS `normalizeSelect`, so the SQL the server compiles, the position the browser gives a pushed row, and the query Sierra puts to a device's own SQLite all come from one parse of `-createdAt`. Re-exported from `@frontierjs/junction/client`, which is how a browser reaches them without pulling the server entry. `compareValues` follows SQLite (NULLs first ascending, numbers before text, a Boolean as its stored 0/1) and states where it cannot be exact. What no client can answer is paging — past page 1 a pushed row is refused and counted on `resource.stale`

# Bridge index — detail

The full entry for each seam the `bridge-index` skill lists. Reached from the index; the index line is the one `seams.js` parses, so an owner changes THERE.

## Data → API

- `$setAuth(user)` / `asSystem()` — the Data-boundary checkpoint / bypass — `litestone/src/core/client.js`
- `$tapEvents(fn)` — every write, announced. `event` is `create` · `update` · `remove` · `transition`, and a transition carries `transition` (the move's name) and `record` where the others carry `result`. **Two shapes and the write says which**: `scope: 'row'` (one row; `result` is it, or `null` where `select: false` skipped the RETURNING) or `scope: 'collection'` (`count` rows matching `where`, never built). Read `scope`; never infer it from `result`. A bulk write's shape is the per-call `announce` — `collection` (default) · `rows` · `none`, floor at `createClient({ announce })` (`FJS-D34`) — `litestone/src/core/client.js`
- `withLitestoneDb(db)` — per-request scoped client on `ctx.locals.db`; auto-installed by `createApp({ db })` — `junction/src/core/litestone.ts`
- `gateAuth()` + `autoValidate()` — schema-derived 401s/400s for model services — `junction/src/core/litestone.ts` + `core/service.ts`
- `validateInput(type)` — **the same 400 for a method no model describes.** `autoValidate` covers create/patch on a model service; for any other method a `methods:` entry may be `{ method, input }`, where `input` names a `type T { … }` in the app's own seed. The payload compiles through the same `jsonSchemaToJunctionSchema` → `createSchema` pair, carrying `@label` and the author's `x-messages` into a 400 that renders in `<Form>` like a CRUD one. A CRUD name may carry one, replacing the model-derived validator. **A named type that is not there THROWS**, where a missing model only warns. **Declaring an input also declares the SURFACE** — `{ method: 'pay' }` narrows exactly as `'pay'` does, so a service gaining its first `methods:` answers 405 to every verb it did not name; `surface.snapshot.md` carries the policy-applied list and the inputs, so that shows as a CI diff. Transforms such as `@trim` are NOT applied here (`FJS-401`): the two boundaries apply transforms on opposite sides of validation, so they would disagree about what is valid — `junction/src/core/litestone.ts` Ruled: `FJS-D458`.
- `customMethodGrade(method, declared, levels)` → `{ source, level, graded }` — **what stands between a caller and a custom method; ask it rather than re-deriving.** `collectCustomMethods` decides that a key IS a method; this decides what grades it. Three answers: `declared` (a `methods: [{ method, gate }]` number, compared against the caller's standing), `floor` (no declaration, so the model's `@@gate` update level is a PRESENCE check and the level is never compared) and `unchecked` (no declaration and no model, so the API boundary checks nothing — a method writing through `asSystem()` from there is reachable by everyone who can sign in). **The declaration is read before the model**, so `gate: 5` on a modelless service is enforced (`FJS-1087`). `levels` separates `null` (no gate) from `undefined` (a describer holding no schema — `strategy database` has no app-wide client), so the declared half is still reported where the floor's number cannot be read. **`@frontierjs/mcp` is the second caller and imports it** to decide which tools a standing may see (`FJS-D197`) — `junction/src/core/litestone.ts`
- `needsBackfill` on a release finding → `fli release:check` — **the middle step of a split, made checkable** (`FJS-D157`). `classifyPivot` refuses a contract on a required column and hands back *expand → backfill → contract*; the finding carries `{model, field}` and stops there, since litestone sits below the package that fills the column. `packages/cli/core/backfills.js` reads the app's own SOURCE for a `defineBackfill` naming that pair, never a directory convention. Whether it has RUN is a row in the deployed database, which no command can answer, and the output says so
- `sessionGateLevel(user)` — `SessionContext` → the 0–7 scale; pass to `GatePlugin({ getLevel })`. Both sides call `gradeStanding` from **`@frontierjs/toolbelt/gate`**, which also owns `LEVELS`, `LEVEL_NAMES` and `levelPasses` — Litestone cannot import Junction, so the kit is the one grader (`FJS-D197`). Sierra's `canAtLevel` and `transitionsAt` read the same `levelPasses`, so a screen's verdict and the boundary's are one function — `junction/src/core/litestone.ts`
- `toDataPrincipal(user)` — the other half of the same translation: `SessionContext` → the principal `auth()` reads (`userId` → `id`). Applied at both `$setAuth` call sites. Without it every row policy compares against `undefined` and matches nothing, silently. **Two functions, one boundary**: change either and ask whether the other needs it too — `junction/src/core/litestone.ts`
- `bearerClaim({ from, model, column, claims, key, subject })` / `BEARER` — **the resolver for a caller with no session who still owns rows** (`FJS-D343`), `junction/src/core/litestone.ts`. `membershipClaim`'s sibling: that one serves a session proving who the caller is, this one a string whose holder is the whole proof. The grant row is READ by `fingerprint(token, { key, purpose })` from `@frontierjs/toolbelt/bearer`, which is what the column holds, so the token is in no query, log line or error; what reaches a policy is the SUBJECT it resolved to, an id compared to an id. `revokedAt`/`expiresAt` are read off columns the app's own model declares. All three refusals wear one sentence, so the refusal is not an oracle for which tokens existed. The resolved row is parked at `ctx.locals[BEARER]`, which is also how `installLogContext` names the grant as the audit actor (`FJS-D342`). `header()` and `cookie()` are the shipped readers and each falls back to `requestMeta()`, since `CallOptions` carries no client
- `resolveTenancy(schema)` / `registry.tenantFor({host, headers, principal})` — **the one reading of `tenancy { }`**; the API asks it rather than re-deriving. `createApp({ tenants })` installs `withTenantDb`, which assigns the same `ctx.locals.db` that `withLitestoneDb` does and therefore replaces it. Under `strategy row` nothing is swapped and `tenantClaimGuard` refuses a signed-in principal with no claim rather than answering an empty list with a 200 (`FJS-D05`) — `litestone/src/core/tenancy.js`
- `accessorCandidates()` — `model Post` ⇄ service `posts` ⇄ `db.post`; shared by query, gate and validation so a naming slip cannot disable just one — `junction/src/core/litestone.ts`
- `db.$checkWhere(accessor, where)` → `[{key, suggestion, allowed}]` — the one definition of "is this a valid filter key", asked rather than copied; junction's `autoFilter` calls it. An unknown accessor answers `[]` — *I cannot judge this* is not *this is wrong* — `litestone/src/core/client.js`
- `db.$checkOrderBy(accessor, orderBy)` → `[{key, reason, suggestion, sortable, message}]` — the sibling, identical contract; junction's `autoSort` calls it. **Both halves throw** — a bad sort key returns the right rows in the wrong order, which nothing downstream can see. `reason` separates *no such field* from *`@computed`* (SQLite can neither sort nor paginate by it) and from *`opaque`* — an array, a `Json`, a `File` or an encrypted column, whose stored TEXT is a serialization rather than the value. A `@from` field sorts — `litestone/src/core/client.js`
- `db.$readAs(accessor, row, principal)` → the row as that principal would have read it, or `null` — **the check a BROADCAST needs, because a broadcast is not a SELECT**: `@@allow` compiles into a WHERE, so a row reaching a caller through a WebSocket frame is filtered by nothing else (`FJS-631`, `FJS-D175`). Takes its subject as an ARGUMENT, as `$capabilitiesFor` does, because the asker holds one client and is answering about somebody else. Three questions in order: the **gate** (about the caller alone, and the whole answer for a stranger), the **row policy** (`policyVerdict`, in JS against the row in hand — no query), then the **field policies**. Every protection STRIPS for a non-system reader and a recipient is never system, so no decrypt branch runs; the row is not re-read, so a `@from`/`@computed` value is the writer's. **Fails closed** — an undecidable policy throws and a throw refuses. **Two readers**: the broadcast fan-out, and a webhook delivery, which grades as the principal that REGISTERED it (`FJS-D193`). `db.$readGrading(accessor)` → `'open' | 'graded'` lets a caller skip grading, and an unknown accessor is `graded` — the opposite of the other siblings' empty answer, because here uncertainty would be a permission — `litestone/src/core/client.js`
- `db.$levelOf(accessor?, principal?)` → the level the APP grades a caller at for that model, or `null` — **ask this rather than re-deriving a level** (`FJS-D308`). The app's mapping from its own standing onto the 0–7 scale is declared once, in `GatePlugin({ getLevel })`, and grades every read and write; grading with the shipped `gradeStanding` instead disagrees wherever a standing is not a column on the session, such as a level read off a membership row (`FJS-1161`). **The principal is OPTIONAL**, unlike `$readAs`: the common caller holds the scoped client of the caller it is asking about, which also picks up the gate's per-request cache; state one to grade somebody else. Per MODEL because `getLevel` is, and an accessor naming no model grades with a `null` model, which is what a modelless service means. **`null` is *I cannot grade*, never a level**: no `@@gate` means no plugin, and junction's `callerGateLevel`/`principalGateLevel` fall back to `sessionGateLevel` there — the resolver such a schema auto-installs — `litestone/src/core/client.js`
- `db.$primaryKey(accessor)` → the key's columns, **in key order**; `[]` for an unknown accessor, same contract on every flavor of client. Ask it rather than the fields: `expandCompositeId` stamps `@id` on every member of an `@@id([a, b])`, so the fields answer all members in declaration order, while the key's own order — the order its implicit index is prefix-matched on — is stated only on the model attribute. Junction's derived `get` reads it to refuse a one-value id against a composite key by name, since a URL segment is one value (`FJS-694`) — `litestone/src/core/client.js`
- `db.$claimsFor(principal)` → `{ <claim>: value | null }` — **the claims the schema reads off a row pointing at the caller**, `claim siteId from Employee(userId).siteId` (`FJS-D359`). The subject is an ARGUMENT, as for `$capabilitiesFor`, and every flavor answers the same. Read as the system, with the model's own exclusions intact, so a soft-deleted role row resolves to nothing; no id is `{}`, no row is `null`. **Junction calls it inside the principal seam** — `withLitestoneDb` and `withTenantDb`, before the app's `principal:` resolver — and merges without marking the request RESOLVED, so the tenant guard's sentence still says which of the two refusals it is. A resolver answering a sourced claim is refused by name. The tenant-keyed shape (one row per tenant per person) is `membershipClaim`'s — `litestone/src/core/client.js`, `junction/src/core/litestone.ts`
- `db.$protectedFields(accessor)` → `{ field: 'guarded' | 'encrypted' | 'hashed' }` — **which columns must never be written down in plain text**; an unknown accessor answers `{}`, every flavor of client answers the same. `@@log(audit)` redacts these in litestone's own JSONL (Invariant 7); an application keeping an audit table of its own asks this rather than hand-copying the names. The value names WHICH protection because the three are not interchangeable — `litestone/src/core/client.js`

Both `$check*` live on **every flavor of client** — root, `$setAuth`, `asSystem`, `$scopedBy`. Filterability is a fact about the schema; auth has no bearing on it.

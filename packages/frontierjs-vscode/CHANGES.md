# Changes — frontierjs-vscode

## 2026-08-27 — real icons, and `.mesa` gets one at all

`0.1.1`. `npm test` 88 pass, `verify:package` green.

**Mesa had no icon in the manifest for its whole life** and Litestone's was a
placeholder: three horizontal lines in a 282-byte SVG, one stroke tinted blue.
Both languages now ship artwork — a sun behind a butte for `.mesa`, a feather
for `.lite`/`.litestone` — cut from three design sheets, and `frontierjs.png`
is the frontiersman rather than the same three lines at 128px.

**The 16px render is what picked them, not the sheet.** Each sheet offered a
file glyph, a circle badge and a monoline mark in five colorways, and at the
size an explorer row actually uses most of that is a smudge — the frontiersman
loses his hat and becomes an orange blob. The two that ship are single-idea
silhouettes, checked at 16, 24 and 32 against a dark and a light ground before
anything was wired up. The frontiersman is the marketplace icon, where it is
drawn at 128 and is the only one of the three that can carry that much detail.

**Nothing is upscaled except the marketplace icon, which has to be.** The tiles
are ~110–130px on the sheet, so `mesa.png` and `litestone.png` are 168 and 166
square with the art centered at native pixels; the brand icon is the 131px
circle scaled to the 128 the marketplace requires. `frontierjs.svg` and the two
`litestone-{light,dark}.svg` placeholders are deleted, and with them the
`convert` line the package map documented — `icons/*.png` is the master now.

**What no check here can see is whether the icon is SHOWN.** A file icon theme
decides that, and Seti — the default — maps extensions itself. `verify:package`
asserts every icon the manifest names is inside the `.vsix`, which is the half
that can be wrong silently; the other half needs an editor and an eye.

The three source sheets are ~5.6MB and were sitting in `icons/`, which ships:
they were 91% of the packaged `.vsix` (5.84MB against 556KB without them).
`0.1.0` predates them, so nothing was published carrying them. They are kept on
disk and renamed `*.image-ref.png`, a repo-wide convention added to the root
`.gitignore` in the same change — a design source is regenerated by asking for
it again, not by cloning it. vsce needs its own spelling (`**/*.image-ref.*`),
because `*` does not cross a `/` there and the gitignore form would have missed
everything under `icons/`.

## 2026-08-27 — publish readiness

Nothing about the extension's behavior. `npm test` 88 pass (46 Litestone over
real LSP/stdio, 36 Mesa, 6 snippets), `npm run verify:package` green.

**The suites were green and the extension was not installed anywhere**, which is
the failure this package is most exposed to: every check here runs the built
output headlessly, and none of them can see whether an editor is loading it.
Three stale rows sat in `~/.vscode/extensions/extensions.json`
(`your-publisher-name.mesa-language-support`,
`undefined_publisher.frontierjs-vscode-extension`,
`frontierjs.mesa-language-support`) with no directory behind any of them, so the
older-copy hazard the package map warns about read as the live explanation while
the real one was that nothing had ever been installed. Both suites accept a path
(`FJS_LSP_SERVER`, `FJS_MESA_CLIENT`), so the installed copy is now checked the
same way the unpacked `.vsix` is — 82 of the 88 assertions run against it.

**`capabilities` is declared, and it is the one entry that is a security
statement rather than metadata.** Mesa diagnostics load the workspace's OWN
`@frontierjs/mesa` and call it, so opening a folder executes code from that
folder. An extension that declares nothing is disabled in a restricted workspace
already, which is the right behavior arrived at by accident — declaring
`untrustedWorkspaces: { supported: false }` says why, where a reader can see it.
`virtualWorkspaces: false` is the same fact one layer down: the Litestone server
is a node process and both languages resolve through the filesystem, so there is
nothing for this to do on github.dev.

**`CHANGELOG.md` is a fifth markdown file at the package root and the allowance
is the answer to Invariant 17's question.** The marketplace renders a Changelog
tab and reads that name and no other; this file is the engineering history and
is written for somebody working in the tree. Two audiences, so two files, and
`CHANGES.md` is `.vscodeignore`d along with `PROJECT_STATE.md`.

The assertion counts in `README.md` and the package map had both gone stale in
different directions — 76/34 and 76/46 against an actual 88/46. A count written
by hand has no way to be wrong out loud; `npm test` prints the real one.

`FJS-309` is closed for this package: `PROJECT_STATE.md` and `CHANGES.md` were
the two files it named here.

**The publisher is `frontierJS` and the capital JS is load-bearing.** The
manifest had `frontierjs`, which is the extension ID VS Code writes on disk and
not the marketplace publisher ID — vsce compares the manifest against the PAT's
publisher, so the first publish would have been refused by a name that reads
identically in a diff. `repository` now names the real monorepo with a
`directory`, alongside `bugs` and `homepage`; it had pointed at
`github.com/frontierjs/vscode`, a repository that does not exist, which the
marketplace would have linked to from the listing page.

# JSON Schema output

`generateJsonSchema(schema, options)` turns a parsed `.lite` schema into one JSON
document. **It is the wire between the Data realm and the two above it** — a
Junction service derives its request validation from it and never restates a
rule, and a Sierra `createResource` derives its labels, constraints, relation
pickers and transition buttons from the same document. One authored `.lite` line
becomes the sentence all three realms say.

Everything below was produced by running the generator, not read off the source.
The fixture that produced it is at the end of this file.

---

## Producing one

```js
import { generateJsonSchema } from '@frontierjs/litestone'

const doc = generateJsonSchema(db.$schema, { mode: 'full' })
```

From the CLI, in the directory whose `litestone.config.js` (or `./schema.lite`)
you want:

```bash
litestone jsonschema                       # → ./schema.json, beside the .lite
litestone jsonschema --mode=full --stdout  # → stdout, safe to pipe
litestone jsonschema --all-modes --out=./schemas/
```

The default output path is the schema path with `.lite` swapped for `.json`,
which is exactly what both apps have committed. Two apps in this repo keep a
generated copy in the tree — [example/db/schema.json](../../../example/db/schema.json)
and [packages/basecamp/db/schema.json](../../basecamp/db/schema.json), both
`mode: 'create'`. Neither is regenerated by a build step, so **a committed copy
can lag the `.lite` beside it** — example's was missing `Order.trackingCode` on
2026-08-07. Regenerate before citing one.

### CLI flags

| Flag | Effect |
|---|---|
| `--out=<path>` | a directory gets `schema.json` written into it; default is the schema path with `.lite` → `.json` |
| `--stdout` | print instead of writing (the banner is suppressed, so it pipes) |
| `--format=definitions\|flat` | `$defs` + `$ref` (default), or every definition at the document root |
| `--mode=create\|update\|full` | default `create` |
| `--all-modes` | write all three, `schema.create.json` / `.update.json` / `.full.json` |
| `--include-timestamps` | keep `createdAt` / `updatedAt` |
| `--include-deleted-at` | keep `deletedAt` |

`audience`, `inlineEnums` and `title` are API-only — no flag reaches them.

---

## Modes

The mode decides **which fields exist**, never what they mean. Every structural
annotation (`x-gate`, `x-relations`, `x-transitions`, `x-version`) is emitted in
all three.

| | `create` (default) | `update` | `full` |
|---|---|---|---|
| `@id` | omitted — server-assigned | present | present |
| `required[]` | non-optional fields with no `@default` | *absent — a patch is partial* | same as create |
| `@version` | omitted | `readOnly` | `readOnly` |
| `@computed` / `@generated` / `@from` | omitted | omitted | `readOnly` |
| `@transient` | `writeOnly` — and in `required[]` when non-optional | `writeOnly` | omitted — no read answers it |
| `createdAt` / `updatedAt` | only with `includeTimestamps` | same | same |
| `deletedAt` | only with `includeDeletedAt` | same | same |

There is **no `includeComputed` option**, despite the name appearing in older
notes and in the CLI's own option object — the generator never destructured it,
so passing it changed nothing. Derived fields are a property of `full`.

Junction calls the generator with **no options at all**, so its server-side
validation runs against the `create` document and drops `required` itself for
`patch`. A field you cannot see in a create schema is a field Junction will not
validate.

## Document shape

```json
{
  "$schema": "https://json-schema.org/draft-07/schema",
  "$defs": {
    "Article": { "type": "object", "title": "Article", "properties": {…} },
    "Comment": {…},
    "Status":  { "type": "string", "enum": ["draft","published","archived"], "title": "Status" },
    "Address": { "type": "object", "title": "Address", "properties": {…}, "required": ["line1","city"] },
    "FileRef": { "type": "object", "x-litestone-file": true, … }
  }
}
```

**`$defs` is the whole definition table** — models keyed by PascalCase model
name, enums, `type T { … }` declarations, and `FileRef` when any model has a
`File` field. It has to travel whole: an enum field is `{"$ref":"#/$defs/Status"}`
and the reference dangles without its target. `--format=flat` moves the same
entries to the document root instead — **but the refs still say `#/$defs/Status`**,
which points at nothing in a flat document. Consumers here resolve a ref by its
trailing name rather than by following the pointer, so both formats work; a
generic validator only works on `definitions`.

The document declares draft-07 but names its definition table `$defs`
(2019-09's spelling, not draft-07's `definitions`). Every consumer in this repo
resolves refs by hand and accepts both spellings —
[sierra/src/junction/schema-registry.js:167](../../sierra/src/junction/schema-registry.js#L167) — but a
strict off-the-shelf draft-07 validator will not follow `#/$defs/…`.

## Every key it emits

### Standard keywords

| Key | Where | Comes from |
|---|---|---|
| `$schema` | document | always, draft-07 |
| `$defs` | document | `format: 'definitions'` |
| `$ref` | field | enum type, `Json @type(T)`, `File` |
| `type` | model, field, def | `object` on models/types; the mapped type on fields |
| `title` | model, field, enum def | model/enum name; on a field it is `@label("…")` |
| `description` | model, field | doc comments above the model or field, joined |
| `properties` | model, type def | one entry per writable field |
| `required` | model, type def | omitted when empty and in `update` mode |
| `additionalProperties` | model, type def | always `false` — strict by default |
| `default` | field | literal `@default`; `now()`/`uuid()` and friends are runtime-only and emit nothing |
| `enum` | enum def, field | `inlineEnums: true` puts the values on the field |
| `anyOf` | field | how a nullable `$ref` or a nullable constrained field is expressed |
| `readOnly` | field | `@version`, `@computed`, `@generated`, `@from`, `@system` |
| `writeOnly` | field | `@transient` — the mirror, and the reason the pair is used rather than an `x-` key |
| `items` | field | array types (`String[]` → `{type:'string'}`, `Int[]` → integer) |
| `format` | field | `@email`→`email`, `@url`→`uri`, `@phone`→`phone`, `@date`→`date`, `DateTime`/`@datetime`→`date-time` |
| `contentMediaType` | field | `@markdown` → `text/markdown` |
| `contentEncoding` | field | `Bytes` → `base64` |
| `pattern` | field | `@regex`, and `@startsWith`/`@endsWith`/`@contains` (anchored, regex-escaped) |
| `minLength` / `maxLength` | field | `@length(min, max)` |
| `minimum` / `maximum` | field | `@gte` / `@lte` |
| `exclusiveMinimum` / `exclusiveMaximum` | field | `@gt` / `@lt` |
| `minItems` / `maxItems` / `uniqueItems` | field | the array validators |

Nullability is `type: ['string','null']` on a plain field and `anyOf: [ …, {type:'null'} ]`
as soon as the field is a `$ref` or carries any other keyword.

### `x-` extensions

Everything Litestone knows that JSON Schema has no word for. **Read the column
before you build on one** — several are emitted and nothing yet reads them.

| Key | On | Value | Read by |
|---|---|---|---|
| `x-messages` | field | `{ ruleName: msg, keyword: msg }` — the same authored string under both aliases | junction `schema.ts`, sierra `field-rules.js` |
| `x-relations` | model | `[{field, model, type: 'belongsTo'\|'hasMany'\|'m2m', fields, references, onDelete, optional}]` | sierra `field-rules.js`, `resource.js`, `fli` |
| `x-gate` | model | `{read, create, update, delete}` — the `@@gate` levels, 0–9 | sierra `field-rules.js` (affordance), static-safety |
| `x-transitions` | model | `{ field: { name: {from: [], to, gate: N\|null} } }` | sierra `field-rules.js`, `example`'s orders screen |
| `x-version` | model | the `@version` column's name, so a client knows what to round-trip | sierra `field-rules.js` |
| `x-litestone-file` | `FileRef` def | `true` — marks the def as a file ref, not a user `type` | junction (maps it to `any`), `fli` |
| `x-litestone-kind` | field | `'version'` \| `'computed'` \| `'generated'` \| `'from'` \| `'system'` \| `'transient'` | junction (`liftTransient`), tests |
| `x-litestone-from` | field | `{target, op}` from `@from(Model, count: true)` | nothing yet |
| `x-litestone-accept` | field | the `@accept("image/png,image/jpeg")` **string**, verbatim — not an array | tests only |
| `x-litestone-policies` | model | `true` when the model has any `@@allow`/`@@deny` | nothing yet |
| `x-litestone-read-policy` | field | `true` when a field-level `@allow('read', …)` may hide it | nothing yet |
| `x-litestone-secret` | field | `true` — `audience: 'system'` only | nothing yet |
| `x-litestone-guarded` | field | `true` — `audience: 'system'` only | nothing yet |

`x-gate` and the `gate` inside `x-transitions` are **UI affordances**. The Data
boundary enforces regardless of what the client believes, so an unknown answer
is permissive by design (Invariant 6).

## `x-messages` — one sentence, several keys

Every validator takes a trailing message. It is published under **both** the rule
name and the JSON Schema keyword the rule compiles to, so a consumer that caught
a `minLength` failure looks up `minLength` rather than carrying a
keyword→rule table of its own:

```json
"title": {
  "type": "string", "minLength": 3, "maxLength": 120, "title": "Headline",
  "x-messages": {
    "length":    "A headline is 3 to 120 characters",
    "minLength": "A headline is 3 to 120 characters",
    "maxLength": "A headline is 3 to 120 characters"
  }
}
```

from `title String @label("Headline") @length(3, 120, "A headline is 3 to 120 characters")`.

Aliases: `email`/`url`/`date`/`datetime`/`time`→`format`, `regex`/`startsWith`/`endsWith`/`contains`→`pattern`,
`length`→`minLength`+`maxLength`, `gte`→`minimum`, `gt`→`exclusiveMinimum`,
`lte`→`maximum`, `lt`→`exclusiveMaximum`, `minItems`/`maxItems` unchanged.
`@required("…")` publishes under `required` only — required-ness lives in the
model's `required[]`, not on the field.

## Audience

`audience: 'client'` (the default) **removes fields rather than marking them**:

- `@secret` and `@guarded(all)` — gone from every mode.
- `@guarded` (select-level) — gone from `create` and `update`, present in `full`.
- A field-level `@allow('read', …)` field is made nullable and annotated
  `x-litestone-read-policy: true`, because whether it arrives depends on who asked.

`audience: 'system'` keeps them all and annotates instead:

```json
"apiKey": { "anyOf": [ { "type": "string", "x-litestone-secret": true }, { "type": "null" } ] }
```

A client-audience document is safe to ship to a browser. **A system-audience one
names your secret columns** — it is for tooling, not for a page.

## Type mapping

| `.lite` | JSON Schema |
|---|---|
| `String` | `{type:'string'}` |
| `Int` | `{type:'integer'}` |
| `Float` | `{type:'number'}` |
| `Boolean` | `{type:'boolean'}` |
| `DateTime` | `{type:'string', format:'date-time'}` |
| `Json` | `{}` — any value |
| `Json @type(T)` | `{$ref:'#/$defs/T'}` — full object schema, required keys and validators included |
| `Bytes` | `{type:'string', contentEncoding:'base64'}` |
| `File` | `{$ref:'#/$defs/FileRef'}` |
| `EnumName` | `{$ref:'#/$defs/EnumName'}`, or inline values with `inlineEnums: true` |
| `String[]` / `Int[]` | `{type:'array', items:{type:'string'\|'integer'}}` |
| relation field | **absent** from `properties` — described in `x-relations` instead |

The FK column of a `belongsTo` is emitted as a plain integer. The browser only
knows it is a reference because `x-relations` says so — that is what turns it
into a picker instead of a number spinner.

## Traps

- **`@default` sits beside `$ref` on an enum field** (`{"$ref":"#/$defs/Status","default":"draft"}`).
  A strict draft-07 validator ignores every sibling of `$ref`, so the default is
  invisible to one. Every consumer here reads it directly.
- **A relation field is not in `properties`.** It used to be, and being
  non-optional put it in `required[]`, so Junction rejected every create that
  did not carry a relation array and Sierra seeded a meaningless `[]`.
- **`x-transitions` is on the model, never on the enum `$def`.** Only a model can
  carry a per-transition `@gate`, and two sources would drift the moment one
  model narrowed the machine.
- **`x-version` is emitted in `create` mode too**, even though the column is not —
  it is structural metadata about the model, not a field listing.
- **`$defs` keys are model names, service names are not.** `model Article` is
  `$defs.Article` while the service is `articles`; sierra's `modelNameFor()`
  handles regular English plurals only.
- **`@default(auth().id)` fields are optional in `create`** — present in
  `properties`, deliberately absent from `required[]`, because Junction stamps
  them from the auth context.

## The fixture

Every snippet above came from generating this schema. It exercises each key at
least once, which no app in the repo does — `example` has no `File`, `@from`,
`@version` or `Bytes` field, and `basecamp` has no `@@gate`:

```
enum Status { draft published archived }

type Address {
  line1 String @length(1, 80)
  city  String
  zip   String? @regex("^[0-9]{4,10}$")
}

model Article {
  id        Int      @id
  title     String   @label("Headline") @length(3, 120, "A headline is 3 to 120 characters")
  slug      String   @unique
  status    Status   @default(draft)
  body      String   @markdown
  score     Float    @gt(0) @lte(100)
  tags      String[] @minItems(1) @maxItems(5)
  thumbnail File?    @accept("image/png,image/jpeg")
  payload   Bytes?
  address   Json?    @type(Address)
  views     Int      @from(Comment, count: true)
  wordCount Int      @computed
  version   Int      @version
  apiKey    String?  @secret
  salary    Float?   @allow('read', auth().role == 'admin')
  authorId  Int      @default(auth().id)
  author    User     @relation(fields: [authorId], references: [id], onDelete: Cascade)
  comments  Comment[]
  createdAt DateTime @default(now())
  updatedAt DateTime @updatedAt
  @@gate("2.4.4.6")
  @@allow('read', status == 'published')
  @@transitions(status, publish: draft -> published, archive: published -> archived @gate(5))
}
```

`mode: 'full'`, `audience: 'client'` — the derived fields, which no other mode has:

```json
"views":     { "type": "integer", "readOnly": true, "x-litestone-kind": "from",
               "x-litestone-from": { "target": "Comment", "op": "count" } },
"wordCount": { "type": "integer", "readOnly": true, "x-litestone-kind": "computed" },
"version":   { "type": "integer", "readOnly": true, "x-litestone-kind": "version" }
```

and the model-level annotations, identical in all three modes:

```json
"x-litestone-policies": true,
"x-version": "version",
"x-gate": { "read": 2, "create": 4, "update": 4, "delete": 6 },
"x-transitions": {
  "status": {
    "publish": { "from": ["draft"],     "to": "published", "gate": null },
    "archive": { "from": ["published"], "to": "archived",  "gate": 5 }
  }
},
"x-relations": [
  { "field": "author",   "model": "User",    "type": "belongsTo",
    "fields": ["authorId"], "references": ["id"], "onDelete": "Cascade", "optional": false },
  { "field": "comments", "model": "Comment", "type": "hasMany",
    "fields": [], "references": [], "onDelete": null, "optional": false }
]
```

# Issues

**The register of everything open in this repo.** Defects, gaps, and questions
awaiting a ruling. One id per item, stable forever.

**This file is the source of truth for what is open.** Nothing is open unless it
is here. Other documents no longer carry their own open-item lists — they link
here. Long analysis may stay where it was argued (`packages/*/PROJECT_STATE.md`,
`IDEAS/*.md`, `drift-report.md`); the **Detail** column points at it. What must
never happen again is an item existing in exactly one document that nobody reads.

**What belongs here:** shipped behaviour that is wrong, a gap that blocks
something, a question that needs a decision. **What does not:** features and
roadmap (`IDEAS/`), settled rulings (`DECISIONS.md`), traps that are correct
behaviour you must know about (`CLAUDE.md` § Live hazards), history
(`packages/*/CHANGES.md`).

**Closed items age out to [ISSUES_ARCHIVE.md](ISSUES_ARCHIVE.md).**
§ Closed below keeps the recent ones; the archive keeps the rest, verbatim.
Together they hold every id ever issued, and an id is never reused — so a
`FJS-###` named in a comment, a handoff, or a package file resolves in exactly
one of the two files. Search both before concluding an id is unknown.

## Conventions

| | |
| --- | --- |
| **Id** | `FJS-###` for a defect or gap, `FJS-D##` for a decision. **Never reused, never renumbered.** Closing an item moves it to § Closed with its id. |
| **Sev** | `S1` blocker — data loss, a security hole, or cannot ship · `S2` high — silently wrong, costs a day to find · `S3` medium · `S4` low or cosmetic |
| **Status** | `open` — verified open on the date shown · `stale?` — inherited from an older audit and **not re-verified**; probe before acting · `contested` — the recorded diagnosis is doubted, see the note |
| **Verified** | The date somebody last ran it. A `stale?` row's date is when it was *written*, not confirmed. |

`stale?` is load-bearing. The eight rows inherited from `drift-report.md`
(2026-07-31) were re-probed on 2026-08-10 and **five of the eight were wrong**:
two were already fixed (conduit's secrets, `admin:generate`), one was never
reproducible (conduit's version skew), and two were right about a defect and
wrong about what it was — sierra's prefetch is not an auth *bypass* but a
cached 401, and caravan's row named three bugs of which two were fixed.
**Treat a `stale?` row as a lead, not a fact** (`VERIFYING.md`).

**The register also goes stale in the closing direction, which nothing here was
watching for.** `FJS-043` was fixed in the tree with a comment describing the
old defect in the past tense, and stayed `open` for eight days because closing
is a second action nobody owed. A row's `Verified` date is evidence about when
somebody last *looked*, not about whether the defect survives — 22 rows carried
`open` at 2026-08-02 when this audit ran, which is the same fiction `stale?`
exists to name, wearing the other label.

| FJS-175 | litestone | **`createMany` derives the INSERT column list from the FIRST row, so a batch whose rows differ silently loses data — or crashes on a column the caller never mentioned.** `const cols = Object.keys(rows[0])` builds one prepared statement for the whole batch, and every row is then bound as `cols.map(c => row[c] ?? null)`. Rows are not required to be uniform and nothing checks that they are, so the shape of row 0 decides what the other rows may write. **Narrow row first → silent loss**: `createMany({ data: [{ id: 1, title: 'a' }, { id: 2, title: 'b', subtitle: 'HELLO', tag: 'x', views: 99 }] })` writes row 2 with `subtitle` null, `tag` null and `views` at its default — no error, no warning, `{ count: 2 }` returned, and the caller has no way to detect it short of reading the rows back. **Wide row first → a raw SQLite error**: the same two rows reversed throws `SQLiteError: NOT NULL constraint failed: post.views`, because a column absent from a later row is bound as an explicit NULL, which defeats the DDL `DEFAULT` that would have filled it. So the same two rows in the same call either drop data or fail, depending only on their order, and one of the two outcomes is silent. Note the second half also means `@default(…)` is applied by the DDL rather than by `writeData` on this path. Found writing a test fixture that needed one row with `deletedAt` set among rows without it. Fix is the column list: union the keys across all rows and bind missing ones as absent rather than NULL, or group rows by shape and prepare per shape. Reproduce: the two calls above, in both orders | open | 2026-08-11 | [client.js:4424](packages/litestone/src/core/client.js#L4424) |

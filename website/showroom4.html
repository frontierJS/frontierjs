The loop

A framework is the easy part.

Most of a developer's life with a stack is not writing the app. It is scaffolding, running, migrating, deploying, watching, and eventually extending it — usually across six tools that have never heard of each other. FrontierJS treats that whole loop as one surface, with one vocabulary, and the same nouns at every stop.

The control plane

    
Basecamp — where you watch your stuff

    

      Every app above already answers the questions an operator asks. Basecamp is the
      FrontierJS app that asks them, for every app you run — and it is built with
      FrontierJS, which is the point. If the framework cannot comfortably build its own
      control plane, it is not ready for yours.

Why it is the honest test

        

          Basecamp is multi-tenant, realtime, permission-heavy and admin-shaped — the
          exact application profile this framework claims to be good at. Building it in
          FrontierJS means every rough edge in gates, policies, jobs and channels gets
          found by the people who wrote them, before it is found by you.
        

        

          The design-system package has already been through this: its first consuming
          app surfaced eight shipped bugs on day one. That is what dogfooding is for.

The structural bet

      

        These should be modes of one build, not separate packages. Today the
        extension container is its own package, and it pays for that with a hand-copied
        resources layer that has already drifted from Sierra's. Folding it onto the
        target axis is what makes desktop and mobile an entry on a list rather than a
        third copy of the same code — and it is tracked as such rather than quietly
        hoped for.
      

    

  







  

    
The through-line

    
Three file types. That is the whole surface.

    

      The reason the loop feels like one tool is that there is almost nothing to learn
      between its stops. Every artifact you author is one of three things, and each is
      readable by a person who has never seen this framework.
    


    

      

        
.lite — the seed

        

          Models, rules, gates, policies, indexes, audit. Everything in the Data realm
          and everything derived from it.
        

        
model Lead {  email String @email  @@gate("0.4.4.5")}

      


      

        
.mesa — the component

        

          A page, a component, an email, a widget. Markdown works as source too, so
          content-shaped pages stay content-shaped.
        

        
<script> … </script>{#each leads.data as l}  <tr>{l.name}</tr>{/each}

      


      

        
.md — the command

        

          A CLI command is a markdown file: frontmatter declares flags and examples, the
          body is the script. Documentation and implementation cannot drift apart,
          because they are the same file.
        

        
---title: reports:weeklyflags: { since: … }---<script> … </script>

      

    


    

      
Where this is honest about itself

      

        The loop above is real and runs today — 186 commands across 24 groups, a deploy
        pipeline with rollback, a port broker, a studio. Basecamp does not exist yet.
        Desktop and mobile targets do not exist yet. Sierra does not yet derive forms
        from a schema, which is the largest single gap in the framework. All three are
        tracked in the open rather than implied by omission, and the project is alpha:
        the ideas are settled, the surface still moves.

The journey

    
One request, every seam it crosses

    

      Most frameworks hide this. FrontierJS names each handoff, because a boundary
      you can name is a boundary you can reason about — and every one of these is a
      real function you can open. Here is a single POST /api/leads,
      end to end.
    

    

  







  

    
The counterfactual

    
What the 13 lines replace

    

      "You didn't write this" means nothing until you see what you would otherwise
      have assembled — and, more to the point, kept in agreement with itself
      forever after.
    


    

      

        
The usual assembly

        

          Every one of these is a good library, and most are better at their one job
          than anything here. The cost is not any of them individually — it is that
          your field list gets restated in ten places, in ten dialects.
        

        

          

            
ConcernWhat a Node dev reaches for

            
              
Schema & migrationsPrisma · Drizzle · TypeORM

              
Validation          Zod · Valibot · Yup

              
HTTP routing        Express · Fastify · Hono

              
Authentication      Auth.js · Lucia · Passport

              
Authorization       CASL · Oso · hand-rolled middleware

              
Row-level access    Postgres RLS · CASL conditions · hand-written WHERE

              
API spec            zod-to-openapi · @fastify/swagger · NestJS Swagger

              
Client types        openapi-typescript · orval · ORM-generated types

              
Data fetching       TanStack Query · SWR · RTK Query

              
Realtime            Socket.IO · Ably / Pusher · raw ws

            
          

        

        

          Add a field: ten edits across ten files, and nothing tells you when you
          have missed one. The compiler cannot help — these tools do not know about
          each other.
        

      


      

        
The seed

        

          The same ten concerns, stated once. Everything downstream reads from the
          schema, so disagreement is not something you have to police.
        

        

          

            
ConcernWhere it lives

            
              
Schema & migrationsthe .lite file, diffed by fli db:migrate

              
Validation          @email @length @gte, on the field

              
HTTP routing        model: on the service

              
Authentication      IAuth — swap the provider, keep the contract

              
Authorization       @@gate, one level per operation

              
Row-level access    @@allow, compiled into the WHERE

              
API spec            derived from the registered services

              
Client types        litestone types, same file

              
Data fetching       createResource — reactive, hooks matching the API's

              
Realtime            channel: — one announcement point, two fan-outs

            
          

        

        

          Add a field: one edit. That is the entire pitch.
        

      

    


    

      
The fair comparison — things that already consolidate

      

        Almost nobody wires all ten by hand any more, and pretending otherwise would
        be a strawman. These are the real alternatives, and each is genuinely good at
        collapsing part of that table.
      

      

        

          
OptionWhat it collapsesWhat is still separate

          
            

              tRPC
              Routing, client types and data fetching — types flow end to end with no spec step
              Your schema, validators and authorization are still three declarations. Nothing derives a UI.
            

            

              Supabase
              Database, auth, realtime, and row-level access via Postgres RLS — the closest thing to this idea in production
              RLS is written in SQL, beside the schema rather than in it; validation and the client layer are yours. Self-hosting is possible but is not the default path.
            

            

              Wasp · RedwoodJS
              The whole stack, from one config — the same ambition as this project
              The glue is declared in a spec file you maintain, rather than derived from the data. Authorization lives in handlers, not on the model.
            

          
        

      

      

        The line worth arguing about is narrower than "fewer dependencies": it is
        whether authorization belongs on the data, and whether the glue should be
        written at all. If those two do not matter to you, the options above are mature
        and this one is not.
      

    


    

      
And the part that is not done

      

        Derivation currently stops at the API boundary. Junction derives services from
        a Model; Sierra does not yet derive forms or tables from one — the JSON Schema
        reaches the browser and nothing renders from it. That is the single largest gap
        in the framework, it is tracked openly, and it is the next thing worth building.
        A page that only showed you the wins would be the wrong kind of page.

Schema-seeded fullstack framework

The schema
is the app.

One .lite file seeds your database, your API, and your UI. Write the schema and a six-line service — CRUD, validation, authorization, pagination and live updates are derived, not written.

Get started See the code Alpha 
// db/schema.lite — the seed
model Lead {
  id        Int      @id
  name      String   @length(1, 200) @trim
  email     String   @email @unique @lower
  status    LeadStatus @default(new)
  value     Float    @gte(0)
  createdAt DateTime @default(now())

  // read · create · update · delete
  @@gate("0.4.4.5")
  @@allow('read', ownerId == auth().id)
}

The idea

One seed, three realms

Every framework helps you write the glue between database, server, and browser. FrontierJS derives glue you never write — and everything traces back to one file.

Data · Model → API · Service → UI · Resource + Release Suite

Derived, not declared

Other frameworks give you a config file to describe your routes and queries. That is still glue you type. Here the schema already knows the shape, the rules, and who may do what — so the API is read out of it, not written beside it.

Authorization travels with the data

Gates and row policies live on the Model and compile into SQL. A query cannot take a code path that forgot to check, because the check is not in the code path — it is in the data layer, under every caller.

One engine on both sides

Litestone is SQLite. The same schema, the same query API and the same gates can run on the server and in the browser — which is what makes offline-first a direction rather than a rewrite.

See it

Schema → Service → Resource

The whole application below is the schema in the hero plus these three files. Nothing is elided.

api/server.ts — the API

import { createApp, createService, publish } from '@frontierjs/junction'

const app = createApp({ db, auth, config: { port: 3200 } })
const live = publish(() => app.channel('leads'))

app.services.register(createService({
  name:  'leads',
  model: 'lead',
  hooks: { after: { create: [live], patch: [live] } },

  // custom action, dispatched by X-Service-Method
  async getStats(ctx) {
    const leads = await ctx.locals.db.lead.findMany()
    return { count: leads.length }
  },
}))

await app.start()

src/routes/leads/index.mesa — the UI

<script>
  import { createResource } from '@frontierjs/sierra'

  // Same four hook phases as the API realm.
  const leads = createResource('leads', {
    hooks: {
      around: { all: [async (ctx, next) => {
        busy = true; await next(); busy = false
      }] },
    },
  })

  let busy = false
  await leads.find()
</script>

<table class="table">
  {#each leads.data as lead}
    <tr><td>{lead.name}</td><td>{lead.email}</td></tr>
  {/each}
</table>

What you did not write

  • Full CRUD at /api/leads
  • 400s from the schema's own rules
  • 401/403s from the Model's gate
  • Pagination and a stable result envelope
  • Row policies compiled into every query
  • TypeScript types for every Model
  • Live WebSocket events on mutation
  • Migrations diffed from the schema
  • JSON Schema, shared by API and UI

Extend

Four concepts, everywhere

Learn these once and they hold across every realm. That is the whole design constraint: keep the mental model small enough to fit in your head.

Declaration change the data's own rules

model Invoice {
  total Float @gte(0)
  @@gate("0.4.4.8")
  @@allow('read', ownerId == auth().id)
  @@log(audit)
}

Hook step into a pipeline

// Same four phases in the API and the UI.
hooks: {
  around: { all:    [timing] },
  before: { create: [setDefaults] },
  after:  { create: [broadcast] },
  error:  { all:    [report] },
}

Plugin attach a capability

export function audit(opts) {
  return {
    name: 'audit',
    register(app) { app.provide('audit', inst) },
    async boot(app)     { await inst.init() },
    async shutdown(app) { await inst.close() },
  }
}

app.configure(audit({ … }))

Provider swap an implementation

// A Plugin adds. A Provider replaces.
const auth: IAuth = {
  verifySession, login, logout,
  createUser, deleteUser, createApiKey,
}

createApp({ db, auth })

Direction

Where this is going

Stated plainly as direction, not as shipped features. Everything above this section runs today; everything in it does not yet.

Slices — installable full-stack modules

One package that ships a Model, a Service, a Resource and its own conformance tests — install only the parts you want. Take the API without the frontend, and have that be checkable rather than hopeful.

Offline-first, small, self-hosted

The same SQLite engine on both sides means the schema, the queries and the gates come along. Local enforcement, a sync queue, and an app you can run as one binary next to one file.

One target axis

One component set, many outputs: SPA, static, widget, extension — and later desktop and mobile. A new platform should be an entry on a list, not a new framework to learn.

MIT licensed. No account, no hosted service, no phone-home — self-hosting is the default path, not the fallback.

Start

Five minutes to a running API

# scaffold a new app
$ npx @frontierjs/cli new my-app
$ cd my-app

# edit db/schema.lite, then
$ fli db:migrate
$ fli dev

  → http://localhost:3200
# or add pieces to an existing project
$ npm i @frontierjs/litestone   # Data
$ npm i @frontierjs/junction    # API
$ npm i @frontierjs/sierra      # UI

# batteries, when you want them
$ npm i @frontierjs/auth @frontierjs/caravan

A fullstack framework · alpha

You already know every part. The wiring is the new part.

Nothing here asks you to learn a new paradigm. Each realm is shaped like something you have already used — and all of them read the same db/schema.lite, so a field you add shows up in the migration, the API's validation and the browser's form rules without being written three times.

FrontierJS

One schema seeds all of it. Three realms, one vocabulary, fourteen packages that were written to fit.

  • Write the schema — the API and its rules are derived from it
  • Write a six-line service when the derived one isn't enough
  • Bind the UI to the same schema, rules and permissions included
A3 Round one's BaaS hero, corrected — the frontend half was missing. Widest audience. Risk: “BaaS” sets an expectation of a dashboard.

Closest thing · Supabase, Firebase, PocketBase

A backend that derives itself. And the frontend that knows it.

A hosted platform gives you the first half: declare your data, get endpoints, auth, realtime and types. Then it hands you a client SDK and the browser starts again from zero — you re-type the validation, re-decide who may see the edit button, and hope the two halves stay in agreement.

Here both halves come from the same file. And there is no platform: it is a package in your node_modules, MIT, over a SQLite file you own.

Get started See the code Alpha

The half you'd get anywhere

  • Schema → REST API, no handler written
  • Validation and 400s from the field rules
  • Row permissions compiled into every query
  • Realtime on mutation, migrations, types

The half that usually stops at the SDK

  • resource.fields — the same rules, client-side
  • resource.can() — the model's own permissions, for hiding a button
  • make() — a form the schema describes
  • Components that also render to static HTML, email and an extension

Client-side permissions are an affordance, never a boundary — the server enforces regardless. That is the point of them living in one place.

Closest thing · Laravel, Rails, Django

That kind of complete. In TypeScript. Past the boundary.

A queue, a scheduler, mail, notifications, policies, migrations, generators, one CLI — the things that make a framework feel finished rather than started. The difference is where they stop. In all three the model layer ends at the network boundary, and the browser starts again from nothing.

Here the schema keeps going: the form knows the field rules and the button knows the permission, because both read the file the migration came from.

Where every other framework stops

Full-stack usually means two stacks and a fetch.

The server has a model, validation, policies, a hook pipeline. The browser has none of it, so it gets a second implementation of the same three facts — in a different language, kept in agreement by hand, and discovered to be wrong by a user.

FrontierJS puts the same four concepts on both sides of the wire, and the same schema under both.

C3 One business rule, written three times — then once. The sharpest of the three. Strongest single argument on the page. Risk: it is a detail, not a category.

Closest thing · how you do it today

One rule. Three places. Until one of them forgets.

“Only the owner can read a lead” is one sentence, and most stacks make you say it in three languages: once in the database, once in the handler, once in the component that hides the row. Three chances to be right, and no error when they stop matching.

Declare it on the Model and it compiles into every query, under every caller — including the ones written after you left.

Get started How it compiles Alpha

Today · database

CREATE POLICY lead_owner ON leads
  FOR SELECT USING (owner_id = current_setting('app.user')::int);

Today · API

router.get('/leads', requireAuth, async (req, res) => {
  const rows = await db.lead.findMany({
    where: { ownerId: req.user.id },   // don't forget this
  })
})

Today · UI

{lead.ownerId === session.user.id && (
  <EditButton />   // a third opinion, in a third language
)}

Here · once, on the Model

model Lead {
  @@allow('read', ownerId == auth().id)
}

// the query is filtered, the API returns 403,
// and resource.can('read', lead) knows in the browser

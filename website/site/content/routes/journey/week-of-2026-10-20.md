Most of the week went into one path: a command that rents a cloud server and installs Basecamp, the framework's deploy console, on it. This week it ran on real machines for the first time, and the token story and the call below both come from it.

## What broke

**A typecheck that reported clean because it checked nothing.** The repo's typecheck script counted the error lines in the compiler's output. In a package with no compiler config, the compiler prints its help text and exits with a failure, but that output has no error lines, so the script counted zero and called the package clean. Five packages had never been typechecked, and a sixth turned up in CI the moment the script started reading the exit status. Each now has a config. One of them held 43 real errors, which we fixed rather than baselined. If a check can pass by doing nothing, it will.

**A one-time token written to the system log.** The command that enrolls a new machine passed a single-use enrollment token on the command line of a `sudo` call. `sudo` writes every command line to the system journal, which the machine's admin group can read. The token is short-lived, but a failed install leaves it valid for a while. We found it on the first real run by reading the journal. The token now travels on standard input, so it never appears in any command line, and we proved the new shape with a stand-in install script.

**A cache that answered for the last person.** The browser client keeps a registry of records it has already fetched. When the signed-in user changed, nothing emptied it, so when the next user asked for a record by id, the client could answer from the previous user's copy without asking the server. Now a change of caller clears the registry, a view that is still open re-reads as the new caller, and a read still in flight under the old identity is thrown away. Five new tests fail if either half of the fix is removed.

And an honest one: a test file that passed alone and failed in the full suite. Setup had started background jobs that raced the tests' own writes, so two requests both created the same DNS record. Setup now waits for those jobs to finish.

## A call we made

When the install command creates the DNS record for Basecamp's own hostname, it starts with the record pointed straight at the server, not routed through the DNS provider's proxy. The command then checks that HTTPS answers with a valid certificate, and at a terminal offers to switch the proxy on. The reason is the order of events. The proxy's strict mode needs the server to already hold a valid certificate, and a new server does not have one yet. So the certificate comes first, then the proxy.

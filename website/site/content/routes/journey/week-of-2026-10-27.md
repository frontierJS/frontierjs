## What broke

**A save that answered "OK" and changed nothing.** A page in a Sierra app patched a record's status through its resource, and the server replied 200. The status did not move. Litestone marks a state-machine column as read-only in the generic update schema, because transitions have their own rules. Sierra's client then stripped every read-only field from a hand-written patch, status included. The patch went out empty, and the server accepted an empty patch and stamped the row as updated. Calling the same API from plain Node skipped the stripping step, so the bug only showed in the browser path. The client now leaves a state-machine column alone.

**A scrollbar that lied.** Mesa's virtual list draws only the rows on screen and sizes the scroll area from the height of one row. It measured the first row drawn and assumed every row matched it. When that first row was taller than the rest, the error multiplied across the whole list. In one case the scroll area came out at 39,652 pixels against 25,500 real ones. A test now pins it. It now measures the distance between row tops over the drawn rows, which also absorbs margins.

**An undo that read half of a rename.** One feature lets a non-developer edit a site's content, limited to certain folders. Its Undo checked the files a change touched with a git command that, by default, folds a rename into one entry and lists only the new name. So undoing a developer's rename into an allowed folder rewrote a file outside the allowed area, and the check never saw the old path. The commands now turn rename detection off, so a rename shows as a delete plus an add and both paths are checked. We found it while reviewing someone else's patch checker that had the same blind spot.

And an honest one: several issues we closed this week were not defects. One test failed because a field had become system-managed, so the request in the test was refused one step earlier than the test expected. One drive failure turned out to be another session's uncommitted edits in the shared working tree. Proving that took time, and it is time the next stressor app will not spend.

## A call we made

`fli ws:publish` is the command that releases our packages. We had to pick what it does when you give it no destination. We chose the GitHub Release alone. Publishing to npm is a separate, explicit choice, and one run can do both. npm serves two things: version ranges like `^1.1`, and people who expect `bun add` to work. Nothing has shipped and we have no outside users yet, so neither was in play. Against that, every npm publish costs a browser two-factor step per package, a login session that can lapse halfway through a run, and a version number promised to the public for good. A default that pays that cost on every release, for readers who do not exist yet, was the wrong default. A later run can still add a destination that was left out.

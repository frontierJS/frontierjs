Comparison

FrontierJS vs Laravel

Laravel is the framework FrontierJS most resembles, and the one it borrowed the most from: a complete stack rather than a library, batteries in the box, one CLI, and a strong opinion about where things live. If you know Laravel, you can read almost all of FrontierJS by translation.

This page is the translation table, the three real differences, and an honest account of where Laravel is simply the better answer today.

Stated plainly first: Laravel is a mature framework with a decade of production behind it, a vast package ecosystem, and a hiring pool. FrontierJS is alpha — its APIs move, several packages are not on npm yet, and its auth is thin.

This is a comparison of shape, not of readiness. If you are choosing a framework to run a business on this quarter, the honest recommendation is at the bottom of this page, and it is not always this one.

No clean translation

Nothing here maps back — the validation rules, live in the browser→resource.fieldsLaravel's answer is Precognition: run the real server rules over the wire. Same goal, different mechanism — a round trip and a running server versus a local check from the same schema.
Nothing here maps back — the model's permissions, in the browser→resource.can()Blade's @can already does this for server-rendered pages. The gap opens in an SPA, where you hand-pass can booleans as Inertia props and keep them in sync yourself.

The same feature, both ways

A Lead resource: validated, owner-scoped, paginated

Same requirements on both sides. Only the owner may read a lead; a member may create and update; an admin may delete. Name, email and value are validated. The list is paginated.

The honest read of this comparison: Laravel's six files are mostly generated by one command, and many developers prefer them — they are explicit, greppable, and trivially customised when a requirement stops being standard.

The difference is not the file count on day one. It is that the validation rule, the ownership rule and the permission levels exist once, so the browser can read the same ones the migration came from.

The service file really is that short — it is empty because everything in it would be a restatement of the schema. Add channel: 'leads' to opt into live updates, which the left-hand column would need Reverb and Echo for.

Beyond the translation

Three differences that are not cosmetic

Everything above is a naming difference. These three are structural — they change what is possible, in both directions.

1 · Derived, not scaffolded

artisan make:model -a writes a controller, a request and a policy into your repo. They are yours: readable, editable, and now your responsibility to keep matching the schema. FrontierJS reads the schema at runtime instead, so there is no generated file to drift.

The cost: less to grep. When behaviour surprises you, the answer is in a declaration and a framework, not in a file you can open.

2 · Authorization under the data

A Laravel Policy is checked where you call authorize(). Forget the call — in a console command, a job, a new endpoint — and nothing stops the read. @@allow compiles into the query, so the filter is beneath every caller including the ones written later.

The cost: policy expressions are a small language, not PHP. Anything that needs a service call has to be a hook instead.

3 · The schema crosses the wire

Laravel's model layer stops at the response. Blade and Livewire hide that by rendering on the server; the moment you go SPA, the browser needs its own copy of the rules. Here the field rules and the gate travel to the client and are read there — as an affordance, with the server still enforcing.

The cost: you inherit a JavaScript frontend stack whether you wanted one or not. Laravel lets you never write JS at all.

One language, one runtime

PHP on the server and JavaScript in the browser is two languages, two package managers and two mental models — a cost Laravel developers pay so routinely they stop counting it. FrontierJS is TypeScript throughout, on Bun, with the same hook vocabulary on both sides.

SQLite, on purpose — and only SQLite

No database server to run, back up or connect to; the app is a process and a file. That is also the sharpest limitation on this page: no MySQL, no Postgres, no read replicas, no managed RDS. Laravel runs on all of them, and if your infrastructure is already Postgres, that alone settles it.

Honestly

Where Laravel is the better answer

Laravel, without argument

  • It is finished. A decade of production, semantic versioning you can trust, and upgrade guides for every release.
  • The ecosystem. Cashier for billing, Scout for search, Socialite for OAuth, Horizon for queues, Nova and Filament for admin — all maintained, all documented.
  • The documentation. Among the best in any language, plus books, courses and fifteen years of Stack Overflow.
  • You can hire for it. A Laravel developer starts contributing on day one. Nobody has FrontierJS on their CV.
  • Any database. Postgres, MySQL, read replicas, managed instances — whatever your infrastructure already is.
  • You can avoid JavaScript entirely. Blade and Livewire are a complete answer for interactive UI without a frontend stack.
  • Paid support paths exist. Forge, Vapor, Cloud, and consultancies who will take your call.

What FrontierJS is doing differently

  • One schema across all three realms — the migration, the API's validation and the browser's form rules are the same declaration, not three copies.
  • Authorization beneath the query, so a new endpoint or a background job inherits it rather than re-checking it.
  • One language and one hook vocabulary from the database to the DOM.
  • No database server — the app is a process and a file, which makes local development and small deployments genuinely small.
  • One component set with several targets — SPA, prerendered HTML with islands, transactional email, browser extension.
  • No hosted service in the design. MIT, no account, no phone-home; self-hosting is the default path rather than the fallback.

The recommendation

Which one you should actually use

Use Laravel if…

  • You are shipping something a business depends on, this quarter
  • Your infrastructure is already Postgres or MySQL
  • You need OAuth, billing, search or an admin panel and you need them now
  • You will hire for this codebase, or hand it to someone else
  • You want to write no JavaScript
  • “Alpha” is not a word you can put in a plan

Try FrontierJS if…

  • Keeping the same rule in three places is the tax you most resent
  • You want one language across the whole stack
  • Your app fits comfortably on one machine with SQLite — and most do
  • Self-hosting with no vendor in the loop is a requirement, not a preference
  • You are building something internal, personal, or exploratory, where an alpha framework is a reasonable risk
  • You want to read the whole framework — fourteen packages is a size one person can hold

If you are weighing this seriously: take the schema in the code comparison above, run fli project:new, and see how far it gets in an afternoon. That is a better basis for a decision than any table on this page — and it is the only test that will surface the parts still marked alpha.

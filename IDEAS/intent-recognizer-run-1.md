# Assessment — the intent recognizer, run 1: sixty synthetic requests against `example`

**Status: ASSESSMENT.** Dated 2026-09-12. It reads the tree and proposes nothing;
the proposal is `intent-recognizer.md`, and the findings below are folded into it.
Never cite this as behavior.

**The input is synthetic and that bounds what it can say.** Sixty support messages
from `example-requests-1.md` (rows A1–A30) and `example-requests-2.md` (B1–B30),
generated by a smaller model that was shown a customer's description of the app's
screens and never its schema. A synthetic set can disprove the design; it cannot
confirm it. Each message was resolved by hand, by somebody who had just read the
whole seed — which flatters the lookup, and § *Threats* says by how much.

**What each message was resolved against**, in this order, stopping at the first
that answered:

| Tier | Artefact | Committed and gated? |
| --- | --- | --- |
| **S** | `db/schema.lite` (including its `///` prose), `access.snapshot.md`, `surface.snapshot.md`, `jobs.snapshot.md`, `notifications.snapshot.md` | yes |
| **U** | a `.mesa` file under `web/`, `site/`, `widgets/` or `extension/` | no index |
| **src** | a service or domain module under `api/src/` | no index |
| **R** | a row in a live database | not an artefact at all |
| **J** | nothing in the tree — performance, a third party, the law, a vague complaint | — |

## The two numbers the record asked for

**How many the committed artefacts alone answered: 31 of 60 (52%).**

| Tier needed | Count |
| --- | --- |
| **S** — committed artefacts | **31** |
| **U** — a UI source file | 14 |
| **src** — a service or domain file | 4 |
| **R** — a live row | 7 |
| **J** — nothing in the tree | 4 |

The record set a bar before the run: seven in ten means the middle really is a
lookup, four in ten means the shape changes. **5.2 lands between them, and the
14 in U decide which side.** With the UI realm indexed the same number is 45 of 60,
7.5 in ten, over the bar. The design survives conditionally, and the condition is
a route-level index of what each screen shows — **and not `lexicon.md`'s string
catalog, which would have answered none of the fourteen**: not one was about wording.

**How many never reached the Data realm: 43 of 60 (72%).**

| Deepest change needed | Count |
| --- | --- |
| **none** — already true, doable today, declined by design, or an incident | **25** |
| UI | 12 |
| API | 6 |
| Data | 17 |

**And Data is not one cost.** Five of the seventeen are a single declaration that
moves no column: a missing transition edge (A22), `@@export` on a model (A17), a
`view` (B7), `@@createdBy` (B10) and a `@from` sum (B19). The ladder in the record
prices all seventeen as a migration and a deploy, which overstates a third of them.

## Findings

**1. Two verdicts the record did not have, and they were a quarter of the run.**
*Declined by design* — the seed says no and says why — appeared in nine messages
(A7, A18, A19, A29, A30, B11, B18, B22, B24). *Incident* — a live row is wrong, no
design question at all — in seven (A2, A6, A26, B2, B6, B13, B17). Both are
answers a customer needs and neither is *exists* in the sense a person hears it.
An incident is routed, never answered; but the lookup still earned its place on
five of the seven, by saying where the truth is kept or which move fixes it.

**2. Correcting the premise was the most valuable single output.** Seven messages
rested on a belief the seed contradicts: holds add to stock (B2), a scanner exists
(B9), the export mixes tax rows (B12), the app sent the dunning emails (B13), a
code can target a product (B18), a price change reprices invoices (A19), the buy
button has a staff login (B27). B13 is the clearest case of a register doing the
work — a notification the app does not declare is not an email the app sent.

**3. The seed answered one message wrongly and nothing said so.** A24: `settle` is
`@system` in `@@transitions`, so a person cannot mark an invoice paid — except that
`invoices.settle` is the staff button for a hand-reconciled transfer, running the
same move through `asSystem()`. `surface.snapshot.md` lists `settle` and not who may
call it. This is the record's ninth question answered by a real case: a service
method wrapping a `@system` move is an affordance no committed artefact grades,
and `@frontierjs/mcp`'s `move-system` verdict would make the same mistake.

**4. The UI realm is the dependency, measured.** Fourteen messages needed a `.mesa`
file read, and five of them were *the data already exists, only a screen is
missing* (A14, A23, B3, B8, B23) — the cheapest changes in the run and the ones a
lookup could not reach. **None of the fourteen was about wording.** Every one asked
what a screen shows or does — a column, a filter, an action, a component's options,
whether a control exists — which is an index of screens and not a catalog of strings.

**5. Subtypes are not the thin spot.** One message (A8, a class as a product with a
date). `polymorphic-relations.md` is not a dependency.

**6. Dedupe by identifier held.** A22 and B17 resolve to the one missing edge on
`Order.status`; A1 and B1 to `Customer.notes`; A26 and B2 to `inventory.adjust`.
A28 and B5 both ask for dark mode and correctly do NOT collapse — one is `web/`,
which has sierra's theme switch, and one is `site/`, which does not. Text
similarity would have merged them.

## Threats

**The `///` prose did real work.** Roughly five of the 31 S answers leaned on a doc
comment rather than on structure — "staff see it" on `Product.active` (A27), "that
is the inventory screen" on `StockReservation` (A9), people per shop on `tenancy`
(A18), the line-rule sentence on `DiscountKind` (B18). `example` is the most heavily
commented schema in the repo and a client app will not be. **Structure alone
answered about 26 of 60.** The consequence for the design is narrow and worth
stating exactly: the lookup still finds the node, and reading the prose attached to
that node is bounded model work over one paragraph — retrieval stays exact.

**The resolver was a person who had just read the schema.** A mechanical resolver
would miss inferences made here, such as reading A30's *name and phone before
checkout* as a policy question about a level-0 stranger.

**Synthetic messages are tidier than real mail.** None had an attachment, a
screenshot, or a customer who was wrong about which shop they were in.

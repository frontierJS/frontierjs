# Rulings owed

Questions a fix ran into and could not answer alone, for which no other paper
had room. Each one is filed first with `fli file --sev decision --blocks
<row>`, which writes a row in `ISSUES.md` § Needs a decision and sets the fix's
row aside in `fli next`. Its options then go here, in a bullet whose lead names
that row's id. `fli decide` answers the bullet under the row's own id and closes
the row, so the held row comes back naming its ruling.

A question an existing paper argues belongs in that paper's `## Open questions`,
not here.

## Open questions


- **FJS-D505 — Is *never keep* a declared word, a custom method declared a read, or a checklist?** *Portal, the search stressor* measured it (FJS-1403, Phases 1 and 3). A search query is never stored, and today that takes six app decisions: `$.dispatch = false`, no model (so no `@@log`), no `q` in an error, idempotency off app-wide or no key ever sent (FJS-1412), conduit's trace rewritten conduit-wide (FJS-1413), and the query never taken as a command-line argument. None of the six is graded. One default the author would reach for, `cache:`, does nothing for a custom method. FJS-1424 is the same question asked of the audit trail.
  - **A** — one word on a method's input (on the `methods:` entry or the input `type`), read by five consumers: idempotency refuses to keep the answer, the bus announces nothing, the request logger and error paths never quote it, conduit sends no correlation id on a send made inside the call, and `fli check` flags a method whose answer echoes it. Covers all six. It is a new word across four packages.
  - **B** — let a custom method declare that it is a READ (`{ method: 'search', read: true }`). `READ_METHODS` already means *not idempotency-cached and not announced* for `find` and `get`, so FJS-1412 and the announcement close without a new concept. The trace half stays FJS-1413's own fix, a per-target or per-send switch. The logger and error halves already hold, measured.
  - **C** — no word. Write the six decisions into junction's AGENTS.md, and add a `fli check` rule that finds a custom method whose answer contains its input.
  - **Recommend B** — the two stores that actually leaked (idempotency, and the announcement without `$.dispatch = false`) both leak because a read cannot say it is one. `read` is a word junction already uses. Leave A open until a second product needs the trace and trail halves declared rather than switched.

- **FJS-D468 — Which rows does a resource keep the read `@version` of, and what does a patch of a row it holds none for do?** `_read` in `createResource` (`packages/sierra/src/junction/resource.js`) is a 200-entry insertion-ordered map, so a screen that read 300 rows sends its first rows' patches with no version. It also records only READS (the `FJS-341` rule, restated in the `record()` comment and pinned by *nothing read means nothing sent* in `test/resource-version.test.js`), so a row that reached the screen only by push, or through a `record(id)` over a node a push filled, has none either. Both are refused 400 in the server's words (*use asSystem()*), and offline the held write carries no version and no `base` and is refused at the drain (`FJS-1302`). The red test is to load 201 rows and patch id 1: `expect(lastPatch().version).toBe(3)` fails today, and so does `store.upsert({ id: 2, version: 5 })` followed by patching id 2 and expecting version 5. Two facts constrain the answer. The linear lab reads its 300 rows through `service.find`, which no view holds. And recording a push only when `_read` has NO entry for that id is the one form compatible with `FJS-341`, since a later push must still not move it.
  - **A** — Evict only rows no view holds (`client.nodes.peek(model, id)?.held`), and treat the first sight of a never-read row in a held view as its read (a `store.subscribe` / `record()` watch that calls `_remember` only when the id is absent). This amends the doctrine's *never from the store* to *never over a read*. It leaves a `find()` read into a plain array, as in the lab, still forgetting silently.
  - **B** — Keep the cap and the rule as they are, and add a device-side refusal. A patch on a `@version` model with no remembered version and no explicit one throws a `ResourceError` naming the row, *read too long ago, or never read, to edit safely — reload it*, before anything is queued. The pushed-row case then becomes a refusal too, and linear's board has to re-read before every drag.
  - **C** — A's eviction and first-sight rule, plus B's refusal for whatever still misses (an unheld `find()` row past the cap). No screen showing a live row is ever refused, and no miss reaches the server or the queue.
  - **Recommend C** — the push case is what the person saw, so refusing it (B) punishes the ordinary live screen. A alone keeps a silent 400 for `find()` readers, and the offline drain is where that miss is destructive.
- **FJS-D470 — Where may a row under an enum `@@transitions` START: is `@default` the one entry a caller may name, or does the machine declare its entries?** `create` is the one write the machine never grades. Probed 2026-09-26 against `Doc` in `packages/litestone/test/bulk-transitions.test.ts`'s schema (`approve: review -> published @gate(5)`): the same level-4 caller is refused `update({ status: 'published' })` with *level 5* and ACCEPTED on `create({ data: { status: 'published' } })`, so a gated destination is reached by starting there (FJS-1257, connectteam `LeaveRequest`). The red test is that pair, and it asserts the create is refused. The form half follows whichever rule wins, because `x-transitions` already reaches the kit: a generated create form offers only the entries, and leaves the column out when there is one. The per-tenant default lookup is not part of this question. It is FJS-D365's.
  - **A** — `@default` is the only entry. A non-system caller whose create names any other state is refused with `TransitionViolationError`, and the message names the default. A row that genuinely starts elsewhere is made by `asSystem()` or by create-then-`@system`-move. Nothing new to spell: the entry is derived from a declaration that already exists, and `IDEAS/state-machines.md`'s *a create is not graded* is struck.
  - **B** — the machine declares its entries as moves with no `from`: `@@transitions(status, start: -> draft, rush: -> urgent @gate(5), …)`. A create must land on an entry that the caller's level reaches. With no entry declared, `@default` is the only one (A's rule), and a declared `@default` that is not an entry is refused at parse. This is the spelling `IDEAS/tenant-authored-workflows.md` gives the enum form, next to D365 B's `fromId: null` row.
  - **C** — no Data-boundary rule. The kit leaves a `@@transitions` column out of a generated create form, and apps keep a hook per machine (`example`'s `checkOrderRules`). A direct `create()` still skips the gate, against Invariant 6.
  - **Recommend A** — it closes the Invariant-6 bypass with no new word, derived from `@default`. A is also B's zero-declaration case, so B's `start:` spelling can arrive later as an addition once a product needs a second entry, or once D365 coins entry rows.

- **FJS-D502 — Does `asSystem()` lift `@@transitions`, or does a system principal drop authority rules and never integrity ones?** `IDEAS/corpus-synthesis.md` § 2. Probed 2026-09-27: the split is already made for every integrity rule but one. `@check`/`@@check`, `@@arc` and `@required(where:)` are DDL CHECKs, and `@immutable`, seals, `@unique` and the soft-delete and template filters all refuse under `asSystem()` (FJS-D162 names this "the short list"). `@@transitions` is the exception, and it is lifted whole: `checkTransitions` returns before grading (`packages/litestone/src/core/client.js`, `if (ctx.isSystem) return null`). With it go the `AND status = <from>` compare-and-swap that FJS-D353 makes once-ness from, the transition event, and the move name in the audit row. Run under `sys`: a backwards move, a move off a one-way door, and a named move from the wrong state all succeed. Commitments already route around it: `fireCommitment` reads as system and MOVES as the caller with `{ system: true }`, because a system move "would take a row that was paid a moment ago straight to cancelled". Creation is D470's question, not this one.
  - **A** — `asSystem()` holds the machine and lifts only what is authority. A system move must be a declared move from the row's current state, and it still takes the compare-and-swap. A move's `@gate(n)` and `@system` marker, which are authority, stay lifted. A bulk write of a status column is refused for system as it is for everyone. A row put where no move leads (a fixture reset or a repair) goes through `sys.sql`, the one bypass that already says it is one. Callers that break: `example/db/seed.ts` (a reset from shipped back to pending, and a subscription revived from `cancelled`), and any litestone, basecamp or orion test that sets a state through `sys`. That count is the first thing the build measures. `@version` stays lifted: it grades what the caller last saw of a row, and a system write that read nothing has no stale view.
  - **B** — A, plus a declared reach: `db.asSystem({ lift: ['transitions'] })` for the callers that must move a row off the machine, recorded in the audit row. This adds an option and a word for two fixtures.
  - **C** — keep today's behavior and write it down: `asSystem()` lifts `@@transitions`, and the litestone docs state the short list it does not lift as the whole rule.
  - **Recommend A** — `@@transitions` is the one integrity rule on the authority side of the switch. Its compare-and-swap is a lock other rulings depend on, and the one package that needed the lock already works around the switch. A adds no option and no noun, and costs two fixture call sites a raw statement. B is the answer if a third caller needs the lift, because by then the workaround is a measurement of the road (§ IV). C leaves Invariant 6's "No exceptions" as a goal.

- **FJS-D471 — Does a transactional service method get a bounded wait on SQLite's write lock?** FJS-706 `core-8`, measured: 20 concurrent creates with a 50 ms after-hook take 60 ms with `transactional: false` and 1023 ms with it on. The after-hook runs inside the transaction, so every write waits in line for the lock.
  - **A** — `transactional: { timeout }`: a caller that waits longer than the timeout is refused with a retryable 503, and nothing is written.
  - **B** — no option. The docs and `api-hazards` say that an after-hook doing slow work belongs in `ctx.enqueue` (the outbox), where it runs after the commit.
  - **Recommend B** — the lock is held by work the author put inside the transaction, so the fix is to move that work out rather than add a knob. It adds no option and reuses an owner that already exists (the outbox).

- **FJS-D472 — May a `channels({ claims })` resolver read the database, and if so, is its answer recomputed per frame or cached per (connection, channel)?** `FJS-1316`. `ChannelClaimsFn` is synchronous, so linear reads `memberRole` and `teamIds` in the `'connection'` handler and keeps them in a `WeakMap`. A person removed from a private team keeps receiving its rows until they reconnect. Probed 2026-09-26 against `gradeRecipients` (`packages/junction/src/transport/channels.ts`) with a fake `$readAs` that admits `who.teamIds ∋ row.teamId`: the sync resolver `() => ({ teamIds })` delivers to the member (1 cohort), and the same resolver written `async` delivers to nobody (0). `resolveClaims` reads a Promise as an object with no own keys, so it grades the recipient as holding no claim and says nothing. The request path is already per request and uncached (`applySchemaClaims` in `core/litestone.ts` gives the reason: a claim fixed at sign-in keeps answering after the row moved). The part of the row about a workspace joined mid-session is channel MEMBERSHIP, not claims, and no option here answers it.
  - **A** — `ChannelClaimsFn` may return a Promise. `gradeRecipients` awaits it for each frame, once per distinct (principal, channel) cohort, with no cache. This is the request path's rule carried over to a broadcast. The cost is one resolver call per recipient principal per frame.
  - **B** — A, plus a cache per (connection, channel). The resolver declares the models it read (`claims: { reads: ['TeamMember'], resolve }`), and a `$tapEvents` write to any of those models invalidates the cache. This adds an option, and the declared list is a second origin for what the resolver's body already says.
  - **C** — no database reads in the resolver. Extend the schema's `claim … from` so it can yield a list and so it can be keyed by the channel's tenant. `gradeRecipients` then calls `db.$claimsFor(who)` for each frame. The claim becomes derived and also closes `FJS-1291`'s resolver half, but it is a litestone language change that a junction row cannot make.
  - **Recommend A** — it matches the request path (per call, uncached), adds no option and no noun, and turns today's silent drop of an async answer into a supported shape. B's cache can arrive when a measurement asks for it, and C can land later as an addition that A's resolver then no longer needs.

- **FJS-D473 — Who strips a `@guarded`/`@encrypted` column from a service's SUCCESS result before it reaches the wire?** `FJS-1221`. Probed 2026-09-26 on the `wire-safety.test.ts` app: a custom method `mint(ctx) { return ctx.locals.db.asSystem().note.create({ data: { title: 'x', secret: 'hunter2-new' } }) }`, called over HTTP with no session, answered `{"id":1,"title":"x","secret":"hunter2-new"}`. The `@secret` column came back DECRYPTED. `GET /notes/1` of the same row answered `{"id":1,"title":"x"}`. So `expect(res.text).not.toContain('hunter2')` is the red assertion. Junction already redacts on two side channels: the error path, where `sanitizeError` is fed `protectedFieldsFor(ctx)` from `transport/bridge.ts` via `$protectedFields` (FJS-686), and broadcasts, which go through `db.$readAs` (FJS-D175). The success result is neither. It is wrapped as-is at `core/service.ts` (`wrapResult`) and serialized at `bridge.ts` `jsonResponse`. The WS `service_result` frame does the same.
  - **A** — the bridge strips, at the wire only. On the HTTP body and the WS `service_result` frame, the key is DROPPED (not `[redacted]`) for every name `protectedFieldsFor(ctx)` returns, through `redactBy`. Nothing is added: this is FJS-686's owner and list extended from `fe.data` to the result. A success body then has the shape a caller-scoped read already has. An in-process `app.service(x).method()` stays ungraded, since that caller is trusted. The gap is the error path's gap: a protected column on an `include`d relation of a DIFFERENT model is not in the list.
  - **B** — the bridge grades, running `db.$readAs(declaredModel, row, principal)` over each row, as a broadcast does. That covers row visibility as well as columns. But `$readAs` fails closed, and a custom method like `book()` exists precisely to answer a row the caller could not read. A stranger booking would get `null`. That changes what a custom method may return, which is a bigger ruling than this row.
  - **C** — litestone marks. A system client's result carries a symbol (like `Symbol.for('junction.service')`), and the bridge strips only marked objects. A value copied out (`{ ...row }`) loses the mark and leaks again, and this adds a cross-package contract.
  - **D** — `fli check` names a service that returns an `asSystem()` result directly. Static and advisory. It misses a result that went through a local variable or a helper module (`book.ts` in the stressor), and it leaves the wire unchanged.
  - **Recommend A** — it reuses the one owner and the one name list the error path already derives from the schema, adds no option or noun, and closes the destructive case (a decrypted secret to a stranger). A method that MEANS to hand back a protected value once (a freshly minted token) returns it under a key that is not a column name, and that is the one thing the docs say.

- **FJS-D474 — How does the no-overlap declaration name the scope it serializes?** FJS-D346 ruled the word exists in `@@allow`'s tier and left the spelling open; the connectteam drive (FJS-1215) showed all three range shapes share one key, `person:${employeeId}`, across `Shift`, `LeaveRequest` and `AvailabilityWindow`, so D346's sketch `@@exclude([hostId], range: […])` — a column on its own model — excludes nothing cross-model.

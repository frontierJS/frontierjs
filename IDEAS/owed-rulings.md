# Rulings owed

Questions a fix ran into and could not answer alone, for which no other paper
had room. Each one is filed first with `fli file --sev decision --blocks
<row>`, which writes a row in `ISSUES.md` § Needs a decision and sets the fix's
row aside in `fli next`. Its options then go here, in a bullet whose lead names
that row's id. `fli decide` answers the bullet under the row's own id and closes
the row, so the held row comes back naming its ruling.

A question an existing paper argues belongs in that paper's `## Open questions`,
not here.

## Open questions


- **FJS-D468 — Which rows does a resource keep the read `@version` of, and what does a patch of a row it holds none for do?** `_read` in `createResource` (`packages/sierra/src/junction/resource.js`) is a 200-entry insertion-ordered map, so a screen that read 300 rows sends its first rows' patches with no version. It also records only READS (the `FJS-341` rule, restated in the `record()` comment and pinned by *nothing read means nothing sent* in `test/resource-version.test.js`), so a row that reached the screen only by push, or through a `record(id)` over a node a push filled, has none either. Both are refused 400 in the server's words (*use asSystem()*), and offline the held write carries no version and no `base` and is refused at the drain (`FJS-1302`). The red test is to load 201 rows and patch id 1: `expect(lastPatch().version).toBe(3)` fails today, and so does `store.upsert({ id: 2, version: 5 })` followed by patching id 2 and expecting version 5. Two facts constrain the answer. The linear lab reads its 300 rows through `service.find`, which no view holds. And recording a push only when `_read` has NO entry for that id is the one form compatible with `FJS-341`, since a later push must still not move it.
  - **A** — Evict only rows no view holds (`client.nodes.peek(model, id)?.held`), and treat the first sight of a never-read row in a held view as its read (a `store.subscribe` / `record()` watch that calls `_remember` only when the id is absent). This amends the doctrine's *never from the store* to *never over a read*. It leaves a `find()` read into a plain array, as in the lab, still forgetting silently.
  - **B** — Keep the cap and the rule as they are, and add a device-side refusal. A patch on a `@version` model with no remembered version and no explicit one throws a `ResourceError` naming the row, *read too long ago, or never read, to edit safely — reload it*, before anything is queued. The pushed-row case then becomes a refusal too, and linear's board has to re-read before every drag.
  - **C** — A's eviction and first-sight rule, plus B's refusal for whatever still misses (an unheld `find()` row past the cap). No screen showing a live row is ever refused, and no miss reaches the server or the queue.
  - **Recommend C** — the push case is what the person saw, so refusing it (B) punishes the ordinary live screen. A alone keeps a silent 400 for `find()` readers, and the offline drain is where that miss is destructive.
- **FJS-D470 — Where may a row under an enum `@@transitions` START: is `@default` the one entry a caller may name, or does the machine declare its entries?** `create` is the one write the machine never grades. Probed 2026-09-26 against `Doc` in `packages/litestone/test/bulk-transitions.test.ts`'s schema (`approve: review -> published @gate(5)`): the same level-4 caller is refused `update({ status: 'published' })` with *level 5* and ACCEPTED on `create({ data: { status: 'published' } })`, so a gated destination is reached by starting there (FJS-1257, connectteam `LeaveRequest`). The red test is that pair, and it asserts the create is refused. The form half follows whichever rule wins, because `x-transitions` already reaches the kit: a generated create form offers only the entries, and leaves the column out when there is one. The per-tenant default lookup is not part of this question. It is FJS-D365's.
  - **A** — `@default` is the only entry. A non-system caller whose create names any other state is refused with `TransitionViolationError`, and the message names the default. A row that genuinely starts elsewhere is made by `asSystem()` or by create-then-`@system`-move. Nothing new to spell: the entry is derived from a declaration that already exists, and `IDEAS/state-machines.md`'s *a create is not graded* is struck.
  - **B** — the machine declares its entries as moves with no `from`: `@@transitions(status, start: -> draft, rush: -> urgent @gate(5), …)`. A create must land on an entry that the caller's level reaches. With no entry declared, `@default` is the only one (A's rule), and a declared `@default` that is not an entry is refused at parse. This is the spelling `IDEAS/tenant-authored-workflows.md` gives the enum form, next to D365 B's `fromId: null` row.
  - **C** — no Data-boundary rule. The kit leaves a `@@transitions` column out of a generated create form, and apps keep a hook per machine (`example`'s `checkOrderRules`). A direct `create()` still skips the gate, against Invariant 6.
  - **Recommend A** — it closes the Invariant-6 bypass with no new word, derived from `@default`. A is also B's zero-declaration case, so B's `start:` spelling can arrive later as an addition once a product needs a second entry, or once D365 coins entry rows.

- **FJS-D471 — Does a transactional service method get a bounded wait on SQLite's write lock?** FJS-706 `core-8`, measured: 20 concurrent creates with a 50 ms after-hook take 60 ms with `transactional: false` and 1023 ms with it on. The after-hook runs inside the transaction, so every write waits in line for the lock.
  - **A** — `transactional: { timeout }`: a caller that waits longer than the timeout is refused with a retryable 503, and nothing is written.
  - **B** — no option. The docs and `api-hazards` say that an after-hook doing slow work belongs in `ctx.enqueue` (the outbox), where it runs after the commit.
  - **Recommend B** — the lock is held by work the author put inside the transaction, so the fix is to move that work out rather than add a knob. It adds no option and reuses an owner that already exists (the outbox).

- **FJS-D472 — May a `channels({ claims })` resolver read the database, and if so, is its answer recomputed per frame or cached per (connection, channel)?** `FJS-1316`. `ChannelClaimsFn` is synchronous, so linear reads `memberRole` and `teamIds` in the `'connection'` handler and keeps them in a `WeakMap`. A person removed from a private team keeps receiving its rows until they reconnect. Probed 2026-09-26 against `gradeRecipients` (`packages/junction/src/transport/channels.ts`) with a fake `$readAs` that admits `who.teamIds ∋ row.teamId`: the sync resolver `() => ({ teamIds })` delivers to the member (1 cohort), and the same resolver written `async` delivers to nobody (0). `resolveClaims` reads a Promise as an object with no own keys, so it grades the recipient as holding no claim and says nothing. The request path is already per request and uncached (`applySchemaClaims` in `core/litestone.ts` gives the reason: a claim fixed at sign-in keeps answering after the row moved). The part of the row about a workspace joined mid-session is channel MEMBERSHIP, not claims, and no option here answers it.
  - **A** — `ChannelClaimsFn` may return a Promise. `gradeRecipients` awaits it for each frame, once per distinct (principal, channel) cohort, with no cache. This is the request path's rule carried over to a broadcast. The cost is one resolver call per recipient principal per frame.
  - **B** — A, plus a cache per (connection, channel). The resolver declares the models it read (`claims: { reads: ['TeamMember'], resolve }`), and a `$tapEvents` write to any of those models invalidates the cache. This adds an option, and the declared list is a second origin for what the resolver's body already says.
  - **C** — no database reads in the resolver. Extend the schema's `claim … from` so it can yield a list and so it can be keyed by the channel's tenant. `gradeRecipients` then calls `db.$claimsFor(who)` for each frame. The claim becomes derived and also closes `FJS-1291`'s resolver half, but it is a litestone language change that a junction row cannot make.
  - **Recommend A** — it matches the request path (per call, uncached), adds no option and no noun, and turns today's silent drop of an async answer into a supported shape. B's cache can arrive when a measurement asks for it, and C can land later as an addition that A's resolver then no longer needs.

- **FJS-D473 — Who strips a `@guarded`/`@encrypted` column from a service's SUCCESS result before it reaches the wire?** `FJS-1221`. Probed 2026-09-26 on the `wire-safety.test.ts` app: a custom method `mint(ctx) { return ctx.locals.db.asSystem().note.create({ data: { title: 'x', secret: 'hunter2-new' } }) }`, called over HTTP with no session, answered `{"id":1,"title":"x","secret":"hunter2-new"}`. The `@secret` column came back DECRYPTED. `GET /notes/1` of the same row answered `{"id":1,"title":"x"}`. So `expect(res.text).not.toContain('hunter2')` is the red assertion. Junction already redacts on two side channels: the error path, where `sanitizeError` is fed `protectedFieldsFor(ctx)` from `transport/bridge.ts` via `$protectedFields` (FJS-686), and broadcasts, which go through `db.$readAs` (FJS-D175). The success result is neither. It is wrapped as-is at `core/service.ts` (`wrapResult`) and serialized at `bridge.ts` `jsonResponse`. The WS `service_result` frame does the same.
  - **A** — the bridge strips, at the wire only. On the HTTP body and the WS `service_result` frame, the key is DROPPED (not `[redacted]`) for every name `protectedFieldsFor(ctx)` returns, through `redactBy`. Nothing is added: this is FJS-686's owner and list extended from `fe.data` to the result. A success body then has the shape a caller-scoped read already has. An in-process `app.service(x).method()` stays ungraded, since that caller is trusted. The gap is the error path's gap: a protected column on an `include`d relation of a DIFFERENT model is not in the list.
  - **B** — the bridge grades, running `db.$readAs(declaredModel, row, principal)` over each row, as a broadcast does. That covers row visibility as well as columns. But `$readAs` fails closed, and a custom method like `book()` exists precisely to answer a row the caller could not read. A stranger booking would get `null`. That changes what a custom method may return, which is a bigger ruling than this row.
  - **C** — litestone marks. A system client's result carries a symbol (like `Symbol.for('junction.service')`), and the bridge strips only marked objects. A value copied out (`{ ...row }`) loses the mark and leaks again, and this adds a cross-package contract.
  - **D** — `fli check` names a service that returns an `asSystem()` result directly. Static and advisory. It misses a result that went through a local variable or a helper module (`book.ts` in the stressor), and it leaves the wire unchanged.
  - **Recommend A** — it reuses the one owner and the one name list the error path already derives from the schema, adds no option or noun, and closes the destructive case (a decrypted secret to a stranger). A method that MEANS to hand back a protected value once (a freshly minted token) returns it under a key that is not a column name, and that is the one thing the docs say.

- **FJS-D474 — How does the no-overlap declaration name the scope it serializes?** FJS-D346 ruled the word exists in `@@allow`'s tier and left the spelling open; the connectteam drive (FJS-1215) showed all three range shapes share one key, `person:${employeeId}`, across `Shift`, `LeaveRequest` and `AvailabilityWindow`, so D346's sketch `@@exclude([hostId], range: […])` — a column on its own model — excludes nothing cross-model. Inclusion quantifies over a union of rows, exclusion over any one, so the second face is a separate word either way.
  - **A** — a named scope declared once at schema level (`scope person(employeeId)`), each model's `@@exclude(person, range: [a, b])` naming it; litestone compiles every write on any model citing the scope to `$lock('person:…')` plus a check of all its members.
  - **B** — per-model `@@exclude([employeeId], range: […], against: [LeaveRequest, …])`, each model listing its siblings; no new noun, but the fact is stated on every write path and the one nobody wrote is the one that runs (drive finding 2).
  - **Recommend A** — one declaration per fact answers finding 2 by construction, and the scope is exactly the lock key the drive found every service already hand-wrote.

- **FJS-D475 — Where does a non-bearer inbound credential (a signed request) become a principal in junction?** Transport resolves only `Authorization: Bearer` through `IAuth.verifySession`; `verifyApiKey` is reached only from inside better-auth's own `verifySession`. basecamp's `requireOutpostSignature` is an app-level hook standing in for the door (FJS-349 is what happens without it). Red test: a request signed with `@frontierjs/toolbelt/signature` and no bearer reaches a service with `ctx.user` null today; it should arrive as the declared machine principal, and a bad signature should be refused with 401 before any hook runs.
  - **A** — `createApp({ credentials: [signedRequest({ keyFor, window })] })`: an ordered list of verifiers `(req, rawBody) => SessionContext | null | refuse`, tried by transport before the bearer path. Bearer becomes the list's default last entry, and `verifyApiKey` goes into it as well, which ends the one-door hazard.
  - **B** — an optional `IAuth.verifyRequest(req, rawBody)` beside `verifySession`. There are fewer nouns, but every auth provider now owns machine identity, and a signature scheme has nothing to do with the session store.
  - **Recommend A** — a credential kind is not an auth provider's concern. A declared list is one owner (transport) with one order, and the app states its machine identity once instead of guarding each route.

- **FJS-D476 — Which CI tier runs `litestone mutate` over `example` and `basecamp`, and is its score ratcheted by a baseline?** FJS-598: only the tutor lesson is mutated in CI. Measured: `example` 159/159 in 239s; `basecamp` 328 mutants, still running at 25 min when killed (needs `ENCRYPTION_KEY`). A fail-on-any-survivor phase goes red on the first new schema; a printed percentage is read by nobody.
  - **A** — full tier: `example` whole, `basecamp` under a `--kinds` subset sized to minutes; per-app score in a `scripts/mutate-baselines.json` that ratchets like `typecheck-baselines.json` (Invariant 14).
  - **B** — a nightly job running both apps whole against the same baseline file; nothing on push.
  - **C** — fast tier runs `example` with a `--kinds` subset; full tier runs both whole; same baseline.
  - **Recommend A** — CI tiers already exist and a nightly is a new runner nobody watches; the baseline is the ratchet either way.

- **FJS-D477 — Is `litestone restore`'s verify half a flag on restore, its own command, or a separate row?** FJS-552 asks for `litestone restore` (the schema-driven mirror of `replicate`: every declared database, litestream for SQLite, a directory copy for jsonl/logger, `--at`, refuse-not-partial) AND for restore-then-run-the-app-suite via `createTestEnv`. `src/tools/cli.js` has no `restore` today; the first half is fully specified, the second names no shape.
  - **A** — Split: build `litestone restore` under FJS-552 now; file the verify half as its own row, which later becomes `restore --verify <dir>` restoring into a temp dir and running the suite with it as the env's database.
  - **B** — One command, `litestone restore --verify`, built together; restoring without verifying stays possible but verify is the documented default.
  - **C** — A separate `litestone restore:check` that restores into a temp dir only, never over the live files.
  - **Recommend A** — the restore half is specified and owed in an emergency today; the verify half needs `createTestEnv` to accept an existing database file, which is its own design.

- **FJS-D478 — What spells a server-verified credential: one-way, matchable in a `where`, logged, rotatable by reissue?** `KioskDevice.token @secret` can't be looked up (random IV). `@hashed` is refused beside `@secret` at parser.js (§ @secret expansion), and `@secret(deterministic: true)` keeps the plaintext recoverable. So the app decrypts through `asSystem()` and compares with `timingSafeEqual` (FJS-1249). The red assertion: `@hashed @secret` parses, and the field matches in a `where` and writes an access-log entry.
  - **A** — Allow `@hashed` beside `@secret`: the digest replaces the `@encrypted` half, `$rotateKey` skips it the way it skips `@secret(rotate: false)`, and `@guarded` plus logging stay. No new word.
  - **B** — `@hashed(logged: true)`, which adds only the audit half to `@hashed`. It's an option on an existing word.
  - **C** — A new attribute (e.g. `@credential`). It's a new noun for a combination the two existing words can already express.
  - **Recommend A** — both words already mean exactly their halves. Today the refusal protects a reversibility the author is choosing to give up, so lifting it composes two existing words and adds no new one.

- **FJS-D479 — Should a stopped Junction app be restartable, or is one-start-per-app the contract?** `start()` after `stop()` now refuses by name (`app.ts` ~1737, `FJS-950`); making it work means rebuilding the router and re-running plugin `boot()` route registration, which is not idempotent today. Red assertion: `await app.start(); await app.stop(); await app.start()` resolves.
  - **A** — Keep one start per app; the refusal is the contract, and a config reload builds a new app with `createApp()`. FJS-949 closes as by-design.
  - **B** — Make restart real: rebuild the router per `start()` and make plugin `boot()` route registration idempotent (or reset routes on `stop()`).
  - **Recommend A** — no caller exists yet, `createApp()` already covers the embedder, and B makes every plugin carry a re-entrance duty.

- **FJS-D480 — How does Caravan refuse a payload JSON cannot carry honestly?** `dispatch()` runs `JSON.stringify` on `data` unchecked: `defineJob<{ when: Date }>` hands the handler a string typed `Date`, `Map`/`Set`/`RegExp` arrive as `{}`, `NaN`/`Infinity` as `null`, `BigInt` throws a bare `TypeError` naming no job, and a 50 MB payload was accepted and shipped whole in the admin listing (`caravan-13`, `FJS-711`).
  - **A** — refuse at dispatch: walk the payload, throw naming the job and the key path for any non-JSON-plain value, and refuse over a fixed byte bound (e.g. 256 KB) with the bound in the message; type `defineJob<T>` so `T` must be JSON-plain.
  - **B** — encode honestly: a tagged codec (Date, Map, Set, BigInt round-trip) plus the size bound; handlers get what they typed.
  - **C** — A, with the bound declared per job beside `maxAttempts`.
  - **Recommend A** — a job payload is an id-and-scalars receipt, not a store; refusing by name costs no new noun or option, and a large value belongs in a row the job reads.

- **FJS-D481 — A delegated child whose OPTIONAL parent is null: invisible to every tenant, like a null claim column, or visible to all?** A null claim column hides the row from every tenant (FJS-D141). But `check(rel)` over an optional relation compiles to `FK IS NULL OR EXISTS (…)` (FJS-382), so the orphan shows to every tenant (`tenant A sees: [ "a-note", "orphan-note" ]`). `verifyTenantIsolation` reports that case as `unparented` rather than grading it.
  - **A** — Make them agree with FJS-D141: under `@@tenant`, `check(rel)` on an optional relation compiles to `FK IS NOT NULL AND EXISTS (…)`, so an orphan is readable through `asSystem()` only. The FJS-382 tests change, and `verifyTenantIsolation` grades an orphan as isolated.
  - **B** — Keep both behaviors and write down why they differ: a column is the row's own claim, and a null relation is a row nobody has filed yet. The docs in multi-tenancy.md say so, and `verifyTenantIsolation` warns on `unparented`.
  - **Recommend A** — one answer for "belongs to no tenant", and it fails closed. A row that was never filed can still be shared on purpose with `@@tenant(none)`.

- **FJS-D482 — How do a `type`'s transforms reach a declared custom-method input without the two boundaries disagreeing on what is valid?** Litestone runs `applyTransforms` and then `validate` (`client.js`); junction's `FieldDef.transform` runs after validation (`schema.ts`). JSON Schema carries no transform names, so `@trim @length(3,12)` on `'  ab  '` fails at the Data boundary and passes a service. `packages/junction/test/method-input.test.ts` asserts this is still broken today.
  - **A** — Three moves: litestone emits an `x-transforms` keyword into JSON Schema (the snapshot and its three readers move with it), junction adds a PRE-validation transform slot, and one `@frontierjs/toolbelt/transforms` subpath holds the implementations that litestone, junction and sierra all read.
  - **B** — Refuse it: a `type` used as a method `input` that declares a transform is a schema error at boot, so the gap can't be hit silently.
  - **Recommend A** — one owner for the implementations (Invariant 4), the same order at both boundaries, and sierra gets client-side transforms for free. B stays the fallback if A's cost can't be paid yet.

- **FJS-D483 — Where does each `junction.config.js` section's known-key list live, so a misspelled nested key is refused at `start()`?** `FJS-940`: `middleware: { csrfs: true }` and `caravan: { pollIntervel: 1000 }` merge silently. The interfaces are erased at runtime and have drifted from their readers (`cors.credentials`), and `JUNCTION_SECTIONS` covers only the top level. A red test would assert that `unknownKeys({ caravan: { pollIntervel: 1 } })` names `caravan.pollIntervel`; there is no such check today.
  - **A** — Each consuming subsystem exports its keys (caravan `CARAVAN_CONFIG_KEYS`, conduit, attachments, …), and a check in `config/index.ts` reads them and reports at `start()` the way FJS-D199 does. For `middleware:`/`plugins:`, the list is derived from `loadConfig`'s key-by-key map.
  - **B** — One table in `config/index.ts` maps each section to its keys, graded both directions by `config-surface.test.ts`. That puts every list in one place, away from the subsystems that read the keys.
  - **C** — Refuse nested keys only in `middleware:`/`plugins:`, where FJS-D256 already made `loadConfig` the owner. The other four sections keep failing silently, and that gap is recorded as `none` in `invariants.snapshot.md`.
  - **Recommend A** — The reader is the only honest owner of what it reads, as the row itself argues. B is a second origin, and C leaves most of the row open.

- **FJS-D484 — What public surface reports the offline warm's result and what a device holds?** `_armWarm` (`packages/sierra/src/junction/offline.js:210-211`) calls `warmOffline().catch(() => {})`, discarding the per-service report FJS-1279 built; `offlineServices()` names what was declared, not what landed. A red test: after a warm with one rejected model, no export tells the app which.
  - **A** — `offlineStatus()`, a status object beside `pendingQueue`: last warm's report (per service: rows written, error) plus when it ran. One noun an app reads; mirrors the existing queue status.
  - **B** — `lastWarmReport()` returning `warmOffline()`'s answer verbatim, plus exporting `warmOffline` for an app to await itself.
  - **Recommend A** — one status surface in the shape already coined for the queue, rather than a second noun for the raw report.

- **FJS-D485 — Does a device's local db, which holds a partial window, enforce foreign keys on write-through?** `resource.js:1495` fires `writeThrough(model, rows)` unordered as responses land; `local-db.js:174` writes one `upsertMany` per batch, so one child row naming a parent not on the device (not yet arrived, or outside the parent's window) refuses the whole batch — connectteam's `Shift: data[0] of 4 failed … SQLITE_CONSTRAINT_FOREIGNKEY`.
  - **A** — The device is a cache, not the source of truth: open the local db with `foreign_keys = OFF` (or declare device tables without FK constraints). The server already enforced them; a partial window cannot satisfy them by construction.
  - **B** — Keep FKs; on a batch refusal fall back to per-row upserts and drop (or defer and retry) the rows whose parent is absent. Every child outside its parent's window stays off the device, so an offline read of it misses.
  - **Recommend A** — a partial window can never be referentially closed, so B loses rows permanently and costs a row-at-a-time OPFS write on every miss; integrity is the server's (Invariant 6's boundary), not the replica's.

- **FJS-D486 — How does the browser client authenticate its WebSocket without the session token in the URL?** `client/index.ts:2045` opens `/ws?token=<session token>` (a browser `WebSocket` cannot set `Authorization`), so the long-lived credential lands in the console on every failed connect (measured, Firefox), proxy logs and nginx `$request`; `channels.ts:979` documents it. A red test: the URL passed to `new WebSocket` must not contain the token.
  - **A** — Single-use connect ticket: `POST /ws/ticket` with the bearer header returns a short-lived one-shot value; the socket opens at `/ws?ticket=…`. One extra round trip per (re)connect; server holds a small TTL map; a logged ticket is already spent.
  - **B** — Token in `Sec-WebSocket-Protocol` (`new WebSocket(url, ['fjs', token])`); server reads and echoes `fjs`. No round trip, no state; but the header still carries the long-lived token, and some proxies/APMs log headers.
  - **Recommend A** — only A keeps the long-lived credential out of every log, which is the row's whole cost; cookie mode stays as is.

- **FJS-D487 — How does a tenant's declared custom-field list for an @@extensible model reach a generated list's columns and filters?** litestone's `$declaredFields()` (`packages/litestone/src/core/client.js:6563`) is the only reader, and nothing in junction exposes it. The JSON Schema is shared by every tenant and now leaves the slot columns out (FJS-1387), so `resource.columns()`/`filters()` in `packages/sierra/src/junction/resource.js:1711-1811` cannot name a `fields.<key>`. The red assertion: a list resource on an @@extensible model, with a workspace that declares `severity`, gets no `fields.severity` in `columns()` or `filters()`.
  - **A** — junction serves a built-in `declaredFields` custom method on each @@extensible model's service, gated like its `find`. The resource fetches it once per tenant and merges `fields.<key>` into columns and filters.
  - **B** — each tenant gets its own JSON Schema from the schema endpoint, with the declared fields written in as `x-declared` properties. There is one channel, but it has to be cached per tenant.
  - **Recommend A** — the per-tenant fact stays a per-tenant call through the gate, and the shared schema stays tenant-free.

- **FJS-D488 — How does a model declare it may be HELD on a device but never written offline?** Sierra's `offlineQuery` refuses a read without `@@sync` (FJS-D298), but `@@sync`'s argument is a collision policy only. So a read-only roster has to declare a write policy that isn't true: `append` is false, `refuse`/`field` need `@version`, and `server` is just the least wrong. Declaring it also leaks a client-writable **Id** onto forms (seen on `LeaveRequest` in connectteam).
  - **A** — an argument on the existing word: `@@sync(read)`, a held, never-written model. The offline queue refuses writes to it, and no client-mintable id is exposed.
  - **B** — a separate word, e.g. `@@held`, for the read direction, with `@@sync` staying write-only and implying `@@held`.
  - **Recommend A** — it keeps one word for "rows live on a device", as FJS-D298 wanted. The policy set gains a member that states the direction, which `db:explain` already says is the missing question.

- **FJS-D489 — Where does the clock that re-grades a held `@@effective` row live?** FJS-1274: expiry is a CLOCK transition, not a write, so the fan-out emits nothing and a subscriber holds a lapsed `StockReservation` for ever. FJS-D351 (C) rules out widening the carve to removals; FJS-D111 keeps a store (and so a tick) out of toolbelt.
  - **A** — Client tick in the live store (sierra/junction client): the store reads each held row's `to:` bound, schedules one timer for the soonest, and drops the row via `@frontierjs/toolbelt/match` re-grading when it fires. No server work; needs `x-effective` in the JSON Schema so the client knows the field.
  - **B** — Server-side expiry frame: junction schedules a `removed` frame at each broadcast row's `to:` for its subscribers. Contradicts FJS-D351's "never scheduled", and one timer per held row per server.
  - **Recommend A** — the store already owns what it holds and the clock is local; B re-opens the "never scheduled" half of FJS-D351.
